# Links in a git folder stay in bounds

**What / why.** 57o made the git tools confined: they never ask before a read, so a repository they read must be inside the root, and so must what git opens there. Its link check judges a fixed list. `object_store_leak` (`business/tools/git.cpp:127-189`) refuses a link that leads out of the root only at five named entries of the git and common directories (`kReadEntries`, `:120-125`: `objects`, `refs`, `packed-refs`, `HEAD`, `index`), at the entries directly inside `objects/` and `objects/pack/` (`link_out_of`, `:103-118`, one level, never descending), and in `objects/info/alternates`. git reads many more files inside a git directory than that, and a link at any of them leads git out of the root while the check passes. 57o's own record left one of these as found ("loose objects or pack files linked one by one inside the object store's sub-folders are not scanned", [Milestone AT](../../../assistant/cli/MILESTONES.md#milestone-at--the-second-sweeps-cli-findings), 57o's Not done); the probe found it is a class.

Measured, not guessed (2026-11-15). The build-tree binary (`apogee 0.2.0`, v0.2.1 with 57x, built 2026-11-15 00:27), git 2.53.0 on macOS, a sandboxed `APOGEE_HOME` and `HOME`, the mock backend driving `complete --tools`, every link planted by the probe script itself. Five probes, each re-run independently by a second agent, every tool run paired with a plain-git control. The outside repository held the commit subject `OUTSIDE SUBJECT` and a file `OUTSIDE SECRET TEXT`.

- **A loose object linked out.** With the outside commit, tree and blob linked in `x/.git/objects/<2>/<38>` under their own ids, nothing is refused: `git_show{ref:<commit>}` printed `OUTSIDE SUBJECT` and its stat, `git_diff{target:<commit>}` printed `-OUTSIDE SECRET TEXT`, and `git_show{ref:<blob>}` printed the file whole -- one linked blob is enough. The same holds in the launch repository with no `repo`. git does not check a linked object's name on most of these reads (only the range forms and `git_status`'s root tree refuse a wrong-named one). A link to an outside file that is not a git object gives none of its bytes, but its error differs for a missing path, a file, a folder and an unreadable one.
- **A state file `git_status` reads, linked to any outside file.** No object or id needed. `BISECT_START` (with a `BISECT_LOG` beside it) made `git_status` answer `You are currently bisecting, started from branch '<the file>'` -- a 400-line, 15,456-byte file came back whole. `rebase-merge/head-name`, `rebase-merge/onto`, `rebase-apply/head-name` and `rebase-apply/onto` show the whole file the same way; `rebase-merge/done` and `git-rebase-todo` two lines each; `rebase-merge` linked as a folder, its files.
- **`shallow`, linked to any outside file**: all four tools answered `fatal: bad shallow line: <its first line>`. With `info/grafts` linked out and an in-root `shallow` holding one bad line, every line of the outside file.
- **Pseudo-refs**: `CHERRY_PICK_HEAD`, `REVERT_HEAD`, and `logs/HEAD` with `HEAD` detached, linked to an outside ref file, made `git_status` print the outside commit id (7 characters; all 40 when the repository's own config sets `core.abbrev=40`). From that id alone, linking the objects the tools' own errors named next ended in `-OUTSIDE SECRET TEXT`. (`ORIG_HEAD`, `FETCH_HEAD`, `MERGE_HEAD` and other named refs give `bad object` and no id.)
- **Entries the list never named.** `reftable/` (a `--ref-format=reftable` repository) linked out: `git_status` read the outside repository's branch name. `config` linked out is read (an outside `status.showUntrackedFiles=no` changed `git_status`). `modules/<name>/refs/heads/main` linked out: `git_diff` in the superproject printed `+Subproject commit <the outside id>`.
- **Around the one-level scan.** An `objects/info/alternates` line naming a store inside the root, whose loose objects are links out, is followed and read. An `objects/<2>` linked as a folder that lands inside the root, holding links out, is not refused: `link_out_of` sees a link that lands inside and does not look in it.
- **The review fetch launders it (57x).** A folder remote inside the root (`o` -> `proj/r`) is confined by the same `Git` constructor (`git.cpp:786-806`), so the same gap: with `r`'s loose objects linked out and its `main` naming the outside commit, `git_diff{remote:'o', fetch:'always'}` copied the commit, tree and blob into `x` as **real** loose files (no link left, `refs/remotes/o/main` the outside id). With `outside/` then moved away, `git_show{ref:'o/main'}` still printed `OUTSIDE SUBJECT`: the copy outlives the link, so no later check can see it.

**Who can put the link there** (the precondition; same probe). Apogee's file tools cannot: `write_file`, `edit_file` and `delete_file` never create a link (57o's `write_file_atomically` writes a regular file), refuse a path whose link leads out, and write text as UTF-8, so a git object's raw bytes cannot be written; no Apogee tool checks anything out. git's own operations make none (clone `--shared`, `--reference`, local, `worktree add`, submodules, `absorbgitdirs`, `gc`, `repack`), and git 2.45.1 and later refuse a local clone of a source holding a loose link. Three real routes:
- **A shell or the code server, once allowed.** `run_command` (asked; accept-edits does not pass it), and `run_python` through a subprocess or `ctypes` (its guard checks where a link is made, not where it points). That grant can already read the outside file itself, but **the link outlives it**: a later run, a resumed chat, a task's next run -- with no shell grant -- reads through it unasked.
- **A folder the person brings in.** A project extracted from an archive (`tar`, `zip`, `ditto`) or copied (`cp -R`) keeps its `.git` with its links: started inside it, the tools read outside with no `repo` at all (`git_log` printed the outside subject, `git_diff{staged:true}` the outside text).
- **A cloned repository tracking a bare repository folder** (`fixtures/x.git/objects/<2>/<38>` as tracked links): a clone recreates the links (`core.symlinks`), and `safe.bareRepository`'s default opens the folder when the model names it.

For an object link, the outside target must be another repository's loose (not packed) object at a known path, by its id -- one commit id is enough, since the tools' errors name the tree and blob ids next. For the state files and `shallow`, any file the person can read, by its path.

**What already works.** `objects`, `refs`, `packed-refs` and `index` linked out are refused, and so is a link out directly inside `objects/` (an `objects/<2>` folder link) or `objects/pack/` (a pack file), before git reads anything; `HEAD` linked out is refused by git itself (`not a git repository`). An alternates line naming a store outside the root is refused. A folder remote whose store has an `objects/<2>` folder link out is `Not fetched`, nothing copied. `require_ref` refuses a reflog form (`HEAD@{1}`), so a linked `logs/HEAD` is not read that way. A link landing inside the root is followed, as 57o decided.

**Root cause.** `object_store_leak` names what git reads instead of judging the git directory: `kReadEntries` and the one-level `link_out_of` are a list, and git reads past it -- loose objects, deeper refs, `reftable/`, the pseudo-refs, the operation-state files, `shallow`, `info/*`, `config`, `modules/`. A list that already missed `reftable/`, which git 2.53 makes on request, will miss the next file too. The fix is the class: the whole git directory is judged.

**Core constraint(s).**
- **What the gate shows is what it enforces** (57o): a read the person was never asked about stays inside the root. A repository the tools read has no link anywhere git reads that leads out of the root.
- **Judged from the filesystem at every call** (57o's decision): no cache of a past verdict, since the model can change the folder between calls.
- **A link that lands inside the root is followed** (57o): a checkout with `hooks -> ../.githooks`, a linked worktree and a submodule keep reading, and 57o's worktree and submodule rules (`vouched`, `entry_inside`) are unchanged.
- **The review fetch's folder remote is judged as `repo` is** (57x): the walk covers it through the same constructor, so nothing outside is copied in.
- **Cost bounded**: the common git directory has no link at all, and the walk must stay cheap there (measured below).
- Windows link reading is 57k's seam; the git tools are not registered on Windows (57k), so the walk's Windows form is unexercised there.

**Seam + files.**
- `source/business/tools/git.cpp` -- `object_store_leak` (`:127-189`) becomes a walk: the git directory and the common directory, and each store in the alternates chain (which it keeps), recursively, refusing the first link whose target `lands_inside` (`:87-92`, the sandbox's `resolve_in_root`, `fs.cpp:275-325`) says leads out. `kReadEntries` (`:120-125`) and `link_out_of` (`:103-118`) give way to it. Its one caller is `confine` (`:464-485`), reached from the `Git` constructor for `repo`, the launch repository and the review fetch's folder remote (`:786-806`).
- Entry types from the directory listing (`std::filesystem::directory_entry`'s cached type) where the platform supplies one, `platform::is_link` (`infrastructure/platform/platform.h:116`) otherwise.
- `tests/business/tools/git_test.cpp` -- the cases below, beside 57o's `[57o]` and 57x's `[57x]` cases.
- Docs: `reference/cli/tools.md` ("What the gate shows is what it enforces": the git folder is judged whole, with its exceptions); `assistant/cli/CLAUDE.md`'s confinement invariant line; MILESTONES.

**Reference.** 57o (`Git::confine`, `object_store_leak`, `[57o]` cases in `git_test.cpp`) is the seam and the precedent: this item replaces its list with the walk its Not done anticipated. 57x's folder-remote rules (`judge_folder`) are the second caller. git's own `safe.bareRepository` and its 2.45.1 refusal of a local clone holding a loose link are the upstream precedents for distrusting links in an object store.

- 2026-11-15 -- **The class, not one more entry**: the fix judges the whole git directory rather than adding loose objects, state files, `shallow` and `reftable/` to the list, because the list's misses are the bug.
- 2026-11-15 -- **`modules/` is walked**, not excepted: excepting it left `modules/<name>/refs` linked out showing an outside id through the superproject's `git_diff` (probed).
- 2026-11-15 -- **Hard links are out of scope**: no link check can see one (a regular file), a local clone makes them for every object, and a hard link is a path inside the root to the same file, which the file tools read anyway.
- 2026-11-15 -- **v0.2.1, as 57y** (the user's call): fixed before the release that ships 57o's claim -- what the gate shows is what it enforces -- rather than queued as maintenance.
- 2026-11-15 -- **Objects a fetch already copied are not hunted**: once copied they are real files, indistinguishable from the repository's own.

**Open calls:**
- [default: the walk skips `hooks/`, `lfs/` and `annex/` at the top of the git and common directories -- folders the tools never read (`core.hooksPath=/dev/null`; filter drivers off, so no LFS or annex content is opened), and that people do link to their own hooks or to a large store on another disk. Everything else is walked, `rr-cache/` included: never read by these tools, but rare enough linked out that a refusal is the conservative side.]
- [default: a folder link that lands inside the root is walked where it lands, each resolved folder once, so a loop of links ends.]
- [default: `info/exclude`, `config` and `reftable/` linked out are refused like the rest: the tools read all three (probed), so a refusal there is the gap closed, not a false positive.]
- [default: the refusal is 57o's words, naming the first link found: `<path>, a link that leads out of it`.]
- [default: no timing test, which would be flaky; the walk's cost on this checkout and on a 50,000-loose-object store is measured at build and recorded in MILESTONES.]

**Measured cost of the walk** (the `cost` probe and its verifier, warm medians, 2026-11-15). This checkout's `.git` (2,460 entries, 2,031 loose objects, no links): about 7.7 ms with the cached type, about 12 ms with an `lstat` per entry, against about 0.6 ms for today's check. A store at `gc.auto`'s 6,700 loose objects plus 20,000 loose refs with reflogs (46,993 entries): 43 ms with the cached type (27 ms skipping `logs/`), 131-141 ms with `lstat`. 50,000 loose objects: 50-53 ms and 155-166 ms. On the first touch of an idle tree, `lstat` took 525-533 ms against about 51 ms for the cached type. One `git_status` call through the binary costs about 220-230 ms (six git processes; discovery about 11 ms), so a cached-type walk adds about 3% here and about 20% on the largest loose stores. `resolve_in_root` runs once per link (about 90 µs) and never when there are none. Built and run against a whole-directory walk with no exceptions, none of these was refused: linked worktrees (absolute and `--relative-paths`), a submodule from either side, `clone --shared` inside the root, a hardlinked local clone, git-lfs, alternates inside the root, hooks linked into the work tree, and git-new-workdir's links inside the root.

**Guardrail(s).** The probes become fixtures. Cases in `git_test.cpp`, tagged `[57y]` with `[tools][git][sandbox]`, POSIX only (they plant links; skipped on Windows, saying so), each with a plain-git control that shows git reading through the link -- so no case passes vacuously -- and each seen failing on the code before (the fixed list):
- loose-object links to an outside commit, tree and blob: `git_show`, `git_log` and `git_diff` refused naming the link, `OUTSIDE SUBJECT` and the file's text in no answer;
- `BISECT_START` (with `BISECT_LOG`) and `rebase-merge/head-name` linked to an outside plain file: `git_status` refused, none of the file's text shown; `shallow` linked out: all four refused;
- `CHERRY_PICK_HEAD` and `refs/heads/<name>` linked out: refused, no outside id; `reftable/` linked out where git supports `--ref-format=reftable` (skipped and said otherwise);
- an alternate store inside the root holding a loose link out, and an `objects/<2>` folder link landing inside the root on a folder holding one: refused;
- the review fetch from a folder remote whose store holds loose links out: `Not fetched`, and the fetching repository holds none of the outside objects afterwards;
- still reading: `hooks/`, `lfs/` and `annex/` linked out; a link landing inside the root; a loop of in-root folder links (ends, reads); 57o's linked-worktree and submodule cases unchanged.
