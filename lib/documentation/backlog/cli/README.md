# Apogee — Backlog

**The work queue: one document per work item.** This directory holds every feature and fix that has been discussed and specced but **not yet built** — the layer between the loose ideas in [ROADMAP.md](../../assistant/cli/ROADMAP.md) and the shipped record in [MILESTONES.md](../../assistant/cli/MILESTONES.md). There is no separate TODO file: an agent takes an item from the index below and **implements it straight from its document**. The release-by-release view across every product is the [backlog overview](../README.md); this index is the authority on its rows, and every change to it reaches the overview in the same pass ([Keeping this page true](../README.md#keeping-this-page-true)).

## Lifecycle

1. A feature is **discussed in chat** and gets a line on [ROADMAP.md](../../assistant/cli/ROADMAP.md) (and a [SPEC.md](../../assistant/cli/SPEC.md) update if it changes product shape).
2. Once specced — files, decisions, open questions — it gets **its own document in its table's subdirectory**, written as a ticket ([Document format](#document-format)) (the directory tree mirrors the index: `architecture/`, `maintenance/`, `v0.1.<x>/` — kebab-case filename, listed in the index below in priority order; the subdirectory is created with a table's first item). The same pass adds it to the [backlog overview](../README.md#keeping-this-page-true): its release's section, or its track's line under Later releases.
3. When an agent **takes** it (told explicitly, or via the bare-"Continue" convention: the topmost item whose gate is satisfied), the document **is** the working spec — confirm scope with the user first (the document's **Open questions** are the natural questions), mark its index row **in progress** and its ticket's header Status (🚧 In progress), and build. One item at a time.
4. When it **ships**, the work is recorded in [MILESTONES.md](../../assistant/cli/MILESTONES.md) per the docs flow in [CLAUDE.md](../../assistant/cli/CLAUDE.md), and the document is **deleted, along with its index row** — **a completed item must never remain in the backlog**. On the same pass, every item it gated has its index row and its ticket's header updated in the same pass: **Blocked by** loses the shipped id, **Status** turns 🟢 Ready when that was its last gate, and the shipped id leaves any **Blocks**. Its row leaves the [backlog overview](../README.md#keeping-this-page-true) too, with the counts, "can start today" and any "Waits on" it satisfied updated.
5. When a **version's table empties** — every item it held shipped or moved — the table is retired at the pre-merge docs pass (`/apogee-maintenance-update-documents`): its heading, track preambles and empty table leave the index, and the shipped-tracks paragraph above the tables says where its tracks went. The merge is the release, so a release's table never outlives its pull request (the user's call, 2026-10-16). The standing Architecture and Maintenance tables are never retired. The CLI's section of the [backlog overview](../README.md#keeping-this-page-true) then says its tracks shipped; when the release ships, the overview moves on to the next release.

**The standing invariant:** every document in this directory is pending work. If it's shipped (in MILESTONES.md), it's not here.

- **The key** names the queue: `CLI` here (`APP` for the Apple apps, `DSN` for the design, `MOD` for the mod), followed by the item's id from the index (`CLI-59d`, `CLI-M12`). The title words are the index row's.
- **The header restates the index row.** Status, Fix version, Blocked by and Blocks say what the item's row in the index says; **the index stays the authority**, so any change to a row (a status, a move to another table, a gate added or satisfied) changes the document's header in the same pass, along with the Epic and the key-id H1 when the move changes them.
- **The Status cell of an open question** is one of three tags: `[user]` (a genuinely user-owned decision: **blocks the build** until answered); `[default]` (the Answer is the recorded default: the agent takes it, records it as a dated row in the Decision log, and the user may veto); `(consumed decision)` (owned by another item, named in the Answer). An answered question leaves the table and becomes a Decision-log row.
- **Type** is 🐞 Bug for behaviour that is wrong today, ✨ Feature for a new capability, 🛠️ Task for upkeep with no user-visible change. A bug's Steps to reproduce come only from what was actually seen.
- **Line references into other backlog documents** name the document and its section, never a line number, since documents are re-shaped; line references into source code stay.

**On real weights.** A Testing line or acceptance criterion that runs on real models names the capability and the measure, not the models: it runs on [the model families](../../assistant/cli/DEVELOPER.md#on-real-weights-the-model-families) — Meta, Qwen, Google and OpenAI, one installed model each (its Q4_K_M build when there is one), never the excluded ones, one family at a time with its model loaded once (the user's calls, 2026-10-03). It is optional: a family with no local model is skipped and said. Where an older document names its acceptance models, the families replace them.

## Index

**One table per version target, every table in one shape.** Each release the queue is prescribed against — `v0.1.2`, `v0.1.3`, and every `vx.x.x` after them — gets its own table, and the tables appear in release order, nearest first — with two standing tables above them all: **Architecture** — the structural reshaping queue, numbered `A1, A2, …`, carrying `arch.` in the Version cell — and below it **Maintenance**, the release-agnostic upkeep queue (polish, performance, developer ergonomics), numbered `M1, M2, …` with `maint.` in the Version cell. The two standing tables are **permanent fixtures**: each keeps its heading, preamble and table even when every row has shipped or moved — an empty Maintenance table means nothing is queued, never that the queue is gone (version tables, by contrast, come and go with their releases). This is the format **all** index tables follow, now and as new versions open:

| Column | Contents |
|---|---|
| **#** | The item's number — its identity. Numbers ascend down the rows and across the tables; other documents cite them, so a renumber is a deliberate act, never a side effect of moving rows. Numbers are never reused: shipped items keep theirs in the [MILESTONES.md](../../assistant/cli/MILESTONES.md) record (1–23 are spent), so a new item continues from the highest number ever assigned — **unless it joins a release whose pending items already share a track prefix: then it takes that track's next letter** (26m, 26n, …), so a release's rows keep one prefix and the version tables stay ascending end to end. A **Maintenance** item takes the next `M<n>` and an **Architecture** item the next `A<n>` — each standing sequence ascends on its own, outside the release ascent. |
| **Item** | Plain title — em dash — one-line description. No link here; the link lives in **File**. |
| **Version** | The release the item is prescribed for — or `arch.`/`maint.` for the standing queues, which are prescribed to no release. The column stays even inside a per-version table, so a row keeps its meaning when it moves between tables and every table keeps the same shape. |
| **File** | The item's document, linked into **its table's subdirectory** (`architecture/…`, `maintenance/…`, `v0.1.<x>/…`) — the complete context for the item. The display name stays the bare filename. |
| **Status** | One emoji, plus the gate when blocked: 🟢 workable now (its gate is satisfied) · 🔒 blocked on the items named · 🚧 in progress · ❌ cancelled. |

Within a table, rows are in the **suggested build order**; the topmost 🟢 row of the earliest **version** table is the next item to take — the bare-"Continue" convention skips the standing queues (Architecture, Maintenance), whose items are claimable at any time *by name*. Moving an item to another version (or into a standing queue) means moving its row to that table, updating its Version cell, **and `git mv`-ing its document into that table's directory** (fixing the handful of relative links that cross directories), and moving its row on the [backlog overview](../README.md#keeping-this-page-true) to match — creating the table and the directory if it is the first item there. Same-table links are bare filenames; cross-table links are `../<table-dir>/<file>`; links out of the backlog climb to `lib/documentation/` and back down (`../../../assistant/<app>/…` from a version folder; one level more from a platform's own folder, `darwin/macos/v0.2.1/`).

**Gate convention:** every pending item builds on top of everything already shipped; a gate — the 🔒 cell in a table, restated in the document header's **Blocked by** — names only the ordering among the pending items here, and an item is buildable from its transitive gate chain alone. Items marked **split first** must be groomed into their listed sub-documents before an agent takes them; do not build from the guard document directly. A changed gate, or a split, changes the item's row on the [backlog overview](../README.md#keeping-this-page-true) in the same pass.

### v0.2.3

**The Apple-platforms plan: tracks 59, 60 and 61**, opened 2026-11-07. It came from a brainstorm run with Superpowers, on the user's vision: Apogee as a private, self-hosted harness that feels like Claude on every device the person owns. One strong machine (512 GB of RAM, a finely tuned large model, say) serves the person's own desktops and phones. The user's calls: server tools by default, with a connected desktop offering **its own files and shell**, as Claude Code does; the server **an add-on, never the only way Apogee runs**; iPhone and iPad clients of the person's server only; and **v0.2.5 the target** for macOS, iPadOS and iOS (the foldable iPhone included). A common tool definition comes before it, and Apogee-tuned training after it. The CLI's and the GUI's SPECs were amended the same day: the GUI reaches the CLI over stdio locally, or over an authenticated connection to the person's `apogee serve`. Measured the same day, `serve` is a model server. Its inference plane is unauthenticated (`--allow-remote` and "your own access control"), it has one admin token per install, and it serves one inference at a time. None of machine mode's events, questions or task progress go over the network. The split, release by release:
- **v0.2.3, the harness server** (59a–59e): paired devices, machine mode over the network, many sessions at once, reads and commands, and tasks that outlive the connection.
- **v0.2.4, one tool definition and device tools** (60a, 60b), beside the GUI's track 7.
- **v0.2.6, Apogee-tuned training** (61a, 61b).

One [user] call blocks only part of an item. In **59d**, training and the other long verbs, run from a paired device, would revise the SPEC's "Training control is CLI-only over HTTP"; those rows stay refused until it is answered. The GUI's half is [its tracks 7–9](../darwin/README.md).

**Apps as clients: 59f–59h, 60c–60e, and darwin 7d and 7e**, opened 2026-11-14 from that day's spike. The user's goal: other apps use Apogee as their AI back end, and Taylor'd Portfolio, the user's job hunter, is the first. The spike drove the branch binary (`b37b0a9f`) as such an app would. Plain answers already come back locally (`complete -q`, and `stream-json`'s closing `result` event). But `serve` **silently ignored** a `response_format` JSON-schema request, and it **refused an app's own tools** ("client-side tools are not supported"). Nothing limits what a paired credential may do. The Mac app's client core is 8 modules, 56 files and about 8,300 lines with no UI imports, but there is no `Package.swift` to depend on. The user's calls: the **full harness**; **both doors** (the OpenAI-compatible one, and Apogee's own protocol); a **scope per app**; a **Swift package** from the app's own code; standard OpenAI function-calling on the OpenAI door (reversing `serve`'s recorded "It does not run tools the client defines"); the CLI SPEC amended (Core surfaces 4, 2026-11-14); and the integration's maintenance written down as ADRs and contributor rules (60e, darwin 7e). Taylor'd Portfolio's own side is not specced now. No [user] call blocks any of these items.

### v0.2.4

**Track 60, one tool definition and device tools**, from the Apple-platforms plan ([preamble](#v023)).

**The server console: track 62**, opened 2026-11-14 from that day's admin-mode and people spike. The user's goal: Apogee is also where an owner decides what other devices and apps may do, from screens of their own. The spike drove the branch binary (`b37b0a9f`) against a scratch home and found nine walls (A1–A9): a running `serve` never sees a config change, and the admin plane reports the file rather than what it enforces (A1); nothing local can find or ask a running server, since `serve status` is refused and a serving home holds no record of the server, its address shown only on stderr (A2); nothing shows who is connected or what each client does (A3); there is no audit trail (A4); administering still crosses the network (A5); how clients connect lives in command-line flags, not settings (A6); the app cannot own the server's lifecycle (A7); a local admin screen lacks pending pairings, asked-for scopes, rename, the QR payload and JSON policy reads (A8); and no admin screen is designed (A9, darwin 10a). **People and access: track 63**, the same spike's second half (track 62's paragraph above).
