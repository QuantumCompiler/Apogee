# serve status: what the running server is doing, readable over pipes

**What / why.** The user's calls of 2026-11-14 (the admin-mode and people spike) give the Mac that serves an **"Apogee Server" window** that administers that Mac's server by driving the local CLI over pipes ([GUI SPEC](../../../assistant/gui/SPEC.md) → Core surfaces 3; [CLI SPEC](../../../assistant/cli/SPEC.md) → Core surfaces 4, "Revised again 2026-11-14": "The server is administered on its own Mac"). The window's first question, and every admin read's, is whether this install is serving, where, how, and what the server is doing now. Today only the running `serve` process knows, and it tells nobody but its own stderr. This item makes a running server findable and askable from any local process: `serve` keeps a private **runtime record** while it runs, and **`apogee serve status`** reads it and asks the server itself, over loopback with the admin token, for its live state. Every other admin read in track 62 builds on it: reload and served-vs-disk ([62b](serve-reload-and-served-vs-disk.md)), the background service ([62d](serve-as-a-background-service.md)), connections and activity ([62e](connections-and-activity.md)), and the server window ([darwin 10b](../../darwin/macos/v0.2.4/server-window.md)).

**A2 — the CLI cannot find or ask a running serve.** Found by the spike on 2026-11-14 and re-measured the same day against the branch binary (`apogee 0.2.0 (b37b0a9f)`), a scratch `APOGEE_HOME` under the session scratchpad, and the `mock` backend, with `serve --bind 127.0.0.1 --port 0` killed after:

1. **No verb asks a server anything.** `apogee serve status` exits `109` with "The following argument was not expected: status". `serve --help` lists start flags and `--print-admin-token` only. The root help names no stop or status verb.
2. **Nothing on disk says a server is running.** While it served, the home held exactly `config/admin-token`, `config/config.json`, `config/config.json.lock` and `logs/apogee-2026-11-14.log`: no pid, address or runtime file. After `kill -TERM` the tree was identical. After `kill -9` it was identical too, so today there is nothing to be stale, and nothing to find.
3. **The address goes to stderr only.** The listener reports the bound port through `on_listening` (`presentation/httpserver/serve.cpp:198-200`), and the command prints it and nothing else (`presentation/cli/serve_cmd.cpp:448-450`, `listening on http://127.0.0.1:54989` in the probe). The operational log's start line names the served backends but no address, port, pid or flags (`serve_cmd.cpp:476`; the probe's log: `INFO [serve] serving mock (default mock) -- tools: none -- rag: off -- sessions idle out after 60 min`). With `--port 0`, the port exists nowhere but that stderr.
4. **The server has no status route.** With the admin token, `GET /v1/admin/status`, `/v1/admin/connections` and `/v1/admin/server` answered `404`; `GET /v1/admin/backends` answered `200`. `GET /health` is `{"status": "ok"}` and "Never calls a model" ([http-api.md](../../../reference/cli/http-api.md):238-240; `handler.cpp:909-911`). The live session count exists in memory (`SessionStore::size`, `httpserver/session.h:75`) and reaches no route as a number. The listener counts no connections: httplib's server gets routes and a logger only (`serve.cpp:141-185`).
5. **`check` has no server row.** `check --output-format json` (91 rows) mentions the server only as `Admin token: present, private (0600)` (`check_secrets`, `check.cpp:1298-1326`, the row at `:1326`), which says a server once ran, not that one runs.
6. **Two servers on one install both start.** Two `serve --port 0` on the same home listened on `:55005` and `:55006` side by side. Whatever this item writes must not assume one server per install.

So an app driving the CLI over pipes cannot tell whether the server is running, on which address, with which flags, or what it is doing, unless it started the server itself and scraped stderr. The window's own lifecycle answer (a background service, 62d) has nothing to report through either.

This item delivers:
- **The runtime record.** Once the port is bound, `serve` writes one `0600` JSON file per running server: pid, an instance id, version and channel, start time, the address (scheme, host, port, URL, whether loopback), the admin plane's location (its URL and the path of the token file, never the token), the config path, the effective flags, and the served backends with the default. It is removed on every stop. A record whose pid is not running is **stale**, and is said so.
- **`GET /v1/admin/status`**: the server's live state behind the admin bearer. It carries the instance id, start time and uptime, version, each served backend with its load state, the live session count, open connections and requests in flight, and running admin jobs.
- **`apogee serve status [--output-format text|json]`**: it reads the records and asks each live server over loopback with the admin token, and prints one document per server: `running`, `not_running`, `stale` or `unresponsive`. With no server it says so: "no server is running for this install".
- **`check`'s Server rows**: whether this install serves, from the record and its pid alone (no socket), with stale records removed by `--fix`.

**Core constraint(s).**
- **Remote mode is an add-on (the anti-goal).** Nothing here may make standalone use need a server or an account. `chat`, `complete`, `execute`, `task`, `acp`, `mcp serve` and the Mac app over pipes never read the runtime record and never need it. The record exists only while a `serve` runs. `serve status` on an install that has never served answers "not running" and **creates nothing**: no record directory, and no admin token (it reads the token with a read-only load this item adds, never `load_or_create_admin_token`, `admin_auth.h:29-31`; at HEAD that and `generate_admin_token` (`:34`) are the header's only token functions, so there is no read-only load yet). A fresh install with no keys and no models still passes `check` (SPEC → Success criteria), with the new row Ok ("not running").
- **Serving = server; interactive turns never listen** ([CLAUDE.md](../../../assistant/cli/CLAUDE.md) → Interactive turns never open a listening socket). Only `serve` owns a port, and `httpserver/serve.cpp` stays the only object that references `listen`/`accept`. `serve status` is an HTTP **client** of its own install's server, as `curl` is: it connects to the address the record names and opens no socket of its own to listen on. `cli.no_listen_symbols` stays green unchanged. Nothing in `httpserver/` becomes load-bearing for `chat` or `complete`. The GUI law "the app never connects to a server on its own machine" ([GUI SPEC](../../../assistant/gui/SPEC.md):34) holds: the server window spawns `apogee serve status` over pipes, and the CLI does the asking.
- **Secrets are unleakable by construction** ([CLAUDE.md](../../../assistant/cli/CLAUDE.md) → Secrets are unleakable by construction). The record names the token **file**, never the token, and no type that serializes the record or the status document has a token field. `serve status` reads the token into a local string, sends it as `Authorization: Bearer` (header-only, as the gate requires, `mux.cpp:638-639`), and never prints, logs or returns it. The record is written `0600` through `harness::write_file_atomically(…, /*private_mode=*/true)` (`contracts/config_edit.h:478`) in a `0700` directory. `GET /v1/admin/status` carries no path, no pid and no config value: the record, read locally, is the one place those live.
- **One config mutation path** ([CLAUDE.md](../../../assistant/cli/CLAUDE.md) → One config mutation path). The record is not configuration and is never written through or into the config. Nothing in this item edits `config.json`. The effective flags are reported, not stored as settings: storing them is [62c](serve-section-in-config.md)'s.
- **Older versions keep working** ([ADR 0006](../../../adrs/cli/backwards-compatibility.md)). Everything is additive: a new file, a new subcommand, a new admin route, new `check` rows. `apogee serve` with no verb serves exactly as today, with the same flags, start lines and exit codes. Two servers on one install still both start. The record carries `"schema": 1`, and later items (62b-62e, 59a) add fields, never rename or remove one.
- **Parity** ([ADR 0002](../../../adrs/cli/mode-parity.md); [ADR 0010](../../../adrs/cli/the-shell-is-a-mode.md)). `serve status` is a read served by `GET /v1/admin/status` in the CLI↔HTTP parity table (`tests/presentation/httpserver/parity_test.cpp`, whose `serve` row is `carve_out("it is the server")` at `:172`). The live half is the route; the record half (pid, paths) is host-local by nature, and the row says so. The shell's exec line refuses `serve` by word prefix today (`cli/tui_parity.cpp:126-128`), which would refuse `serve status` with it. That changes here (Open calls). The app's own table is darwin 10b's.
- **The layers** ([ADR 0001](../../../adrs/cli/layer-enforcement.md), [ADR 0008](../../../adrs/cli/module-map.md)). The record's shape, its reader and writer, and the stale sweep sit in Data. The status route and the connection counters sit in `httpserver` (Presentation). The verb and the `check` rows sit in `cli`. The loopback query goes through `data/transport`'s `HttpTransport` (`transport/http_client.h:16-29`, the class at `:108`), so its tests run against a scripted transport. A new module is declared in `cmake/modules.cmake`, and its links point down.
- **The dev channel** ([CLAUDE.md](../../../assistant/cli/CLAUDE.md#development-runs-on-the-dev-channel)). Any live pass runs `apogee-dev serve` and `apogee-dev serve status` over `~/.apogee-dev` and never touches the release `apogee` or `~/.apogee`. No launchd agent is loaded or bootstrapped by this item or its tests; that is [62d](serve-as-a-background-service.md)'s, and its tests' own rules.

**Reference.**
- In-house precedents:
  - The PID lock (`platform/pid_lock.h:8-23`, Milestone Z and 27h): a file holding a pid, made exclusively, its holder read as running through `process_running`, a dead holder's file taken over only by the one who means to (`take_stale`). The record follows that shape, and its reads never take over.
  - The admin token beside the config (`admin_auth.h:9-31`): it follows `--config` and `--custom`, and `check` says "not generated yet" as an Ok row (`check.cpp:1303-1307`). The record follows the same rules, since it names that token.
  - `write_file_atomically(…, true)` for private writes (`config_edit.h:478`).
  - `data/transport`'s scripted `HttpTransport` seam (`http_client.h:16-29`, `:108`), which keeps the cloud backends' tests off the network.
  - `GET /v1/model/status` (`handler.cpp:887-907`), whose per-backend load state the status route reuses rather than re-deriving.
- Prior art:
  - Jupyter's runtime files: each server writes `jpserver-<pid>.json` (pid, URL, port and more) in a per-user runtime directory, and `jupyter server list` reads them and drops the dead ones. Divergences: Jupyter's file carries the server's token, and ours names the token's file only. A read here never deletes: the next `serve` and `check --fix` do.
  - Ollama's CLI asks its own local server over loopback HTTP (`ollama ps` lists what the server has loaded). Apogee's verb does the same, but finds the server through the record instead of a fixed port, since `--port 0` and two servers on one install are both legal.
  - Pid files under a service manager (`/var/run/*.pid`, `systemctl status`): a pid alone cannot tell a hung server from a reused pid. The instance id answered over loopback is what tells this server from any other process.

**Decisions made** (dated):
- 2026-11-14 — The user's call: an admin mode, a separate "Apogee Server" window in the macOS app, offered only on the Mac that serves, driving the **local CLI over pipes**. That makes a server's state a thing the CLI must be able to read over pipes, which is this item's reason to exist.
- 2026-11-14 — The user's call: the window installs the server as a background service (launchd) and starts, stops and restarts it ([62d](serve-as-a-background-service.md)). A managed server and a hand-started one must both be findable the same way, so the record is written by `serve` itself, never by the service wrapper.
- 2026-11-14 — The user's call: administering is local by default, and the owner may mark chosen paired devices as allowed to administer remotely ([62g](administering-local-and-marked-devices.md)). That revises [59d](../v0.2.3/reads-and-commands-over-the-network.md)'s default of one admin token for any network caller; otherwise the admin plane stays local-only. `serve status` asks only the server on its own machine. A remote device's view of server status goes through 62g's path, not this verb.
- 2026-11-14 — The user's call on placement: the server console (CLI track 62, darwin/macos track 10's 10a-10b) and people and access (CLI track 63, darwin/macos 10c) both go in v0.2.4, with nothing already queued renumbered. This item is 62a, the first of the track and ungated, because 62b, 62d, 62e and darwin 10b all need a server they can find.
- 2026-11-14 — The standing law, restated by the user the same day: remote use is an add-on, and the CLI alone and the Mac app over pipes stay complete and need no server. Hence the anti-goal above: nothing reads the record except `serve status` and `check`.
- 2026-11-14 — The user's calls on people and access (v0.2.4, track 63) shape what this item may report. The owner sees members' metadata (devices, apps, activity, which model, when), never chat contents, so the status route and the record carry counts and states only: no session id, no message, no prompt, and no person, since a person exists only from [63a](people-on-one-server.md). The user's words are "people" and "access" (Owner, Member), never "roles", which in Apogee means model roles; nothing here names either. The taken default that live changes apply on the spot, with what still needs a restart said, is [62b](serve-reload-and-served-vs-disk.md)'s, and this item's record is what 62b compares against.
- 2026-11-14 — The SPEC amendments this item serves are already written: CLI SPEC Core surfaces 4 ("Revised again 2026-11-14") and GUI SPEC Core surfaces 3 (the server window). No SPEC edit rides with this item.

**Open calls:**
- [default: the record lives at `<dir of the config file>/servers/<pid>.json`, beside the admin token it names. It follows `--config` and `--custom` as the token does, so `serve status` with the same root flags finds the server started with them. It sits inside `config/`, which the layout already marks private, so no layout row is added and `cli.install_parity` is untouched (the directory is created by the first `serve`, never seeded). The alternative, a new private `run/` layout row in the data directory, would change every install path and `check`'s Filesystem rows for one file a running server leaves, and is not taken.]
- [default: one record per running server, named by its pid. Two servers on one install both start as today (ADR 0006), and `serve status` lists each. The usual case, and what the server window shows, is one. When it finds more than one, the window says so; that is darwin 10b's to draw.]
- [default: the record is written once the port is bound, in `on_listening`, so it always holds the real port, `--port 0` included. It is removed on every return from `run_server`, normal or thrown. A `kill -9`, a crash or a power loss leaves it stale.]
- [default: stale means the pid is not running (`process_running`). The next `serve` sweeps stale records before it writes its own, and `check --fix` removes them. `serve status` and plain `check` report a stale record and never delete it (a read writes nothing).]
- [default: a record whose pid is running but whose server does not answer within the timeouts, or answers with another instance id, is `unresponsive`, with the reason ("no answer on <url>", "another server answers on <url>"). That covers a hung server and a reused pid alike, and the verb does not guess which.]
- [default: the record holds the **effective** values (the bind, the requested and the actual port, `allow_remote`, `-m` or `--all-backends`, the served list and the default, `tools`, `search`, the RAG collection and its source, `rag_limit`, `retriever`, `rerank`, `preload`, `ignore_timeout`, `session_ttl` in minutes, `verbose`), never the raw argv. A later flag can't then smuggle anything into the file unexamined.]
- [default: `GET /v1/admin/status` answers `{instance, started, uptime_seconds, version, backends: [{name, default, state}], sessions: {live}, connections: {open, in_flight}, jobs: {running}}`. `connections.open` counts the asking connection, and the reference says so. No path, pid or config value is included: those are the record's, read locally.]
- [default: `serve status` exits `0` whenever it answers, in every state, the state being in the document. That is the house rule for a read that succeeded. A record directory it cannot read is the usual user error, naming the path.]
- [default: the text form is one block per server: state and pid, the URL and whether it is loopback, since when (and uptime), what it serves, live sessions, open connections and requests in flight, running jobs, the admin URL and the token file's path. With no server: "no server is running for this install (<config dir>)".]
- [default: `check` gains a `Server` section from the record and the pid alone. It opens no socket, so `check` stays offline and fast. The live half is `serve status`'s.]
- [default: the shell's exec line runs `serve status`. The `serve` refusal becomes an exact match on bare `serve`, keeping its reason, and the refusal's tests pin both. If the table cannot express an exact match without growing a new kind of row, it gains one, and the tests pin it.]

**Guardrail(s).**
- **The spike's probe is the regression fixture**: `cli.serve_status` (`tests/scripts/sh/serve_status.sh`) runs the branch binary against a temp `APOGEE_HOME` with the mock backend, and `serve --bind 127.0.0.1 --port 0` in the background, with stdin from `/dev/null`:
  - While it serves, `serve status --output-format json` reports `running` with the pid, and with the port the start line printed.
  - A served chat with a `session_id` moves `live.sessions.live` to 1.
  - After `kill -TERM` the record is gone and the state is `not_running`.
  - After `kill -9` the state is `stale`, `check` warns and `check --fix` removes the record. A second `serve` started over a stale record sweeps it.
