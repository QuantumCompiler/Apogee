# Provider credential store: 0600 slots, `apogee auth`, one key resolver, and the `/v1/admin/auth` routes

**What / why.** Apogee calls three vendors' APIs directly, so it owns the keys — where Ommi could delegate Claude's auth to the `claude` CLI, Apogee cannot. Today a key lives in `config.yaml` (`api_key: "${OPENAI_API_KEY}"`, expanded at load) or in nothing at all. This item gives a key one proper home and **one** way to find it. **The store**: a `0600` JSON file beside the config (`~/.apogee/config/credentials.json`, following `--config`, exactly where the admin token lives) with one slot per **API-billing provider type** — `anthropic`, `openai`, `google` — holding the key and when it was stored. Vendor-CLI types are **not** slots: `claude-cli`, `codex-cli`, `gemini-cli` and `ollama-cli` authenticate through their own CLIs, and Apogee never stores, reads, or proxies their credentials (SPEC.md → *a vendor CLI is spawned, never opened*); asking to store one is refused with that sentence. **Unleakable by construction**: the only type any listing, response or event ever serializes is a `CredentialMetadata` that structurally has no key field — `provider`, `stored_at`, and which source currently answers for that provider — so a code path that marshals it cannot leak a secret even when a later contributor forgets the rule. **One resolver**, in a leaf package, that every consumer calls — the provider factory when it builds a cloud backend, `apogee check` and `models status` when they report, `auth list` when it says what is in effect — with the precedence decided 2026-08-24: the entry's `api_key` (which may itself be `${ENV}`-expanded) **>** the stored slot **>** the ambient conventional variable (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY` then `GOOGLE_API_KEY`), with the environment **snapshotted once at process start** so two writers racing on one process cannot change a resolution mid-run. The three cloud backends stop reading `config.api_key` themselves and receive the resolved key from the factory, so they stay unaware of where it came from. **The CLI**: `apogee auth add <provider>` (a hidden prompt by default, `--stdin`, or `--from-env` copying the ambient variable into the store — never the key on the command line, which lands in shell history and process listings), `auth list` (metadata only), `auth clear <provider>`. **The routes**, on the admin plane doc A builds: `GET /v1/admin/auth` (metadata), `PUT /v1/admin/auth/{provider}` with the key in the **body only**, `DELETE /v1/admin/auth/{provider}`. The secret-accepting route is served to **loopback peers only** — `403` otherwise, whatever the bind — judged from the connection's own peer address (`HttpRequest::remote_address`, which the listener fills from the accepted socket), never from a forwarded header a client can set.

**Core constraint(s).**
- **Secrets are unleakable by type construction, not discipline**: serialized types have no secret field; intake is body-only; the key appears in no response, event, log line, error message, or `check` row. A leak grep across every surface is the standing test.
- **Env precedence snapshotted once at process init.** Two environment writers on one process race (Ommi's OMMI-9 lesson); the snapshot is taken before anything resolves and never refreshed.
- **Loopback peer judged from the socket address, never a forwarded header**, on any secret-accepting route, regardless of `--allow-remote`. A spoofed `X-Forwarded-For` must change nothing.
- **API-billing providers only.** No slot, no resolution, no route for a vendor-CLI type — the principle that Apogee never routes a subscription credential holds here exactly as it does for serving.
- **Per-install secrets are install-parity-exempt but doctor-checked.** The credentials file is never seeded, so `cli.install_parity` never sees it; when it exists, `apogee check` requires `0600` (`skipped` on Windows, never a pass).
- **One resolver.** `cli.one_role_resolver` has a sibling here: no file outside the resolver, the factory and the two reporting commands may read `api_key` or the conventional variables directly. A second precedence chain is how the CLI and the server come to use different keys.
- **One config mutation path** is untouched: the store is a separate `0600` file, and this item writes nothing into `config.yaml`.
- **Layering**: the store and resolver are a leaf package; `backends/factory.cpp` (the composition root's factory) includes it, the providers do not; `harness/` includes nothing from it or from `backends/`.

**Seam + files.** `lib/src/cli/source/secrets/store.h/.cpp` (`CredentialStore` over the `0600` file: `load`, `put(provider, key)`, `clear(provider)`, `list() -> std::vector<CredentialMetadata>`; the `Credential` type is private to the package); `lib/src/cli/source/secrets/resolve.h/.cpp` (`EnvSnapshot` taken once, `resolve_api_key(entry, store, snapshot) -> Resolution{key, source}`, `KeySource{Config, Store, Environment, None}`, the conventional variable table per provider type); `lib/src/cli/source/secrets/secrets.h` (umbrella for `tests/packages_test.cpp`); `lib/src/cli/source/backends/factory.cpp` (resolves before `from_config`, hands the key in; `anthropic.cpp`/`openai.cpp`/`google.cpp` take the key as an option and stop reading `config.api_key`); `lib/src/cli/source/commands/auth_cmd.h/.cpp` (`auth add|list|clear`, the hidden prompt through the platform seam); `lib/src/cli/source/commands/check.cpp` (the credentials-file mode row; the backend rows say which source answers, never the key); `lib/src/cli/source/commands/models.cpp` (`models status` names the source); `lib/src/cli/source/httpserver/admin_auth_routes.h/.cpp` (the three routes over the store, `require_loopback_peer` from `remote_address`); `lib/src/cli/source/httpserver/mux.cpp` (three rows) and `lib/documentation/reference/http-api.md` (their headings). Tests: `lib/src/cli/tests/secrets/store_test.cpp` (round trip, `0600`, a corrupt file degrades to an empty store with a warning, never a crash), `resolve_test.cpp` (the precedence table; the snapshot ignoring a later `setenv`), `leak_test.cpp` (the grep: configured secrets never appear in `auth list`, `check`, `models status`, any admin response, any bus event, any log line), `lib/src/cli/tests/httpserver/admin_auth_routes_test.cpp` (loopback peer required for `PUT`, `403` with a spoofed forwarded header from a non-loopback `remote_address`, metadata-only responses), the backend fixtures extended (each cloud backend built with a store-resolved key sends it in the header the wire tests already check), and `tests/serve_e2e.sh` (a key stored with `auth add --stdin` is used by a served backend and appears in no output).

**Reference (Ommi).** `src/gitlab/store.go` (the `0600` sibling file, the `Credential`/`Metadata` split where `Metadata` "deliberately has no Token field, so a code path that marshals Metadata cannot leak the secret by construction"), `src/gitlab/env.go` (the environment interplay and the race it records — OMMI-9), `src/httpserver/git_auth.go` (`peerIsLoopback` reading the connection's `RemoteAddr`, "deliberately not X-Forwarded-For", failing closed on an unparseable address; `requireLoopbackPeer` → `403`). Divergences: the credential plane centres on cloud provider API keys rather than GitLab personal access tokens, using git-auth's exact security pattern; there is no rotate/verify against a vendor endpoint (the vendors expose no key-introspection API); and the precedence puts the config entry **first** — Ommi's git token had env-always-wins, but a multi-backend config can point different backends at different keys, and `${ENV}` expansion already covers env-driven config.

**Decisions made** (dated):
- 2026-08-24 — Precedence: config `api_key` (possibly `${ENV}`-expanded) > stored slot > ambient conventional env, snapshotted once at init. This deliberately diverges from Ommi's env-always-wins git-token convention (above); revisit if it surprises.
- 2026-09-13 — **Split out of `admin-plane-foundation` at grooming** as doc B, gated on the admin plane (shipped the same day, Milestone U): the `PUT` route accepts a secret, so it needs the bearer gate and the loopback-peer rule before it can exist.
- 2026-09-13 — **Slots are keyed by provider type, not by backend entry.** Two `openai` entries with different keys is exactly what a per-entry `api_key` in the config is for (the first rung); the store answers "the key for this vendor", which is the case a user actually has.
- 2026-09-13 — **The resolver runs in the factory, not in each provider.** The providers take a key and stay unaware of stores, snapshots and precedence; one place resolves, and the three wire fixtures that already assert the auth header prove the retrofit without learning anything new.

**Open calls:**
- [user] OS keychain (Security.framework / libsecret / the Windows credential vault) as the backing store versus the plain `0600` file. The plan's default is file first, with a keychain as an upgrade behind the same `CredentialStore` interface — but whether a keychain is wanted at all, and on which platforms, is yours.
- [user] Whether `api_key` in `config.yaml` remains a supported first-rung fallback long-term, or is deprecated toward the store once it exists (with a `check` warning nudging the move). The precedence above assumes it stays.
- [user] Whether git-forge (GitHub / GitLab) credential slots land here, or with the analyze/agents grooming — rides the forge-target decision, which is also yours.
- [default: no key fragment in metadata] Not even the last four characters: a fragment is a partial secret, the vendors do not show one for these keys, and `stored_at` plus the source in effect is enough to know what will be used.
- [default: `GEMINI_API_KEY` before `GOOGLE_API_KEY`] The `google` provider's conventional variable — the Gemini SDKs read `GEMINI_API_KEY` first; both are honoured, in that order.
- [default: `auth clear` is bearer-only, not loopback-gated] It accepts no secret and mints none; a remote operator may revoke.

**Guardrail(s).** The leak grep across every surface is the standing test, run with a distinctive fixture key so a match cannot be accidental. The precedence table is exhaustive (each source present/absent × the others). The snapshot test mutates the environment after init and asserts the resolution did not move. The loopback test sends a spoofed forwarded header from a non-loopback `remote_address` and asserts `403`, and sends nothing special from a loopback one and asserts `200`. The `0600` test asserts the mode after `put`, and that `check` fails a file left `0644`. The CLI test asserts the key is never accepted as an argument. The wire fixtures assert each cloud backend sends the resolved key in its header.

**Acceptance criteria:**
- [ ] A key stored with `apogee auth add` is used by the matching cloud backends without appearing in `config.yaml`; `auth list`, `check`, `models status`, every admin response, event, error and log line show metadata only (the leak grep is green across surfaces)
- [ ] Precedence holds in every combination — config entry, then store, then environment — and is snapshotted once: mutating the environment mid-process cannot change a resolution
- [ ] `PUT /v1/admin/auth/{provider}` `403`s a non-loopback peer regardless of the bind, ignoring any forwarded header; `GET` returns metadata only; `DELETE` clears
- [ ] A vendor-CLI provider type is refused by `auth add` and by the route, with the principle named
- [ ] The credentials file is `0600` after every write and `apogee check` fails a wrong mode (`skipped` on Windows); `cli.install_parity` is unaffected
- [ ] The anthropic/openai/google backends resolve keys through the shared resolver under the decided precedence, covered by the existing backend fixtures, and no file outside the allow-list reads `api_key` or the conventional variables directly

**Scope note.** Its gate is satisfied: the admin plane shipped 2026-09-13 ([MILESTONES.md](../assistant/MILESTONES.md) → Milestone U) — the bearer gate in `httpserver/mux.cpp`, the loopback-peer rule already applied to a literal `api_key` in `httpserver/admin_config.cpp` (reuse `is_loopback_host` on `HttpRequest::remote_address`), the `0600` private-mode write in `harness::write_file_atomically`, the doctor's `Secrets` section with `fix_secret_mode`, and the parity table in `tests/httpserver/parity_test.cpp` (add the `auth` subcommands as twins) all exist. Out of scope: an OS keychain (a `[user]` call above; the `CredentialStore` interface is the seam), key rotation or verification against vendor endpoints (none exist for these keys), git-forge credentials (a `[user]` call above), and any change to how vendor-CLI backends authenticate — they never will through Apogee.
