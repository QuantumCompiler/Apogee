# The iPhone app

**What / why.** The user's vision, 2026-11-07: Apogee as a private, self-hosted harness that feels like Claude on every device the person owns, with one strong machine of theirs serving their desktops and phones. On the iPhone that means a person picks up their phone, opens Apogee, and is in their conversation, with every place of the Mac app within reach. The iPhone is a client of the person's own Apogee server only (the GUI SPEC's [mobile applications](../../../../assistant/gui/SPEC.md#core-surfaces)). By this item, the code builds for iOS ([8a](../../v0.2.5/app-builds-for-ios-and-ipados.md)), the app reaches a server ([7a](../../v0.2.4/app-connection-local-or-server.md)), every place works against one ([7c](../../v0.2.4/every-place-against-a-server.md)), and the iPad has its regular-width app with pairing ([8b](../../ipados/v0.2.5/ipad-app.md)). What remains is the phone's size. Measured at HEAD (`4f92316d`) on 2026-11-07:

**W10 — no compact layouts.** The app has one shape: a wide window with a sidebar beside the place.
1. **The window is at least 960 × 640 points** (`source/presentation/styles/Metrics.swift:26-27`, applied at `source/presentation/app/Views/ApogeeApp.swift:83`). An iPhone in portrait is 375 to 440 points wide. The Settings window asks for 860 (`settings/Views/SettingsView.swift:58`) and the console for 720 × 480 (`console/Views/ConsoleView.swift:127`). Training and Knowledge each set a fixed 380-point page beside a list at least 380 and 360 points wide (`training/Views/TrainingScreen.swift:201`, `:213`; `knowledge/Views/KnowledgeScreen.swift:125`, `:137`), wider together than any phone.
2. **The narrowest layout the shell knows is still a sidebar.** `ShellLayout` (`shell/ViewModels/ShellViewModel.swift:111-135`, the struct from `:114`) has three cases: the full 256-point sidebar, a 56-point column of icons below 900 points (`collapseBelow`, from `tokens.json` `layoutPx.collapseBelow`, `lib/design/spec/json/tokens.json:365-368`), or hidden. `ShellView` lays out an `HStack` of sidebar and place (`shell/Views/ShellView.swift:31-34`). There is no tab bar, no navigation stack and no size-class read: a search for `horizontalSizeClass`, `NavigationStack`, `NavigationSplitView` and `TabView` over `source/` finds none.
3. **A narrow window loses whatever sits in a side pane, so it cannot just be shrunk.** Below 900 points `sidePanes` is false (`ShellViewModel.swift:128`, set at `:131-133`). The Sessions inspector's button is then disabled (`sessions/Views/SessionsScreen.swift:30`, `:113`, and its ⌥⌘I at `:373-374`), a backend's details are not drawn (`models/Views/ModelsScreen.swift:56`), a stored set's details are not drawn (`models/Views/StoreView.swift:18`), and a graph node's explanation is not drawn (`graph/Views/GraphScreen.swift:88`). On a phone those would have no way in at all. That would be a parity loss under [ADR 0003](../../../../adrs/gui/parity.md).
4. **The keyboard carries many acts.** There are 77 `.keyboardShortcut` call sites under `source/`, and the shell's `KeyMap` lists the design's whole keyboard. Without a hardware keyboard, every act needs a control a finger can reach.
5. **The design draws no phone.** No file in `lib/design/spec` mentions an iPhone, an iPad or a mobile layout (a case-insensitive search for `iphone|ipad|mobile` matches none).

**Context, owned elsewhere (not this item's walls).** The project builds macOS only: `SDKROOT = macosx` in both configurations (`Apogee.xcodeproj/project.pbxproj:7889`, `:8744`). That is 8a's. The served API has no pairing: `apogee serve --help` on the branch binary (`apogee 0.2.0 (4f92316d)`, a scratch `APOGEE_HOME`) names no pairing or device flag (a search for `pair|device` returns 0). `apogee __machine-schema` (53,726 bytes) has no transport or pairing field, and its one `device` property is the `ready` event's runtime (`cuda`, `mps`, `cpu`). That is CLI [59a](../../../cli/v0.2.3/paired-devices.md) and [59b](../../../cli/v0.2.3/machine-mode-over-the-network.md). A served session is already a chat session, written to the file `apogee chat` writes under the same id, so a conversation started over HTTP continues with `--resume` ([http-api.md:210-214](../../../../reference/cli/http-api.md#sessions)). The machine mode names each session's chat by `chat_id` ([machine-mode.md:107-116](../../../../reference/cli/machine-mode.md#which-chat-chat_id)). Continuing a conversation on another device builds on both.

This item delivers:
- **The iPhone app**: every place of the app in compact layouts (a tab bar and stacks), opening on the conversation first.
- **Remote only**: the server reached over 7a's connection, which is the only transport on the phone.
- **Pairing on first launch**: 8b's pairing in a phone-sized flow.
- **The same parity table**: every place, the console, the monitor and Settings reachable by touch.
- **A session continued across devices**: a conversation started on the Mac against the server is opened and continued on the iPhone, through the server, and back.

**Core constraint(s).**
- **Anti-goal: nothing here may make standalone use need a server** (GUI SPEC → [No server requirement](../../../../assistant/gui/SPEC.md#non-goals)). The Mac app over pipes to its local CLI, and the CLI alone, stay complete and the default. Compact layouts are Presentation views selected by size class. The Mac's local transport, its discovery and its settings are untouched. Cross-device continuation covers conversations that live on the server. A Mac in local mode keeps its chats in its own `~/.apogee`, uploads nothing and contacts no server.
- **The machine-mode client rule, as amended 2026-11-07** ([GUI CLAUDE.md → The GUI is a machine-mode client](../../../../assistant/darwin/CLAUDE.md#-the-gui-is-a-machine-mode-client)): on the iPhone the machine mode arrives only over the authenticated connection to the person's own `apogee serve`. It is the same protocol, decoded with the same tolerance, with no capability of the app's own. The phone never listens. Its connection is outbound, and serving stays the server's job (the CLI's [never-listens rule](../../../../assistant/cli/CLAUDE.md#-interactive-turns-never-open-a-listening-socket): interactive = pipes, serving = server).
- **Secrets are unleakable** (the CLI's [invariant](../../../../assistant/cli/CLAUDE.md#-secrets-are-unleakable-by-construction); the GUI rule's last line): the pairing credential is held in the iPhone's Keychain by 8b's mechanism and never appears in a view, a log, a preview or a recorded fixture. Keys for providers are still entered through the CLI's own flows on the server.
- **Additive protocol** (the CLI's [ADR 0006](../../../../adrs/cli/backwards-compatibility.md)): the phone tolerates every event and field it does not know, and never needs a protocol change that breaks an older front end. A server without the cross-device fields still opens its chats from the library (the M7 path), without the "continued from" line.
- **Parity** (the GUI's [ADR 0003](../../../../adrs/gui/parity.md); the CLI's [ADR 0002](../../../../adrs/cli/mode-parity.md) on the far side): one `ParityTable` for every size. The phone adds no carve-out of its own. A place that is awkward on a small screen is still a place.
- **The layers and MVVM** ([ADR 0001](../../../../adrs/gui/layer-enforcement.md), [ADR 0002](../../../../adrs/darwin/presentation-mvvm.md), [ADR 0004](../../../../adrs/darwin/module-schemes-and-previews.md)): compact is a view concern. View-models stay shared, SwiftUI-free and unchanged in meaning. Size class is read in Views and handed to the shell's view-model as a value. Compact views live in their own modules' `Views/`, shared pieces in `styles`, and every compact state has a named `#Preview`.
- **The dev channel** (the CLI docs' [Development runs on the dev channel](../../../../assistant/cli/CLAUDE.md#development-runs-on-the-dev-channel)): a development build of the iPhone app is the dev identity (8a's and M18's identifier) and pairs only with an `apogee-dev serve` over `~/.apogee-dev`. It never pairs with the person's production server.

**Seam + files.** All under `lib/src/darwin/`.
- `source/presentation/shell/ViewModels/ShellViewModel.swift`: `ShellLayout` gains a `compact` form, chosen from the horizontal size class handed in (compact means tabs and stacks; regular means 8b's iPad shell, and the Mac is unchanged). `sidePanes` stays a question for regular layouts. In compact, a side pane is presented, never dropped.
- `source/presentation/shell/ViewModels/CompactNavigation.swift` (new): the phone's map. It defines the tabs, each tab's root, the stack of each, where each of the eleven `Destination`s, the console, the monitor and Settings is reached, and the route kept in `Preferences` across launches. It is pure and tested.
- `source/presentation/shell/Views/CompactShell.swift` (new): the `TabView` with a `NavigationStack` per tab. `ShellView` picks it in compact. The toast and overlays are presented as sheets.
- `source/presentation/styles/Metrics.swift` and `Components/`: the compact metrics (gutters, row heights, the input bar's), and a shared `PaneSheet` that presents a side pane (inspector, details, explain) as a sheet or a pushed page. It is promoted to `styles` on its second use, per ADR 0002.
- Each place's `Views/`: compact variants only where the regular view cannot reflow. These are the session window (transcript, the input bar above the keyboard, question and permission cards full-width), Sessions (the library as the Chats tab's root, the inspector as a sheet), Models and its store (details pushed), Graph (the canvas full-screen, explain as a sheet), Training and Knowledge (their fixed 380-point run and record pages pushed), Settings as a place (8b's) and the console (full-screen, on-screen keyboard). A place's view-model changes only where a compact act needs a new intent, such as "present the inspector".
- `source/presentation/sessions/`: the cross-device continuation. The library lists the server's chats (7a and CLI [59d](../../../cli/v0.2.3/reads-and-commands-over-the-network.md)), an opened chat resumes by `chat_id` over 59b's transport, and its earlier turns are drawn from `chats show` above the M7 divider. The "continued from" line uses the server's words where it sends them.
- `source/presentation/app/`: the compact scene's composition. There is no `Settings` scene on iOS, so Settings is a place (8b's).
- `lib/design/spec/` (every design update lands there; read `spec/CLAUDE.md` first): phone boards. The chat first, the tabs and More, a side pane as a sheet, pairing, and a conversation continued from the Mac. Also the compact values in `json/tokens.json`'s `layoutPx` and `html/BuildLayout.dc.html`.
- Tests (hermetic: scripted fakes, recorded documents, no binary, no network, no window): `tests/presentation/shell/ShellViewModelTests.swift` (the compact form from a compact size class; regular unchanged); `tests/presentation/shell/CompactNavigationTests.swift` (new: every `Destination`, the console, the monitor and Settings reachable; chat first; the route restored; a side pane presented, never dropped); `tests/presentation/shell/ParityTests.swift` (the table unchanged, every screen place reachable in compact); `tests/presentation/shell/KeyMapTests.swift` (every key-bound act has a touch control in compact); `tests/presentation/sessions/` (a recorded `chats list` from a server holding a chat begun on another device, the open resuming by its `chat_id`, the earlier turns drawn, a turn sent, a server lacking the new fields still opening it). `#Preview`s run under a compact trait for each compact state, over the modules' `Previews/` fakes.

**Decisions made** (dated):
- 2026-11-07: Specced from the Apple-platforms spike and brainstorm. The user's calls that shape this item:
  - the vision, Apogee feeling like Claude on every device the person owns, served by their own strong machine;
  - iPhone and iPad are clients of the person's Apogee server only, with no on-device core;
  - the server is an add-on, never the only way the app runs, so nothing may make the CLI or the Mac app need a server, a network or an account;
  - the foldable iPhone ("iPhone duo") is in scope, as its own item (9b) on this one's shell;
  - v0.3.0 is the target where macOS, iPadOS and iOS fully work, reached in successive versions, with Windows and Android after it (a recorded default);
  - no customer accounts, billing or metering: the server admits the person and their devices only.
- 2026-11-07: Placed in v0.3.0 (track 9), first of the track and gated on 8b. The phone reuses the iPad's iOS shell, Settings place and pairing, and adds only the compact size. 9b's foldable switches between this item's compact shell and 8b's regular one, so it follows this item.
- 2026-11-07: Where the work happens (the user's call C): server tools by default, plus a connected desktop's own files and shell. The iPhone offers no device tools of its own (iOS starts no shell), so a session driven from the phone runs on the server's tools, plus whatever a connected desktop offers through 60b. A desktop's device tools touch that desktop's own files: a change asked for from the phone to a project on the Mac lands in the Mac's files, never a server copy.

**Open calls:**
- [default: navigation is a tab bar of four. **Chats** (the Sessions library as its root, the last open conversation pushed on launch, so the conversation comes first), **Tasks**, **Models**, and **More**. More is a stack listing the other places, the console, the monitor and Settings in the sidebar's order. A tab is not a new route: each maps to a `Destination` the shell already keeps.]
- [default: compact means the horizontal size class is compact, not a point width. On the Mac nothing reads it, so the Mac's `ShellLayout` is byte-identical.]
- [default: a side pane in compact becomes a sheet (the Sessions inspector, a graph node's explanation) or a pushed page (a backend's or a stored set's details, Training's and Knowledge's panes). None is ever disabled the way `sidePanes` disables it today.]
- [default: on first launch with nothing paired, the app opens on 8b's pairing flow laid out for compact, then on Chats. A failed or refused pairing is drawn in the server's words, with Try again.]
- [default: going to the background drops the connection (iOS suspends the app), with no background execution on the phone. On return the app reconnects and redraws the open conversation from the server's record. What the server does with a turn left running is (consumed decision: 59b for a chat turn, 59e for a task), and the phone draws what they say.]
- (consumed decision: 59c owns whether two devices may hold one chat at once, and what the first one is told.) [default: the app renders 59c's answer. Where the server says a chat moved to another device, the window says so in its words and offers Continue here. Against a server that says nothing, opening a chat that another device holds shows the refusal it sends.]
- (consumed decision: 60b owns whether a desktop's device tools stay with a session after its driver moves to the phone.) [default: the phone draws a tool call on a desktop's files like any other, with its permission card answerable from the phone, and shows the CLI's refusal when the desktop is gone.]
- [default: a conversation from a Mac in local mode never appears on the phone. Moving a local chat to the server is not part of this item and is not queued.]
- [default: no push notifications. A finished task is seen on the next foreground read. Notifications need the Apple Developer Program, which is [8c](../../v0.2.5/iphone-and-ipad-distribution.md)'s [user] call, so they wait for it.]
- (consumed decision: 8a owns the iOS target, universal for iPhone and iPad, and its dev-channel identity; 8c owns distribution.)

**Guardrail(s).**
- `CompactNavigationTests` pins that every `Destination`, the console, the monitor and Settings can be reached, that chat comes first, and that the route survives a relaunch.
- `ParityTests` pins one table for every size, with no compact-only carve-out.
- `KeyMapTests` pins a touch control for every key-bound act.
- The `ShellLayout` regular and Mac cases are pinned unchanged.
- The sessions tests pin cross-device continuation by `chat_id` over a recorded server document, and an older server's fallback.
- A planted pairing credential never appears in a fixture, a preview or a log line.
- The layering check stays green (no UIKit type below Presentation; size class read only in Views).

**Acceptance criteria:**
- [ ] On an iPhone (the Simulator's smallest and largest current phones), the app opens on its last conversation. Every place, the console, the monitor and Settings are reached by touch, and no inspector, details or explanation is unreachable.
- [ ] First launch with nothing paired leads through pairing to Chats, and a refused pairing says why in the server's words.
- [ ] A conversation started in the Mac app pointed at the server is listed on the iPhone, opens with its earlier turns, takes a new turn whose answer streams with its thinking, tool narration and cards, and then continues on the Mac with that turn in place.
- [ ] Backgrounding the phone mid-turn and returning redraws the conversation from the server's record without losing a turn.
- [ ] The Mac app in local mode behaves exactly as before: local stays its default, it opens no network connection unless the person points it at a server (7a's opt-in), and the Mac's suite is unchanged.
- [ ] Every compact view has its named `#Preview`. The design canvas carries the phone boards. The full suite is green.
- [ ] A live pass: the dev build in the iOS Simulator paired with a sandboxed `apogee-dev serve` over `~/.apogee-dev` and a mock backend (the user's live pass on a device is optional and said).

**Scope note.** Earmarked for v0.3.0 (track 9). Gated on 8b, and through it on 8a, 7a and 7c, and CLI 59a, 59b, 59d and 59e. It also reads CLI 59c's answer on two devices holding one chat, which no gate in the chain requires: against a server without it, the app shows the refusal the server sends (the open call above). Out of scope:
- the foldable's folded and unfolded switching (9b);
- distribution to a device beyond the Simulator and a development install (8c);
- push notifications;
- moving a local Mac chat to the server;
- any on-device model or core;
- Android (after v0.3.0, a recorded default).
