# Renames that propagate: the backend and the model

**What / why.** There is no way to rename anything (the user's finding, 2026-10-14, trying it: the pasted verb tables — `apogee models`' nine verbs and `apogee config`'s twenty-four contain no rename and no edit), and both names are load-bearing references: a **backend key** is named by `models.default`, the five role pointers, every suite's `members:`, and **every saved chat** (`logger/session.h:148` keeps the backend per session — with the orphan case already documented at `session.h:58`, *"The saved backend is no longer in the config"*, which is exactly what a hand-edited rename causes today); a **stored model's name is its identity** — the store directory (`modelstore/store.h`, the 2026-09-23 one-declaration rule) that every pointing backend's `model_path` spells out, with the lineage and provenance records living inside it. This item ships the two verbs and the propagation the user asked for ("any changes… should propagate immediately and vice versa"): **`apogee config rename-backend <old> <new>`** — the key renamed and **every in-config reference rewritten in the same atomic edit** (default, role pointers, suite members), the saved-sessions sweep so resume survives, the admin twin; **`apogee models rename <old> <new>`** — the store directory moved (records riding inside it), every pointing backend's `model_path` repointed through the one editor — and **the coupling**: bidirectional and automatic where the mapping is 1:1, withheld and said where it is not.

**Core constraint(s).** **One config mutation path**: each rename is **one** editor transform producing one atomic write — the key change and every reference rewrite land together or not at all, comments kept, re-parsed before landing; never a sequence of partial edits a crash can split. **The store's identity rule stands**: `models rename` is the one deliberate act that moves a store directory and repoints the config in the same breath (the very pairing `check` refuses to do implicitly — its "never edits config" rule is untouched; this verb is the explicit opposite, asked for by name). **The coupling rule** (the spike's recommendation (a), standing — the user executed without a veto): `models rename` always repoints every pointing backend, and **renames the backends whose names are M3-derived** from the old base (`<base>-F16`/`<base>-Q4KM`) to the new base's spelling, their references rewritten transitively; `config rename-backend` always renames the key and its references, and **moves the store directory only when that backend is the directory's sole referrer and its name was the M3-derived spelling** — otherwise the store stays, said with why (`store 'X' unchanged -- 'Gemma4-12B-F16' still points at it`). Refusals by name: a taken backend key, a taken store name, a model mid-pull. **Secrets and sessions**: the sweep rewrites each session file atomically through the logger's own writer (the backend field and the roster pin where they name the old key); a file that cannot be rewritten is left to the existing graceful orphan path, counted and said. **Every mode** (ADR 0002): the admin plane gains the rename twins (byte-identical config out); the exec line covers the verbs in the shell (ADR 0010's floor — the classification table rows updated); completion offers old names to rename and refuses nothing it shouldn't (ADR 0007, free).

**Seam + files.**
- `data/contracts/config_edit.h/.cpp` — `rename_backend(content, old, new)`: the entry key plus every reference (`models.default`, the role pointers, suite `members:`) in one transform; the goldens' comment-dense fixtures grown for it.
- `presentation/cli/config_cmd.cpp` — the verb, its refusals, the sessions sweep (via `logger/`'s writer), the coupling's store check (via `modelstore/store.h`'s one declaration).
- `presentation/cli/models.cpp` (or the models verb home) — `models rename`: the directory move (same-filesystem, atomic), the repoint through `rename_backend`-adjacent transforms, the M3-derived backend renames, the narration of everything done.
- `logger/` — the session sweep entry point (each file atomic; the count said).
- `presentation/httpserver/` — the rename twins in the config slice, parity-tested byte-identical.
- `cli/tui_parity.cpp` — the classification rows' wording where touched. Tests: the golden matrix (comment-dense config: rename rewrites exactly the references, bytes stable elsewhere; idempotence; every refusal), the sweep (a renamed backend's old chat resumes), the store move (records intact inside, repoint exact, the coupling's three cases: 1:1 renamed, shared said, underived said), admin twin parity, `cli.config_lifecycle` grown.

**Reference.** The one-mutation-path invariant and its golden idiom (the editor this extends); M3 — the derived-name spelling the coupling recognizes; M9/M10 and `store.h` — the store's one declaration; `session.h:58/:148` — the orphan path kept as the net under the sweep; ADR 0002/0007/0010 — the twins, completion and classification that ride along; the user's finding (2026-10-14) for the verb-table evidence.

**Decisions made** (dated):
- 2026-10-14 — The set lands in v0.1.8 as track 46 (the user's placement call); the verbs are `config rename-backend` and `models rename`.
- 2026-10-14 — **Coupling rule (a)**, refined: bidirectional and automatic where 1:1 (M3-derived names follow the model; a sole-owner derived backend carries the store with it), withheld **and said** where shared or underived — never a guess, never a silent half-rename (the spike's recommendation, standing — the user executed without a veto).
- 2026-10-14 — Saved sessions are swept (the user's "propagate immediately"), the graceful orphan path kept as the net for what the sweep cannot touch.
- 2026-10-15 — A derived-name collision on `models rename` renames the model and repoints the paths but leaves the colliding backends' names, each collision said by name — never auto-suffixed (the default, confirmed 2026-10-15).
- 2026-10-15 — No curated TUI key in the first cut: the exec line runs both verbs, the Models/Config views show the new names on their next read (the default, confirmed 2026-10-15).


**Guardrail(s).** The transform goldens over comment-dense fixtures (references rewritten exactly, everything else byte-stable, re-parse green, idempotent); the refusal matrix (taken key, taken store name, unknown names, mid-pull); the sweep proven by a resume across a rename; the store move's records intact and the three coupling cases pinned; admin twin byte-parity; the classification and completion rows green.

**Acceptance criteria:**
- [ ] `config rename-backend old new` renames the key and every in-config reference in one atomic edit, sweeps saved sessions, and old chats resume on the new name.
- [ ] `models rename old new` moves the store directory with its records, repoints every `model_path`, and renames M3-derived backends with it; shared/underived cases are said, never guessed.
- [ ] Every refusal names its reason; the admin twins are byte-identical; the exec line runs both; the full suite is green.

**Scope note.** Earmarked for v0.1.8; first of track 46, ungated. Out of scope: field editing ([`edit-backend.md`](edit-backend.md)), any broader model↔backend sync beyond renames (dangling paths stay `check`'s to report), curated TUI keys.
