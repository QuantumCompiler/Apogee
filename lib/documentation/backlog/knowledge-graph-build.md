# Knowledge graph: extraction, resumable builds, retrieval-time expansion, and records as decision nodes

**What / why.** Top-k retrieval — lexical or vector — can only surface chunks that *resemble* the query. A **knowledge graph** surfaces **connected context**: things related to what was asked that share no vocabulary or embedding proximity with it, walked by exact SQL over extracted edges, so its quality does not degrade with the embedder's — it compensates for a mediocre one. `apogee graph build <collection> [-m] [--dry-run] [--force] [--limit N]` runs an **extraction clerk** once per chunk — a prompt and a JSON Schema compiled into the binary, executed as one provider-native structured-output call through the shared loop — pulling the entities a chunk is about (a **closed whitelist** of eight types: person, organization, system, component, location, event, concept, artifact) and the relations it states between them, **validated in host code** (types outside the set dropped with their relations, self-loops and within-chunk duplicates dropped, capped at 12 entities / 16 relations per chunk) into `kg_*` tables stored **inside the collection's own database** beside the chunks. Node identity is `(normalised name, type)`; descriptions merge first-non-empty-wins and a description change clears the stored vector; an edge's weight increments each time another chunk re-states it (corroboration). Builds are **incremental and resumable**: a source is re-extracted only when it is stale — no state row, its chunk count changed, its **highest chunk id moved** (chunk ids are never reused, so a re-ingest that keeps the same count is still caught — the fingerprint Ommi added after a same-count re-ingest silently lost every decision node), or the extraction model changed; a file's state row is written only after every one of its chunks finished, so an interrupted build resumes without re-extracting finished files; per-chunk failures are soft (one retry, then counted, the file left unstamped so the next build retries it); every build starts by **reconciling** rows whose chunks no longer exist. After extraction, new or changed entities are embedded (`"name: description"`) through the collection's embedder chain when one resolves — a graph with no embedder still works end to end, entity lookup falling to FTS. The first successful build sets `graph.enabled: true` on the collection's entry through the config editor. Once built, the graph feeds **retrieval-time expansion on every RAG surface** — `complete`, `chat`, `analyze`, `serve` — through the one place a turn's retrieval is assembled: the entities mentioned by the turn's retrieved top-k seed a walk of `hops` (1, max 2) edge steps, captured **before the rerank judge runs** so graph context survives a judge that drops every chunk; on a lexical turn the query's own terms additionally seed through the entity full-text index, so an entity-name hit expands with **no embedder at all**; neighbours rank by connecting edge weight × mention count, capped at `max_entities` (8), rendered as a `[Knowledge graph: <name>]` section of entity lines and `A —[relation]→ B` triples under a **1,500-codepoint budget** with whole-line truncation, appended after the chunk list in the **transient** prefix — never persisted history — and **best-effort**: a failure is a note, never the reason a turn loses its chunks. Every surface reports `+N graph entities`. **Knowledge records become first-class nodes**: every build materialises each record in the collection **deterministically, with no model call** — one node of the **reserved type `decision`** (which the extractor can never emit: it is not in the whitelist and host validation drops it), named by the record id so it can never collide with an extracted entity, described by decision + intent (capped at 400 codepoints), carrying `status`/`discipline` as node metadata replaced on every run so a status change since the last build shows, mentioned by the record's own chunk so the ordinary reconcile retires it when the record is deleted or re-captured — plus `concerns` edges from the decision to every entity the extractor pulls from the record's own text (the link that lets a documents chunk about the same thing reach the *decision* in one hop) and a `supersedes` edge mirroring the record's lineage when the target record is in the graph too (a missing target is counted, never a dangling node). Deterministic edges are **facts** (idempotent, weight 1); extracted relations gain corroboration weight. Expansion renders a decision as `kr-… (decision, shipped): …` so a superseded rationale is never mistaken for the live one, and `knowledge query --graph` / `GET /v1/admin/knowledge?q=&graph=true` walk the same graph from the matched records. `graph stats`, `graph show <collection> <entity>`, `graph delete` inspect and clear it; the admin twins run builds as async jobs.

**Core constraint(s).**
- **Extraction output is validated in host code**: the closed type set, the per-chunk caps, self-loops and duplicates, endpoint resolution against the chunk's own entities — whatever the schema asked, the host decides. **The extractor can never emit the reserved `decision` type**; only the deterministic materialise pass creates it.
- **The staleness fingerprint is (chunk count, max chunk id, model).** A same-count re-ingest, a `knowledge reindex`, or a re-capture always moves the max id and re-extracts; a legacy row with no recorded max id compares the count only, so an upgrade never forces a full rebuild.
- **Deterministic edges are facts** — `ensure_edge` is `INSERT OR IGNORE`, weight 1 across rebuilds — distinct from `upsert_edge`'s corroboration increment.
- **Expansion is transient, budgeted, best-effort, and seeded before rerank.** It rides `Options::transient_prefix` like the chunks; its failure never costs the turn its chunks; the section never exceeds 1,500 codepoints; the seeds are the retrieval-ordered top-k captured before the judge.
- **Local extractor by default** *(user decision, 2026-09-13)*: a full build never runs on a **metered** generation backend on Apogee's initiative — it extracts on a metered one only when that backend was named explicitly (`-m`, the collection's `graph.extract_backend`, or `models.default_extraction`); a fall-through to a metered `models.default` is refused with the three ways named. Whether a generation backend is metered is a **fact the provider states**, never a type list; unknown is metered. The **entity embedder** follows the embedding spend rule already in force. Batch APIs stay a later upgrade behind the same `ExtractFn` seam.
- **Vendor-CLI backends are refused as extractors, by type** — the same rule `analyze`, `serve` and the capture clerk apply.
- **Model-free domain core.** `graph/` and the `kg_*` layer of `embedstore/` include no backend and never make a model call: generation and embedding arrive as injected closures (`ExtractFn`, `EmbedFn`) so every test runs on fakes; the CLI binds them to `run_structured` and the embedder resolution, the admin plane to its harness. Both join the `harness.layering` guard.
- **One config mutation path**: `graph.enabled` and `models.default_extraction` are written through editor transforms only; **one layout declaration**: nothing new lands under `~/.apogee/` (the tables live in existing collection databases; the prompt and schema are compiled in).
- **Parity is the product**: `graph build` (an async job), `graph delete` and the `enabled` write get twins in this item; `stats`, `show`, `query --graph` are read-only rows. `--dry-run` is CLI-only (it exists to eyeball extractions in a terminal).
- **Capability probes never leak a cast**: metered-ness and the embedder are discovered through the Harness.
- Code Style: `.h`/`.cpp` pairs, smart pointers only.

**Decisions made** (dated):
- 2026-09-13 — **Split out of `knowledge-graph-stack` at grooming** as the third of four, gated on `knowledge-query-lifecycle` (it extends `knowledge query` and reads the record decoder); the records-as-nodes pass lives here because it runs inside the build loop, and the staleness fingerprint with it.
- 2026-09-13 — **Local extractor by default** *(user decision)*: a full build extracts on a metered backend only when that backend was named explicitly; the fall-through to a metered `models.default` is refused naming `-m`, `graph.extract_backend` and `models.default_extraction`. Mirrors the embedding spend rule of the same day. Batch APIs deferred behind the `ExtractFn` seam.
- 2026-09-13 — **Metered-ness is a provider fact**: `generation_is_metered()` on `LLMProvider`, default true (unknown is metered), discovered through the Harness — never a type list.
- 2026-09-13 — **Extraction rides `run_structured`** *(consumed decision)*; a chunk whose extraction misses twice counts as failed and the build continues.
- 2026-09-13 — **The expansion budget is a constant, 1,500 codepoints, whole-line truncation** *(Ommi's, kept)*; no config knob until the number proves wrong. `hops` ≤ 2, `max_entities` 8, both on the collection's `graph:` block.
- 2026-09-13 — **Seeded before rerank, transient, best-effort** *(Ommi's scope decision, kept)*; the section is appended after the chunks so it augments and never crowds them out.
- 2026-09-13 — **`decision` is a storage-only reserved type; node name = record id; status refreshed every build** *(Ommi's C3 calls, kept)*: the materialise pass runs on every build precisely so an in-place status edit — which churns no chunk — still refreshes the node.

**Guardrail(s).** Storage: the migration idempotent with a dropped-trigger self-heal; upsert dedup and description merge with the vector cleared on a text change; edge weight corroboration vs `ensure_edge` idempotence (weight stays 1); mention dedup; reconcile pruning dead mentions and recomputing counts; entity FTS with hostile input; `delete_graph`; `source_chunk_spans`. Extraction: the whitelist (an unknown type dropped with its relations; **an extractor-emitted `decision` dropped**), the caps, self-loops, endpoints resolving only to surviving entities, fenced JSON tolerated, the schema and prompt byte-equal to the shipped files. Build against fakes: populate; dry-run commits nothing; **incremental resume** (an interrupted build re-extracts only the unfinished file); model change and `--force` staleness; **the fingerprint** — a same-count re-ingest re-extracts, a third build is a no-op; failed chunks continue and the file stays unstamped; the retry absorbed; limit stop and resume; cancellation; a soft embed failure keeps extraction. Records: nodes, mentions, `concerns` and `supersedes` edges (a missing target skipped, no placeholder); an idempotent rebuild with weight-1 edges and a status refresh after `status`; delete → pruned; re-put → re-materialised on the **new** chunk; description-only embedding. Cost: a metered `models.default` fall-through refused; a named metered backend allowed; the mock and llamacpp unmetered; the API-billing providers metered; a vendor CLI refused by type. Expansion: 1 and 2 hops, the cap, weight × mentions ranking, hop-0 lexical seeds, empty seeds; the acceptance fixture — **two chunks sharing no vocabulary, linked only by an extracted edge: a lexical query matching A injects B's entity**; seeded before rerank (a judge that drops every chunk still yields the section); the budget truncates whole lines; a failing store is a note and the turn keeps its chunks; the section reaches the outgoing request and never persisted history (the existing transient guard); `+N graph entities` on the status line and the `rag_result` frame; a docs-only turn reaching `kr-… (decision, shipped)` and `kr-… (decision, superseded)` through a shared entity; `query --graph` from a matched record, the no-graph note distinct from "nothing related". `check` rejecting `hops: 3`. Parity rows; `cli.machine_schema_conformance` if the `rag` event grows; `cli.http_api_conformance`. `cli.graph_lifecycle` on the real binary with the scripted mock as extractor: ingest a fixture, `build --dry-run`, `build`, `stats`, `show`, a `complete --rag` turn whose stderr shows `+N graph entities` while the answer carries B's entity, a captured record materialised as a decision node, `delete`. All mutation-tested.

**Acceptance criteria:**
- [ ] `graph build` extracts entities and relations per chunk through one structured-output call into `kg_*` tables inside the collection's database, validated in host code (closed types, caps, no reserved type), incrementally and resumably, with the (count, max id, model) fingerprint, one soft retry per chunk, and entity vectors embedded last
- [ ] A full build never runs on a metered backend unless that backend was named; a vendor CLI is refused by type
- [ ] Every RAG surface expands its retrieved chunks through an enabled collection's graph — seeded before rerank, on lexical turns by query terms too — under a 1,500-codepoint transient budget, best-effort, reported as `+N graph entities`
- [ ] Knowledge records are `decision` nodes with `concerns` and `supersedes` edges, materialised deterministically on every build, retired by reconcile, never emitted by the extractor; `knowledge query --graph` and `?graph=true` walk the graph from the matched records
- [ ] `graph stats|show|delete`, the async build job and its twins, the `graph.enabled` transform and its twin, and the doctor's checks exist; `graph/` is layering-guarded; nothing new lands under `~/.apogee/`

**Scope note.** Gated on `knowledge-query-lifecycle`. Out of scope, in `knowledge-graph-global`: communities, dedupe, named multi-collection graphs, `embed ingest --graph`. Out of scope entirely: grammar-constrained local extraction, a `downstream_link` → artifact node, `capture --graph` chaining, batch-API builds (behind the `ExtractFn` seam, on the roadmap once a provider capability for batches exists).
