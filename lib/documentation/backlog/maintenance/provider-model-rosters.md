# Provider model rosters: registration brings the models

**What / why.** The user's ask (2026-10-08): registering a cloud provider (Anthropic, OpenAI, Google) should automatically bring **all its specific models** — Opus 5.5, Sonnet 5.5, and kin, at their precise versions — with **nothing hardwired**: the executable learns what a provider offers *from the provider, live, when the user registers it*. The architecture has been ready since day one: `LLMProvider` has carried **`list_models`** among its four methods since 2026-08-25 (`harness/provider.h` — chat, stream_chat, complete, list_models), and the provider chain shipped with v0.1.5: `providers scan [--register] [--refresh]`, the disposable schema-1 `cache/providers.json` (atomic writes, absent-reads-as-empty), and the asked-once first-launch offer. This item closes the loop: **registration fetches the provider's live model roster** through its own `list_models` (each vendor's models endpoint over the existing HTTP client), caches it beside the provider record, and surfaces it everywhere a model name is wanted — `models list` shows the provider's roster under its entry, `-m`/`/model` accept and **tab-complete** every roster model, and `config add-backend --model` completes from it. The roster is the vendor's answer **verbatim** — no baked-in model names, no client-side allowlist that would rot the day a vendor ships a new model; "what can this provider run" has exactly one source of truth, and it is the provider. Refresh is on the user's word (`providers scan --refresh`, or re-registration), never ambient: a roster's age is shown, staleness is said, and no listing ever makes a network call behind the user's back.

**Core constraint(s).**
- **Nothing hardwired, anywhere:** no model id, family name or version appears in source as a roster; the roster is `list_models`' response, cached. A curation (hiding, grouping) would be the hardwiring returning through the back door — out of scope by principle.
- **Key-bearing calls on the user's initiative only:** the fetch runs at registration (an act the user just took), at `providers scan --refresh`, and nowhere else — never at startup, never on a listing's hot path (the 28a discipline: the hot path reads the cache; `cli.no_provider_probes`' startup list extends to the roster fetcher). A missing or stale roster renders as exactly that, with the refresh named.
- **The cache is disposable state, the 28a pattern verbatim:** per-provider roster with its fetched-at date in the provider cache's idiom — absent, truncated, wrong-schema each read as empty and rebuilt on the next user-initiated fetch; written atomically; a failed write costs the record, never the command.
- **One config entry per provider; the roster rides the cache** *(the design default, vetoable — see Open calls)*: registering Anthropic writes the one backend entry 28b's chain already writes; the roster makes every model on it addressable and completable through that entry (`-m claude-opus-5-5` is the entry with the model override the router already honors). The user's config stays the user's file; a vendor's weekly-changing roster is provider-owned data and lives in disposable cache — the not-hardwired rule applied to the config too. Pinning one model as its own named entry stays `config add-backend`'s ordinary move.
- **A bare model name resolves if exactly one registered provider's roster holds it;** two providers claiming it is a refusal naming both and the qualified spelling — never a silent pick.
- **Secrets hygiene carries whole:** the fetch authenticates through the one key resolver; the roster cache stores model ids and dates, never a key, never a response body beyond the model records.
- **Completion per [ADR tab-completion](../../adrs/cli/tab-completion.md):** roster models join `-m`, `/model`, and `config add-backend --model` completion through the store-aware precedent (M7) — answered from the cache, by the binary, within the per-keystroke budget; an empty cache completes to nothing, never to a guess.
- Code style carries: `.h`/`.cpp` pairs, smart pointers only; tests in the layer of what they test ([ADR](../../adrs/cli/tests-mirror-architecture.md)).

**Seam + files.**
- `data/backends/anthropic.cpp` / `openai.cpp` / `google.cpp`: `list_models` implemented where still stubbed — each vendor's models endpoint (`/v1/models`, `/v1/models`, `/v1beta/models`) over the existing HTTP client and `*_wire` translators, returning the interface's model records.
- `data/backends/model_roster.h/.cpp` (new, beside `provider_cache`): the per-provider roster record (models, fetched-at), the cache read/write in the provider cache's idiom; `contracts/layout`: the cache path row (a created file, like `cache/providers.json`, not a seeded one).
- `cli/providers_cmd.cpp` (shipped, 28b): the registration chain and `--refresh` extended — fetch after a successful registration, the per-provider row gaining its model count and roster age.
- `presentation/cli/models.cpp` (`models list`): registered providers' rosters rendered under their entries (the M4 folding precedent: compact by default, `--all` the full roster), each row the vendor's id verbatim with the roster's age; `models info <roster model>` says which provider offers it.
- The completion seam (M7's): `-m`, `/model`, `config add-backend --model` fed from the cache; `harness/` router: the bare-name resolution rule above, in the resolver's idiom with `ResolvedFrom` saying so.
- Tests: `tests/data/backends/` — `list_models` against recorded vendor fixtures per provider (shapes, paging where a vendor pages, auth through the resolver); roster-cache disposability tables; `tests/presentation/cli/` — listing goldens (fresh/stale/absent roster), completion goldens, the ambiguity refusal; `cli.no_provider_probes` extended to the fetcher.
- Consumes: `LLMProvider::list_models` (shipped 2026-08-25); 28a's cache pattern + 28b's registration chain + 28c's surfacing conventions (shipped, v0.1.5); M7's completion precedent (shipped); M4's folding precedent (shipped).

**Reference.** In-house, and the design is mostly their composition: the provider cache's disposable-state idiom (28a), the registration chain (28b), `models list`'s snapshot folding (M4), store-aware completion (M7). External: each vendor's public models endpoint — the one source of truth this item refuses to duplicate.

**Open calls:**
- [default: one provider entry + the roster in cache (as specced above), with `config add-backend` the way to pin any roster model as its own named entry — the veto path is materializing every roster model into the config at registration, which puts a vendor's weekly churn into the user's hand-edited file]

**Guardrail(s).**
- Vendor fixtures: `list_models` per provider against recorded responses — ids verbatim, paging followed where the vendor pages, a malformed response an honest error naming the provider, never a partial roster written silently.
- The initiative pin: `cli.no_provider_probes`' startup sweep covers the fetcher; a `models list` with a cold cache performs zero network calls (asserted through the seam) and says how to fetch.
- Disposability tables: absent/truncated/wrong-schema roster caches read as empty; the next registration or refresh rebuilds; atomic-write failure costs the record only.
- Resolution: the bare-name table — one owner resolves (with `ResolvedFrom` saying so), two owners refuse naming both, zero owners fall through to today's error; goldens for listing (fresh/stale/absent) and completion.
- The leak sweep extended: the roster cache and every roster rendering carry no key material.

**Acceptance criteria:**
- [ ] `apogee providers scan --register` with an Anthropic key resolving registers the entry **and** fetches its roster: `models list` immediately shows the provider's current models (Opus 5.5, Sonnet 5.5, … — whatever the endpoint returns that day), each id verbatim, with the roster's age.
- [ ] `apogee chat -m <any roster model>` runs on it through the provider entry, and `-m <TAB>` offers the roster; a model two registered providers both list is refused with both named.
- [ ] `providers scan --refresh` re-fetches rosters; with the network down, the stale roster keeps rendering with its age and the failure is said — nothing blanks, nothing blocks.
- [ ] With a cold cache, no command performs a network call until the user registers or refreshes — asserted by the startup sweep and the seam test.

**Scope note.** Maintenance item **M13** (32f at birth, 2026-10-08, v0.1.6's tail; moved to Maintenance the same day — the user's call, 32f a vacated identity kept here); gated on nothing (the v0.1.5 provider chain shipped; [32d](../v0.1.6/tui-workbench-views.md)'s models view renders what this item caches, interplay not a gate). Out of scope: vendor-CLI rosters (no endpoint; a later item); client-side model curation or grouping (the verbatim rule); pricing/capability metadata beyond what the models endpoint returns; auto-refresh by age (a later deliberate item if wanted — the age is shown, the refresh is named).
