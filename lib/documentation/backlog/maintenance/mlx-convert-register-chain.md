# Convert-and-register covers MLX: one command to runnable, both engines

**What / why.** The one-command chain that made GGUF conversion ergonomic (M3: convert, quantize per level, register each as a backend) deliberately excludes MLX — the user hit both halves on 2026-10-19: `apogee models convert --mlx … --register --base-name …` answers `--register makes GGUF backends; an MLX model is registered with the 'config add-backend' line --mlx prints` (`presentation/cli/models_pull.cpp:2110-2111`, the designed refusal), and `--register-with`'s value set speaks GGUF alone (`{Q2_K,…,F16}`; `--base-name`'s help says `-F16, -Q4KM …`) — and asked for the capability: **this should work with `--mlx`**. Everything it needs already exists: the conversion lands a verified `mlx/` directory (27b), the exact registration is already printed as a hint — `config add-backend <name> --type mlx --model-path <dir>` (`models_pull.cpp:870-871`) — and M12's register core writes byte-for-byte what that hand-typed line writes. This item executes the hint instead of printing it: with `--mlx`, **`--register`** registers the one converted build as an `mlx` backend, and **`--register-with <p1,p2,…>`** takes the MLX precisions (`--type`'s own set: `3bit,4bit,6bit,8bit,bf16,f16,mxfp4`), runs **one conversion per named precision** — MLX quantizes at conversion, so each level is its own conversion from the same snapshot, never a quantize-after step — and registers each as its own backend, `--base-name` (default: the model's name) plus the precision suffix. M3's chain honesty carries over whole: each step reports as it runs, a failing step leaves everything before it standing and prints the one command that resumes, offline, without redoing anything.

**Core constraint(s).** **One registration path**: each entry is written through the add-backend core (M12's), byte-for-byte what the printed `config add-backend <name> --type mlx --model-path <dir>` line writes — never a second editor. **The value sets stay honest per engine**: `--register-with` with `--mlx` accepts exactly `--type`'s MLX precisions and refuses a GGUF level by name (and vice versa), with completion answering per context (ADR 0007); the flags' help says both engines' stories. **Store discipline unchanged**: each precision is its own verified `mlx/` directory (the whole-directory rule), identical to running `convert --mlx -t <p>` by hand; identical weights already stored register against the existing directory rather than converting again (the GGUF chain's "already here" behavior, kept). **Chain honesty is M3's**: steps said, failures leave finished work, the resume command printed. The refusal at `:2110` retires with its reason gone; today's hint line still prints for a bare conversion (no `--register`), unchanged. Parity: CLI-only verb, no HTTP/TUI twin added (ADR 0002, said); the machine-readable story unchanged beyond the chain's existing output.

**Seam + files.**
- `presentation/cli/models_pull.cpp` — the refusal (`:2110`) replaced by the MLX chain: the per-engine value set on `--register-with`, `--base-name`'s help widened, the per-precision conversion loop over the existing convert core, each registration through the add-backend core, the step narration and resume line; completion for the per-context value set.
- `business/models/convert.h/.cpp` — nothing new expected (the convert core already takes one precision per run); grown only if the chain needs a seam the CLI should not own.
- Tests: `tests/presentation/cli/` — the chain over a scripted converter: `--register` registering exactly the printed line's bytes; `--register-with 4bit,8bit` converting twice and registering two entries with the suffixed names; a GGUF level with `--mlx` (and an MLX precision without) refused by name; a mid-chain failure leaving the finished build and its entry, the resume command golden; the already-stored case registering without converting; completion per context.

**Reference.** M3 ([Milestone N](../../assistant/MILESTONES.md#milestone-n--model-operations)) — the GGUF chain whose ergonomics and failure honesty this mirrors; M12 (the same milestone) — the register core consumed as-is; 27b — the MLX conversion and the printed hint this executes; M15 ([shipped, Milestone N](../../assistant/MILESTONES.md#milestone-n--model-operations)) — the override interplay: a conversion run under `--model-type` registers through this same chain, nothing extra.

**Decisions made** (dated):
- 2026-10-19 — **The user's call**: `--register`/`--register-with` work with `--mlx`; the GGUF-only refusal (a 27b design decision) is superseded.
- 2026-10-19 — With `--mlx`, `--register-with` means one conversion per precision (MLX quantizes at conversion); the value set is `--type`'s own, per engine, refusals by name.
- 2026-10-19 — Registration is the printed hint executed: the add-backend core, byte-for-byte, `--type mlx`, the directory as model_path.

**Open calls:**
- [default: the backend-name suffix per MLX precision (`-4bit`, `-8bit`, `-F16`, …) finalized at build consistent with `stored_mlx_name` and the GGUF chain's spelling; `--base-name` keeps its default (the model's name).]
- [default: `--register` with `--mlx` registers the one `--type` build; naming and the already-stored short-circuit mirror the GGUF chain exactly.]

**Guardrail(s).** The user's refusal transcript inverted as the fixture (the exact command now chaining over a scripted converter); registration bytes held to the printed line's own (the hand-typed add-backend equality, M12's bar); the per-engine value-set refusals; the mid-chain failure and resume golden; no network, no weights — the real multi-precision run is the user's, recorded.

**Acceptance criteria:**

- [ ] A GGUF level with `--mlx` (and an MLX precision without) is refused naming the engine's own set; completion answers per context.
- [ ] The full suite is green over scripted converters.

**Scope note.** Maintenance item — release-agnostic, claimable by name, ungated (M15 is independent: an Assistant model still needs its override to convert, and then registers through this chain unchanged). Out of scope: roles or suite membership for the new backends (the user's, as ever), GGUF chain changes, auto-deleting the GGUF twins a model may still have, an HTTP/TUI twin.
