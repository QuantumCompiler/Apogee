# Deleting weights offers the config cleanup, and the doctor names real doors

**What / why.** Deleting stored weights strands every backend entry that ran from them, and the product's two answers to that are one warning with no door and one hint that names a command the binary refuses — measured 2026-10-19 (the user's bulk GGUF removal, 26 sets, then a sandboxed `APOGEE_HOME` replay of the lifecycle; the user's report: `models list` rendering **32 dangling llamacpp backends**, two lines each — `missing / no record` plus `cannot read '…': No such file or directory`). The facts, by `file:line`: **(W1)** `models delete` computes the affected backends (`backends_inside`) and says `backend 'X' points into this and will stop working until it is repointed.` (`presentation/cli/models_pull.cpp:2449`) — correct, but it offers no cleanup: no flag, no mention of `config delete-backend`, and under `-y` in a script the warning scrolls by unanswered; afterwards the only way out is one hand-typed `config delete-backend <name>` per entry. **(W2)** `check`'s dangling-backend hint (`presentation/cli/check.cpp:464-466`) says `run: apogee config add-backend <name> --type llamacpp --model-path <an existing .gguf>` — on an existing name that exact command is **refused**: `backend '<name>' already exists; pass --force to replace it` (sandbox bytes, 2026-10-19). This item closes both: the delete's warning becomes an offer — the entries it already names removed on consent (an interactive ask, default no; a flag for unattended runs; never silently) through the one config editor — and the doctor's hint names the two real doors: repoint (`config set-backend <name> --model-path …`, 46b's field editor) or remove (`config delete-backend <name>`).

**Core constraint(s).** **One config mutation path**: entry removal goes through `contracts/config_edit.h`'s existing delete-backend transform — byte-for-byte what `config delete-backend` writes, never a second editor (the 46a rename cores are the precedent for a model operation editing config through the one path). **Nothing silent**: without the flag and without a yes, the config is untouched and the warning says the doors; `-y` alone keeps today's meaning (skip the *weights* confirmation) and never implies the config half. **The plan prints before anything happens** (today's shape kept): what goes, which backends, what will be done about them. **The doctor's hints are runnable**: a hint `check` prints for a dangling backend must be a command the binary accepts on that install's state — pinned by test, so a wrong door cannot come back. Roles and suites that named a removed entry dangle exactly as they would after `config delete-backend` today; `check` reports them (no new scope here). Every mode: the flag completes (ADR 0007), the exec line carries it (ADR 0010, the verb already classified), parity per ADR 0002 — `models delete` has no HTTP or TUI mutation twin today, and this change adds none (said, not skipped silently).

**Seam + files.**
- `presentation/cli/models_pull.cpp` — the delete callback (`:2407-2470`): the offer after the plan print (interactive ask when a terminal is present, default no), the `--and-backends` flag for unattended runs, the removal through the one editor per affected name, the summary line naming what was removed and what was kept.
- `presentation/cli/check.cpp` — the dangling-backend hint (`:464-466`) rewritten to the two real doors (repoint via `set-backend --model-path`, remove via `delete-backend`), the wording golden-tested.
- Tests: `tests/presentation/cli/` — the lifecycle fixture (a scripted store set + a config entry pointing into it): delete with neither flag nor yes leaves config byte-identical and says the doors; the ask answered no leaves it byte-identical; `--and-backends` (and the ask answered yes) removes exactly the affected entries, byte-for-byte what `config delete-backend` writes; `-y` alone never touches config; the check hint's exact command accepted by the binary against the same fixture.

**Reference.** 46a ([Milestone N](../../assistant/MILESTONES.md#milestone-n--model-operations)) — the rename cores: a model operation editing config through the one editor, references swept; M12 — `config scan --register`, the same bridge in the registering direction; M11 — the doctor's honest-fix discipline the hint rejoins.
