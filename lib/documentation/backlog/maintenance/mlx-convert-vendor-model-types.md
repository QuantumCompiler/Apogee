# MLX conversion of a vendor's variant model_type: an explicit door, a named way out

**What / why.** `models convert --mlx` refuses the user's four Assistant models with a door-less upstream error — the transcript's bytes (2026-10-19): `apogee models: ValueError: Model type gemma4_unified_assistant not supported. -- stderr: [INFO] Loading`. Root cause, measured the same day: the snapshot's own `config.json` declares `model_type: gemma4_unified_assistant` / `architectures: ['Gemma4UnifiedAssistantForCausalLM']` — **the vendor's spelling, not ours** (`apogee-snapshot.json`: `source: huggingface`, `ref: google/gemma-4-12B-it-assistant`, pulled 2026-10-14; nothing under `training/` writes a `model_type`, grepped) — while the installed mlx-lm resolves a converter class by `model_type` through its `MODEL_REMAPPING` table (`mlx_lm/utils.py:48`, applied at `:220`), which knows the base (`"gemma4_unified": "gemma4"`, `:59`) and not the variant, so `convert()` raises; the seeded driver's generic fold (`assets/mlx/mlx_convert.py:110`, the `except Exception` arm) relays it honestly and names no way out. The GGUF ladder coped with the very same weights (its conversions on record, 2026-10-14) because the vendored converter resolves by `architectures` through its own mapping (`convert_hf_to_gguf.py:247-250`) — the gap is MLX-only. This item adds the two missing halves: **an explicit override** — `models convert --mlx <model> --model-type <type>`, the user's word that these weights are architecturally a type mlx-lm knows, staged as an **overlay view** of the snapshot (a `config.json` rewritten to the named type; every other file linked, never copied; the stored snapshot untouched) handed to the same driver, the override recorded in the conversion's record and the `mlx/` directory's provenance — and **a refusal with its door**: a failure matching `Model type <X> not supported` folds in the hint, naming `--model-type` and the near candidates read from mlx-lm's own lists (its model modules and remap keys), suggested and never auto-applied.

**Core constraint(s).** **Never guessed**: Apogee carries no equivalence table of its own (it would rot with every mlx-lm release and every vendor variant); the override happens on the user's word alone, and the candidates are read from the installed mlx-lm's own files at failure time. **The store is immutable**: the overlay lives under the conversion's working directory; the snapshot's bytes are untouched (held by `models repair` passing after), and the overlay is gone on success or failure alike. **One spawn path**: the driver runs over the one script runner exactly as today; if the driver changes, byte-identity and the retired digest (27c's mechanism) ride along. **Provenance tells the truth**: the record and the `mlx/` directory note `converted as <type> (model_type was <original>)`, so `models info` explains a converted-under-override model forever. The flag completes (ADR 0007); the verb's classification is unchanged (ADR 0010); no HTTP/TUI twin exists or is added (ADR 0002, said). Tests run a **stub mlx_lm** (the driver-test precedent) — no network, no weights, ever.
