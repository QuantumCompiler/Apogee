# MCP stdio client: `mcp__<server>__<tool>` in the loop, `apogee mcp`, and the in-binary server

**What / why.** The native toolsets give the model Apogee's own hands; this item lets it pick up anyone else's. A from-scratch **MCP client for stdio servers** — JSON-RPC 2.0 over newline-delimited JSON, the `initialize` handshake and `notifications/initialized`, `tools/list` fetched once and cached, each tool registered into the same `agent::ToolRegistry` as `mcp__<server>__<tool>` (double underscore, because tool names contain single ones), `tools/call` with the text content joined, and a background read loop demultiplexing responses by id — with the **subprocess discipline** Ommi earned the hard way: the server's stderr is **captured, never inherited** (a bounded 8-line tail kept per server and folded into a connect-failure message as one `— stderr: …` note, so discarding it costs no diagnostics), a server that dies mid-handshake fails **immediately** from the read loop's error path rather than after the connect timeout, connection failures are logged and **skipped, never fatal**, and every startup message repaints the one status line rather than scrolling. Servers are configured under `mcp_servers:` (`name`, `command`, `args`, `env`, `enabled`), managed by **`apogee mcp create|list|test|enable|disable`** — `create` scaffolds a runnable Python server from a template compiled into the binary and registers it through the config editor, or registers an existing executable; `list` shows live connection state per server; `test` invokes one tool through the production dispatch path; `enable`/`disable` flip the key — and by their admin-plane twins. And the **in-binary server pattern**: a `mcp::serve_stdio` loop that answers the same four methods over the process's own stdin/stdout, used by a hidden `apogee __mcp-tools` subcommand that exposes the **read-only** native toolsets to any other MCP client (Claude Code, an editor) with nothing to install — `command: apogee, args: ["__mcp-tools"]`. That pattern is also the hermetic fixture the client's own tests spawn, so the test fleet needs no Python.

**Core constraint(s).**
- **No subprocess inherits the terminal's stderr on an interactive path.** Every stdio server gets an explicit sink: discarded by default with the bounded tail retained, the raw stream under `--verbose`, and `serve` keeps stderr as its daemon log. The PTY test that locks this is the guardrail, not a review rule.
- **`done` closes from the read loop's error path, not only from `Close()`.** A pending call is released the instant the connection dies; a dead server never holds the status line for the connect timeout.
- **Interactive turns never open a listening socket.** A stdio server is a child on pipes — a long-lived child is not a violation — and nothing here references `listen`/`accept`. Remote transports are out of scope precisely because they would.
- **The harness never includes backends; `mcp/` is guarded too**: it includes `agent/`, `platform/`, `harness/` and the JSONL framer, never `backends/` providers or `commands/`.
- **One permission gate, one config mutation path, one layout.** An MCP tool is `writes` unless its `annotations.readOnlyHint` says otherwise, so a third-party tool is gated by default and `permissions.mcp__<server>__<tool>` overrides it. `create`, `enable`, `disable` and their twins edit `mcp_servers:` through new `config_edit` transforms and nothing else; scaffolded servers live under a new `mcp/` layout row; the templates are compiled in so install seeds nothing.
- **A vendor CLI is spawned, never opened** and **secrets are unleakable**: `env:` entries are `${ENV}`-expanded at load like every other config string, and a server's environment is never logged or listed back — `mcp list` shows names, state and tools.
- **Parity is the product.** `mcp create`/`enable`/`disable` are twins of admin routes in the same item; `mcp list`/`test` are read-only. The parity table's completeness check refuses an unclassified subcommand, so the rows land with the commands.
- Code Style: `.h`/`.cpp` pairs, smart pointers only.

**Reference (Ommi).** `lib/cli/src/mcp/{types,transport,client,registry,serve}.go` — the whole client is a port: `Transport` as an interface so "adding a new transport requires only implementing this interface"; the stdio transport's `io.Discard` default sink and the reason ("MCP proxies are chatty: `mcp-remote` narrates its OAuth discovery… interleaving with (and destroying) the caller's overwriting status line"); `Client.readLoop` calling `markDone()` on a read error "so no pending call can ever be answered… what turns a server that dies during startup into an immediate connect failed instead of a wait for the full mcpConnectTimeout with a frozen status line", closed exactly once via `sync.Once` "which would race when a server dies while the caller is shutting it down"; `namespacedName` and `parseNamespacedName` splitting on the **first** `__` after the prefix; the registry's `mcpConnectTimeout` rationale ("the difference between tools unavailable and the whole app never comes up"), `[mcp] connecting:` before the dial, `stderrTail` (8 lines, "enough for a stack-trace tail or a command not found, small enough that a chatty proxy can't grow the process") and `stderrNote`; `startupLog` handing diagnostics to the progress writer only during construction "because after startup that writer may be a status line a live turn owns"; `ExecuteTool`'s three-valued contract where a tool of a server that failed to connect is handled **with an error**, never a fall-through; `ServeStdio` and its one production user `cmd/ommi/mcp_gitlab.go` ("stdout is JSON-RPC only"); `cmd/ommi/mcp.go` and `src/scaffold/mcp.go` (templates compiled in "so nothing new lands under ~/.ommi/ at install time — only what the user creates"; `cmd/ommi/check.go:287-326`; `documentation/assistant/CLAUDE.md` → "⚠ Startup Speaks On One Line" and MILESTONES → Milestone P (the postmortem of `chat` coming up "behind a wall of output"); `test/mcp/stdio_output_test.go`, `test/mcp/serve_test.go`, `test/mcp/scaffold_test.go`, `test/cmd/startup_output_test.go` (the fleet and the PTY assertions, ported case for case). Divergences: **stdio only** — the SSE and Streamable transports, the auto-probe fall-back rule, `url`/`headers`/`transport` keys and the `mcp-remote` OAuth path are deferred with the remote-transports call; **no `scope`** — the llama/shared axis existed to forward servers to the `claude` CLI, which Apogee never does; the sink is **mandatory** in the API (Ommi kept an inheriting constructor "for compatibility" beside the safe one); `~` is expanded (Ommi's docs promised it and its loader did not); MCP tools are gated by `readOnlyHint` rather than by a two-name suffix set; Python-only scaffold, no Go template; the in-binary server exposes Apogee's own toolsets rather than a forge; one registry rather than a fall-through pair.

**Decisions made** (dated):
- 2026-08-24 — Planned from Ommi's documentation; sits on the loop's dispatch chain.
- 2026-09-13 — **Split out of `mcp-client-tools-agents` at grooming** as the second of three, gated on the native toolsets: the in-binary server serves them, the permission schema they bring gates MCP tools, and "built-ins always work regardless of MCP config" needs built-ins to exist.
- 2026-09-13 — **Stdio only in this item.** Remote transports need an outbound HTTP long-poll or SSE reader inside the loop's startup path and an OAuth story; both are the deferred `[user]` call recorded on the roadmap, not a rung of this one.
- 2026-09-13 — **The in-binary server exposes the read-only native toolsets.** Ommi's pattern had one user (its GitLab server); Apogee's first user is itself, so the pattern ships proven and the test fleet gets a real subprocess fixture with no interpreter dependency. Writing tools are withheld over stdio because the permission gate lives in the loop, not in the server.

**Open calls:**
- [default: `protocolVersion` `2025-03-26`, accepting whatever the server answers] Ommi sent `2024-11-05`; the newer date adds `annotations` (the `readOnlyHint` the gate reads) and every server in the wild accepts either. The negotiated version is recorded in `mcp list`.
- [default: 20-second connect bound, 60-second call bound, 8-line tail, 1 MiB frame] Ommi's numbers, each with its reason in the file; none is configurable until someone needs it to be.
- [default: `~` and `${ENV}` both expanded in `command`, `args` and `env`] Ommi expanded only `${ENV}` while its documentation showed `~`; expanding both removes the trap.
- [default: MCP tools are gated unless `readOnlyHint` is true] A third-party tool with no annotation is treated as destructive; `permissions.mcp__<server>__<tool>: allow` opts it out per tool.
- [default: Python-only scaffold plus register-only] The Go template assumes a toolchain Apogee never checks for; an existing executable of any language registers with `--command`.
- [default: `tools/list_changed` notifications are logged and ignored] Tools are fetched once at connect, as in Ommi; live refresh is new behaviour for a later item.

**Guardrail(s).** The fleet in CI, first as scripted transports (deterministic, every platform) and then as real children: the *chatty* server's stderr never reaches the progress writer and lands in the sink; the *dying* server fails in well under a second with `connect failed` **and** its last stderr line on one line; the *slow* server times out at the bound and is skipped while the next server still connects; the *malformed* server's junk frames are skipped and its valid ones answered; an `isError` result is an error outcome the model reads; a 200-line stderr flood keeps exactly the last 8; `[mcp] connecting:` precedes every dial; `mark_done` is idempotent under a server dying during `close()`. The registry never returns an error for a bad server, and built-ins dispatch identically with zero, one failed, or one connected server. `serve_stdio` answers three frames for four sent (the notification has no reply), `-32601` for an unknown method, and skips junk. The scaffold produces a server `mcp test` can drive, the config entry byte-identical from CLI and route, and a duplicate refused without `--force`. The PTY test on the real binary: every pre-prompt repaint is Apogee's own, no newline in the startup window, the tail survives, and the wall clock stays under the timeout. `check` names a missing command with the delete command. `cli.machine_schema_conformance` and `cli.http_api_conformance` pin the new rows. All mutation-tested.

**Acceptance criteria:**
- [ ] A scripted stdio server's tools appear in the loop as `mcp__<server>__<tool>` and dispatch end to end on `chat`, `complete` and `serve`; a namespaced tool whose server is down is an error result, and built-ins work regardless of MCP config
- [ ] A server dying mid-handshake fails in under a second with its stderr tail in the message; a deliberately noisy server's stderr never reaches the terminal and the status line survives (PTY test); connect failures are logged and skipped, never fatal
- [ ] `mcp create` scaffolds a runnable server and registers it; `mcp test` invokes a tool through the production dispatch path; `mcp list` shows live state; `enable`/`disable` edit exactly one line; the admin twins leave byte-identical files
- [ ] `apogee __mcp-tools` serves the read-only native toolsets to an external MCP client, and is the fixture the client's own tests spawn
- [ ] An MCP tool without `readOnlyHint` goes through the permission gate like a native destructive tool
- [ ] `mcp/` is guarded by `harness.layering`, `mcp/` is a layout row, and the templates are compiled in so install seeds nothing

**Scope note.** Gated ring; gated on `native-toolsets.md`. Everything else it needs has shipped: the child-process seam with its bounded stderr tail (Milestone L), the JSONL framer, the status line and PTY harness (Milestone G and the chat items), the events bus and admin plane (Milestone U), the config editor.
