# Knowledge graph: communities, dedupe, named multi-collection graphs, and ingest chaining

**What / why.** The global layer over the graph the previous item builds, and the shape that makes it span a whole organisation's corpora. **Communities** answer the question top-k retrieval plus expansion cannot — "what are the main themes in this corpus?": `apogee graph communities <name> [-m] [--force] [--min-size N] [--list]` partitions the graph into thematic clusters by **deterministic weighted label propagation** over the extracted relations (no model involved in detection), summarises each cluster of at least `min_size` (3) entities with **one generation call** under a compiled-in summariser prompt (plain prose, no schema), and stores each summary as an **ordinary retrievable pseudo-chunk** under a `graph://community/<id>` source — so corpus-level summaries surface through plain `embed query`, every RAG turn, and every retriever with zero new query paths, while being excluded from extraction, stale-file accounting and coverage stats so a summary never yields self-referential entities. A community's **identity is its exact member set** (the hash of its sorted member ids): any membership change makes the old summary stale — pruned and regenerated on the next run — while unchanged communities cost nothing; `--force` regenerates all. **Dedupe** merges what the exact name key cannot know are the same thing: `graph dedupe <name> [--threshold 0.92] [--dry-run]` unions same-type entities whose vectors exceed the cosine threshold — the earliest-extracted node survives, edges repoint to it (weights summed on collision, would-be self-loops dropped), mentions are unioned and recounted, descriptions merge first-non-empty (the survivor's vector cleared on a text change), the merged nodes' derived community memberships are removed so the next communities run recomputes them; entities without vectors are skipped, **decision nodes are never merged** (two records with near-identical text are still two decisions), it never runs automatically, and `--dry-run` previews the merge groups. **Named graphs** fix the per-collection graph's blind spot: the same person, system or project mentioned in `docs`, `meetings` and `tickets` becomes three disconnected twins. A `graphs:` config entry (`name`, `collections`, `extract_backend`, `hops`, `max_entities`; no `enabled` — building is the enablement) spans several collections into **one node per entity with aggregated salience**, stored in the graph's **own database** under the embeddings directory's `graphs/<name>.db` (derived data, created lazily by the first build — never by an installer; member databases are never written to); every `kg_mentions` row carries its member collection, `kg_state` is keyed per `(collection, source)`, `graph_meta` records the graph's name, its as-built member set and its **own** entity-vector model (a named graph embeds through the default chain; members may use different chunk embedders freely); building **re-extracts** members' chunks into the graph's database incrementally (rebuild, never absorb — an existing per-collection graph is neither consulted nor migrated); membership **converges** — removing a collection prunes everything it contributed on the next build; **a built named graph takes retrieval precedence** for its members (their own `graph:` blocks are untouched and resume the moment the collection leaves), uncovered collections keep their own expansion, so one turn may render several `[Knowledge graph: …]` sections under the one budget; resolution is **graphs-first**, so a graph name must never collide with a collection name — `check` enforces it. `config add-graph`/`delete-graph` manage the entry (the data is `graph delete`'s). Communities and dedupe run against a named graph exactly as against a collection's — where they matter most. Finally, **ingest chaining**: `embed ingest --graph` builds immediately after a successful ingest, targeting whichever graph covers the ingested collection (the first `graphs:` entry listing it, else its own), so one command goes from documents to a queryable graph; over HTTP `"graph": true` on the ingest body chains the build job (`graph_job_id`), never after a failed or cancelled ingest.

**Core constraint(s).**
- **Dedupe never merges decision nodes**, never runs automatically, and commits in one transaction; a dry run writes nothing. Nodes without vectors are never considered.
- **A community's identity is its member set**; unchanged communities are never re-summarised; pseudo-chunks are graph output, never corpus input (excluded from extraction planning, staleness, coverage), and travel with the graph on delete.
- **Graph names must never collide with collection names** — resolution is graphs-first, everywhere (CLI and every data route), and `check` fails the collision.
- **A named graph never writes to a member's database**; its database is derived data under a lazily created `graphs/` subdirectory of the embeddings row — **not** a new layout row (Ommi's rule: like `knowledge/raw` was there; here the raw archive became a row because it holds the user's own words, while a graph database is rebuildable from its members).
- **Retrieval precedence only** (Ommi's scope decision, kept): a built named graph covers its members; nothing auto-disables a member's own `graph:` block.
- **The cost policy is inherited**: a named build's extractor resolves `-m` > the entry's `extract_backend` > `models.default_extraction` > `models.default`, with the metered fall-through refused; the summariser resolves through the same chain; dedupe makes no model call.
- **One config mutation path**: `append_graph`/`delete_graph` transforms, **section-scoped end to end** so a `graphs:` entry sharing an agent's or a server's name can never touch the other section's entry.
- **Parity is the product**: `graph communities` (an async job), `graph dedupe` (synchronous), `config add-graph`, `config delete-graph`, `embed ingest --graph` get twins; `communities --list` and named `stats`/`show` are read-only rows.
- **Model-free domain core** (consumed): detection is pure code; the summariser and embedder are injected closures; `graph/` stays layering-guarded.
- Code Style: `.h`/`.cpp` pairs, smart pointers only.

**Guardrail(s).** Communities: two clusters detected, the min-size filter, weighted-majority assignment, determinism across runs; storage round trip (row, memberships, the pseudo-chunk retrievable through `search` on any retriever), vectorisation, prune, `delete_graph` clearing them, exclusion from planning and coverage; `build_communities` populating, the unchanged-hash skip (a second run summarises nothing), `--force`, a membership change pruning and regenerating, a soft summariser failure leaving the old summary in place. Dedupe: dry-run writes nothing; earliest-id survival; edge fold to a summed weight with a description merge; self-loop drop; mention union and recount; cross-type namesakes never merge; the threshold respected; **decision nodes skipped with an entity control merge in the same run**; an idempotent second run. Named graphs: the provenance migration from the per-collection shape (rows rebuilt with `''` labels; `store_meta` keys moved to `graph_meta`); **cross-collection identity** — one node, labelled mentions, weight accumulating across members, per-collection state, identity stamped, a no-op second build; member removal converging; limit/resume across members; a missing member contributing nothing; **retrieval precedence with a per-collection decoy tripwire** (a member's own graph carries a node the named graph does not; the named graph wins); partial-membership turns rendering both section kinds under one budget; an unbuilt entry falling back; `named_graph_covering`; `graph show` naming each chunk's collection; the config helpers round-tripping with comments preserved, `--force`, the **section-scoped delete leaving a same-named agent and MCP server intact**; the collision ban and every other `graphs:` rule in `check`. Chaining: `ingest --graph` builds the covering graph after success and never after a failed ingest; the admin body validated before any write (`501` no generation backend, `400` unresolvable). Parity rows; `cli.http_api_conformance`. `cli.graph_lifecycle` extended on the real binary: a named graph over `docs` and `knowledge`, a docs-only turn surfacing the decision one hop away, `communities` producing a summary that is the top lexical hit for "main themes", an immediate re-run reporting unchanged, `dedupe --dry-run` on a distinct-entity fixture finding nothing, `config delete-graph` leaving the database and `graph delete` removing it. All mutation-tested.

**Acceptance criteria:**
- [ ] `graph communities` detects clusters deterministically, summarises new or changed ones with one call each, stores summaries as retrievable pseudo-chunks excluded from extraction, and leaves unchanged communities untouched
- [ ] `graph dedupe` merges vector-identical same-type entities with edges repointed and weights summed, previews with `--dry-run`, never merges decision nodes, never runs on its own
- [ ] A named graph spans its member collections into one node per entity in its own lazily created database, converges on membership changes, takes retrieval precedence for built members, resolves graphs-first, and cannot share a collection's name
- [ ] `embed ingest --graph` and `"graph": true` chain the covering graph's build after a successful ingest only
- [ ] Every mutating action is a twin (`communities`, `dedupe`, `config add-graph`/`delete-graph`, ingest chaining); `check` validates every `graphs:` entry; nothing new lands under `~/.apogee/`
