## What this is

Apogee is an AI harness: one system for running LLM workloads against the Anthropic, OpenAI, and Google cloud APIs as well as local models served through llama.cpp (and, opt-in on Apple silicon since 27a, through MLX). It is primarily C++ and built docs-first, with its foundational choices recorded in [SPEC.md](SPEC.md) → Background. The repo is brand-new — these docs are the source of truth from which the first code will be built. See [SPEC.md](SPEC.md) for scope and principles and [MILESTONES.md](MILESTONES.md) for the shipped-feature record.

## Stack & environment

- **Language:** **C++20** (decided 2026-08-25 — the only standard uniformly supported across all five targets; promotion to C++23 would be a deliberate one-line change in `lib/src/cli/CMakeLists.txt`, not a drift). Satellite scripts (training drivers, MCP servers) may be Python.
- **Build & tooling:** **CMake ≥ 3.25** with **FetchContent** for dependencies (pinned tags, `FIND_PACKAGE_ARGS`, `SYSTEM`), **Catch2 v3** for tests via ctest, clang-format + clang-tidy for style and the ownership gate. Each application under `lib/src/<app>/` is a self-contained CMake project owning its own build; `lib/scripts/cicd.sh` drives them all.
- **Key dependencies:** the Anthropic, OpenAI, and Google LLM APIs (cloud backends, called directly over HTTPS); llama.cpp (local inference, in-process, pinned at release `b11151` under `lib/src/cli/third_party/`, including its `mtmd` multimodal library for local vision — added as a single subdirectory rather than via `LLAMA_BUILD_TOOLS`, which would build half a dozen binaries Apogee has no use for — and its `common` chat layer (`llama-common`, 25b: each model's own template rendered with tools, its call parser, the lazy grammar), linked into its own `apogee_llama_chat` library without its vendored httplib; **off by default** — `-DAPOGEE_ENABLE_LLAMA=ON` builds it, and without it the llamacpp backend refuses construction with a message saying how to turn it on); and, opt-in since 27a, Apple's MLX on Apple silicon through `mlx-lm` in the Python environment Apogee owns (`training/venv`) — and, for a vision model since 27c, `mlx-vlm` there too, installed on demand — never linked: the `mlx` backend runs it as a persistent child over pipes, and llama.cpp stays the zero-dependency default (SPEC.md → Background, the 2026-10-03 amendment). Standardized library picks, decided once for the whole project: **nlohmann/json** (JSON), **yaml-cpp** (YAML — **read path only**; config writes go through text surgery, never a marshal), **CLI11** (CLI parsing + completions), **libcurl** (HTTP client — wired 2026-08-26; **found on the system, never fetched**, so it uses the platform's own TLS stack and trust store), **replxx** (chat line editing; readline was ruled out on licence grounds), and **SQLite** (the chunk store and its FTS5 lexical index — the one dependency deliberately *fetched* rather than found, because FTS5 is a compile-time flag and a system copy without it fails only once a user has ingested a corpus). Since 27k, **tree-sitter** (the code graph's parser: the runtime and twelve grammars, each *fetched* at its own pin and compiled as a plain C static library in every build, for the same reason as SQLite — the golden fixtures pin the exact tree a grammar produces; linked privately into `apogee_business_graph` alone, see `third_party/README.md`). Since 32b, **FTXUI** (the full-screen shell's compositor, v7.0.3, *fetched* at an exact commit with its hash, as tree-sitter is, since the shell's headless goldens pin what one version renders; linked privately by `tui/` alone, its headers naming none of FTXUI's types -- `cmake/ApogeeLinkPolicy.cmake` refuses any other target that links it). Downstream items consume these rather than reopening them.
- **Platforms:** decided 2026-08-24, revised 2026-09-19 — Linux and Windows on both ARM and x86, macOS on Apple silicon only: **five targets** (`linux-x64/arm64`, `macos-arm64`, `windows-x64/arm64`). The Intel Mac was dropped on 2026-09-19 (the user's call: no Intel Mac target, in any capacity — no preset, no runner, no archive). Each target builds natively on its own CI runner via `lib/scripts/cicd.sh --platform <target>`. Windows membership means the POSIX mechanisms named in backlog docs (forkpty PTY tests, tcflush, lsof assertions, 0600 modes, getpeername) need Windows equivalents or recorded per-item skips. **The portability seam exists** at `lib/src/cli/source/infrastructure/platform/` (shipped 2026-08-25) — that is the one place platform `#ifdef`s belong; everything else asks it. Primary dev host is macOS. CI gates on `macos-arm64` only for v0.1.0; the other five targets run informationally until they stabilize.
- **Repository:** https://github.com/QuantumCompiler/Apogee. **GitHub Releases is the distribution host** and GitHub Actions the release pipeline *(confirmed 2026-09-01)*: a pull request merged into `stable` publishes the release `lib/release/VERSION` names — `ci.yml`'s `tag and release` job tags it and releases the CLI archives that pull request's run built, or, with the CLI unchanged since the latest release, that release's archives copied (2026-09-25) — and, dispatched on `stable` with `publish`, the same workflow re-cuts a release: all five targets built on native runners through `lib/scripts/cicd.sh`, then published (since 2026-10-04, M8, `ci.yml` is the only workflow, and a pushed `v*` tag runs nothing). `lib/scripts/install.sh` (macOS, Linux) and `lib/scripts/install.ps1` (Windows) fetch from there.

## Invariants

Apogee starts with **design-time constraints** (see [SPEC.md](SPEC.md) → Principles and Non-goals): interactive turns never open a listening socket — and local front-ends are pipes too: the GUI powers the CLI over stdin/stdout, while `serve` exists solely for server deployments answering remote REST clients; all install paths produce an identical layout; every capability reaches every surface through one shared core; secrets are `0600`, never logged, never returned over HTTP. Each is pinned as a **Core constraint** on the backlog items that own it, and earns a full `## ⚠` section here — rule, rationale, sub-rules, enforcement — as the enforcing code and tests land.

The first of them is now enforced in code:

### ⚠ Nothing links the CLI executable

**Rule.** The modules hold every capability -- one static library each since Architecture A4, aggregated as `apogee_core`. The `apogee` executable is a thin face over them — argv in, exit code out — and **no target may link `apogee`**: not tests, not the HTTP server (which lives inside `apogee_core` like every other surface), not a helper library.

**Why.** "Parity is the product" only holds if it is structural. If a capability can live in the executable, then a second surface either cannot reach it or has to reimplement it — and that is exactly how parity bugs are born. Keeping the executable empty means every capability is, by construction, reachable from anywhere that links the library.

**Sub-rules.**
- Shared code goes in a module under `lib/src/cli/source/<layer>/`, never in `main.cpp`.
- Tests link the modules: a layer's suites compile as `apogee_tests_<layer>`, linking that layer and the ones below ([ADR 0004](../adrs/cli/tests-mirror-architecture.md)); the cross-cutting suites link `apogee_core`; one `apogee_tests` binary runs them all. Running the built binary as a subprocess is fine — that is not linking, and the `cli.*` ctest cases do exactly that to cover the user-facing contract.

**Enforcement.** `apogee_assert_link_policy()` (`lib/src/cli/cmake/ApogeeLinkPolicy.cmake`), called at the end of `lib/src/cli/CMakeLists.txt`, walks every target in the project and **fails the configure step** naming any that links `apogee`. Since A4 it also walks the module graph against `cmake/modules.cmake` -- every module a library linking exactly its row, each link in its own layer or below, no cycle, each module compiling only its own directory, each layer's test library linking its layer and below -- and fails the configure step naming the target and the rule.

### ⚠ One config mutation path

**Rule.** Every config change, from every surface, forever, goes through the helpers in `contracts/config_edit.h`. Nothing else writes a config file. **Never** load the config into structs, modify them, and serialize back.

**Why.** Two reasons, and the second is the one that bites. First, a config file's comments are most of its documentation, and every YAML or JSON library — yaml-cpp and nlohmann included — drops them on parse (or never reads them), so load-modify-save silently deletes the user's file contents. Since 28i the file is JSONC (`config.json`, `//` comments) and the contract carried over whole: an edit touches its key and nothing else, comments included. Second, "parity is the product": when the admin plane lands, an edit made over HTTP has to be byte-identical to the same edit made from the CLI. That is structural only while there is exactly one path.

**Sub-rules.**
- The transforms are pure — text in, text out. Only `edit_config_file()` touches the filesystem.
- Every edit re-parses its own output before it lands, and writes via temp-file-then-rename, so a bad transform cannot corrupt a config.
- Reading is `load_config` / `parse_config`, the format decided by content (`jsonc::looks_like_jsonc`), both formats through one typed walk. The transforms are defined once, over YAML text; a JSONC config is edited through the bridge (`config_yaml.h`) and spliced in place (`jsonc::patch`) — never a second set of transforms. yaml-cpp reads the older YAML config, the bridge and migration, and the spec files; it never writes one.

**Enforcement.** The golden-file suite in `tests/data/contracts/config_edit_test.cpp` asserts byte-identical round trips over a comment-dense fixture, plus CRLF preservation and the atomic-failure paths; `config_jsonc_test.cpp` holds every verb on a comment-dense JSONC fixture to its own span with every comment kept, and `jsonc_test.cpp` the in-place patcher. `apogee config` is a thin caller — it formats no YAML of its own. The one config write a user never types `config` for — `apogee embed ingest` registering a new collection — goes through the same helpers, and `cli.config_lifecycle` holds it to a literal equality over the whole shipped template: pristine bytes plus exactly the new entry.

### ⚠ The harness never includes backends

**Rule.** The dependency runs one way: `backends/` includes the contracts, never the harness, and the harness never includes `backends/`. **The same applies to `agentloop/` and `agent/`** — the loop consumes the IR and the Harness, not backends. When a guarded layer needs something only a backend knows, it crosses as **plain data** (that is what `harness::ModelBehavior` is) or as a capability interface.

**Since Architecture A1 (2026-10-03) the rule is one case of a general law: four layers.** Every package sits in one — **Presentation** (`cli`, `views`, `machine` -- `commands/` split in three by A3 -- `operations`, `httpserver`, `markdown`, `render`, and since 32b `tui`) → **Business** (`harness`, `agentloop`, `agent`, `tools`, `knowledge`, `graph`, `training`, `tasks`, `symphony`, `scaffold`, `models`, `mcp`) → **Data** (`contracts`, `backends`, `embedstore`, `logger`, `secrets`, `modelstore`, `transport`) → **Infrastructure** (`platform`, `ansi`, `events`, `version`) — and includes only its own layer and those below. The interfaces every implementor reads (the provider interface, the IR, errors, cancellation, `ModelBehavior`, the config engine and its editor, the layout, the bundled assets, the host rule) live in **`contracts/`**, the Data floor, so `backends/` reads them without reaching up. What a lower layer needs from a higher one crosses as an interface declared below and implemented above: the provider factory fills the Harness through `contracts/provider.h`'s `ProviderRegistry`, which the Harness implements. Since A2 the directories say it too: `source/<layer>/<package>/`. Since A4 the build holds it: each module is a static library (`apogee_<layer>_<module>`) linked to exactly its row in `cmake/modules.cmake`, and a module's include roots are its own layer's and those its links bring up from below -- so an include that reaches up a layer does not compile.

**Why.** In Go this is free: the reverse edge is an import cycle and the build fails. C++ gives you nothing — a `#include "backends/anthropic.h"` in the harness compiles perfectly and the layering is silently gone. Once it is gone, the harness knows about vendors, and "backend-agnostic core" stops being true in the one place it has to be.

**Sub-rules.**
- A capability a backend has and the harness needs to ask about becomes a **capability interface** in `contracts/provider.h`, discovered by the Harness (see below) — not an include.
- `contracts/` includes the platform seam and itself only; `modelstore/` (the model store, records, the GGUF header reader, the cache arithmetic) and `transport/` (the HTTP client, the SSE parser, the JSONL framer) stand on the contracts and the platform alone. A convenience that drags business logic down into them is the drift the floor exists to prevent.
- Model-family knowledge crosses as `ModelBehavior`, plain strings and bools.
- `agentloop/` and `agent/` are guarded too, as of Milestone F. A loop that includes a backend starts special-casing one vendor's tool dialect, and "one shared loop for all surfaces" quietly becomes "one loop with an Anthropic branch".
- `tools/` is guarded too, as of Milestone V: a native tool that includes a backend is a tool that only works on one vendor.
- `mcp/` is guarded too, as of Milestone W: it reads JSONL off a child's pipe with the one framer, `transport/jsonl_framer.h` since A1 — a provider-free line splitter beside the HTTP client, so the allowance into `backends/` it once needed is gone. A second framer would be a second copy of the chunk-boundary bug class the first exists to hold.
- `knowledge/` is guarded too, as of Milestone Y, and held to its own allow-list — `embedstore/`, `agentloop/`, `agent/`, `harness/`, `contracts/`, `platform/` and itself, never a surface: the record logic the command line, chat and the admin plane all share must not depend on any one of them.
- `graph/` is guarded the same way (Milestone Y, third slice): `embedstore/`, `knowledge/`, `agentloop/`, `agent/`, `harness/`, `contracts/`, `platform/` and itself. The build never makes a model call of its own — generation and embedding arrive as closures — so the extraction that the CLI and the admin plane run is one function, not two. **The code graph goes further** (27k): its files, `graph/code_*`, may include only one another, `embedstore/`, and by name `contracts/sha256.h` and `contracts/cancellation.h` — no harness, no loop, no prose extractor — so "zero model calls" is a property of the include graph, not of care. And tree-sitter's C API has **one boundary**: `graph/code_parser.cpp` is the only file that includes `tree_sitter/`, its handles in `unique_ptr`s with their deleters, plain data out.
- `training/` is guarded the same way (Milestone Z): `harness/`, `contracts/` (whose `sha256.h` the run manifests hash the dataset with), `platform/`, `agentloop/`, `agent/`, itself, and by name the JSONL framer, `transport/jsonl_framer.h` (its Python drivers speak JSONL over a child's stdout, and the one framer is the one tested against every chunk boundary). Generation arrives as a closure, so the synth the CLI and the admin plane run is one function; the eval judge, the GGUF converter, the header verifier and the quantizer arrive as closures too, so `promote` in `training/` never names a backend, edits a config, or knows whether llama.cpp is linked -- `cli/train.cpp` is the composition root that does. The orchestration layer keeps the same shape: the pipeline composes the trainer, `run_eval` and the fuse; the regime composes the synth core and the pipeline; the cycle composes the pipeline and takes the **promote path as a closure** -- the one body `cli/train.cpp` hands to `promote`, the regime and the cycle alike, so "a failing candidate never reaches inference" is one rule in one place.
- `tasks/` is guarded the same way (27h): `agentloop/`, `agent/`, `harness/`, `logger/` (the session linkage), `contracts/`, `platform/` and itself -- never a backend or a surface. A task's turns arrive as a closure: `cli/task_cmd.cpp` hands the runner one ordinary chat turn of the task's session (`cli/chat_turn.h`, the turn the REPL and machine mode run), so the runner decides whether to open another turn and never how one runs -- the loop's bound and its half-turn rollback untouched, and what the turn did with its tools watched (`tasks/unattended`) rather than decided: with no one to confirm, `ask` denies exactly as on any pipe. What a task may do beyond that is declared before it runs and recorded per use (27i, `tasks/policy`): per-tool grants that are chat's own `session` answer given at launch -- composed by `cli/task_cmd.cpp` through chat's `seed_approvals` and `make_permission_checker`, never a second checker -- held by `grant_refusal` no wider than the config's `permissions:` and the agent's tool policy, with no blanket grant at all; one declared answer for questions; and the person at the terminal, when there is one, still asked about anything not granted. Its PID lock is the cycle's, shared as `platform/pid_lock`.
- `symphony/` is guarded the same way (27q): `agentloop/`, `harness/`, `contracts/`, `platform/` and itself -- and since 27t `agent/`, the registry its definitions project tools into -- never a backend or a surface. A stage's model call is the one member call's (`agentloop/member_call`), the same bounded, brief-only, serial, narrated call a consult and a validation make, so no second calling path can be written from it; the definitions, their validation and the stage walk are deterministic around it, and the surfaces -- `cli/symphonies_cmd`, the admin twins -- render its one view (`symphony/view`). A chain is a symphony (27r): a stage that plays another recurses through the same walk on the same turn, so no chain engine exists to drift, and whether a definition loops or nests too deep is one walk (`contracts/symphony_walk`) the parser, the loader, the scaffold and a play's start all ask. The Orchestrator is registration (27t): each definition projects an ordinary tool (`symphony/tools`) the loop offers and dispatches as any other, a play the model starts running through the same walk with `local_only` on -- no planner, no second loop.
- `markdown/` is guarded the other way round (2026-09-25): it may include only `ansi/` and itself, so the renderer's decisions stay testable as operations with no terminal, and never merge with the painter's bytes in `commands/answer_view`.
- `cli/` is deliberately NOT guarded: it is the composition root, and assembling providers is its job. Since A3 the commands are three modules: `cli/` (the commands, the root and registry, the one command table and the slash ecosystem), `views/` (what paints -- the status line, the thinking and answer views, the line reader, download progress, the ask prompt, the terminal adapter `cli_reporter`), and `machine/` (the machine-mode adapter `json_reporter`, and since 28f `driver_input`, the one reader of a driver's stdin, which lets a `cancel` reach a turn in flight, and since 28g `protocol`, the vocabulary declared as data -- what `capabilities` announces and `apogee __machine-schema` (`cli/machine_schema_cmd`) prints as a JSON Schema). `views/` never parses argv or reaches `cli/`; `machine/` never paints; `cli/` composes both -- each held by `harness.layering`.

**Enforcement.** Since A4, the build and a scan, reading one map. `cmake/modules.cmake` declares each module's layer and links; an include up a layer does not compile, and `apogee_assert_link_policy()` fails the configure step on a link up a layer, a cycle, an undeclared link or a misplaced source. The `harness.layering` ctest case (`tests/scripts/cmake/layering.cmake`) reads the same map: a package with no row, a row naming no package, or a directory that disagrees with its row fails, so a new package declares its layer the day it exists; and it holds the includes to the map **in both directions** -- an include of another module its row does not link fails, and so does a declared link nothing includes. The build sees a layer, not a module, so this is where an undeclared edge inside a layer is caught. It then greps every source in `harness/`, `agentloop/`, `agent/`, `secrets/`, `tools/`, `mcp/`, `knowledge/`, `graph/`, `training/`, `tasks/` and `symphony/` for a `backends/` include, and holds `contracts/`, `modelstore/`, `transport/`, `secrets/`, `knowledge/`, `graph/` (and within it the code graph's narrower list, 27k), `training/`, `tasks/`, `symphony/`, `markdown/` and `events/` to their named allow-lists, and every source in the tree to the one tree-sitter boundary -- which it requires to see, so a moved boundary fails rather than passes. It refuses to run against an empty source list for any guarded package, so it cannot pass vacuously; each rule was verified against a planted violation (A1).

### ⚠ Capability probes never leak a cast

**Rule.** Optional provider capabilities (`EmbeddingCapable`, `StatusReporting`, `InTextToolCalling`, `ModelBehaviorReporting`) are **discovered by the Harness**. Callers ask a plain typed question — `harness.can_embed(model)`, `harness.model_behavior_for(model)` — and never write a `dynamic_cast` of their own.

**Why.** Gating embedding behind a hardcoded allowlist of backend types encodes an assumption — that a given vendor cannot embed — which stops being true the day that vendor ships an embedding API; OpenAI and Google both embed over theirs. A capability question answered by testing a type turns into a switch over vendors that has to be edited every time one is added. Asking the object is the version that keeps working.

**Sub-rules.**
- A probe on an unroutable model answers "no" rather than throwing — a caller asking about a capability should not have to handle a routing failure too.
- `ModelBehavior`'s zero value means *unknown*, and **unknown must be treated as permissive**: failing to recognise a tool call means nothing dispatches AND the raw markup is printed to the user as if it were the answer.

**Enforcement.** `tests/business/harness/harness_test.cpp` → the `[harness][capability]` and `[harness][behavior]` cases, and `tests/data/backends/factory_test.cpp` → `[factory][embed][capability]`, which asks the harness about providers the factory actually BUILT: Anthropic answers no, OpenAI and Google yes, and nothing in the test names a type.

### ⚠ Interactive turns never open a listening socket

**Rule.** Only `apogee serve` may own a port. No interactive command, and no backend serving one, opens a listening socket — cloud backends make outbound HTTPS calls and llama.cpp runs in-process.

**Why.** A backend that quietly starts a local server still answers correctly, so nothing looks wrong until someone notices an open port on a shared machine. It is also the structural half of "interactive = pipes, serving = server": once one interactive path listens, "local front-ends are pipes too" stops being true and the GUI's stdio contract loses its justification.

**Sub-rules.**
- A persistent child process is not a listening socket — the vendor-CLI backends stay compliant by construction.
- **`serve` has exactly one reviewed exception** (Milestone T): `httpserver/serve.cpp`, the listener, is the only object file in the whole link that may reference `listen`/`accept`. The allow-list names that object; every other file under `httpserver/` is as socket-free as the rest of the library, which is what lets the handlers be tested with no port at all. Moving the listener is a deliberate edit to the allow-list, never a drift.
- `serve` is for **server deployments** answering remote REST clients. Nothing in `httpserver/` may become load-bearing for a local `chat` or `complete`, and a non-loopback bind fails closed behind `--allow-remote`.

**Enforcement — two checks, and neither is sufficient alone.**
- `cli.no_listen_symbols` (`tests/scripts/cmake/no_listen_symbols.cmake`) — `nm -A -u` on `apogee_core` **and on every library the `apogee` executable links that this build produces, static or shared, transitively** (the list is collected by walking the link graph in `tests/CMakeLists.txt`, so a new in-process dependency is scanned without anyone remembering to add it; for a static library the walk follows what it hands the linker, its `INTERFACE_LINK_LIBRARIES`, since its private `LINK_LIBRARIES` never reach the final link -- so `llama-common`'s cut httplib is out of the scan exactly as it is out of the binary, 25b): every reference to `listen`/`accept` is attributed to the object file — or, for a shared library, the file — that made it, and only `serve.cpp.o` may. Deterministic, no timing; catches our own code however brief the window, and a third-party library's — the gap that became real once llama.cpp started running **in-process** (Milestone J). Shared libraries are scanned by name because llama.cpp *is* one under the llama preset, and a shared library's own imports never appear in the executable's symbol table — so the earlier binary scan, which claimed to cover it, did not (found in Milestone T). Imported system libraries are the platform's and are left out; libcurl legitimately calls `accept` for FTP. Two vacuity guards: it refuses an empty list, and it **requires** the allow-listed object to be seen referencing the symbols — so a stale list or a changed `nm` format fails rather than passes. Blind to a child process.
- `cli.complete_opens_no_listening_socket` (`tests/scripts/sh/no_listen_check.sh`) — polls `lsof` across a real turn. Catches a *spawned* server holding a port. Since 27a it also samples a turn answered by the `mlx` backend's real driver across apogee's whole process tree, and requires to have seen the driver; a stub that listens on load fails it. Since 27c a third phase samples a turn the same driver answers under `serve`, streamed to a client: serve's own process must hold the listener, no descendant may hold a socket of any kind, and the driver must be seen -- the same listening stub fails it there too, and so did the driver's first real served turn, holding the client's connection it had inherited, until `platform/child_process` gave a child its three pipes and nothing else. Blind to a sub-millisecond window. POSIX only; Windows is a recorded skip. Its positive twin, `cli.serve_lifecycle` (`tests/scripts/sh/serve_e2e.sh`), asserts that `serve` **does** hold one — together they are the boundary.

Both were verified against a build that deliberately calls `listen()`: the symbol check failed it, the runtime check did not. That asymmetry is exactly why the pair exists — see MILESTONES.md → Milestone E. The per-object attribution was verified the same way in Milestone T: a `listen()` planted in `http_types.cpp` failed the check naming the file, and a throwaway shared library calling `listen()` handed to the check failed it naming the library.

### ⚠ One layout declaration, and every install path reads it

**Rule.** What `~/.apogee/` contains is declared **once**, in `contracts/layout.h`. Every path that creates the tree, and the one that validates it, enumerates that declaration. No installer, no Makefile target, and no test may carry its own list of directories.

**Why.** *Silent install drift* is the failure this prevents: when `make install` seeds one tree, `install.sh` another, an updater a third, and `check` validates a fourth, each list is correct when written and they diverge one commit at a time. Nothing ever fails loudly — a fresh install simply lacks a directory that some command needs months later, and the report comes back as an unrelated bug in that command.

Making this a review rule ("remember to update all four") holds until the day someone is in a hurry. Making it structural means there is nothing to remember: a contributor adds a row, and the installer and the doctor both learn about it because neither knows anything the row does not say.

**Sub-rules.**
- `seed_data_directory()` is the **only** implementation that creates the tree. `apogee check --fix` calls it; both installers call `apogee check --fix`; `make install` ends with the same call. A shell script that made directories itself would be a second declaration.
- Any asset landing under `~/.apogee/` is added to the declaration in the **same commit** as the code that uses it — the parity rule.
- `check` reports the contract but never edits config. `--fix` may repair the local install (a missing directory, a wrong mode — and, since M11 2026-10-08, the starter config **seeded where no config file exists at all**, at the install's own path only: an absent file has no meaning to preserve, while an existing config of either format is never touched under any flag); it may not decide what a dangling `model_path` meant.
- A check that cannot run on a platform reports **skipped**, never passing. Windows has no `0700`, and "modes OK" there would be a lie shaped exactly like a pass.
- **Which root, chosen once** (M10, 2026-10-04): the declaration says what a root holds; `contracts/paths.h` says which root a run uses, in one chain -- a root flag for that run only (`--dev`, `--test`, `--release`, `--custom <root>/config/<file>`), then `APOGEE_HOME`, then the root of the install channel baked into the executable (`~/.apogee` for release, `~/.apogee-dev`, `~/.apogee-test`). Every row resolves through `apogee_home()`, so a flag re-roots the whole layout, never the config read alone, and a flag and an `APOGEE_HOME` that disagree are refused with both named. A channel changes the root and the binary's name (`apogee-dev`), never the contents. `uninstall` alone skips the flag rung (`install_home()`): a binary removes the install it belongs to.
- **The same rule one level down, inside `models/`** (2026-09-23): where a model file lives -- `<model>/gguf/<id>/`, `<model>/safetensors/<id>/`, and since 27b `<model>/mlx/<id>/` (an MLX model, a directory taken whole), the id the weights' own hash -- is declared once, in `modelstore/store.h`, and pull, convert, quantize, list, delete, repair, check and training promotion all ask it. The flat layout it replaced is found and refused by name, never read in place. `check` reports it and names `apogee models migrate`; it does not move it, because moving a model repoints the `model_path` that names it and `check` never edits the config.

**Enforcement.** `cli.install_parity` (`tests/scripts/sh/install_parity.sh`) installs twice into throwaway roots and requires the sorted directory listings *and modes* to be identical, refuses to pass on fewer than five directories (so it cannot pass vacuously), and requires a freshly seeded install to pass `apogee check` with zero failures. It is a case in the suite (`cli.install_parity`), so every platform build that runs `--test` runs it; the dedicated CI jobs (a POSIX one and a PowerShell one) were removed 2026-09-19. Verified against a deliberate drift — removing one directory from the seeding loop — which it caught. Since M10 it also takes a dev-channel build of the executable and requires the same tree and modes under `.apogee-dev`, nothing under `.apogee`, and that build's uninstall to take its own root and nothing of the release install's (verified against a build that never baked its channel, and an uninstall back on `apogee_home()`); `contracts/paths_test.cpp` pins the re-root by seeding under a `--custom` root from `layout.h`'s own rows.

The first version of this did **not** catch that drift, and the reason is worth keeping: there were two seeding implementations, and the mutation hit the one the installers did not reach. Two implementations of the layout is the bug, even when both are correct.

### ⚠ One retriever per turn, resolved once, reported honestly

**Rule.** A turn searches a collection with exactly one of `lexical`, `vector`, `hybrid`, decided by **one function** — `agentloop::resolve_turn_retriever` — from the flag, the collection's pin, and facts about the embedder and the store. Every surface reports the retriever that **actually ran**, including when it degraded: nothing ever claims `vector` or `hybrid` for a search that ran lexical.

**Why.** Normalised BM25, cosine and RRF are three incomparable scales; a score shown without its scale invites a comparison that cannot be made. And the rules for *which* scale a turn is on are subtle — model match, full coverage, a single vector space, an explicit ask versus a pin. Let those rules drift between surfaces and the same question searches differently on each. A rule that exists once cannot drift.

**Sub-rules.**
- An explicit `--retriever vector` that cannot run is a **hard error** naming lexical as the way out — the user asked for something impossible and must not get something else under that name. A `retriever: vector` **pin** that cannot run **excludes** the collection with a note; it is never silently searched the other way.
- `hybrid` is explicit only; `auto` never resolves to it. A hybrid ask without a vector half runs and is *reported* lexical.
- A store whose vectors came from another model, or that holds any chunk without a vector, or more than one vector width, is demoted **wholesale** to lexical with the re-ingest hint — never queried as a fraction.
- Rerank can never cost context: every judge failure returns raw order with `reranked: false`, and `reranked` is set from the same place as the ordering.
- **How strong a match is, and the floor, are per retriever too** (26s): a turn's best hit is read on its own retriever's scale -- RRF over its ceiling (2/61), a cosine as it is, a lexical hit by how many of the question's words it holds, since BM25 saturates -- and under that retriever's floor the turn injects nothing and its line says so. Never one threshold across the scales, and the raw score and retriever always ride beside the word.
- **Spend** (user decision, 2026-09-13): a whole collection is never vectorised through a metered embedder on Apogee's initiative; a question against one already built is one small call and is allowed. Whether an embedder is metered is a fact the provider states, never a type list.

**Enforcement.** `tests/business/agentloop/retrieval_test.cpp` is the exhaustive rule table (flag/pin/auto × embedder × store) and, since 26s, every band edge and floor per retriever, `tests/business/agentloop/rerank_test.cpp` has one case per failure path, and `cli.config_lifecycle` drives the real binary through a model mismatch, an explicit-vector refusal, hybrid, and a `check` that rejects a `retriever:` typo. All mutation-tested.

### ⚠ Secrets are unleakable by construction

**Rule.** A secret — the admin bearer token, a stored provider API key — has no type that anything serializes. What a route, an event, or a log line can carry is a **view** that structurally lacks the secret field: `backend_view` has `api_key_set` and no `api_key`; nothing at all turns the token into JSON. A secret is accepted **body-only** and, when literal, from a **loopback peer only**, judged from the socket's own address (`HttpRequest::remote_address`) and never from a header a client can set. On disk it is `0600` before it is renamed into place.

**Why.** "Never returned over HTTP" as a review rule holds until someone adds a convenient `to_json` over the struct that happens to hold the key. Making the serializable type *unable* to carry the secret means the leak cannot be written, rather than merely noticed. Apogee has held to this shape from its first secret.

**Sub-rules.**
- The admin token is header-only (`Authorization: Bearer`) and compared in constant time; a query-string token is refused even when correct, because a query string lands in request logs.
- The `/v1/admin/` gate runs **before routing**: an unauthenticated probe gets `401` for every path, and cannot learn which routes exist.
- Per-install secrets are never seeded (install parity never sees them) but are doctor-checked: present means `0600`, `skipped` on Windows, never a pass.
- `harness::write_file_atomically(path, content, /*private_mode=*/true)` sets the mode on the temporary file before the rename; nothing writes a secret any other way.
- The credential store (`secrets/store.h`) hands out `CredentialMetadata` — provider and `stored_at`, structurally no key — and exactly one function, `key_for`, returns a key: the resolver calls it and nothing that renders does. Vendor-CLI types have no slot at all; asking for one is refused with the principle.
- **One key resolver** (`secrets/resolve.h`, the sibling of `harness/roles.h` for the same reason): the entry's `api_key` > the stored slot for its type > the conventional variable, read from an `EnvSnapshot` taken once so two writers on one process cannot move a resolution mid-run. The factory, `check`, `models list` and `auth list` all call it; `cli.one_key_resolver` fails any other file that reads an entry's `api_key` or names a conventional variable, so a second chain cannot start.
- A key is never taken on the command line (`auth add` prompts with echo off, or reads `--stdin`/`--from-env`), and over HTTP it travels in the body of a route served to loopback peers only.

**Enforcement.** `tests/presentation/httpserver/admin_auth_test.cpp` (the 401 matrix, a one-byte-off token, the query-string refusal, the file mode), `tests/presentation/httpserver/admin_config_test.cpp` (the view never carries the key; a literal key needs a loopback peer; a `${ENV}` reference passes), `tests/presentation/cli/check_test.cpp` (the `Secrets` row and `--fix`), `tests/data/secrets/store_test.cpp` (round trip, `0600` after every write, a corrupt file reads as empty with a warning and is never overwritten), `tests/data/secrets/resolve_test.cpp` (the precedence table, exhaustively; a snapshot deaf to a later change), **`tests/presentation/cli/leak_test.cpp`** (one distinctive key in every rung at once, then every listing, doctor row, admin response, build reason, bus event and log line searched for it), `tests/presentation/httpserver/admin_auth_routes_test.cpp` (`403` from a non-loopback peer with a spoofed forwarded header, metadata-only responses, a vendor CLI refused), `cli.one_key_resolver`, `harness.layering` (`secrets/` may include only the contracts and itself), and `cli.serve_lifecycle` on the real binary (the token file and the store are `0600`, a query-string token is refused, a key stored with `auth add --stdin` is attributed by `check` and listed as metadata over HTTP, and neither secret appears in any output, response, event or log).

### ⚠ A child's stderr is captured, never inherited

**Rule.** No subprocess Apogee spawns on an interactive path inherits the terminal's stderr. A vendor CLI, a git or shell tool, an MCP server: each gets an explicit sink, and the sink is **mandatory in the API** — there is no constructor that inherits. By default the stream is discarded with a bounded tail retained (the last eight lines per MCP server, 8 KiB per vendor CLI), folded into the failure message when the child fails and dropped when it does not; `--verbose` routes the raw stream to the terminal, and `serve` keeps its own stderr as the daemon log.

**Why.** An inherited stderr puts `chat` behind a wall of output: a stdio MCP proxy that narrates its whole OAuth handshake writes straight onto the terminal, bypassing the status line entirely — no care on the harness's side can keep the line intact, because the bytes never pass through it. And a server that dies mid-handshake holds the frozen line for the full connect timeout. Both are structural once stderr is a pipe the harness owns: nothing can reach the terminal except through the status line, and a closed pipe is a signal the read loop acts on at once.

**Sub-rules.**
- Discarding stderr must cost no diagnostics: the tail is kept whatever the sink, and a connect failure reports it on **one line**, so it fits a status render.
- Nor does a child inherit anything else (27c): `start_child` hands it its three pipes and closes every other descriptor in it -- the mlx driver's first real served turn was found holding the client's connection `serve` had accepted, kept open for the driver's life. `platform/child_process_test` holds it with a descriptor opened without CLOEXEC.
- A dead child releases its waiters from the read loop's error path — `mark_done` once, from either side — never only from `close()`. A dead server must fail in well under a second, not at the timeout.
- Startup speaks through the status line: `[mcp] connecting:` goes out *before* each dial, results repaint the same line, and a warning stays.
- Once connected, a client logs nowhere: the progress writer may become a status line a live turn owns, and a background thread writing there stops the spinner.
- **One documented exception, and it is not on an inference path**: `platform::run_foreground` gives a child the terminal's own stdio, for `apogee agents edit` -- and since 27q `apogee symphonies edit` -- opening the user's `$EDITOR` at their request while no turn is running. Nothing else may call it; a backend or a tool that did would be reintroducing the wall of output this section exists to prevent.

**Enforcement.** `tests/business/mcp/transport_test.cpp` (the tail bounded and teed; the transport's sink), `tests/business/mcp/client_test.cpp` (a dying server fails at once with its tail on one line; a slow one at the bound), `tests/business/mcp/registry_test.cpp` (the fleet: skipped never fatal, progress before every dial), and **`cli.mcp_server_stderr_stays_off_the_terminal`** (`tests/scripts/py/pty_mcp_check.py`) on the real binary under a pseudo-terminal: a deliberately noisy, dying server's lines appear nowhere on the screen, the connect failure carries its last line, every row is Apogee's own, and startup ends well inside the connect timeout. Since 27a the same holds for the `mlx` backend's Python driver: its stderr is drained into an 8 KiB tail whose last line is folded into a failure, the driver points its own descriptor 1 at stderr before importing anything so a library's print can never reach the protocol channel, and `cli.mlx_lifecycle` holds a noisy stub's lines off both of apogee's streams. Since 27b `models convert --mlx`'s driver too: run over the training track's script runner, its stderr a tail folded into a failure, its own descriptor 1 on stderr before `mlx-lm` is imported, and `cli.mlx_models_lifecycle` holds the converter's own print off both streams. Since 26e the same holds for `ffmpeg`, which decodes attached audio and video through `platform/ffmpeg` (a child of Apogee's own, never mtmd's video helper, which would spawn it from code Apogee does not control): `cli.ffmpeg_stays_off_the_terminal` (`tests/scripts/py/pty_ffmpeg_check.py`) attaches a clip under a pseudo-terminal with a fake `ffmpeg` that narrates on stderr, and none of it reaches the screen.

### ⚠ What leaves the machine is asked about by host, and the host asked about is the host reached

**Rule.** A tool that sends data off the machine is `outbound`, and the gate decides each call by the **host** it reaches — `tools.allowed_hosts`, then the session's answers, then a prompt, and where nobody can answer, deny. The URL a transport is given is **rebuilt** from the parts the gate saw, never passed on as the model wrote it, and every redirect is a new call to the gate before anything is fetched from a new host.

**Why.** A model with tools can read a file and put its contents in a URL, and a web page carrying hidden instructions is enough to make it try (found by the local-tools spike, 2026-09-25). A per-website prompt only guards anything if three things hold: the comparison cannot be fooled by a lookalike host, a second URL parser cannot read a different host out of the same string (`http://allowed.example\@evil.example/` is the classic), and a `302` cannot walk the fetch somewhere nobody was asked about.

**Sub-rules.**
- What a host is, and whether two are the same, is `contracts/host.h` and nothing else: canonical form, **exact** comparison, never a prefix, suffix, substring or pattern.
- `fetch_url`'s fetcher never follows redirects (`HttpRequest::follow_redirects = false`); the tool follows them hop by hop through `TargetGate`. A new outbound tool uses the same gate, not its own: `web_search` (25e) is `outbound` with its SearXNG instance's host as the target of every call, and that host is **trusted by configuration** — `make_permission_checker` counts the one `tools.search` names as listed — while every page a search finds is an ordinary `fetch_url`, asked per website.
- An outbound tool must name its target; a call it cannot name one for is refused unrun.
- `always` for a website adds it to `tools.allowed_hosts` through `contracts/config_edit.h` (`add_allowed_host`), the transform `config add-allowed-host` and the admin twin call too.

**Enforcement.** `tests/data/contracts/host_test.cpp` (the lookalike table), `tests/business/agent/fetch_url_test.cpp` (refusals send nothing; redirects asked hop by hop; userinfo, backslash and percent-escape tricks refused before anything is sent; the rebuilt URL), `tests/business/agent/web_search_test.cpp` (the target is the configured host), `tests/presentation/cli/permissions_test.cpp` (the checker by host; a pipe and a driverless session reach only listed hosts; the real fetcher asks for one hop; the search instance trusted and the page it finds asked about), `tests/presentation/httpserver/handler_test.cpp` (a served fetch), `tests/presentation/httpserver/admin_config_test.cpp` (the twins byte-identical), and `cli.config_lifecycle` on the real binary (a pipe refused, a driver's `always` written exactly, the listed host then reached).

### ⚠ Text is UTF-8 where it enters, so no JSON dump can throw on it

**Rule.** Every string that can reach a JSON dump -- a machine-mode event, an SSE frame, the session file, a task's ledger, a backend's request body, an MCP frame -- is valid UTF-8, mended **where it enters**, not where it is written: what a model streams, at the Harness (`Harness::chat`, `stream_chat`, `complete`); what a tool returns, at `agent::dispatch`; what a person types or pipes, at `build_messages`, `--system`/`/system`, the `/play` line and a task's goal and `--require`. A character cut across two streamed pieces arrives whole; bytes that are not text become U+FFFD (the maximal-subpart policy, `contracts/utf8.h`). Valid text passes byte for byte, and nothing is copied for it.

**Why.** nlohmann's `dump()` throws `type_error.316` on anything that is not UTF-8, and model text is bytes: llama.cpp emits a byte-fallback token a byte at a time, a pipe read cuts anywhere, a file can be Latin-1. Until 2026-10-06 a valid é split across two deltas ended `--output-format stream-json` mid-turn, a Latin-1 `read_file` ended a driven chat at the next Anthropic request, and a piped Latin-1 line ended `chat` at the session save -- three dumps, one cause. Mending at each writer would have to be remembered at every new one; mending at the few doors text comes in through is one rule.

**Sub-rules.**
- **One stream per sink.** `Utf8Stream` holds an incomplete tail until the next piece completes it and flushes U+FFFD at the end; the answer and the reasoning each have their own, so the kept answer is exactly the deltas' concatenation and history, the session file, the ledger and machine mode's `result.text` agree by construction.
- **The outbound request is mended too**, copied only when a message holds something that is not text, because every backend serializes it with a strict dump and its text comes from everywhere -- files, attachments, retrieved excerpts.
- **Machine mode's one writer never throws** (`JsonReporter::write` dumps with `error_handler_t::replace`): an event's other text -- a vendor CLI's stderr tail cut at a byte bound -- is said as U+FFFD rather than ending the session over a notice. Valid text is written exactly as a strict dump writes it.
- A `--require-file` path stays as given: it names a file on disk.

**Enforcement.** `tests/data/contracts/utf8_test.cpp` (every 2-, 3- and 4-byte character split at every boundary; the replacement policy), the `[utf8]` cases in `harness_test`, `loop_test` (an answer cut inside a character kept, saved and written to a ledger as streamed), `anthropic_loop_test`, `tool_test`, `fs_test`, `serve_stdio_test`, `machine_mode_test`, `handler_test`, `helpers_test`, `execute_test` and `task_test`, and **`cli.machine_mode`** on the real binary: the split é through `complete`, a Latin-1 `read_file` in a driven chat, and a Latin-1 line and `--system` piped into `chat` -- each exits 0, emits valid JSONL and saves a session file that parses.

### ⚠ Smart pointers, never owning raw pointers

The Code Style rule below is lint-enforced, not aspirational: `make -C lib/src/cli lint` fails on a raw `new`/`delete`, an owning raw pointer, or `malloc` anywhere in the CLI's `source/` or `tests/` (`cppcoreguidelines-owning-memory`, `cppcoreguidelines-no-malloc`, `modernize-make-unique`/`make-shared`, promoted to errors in `.clang-tidy`). `third_party/` is out of scope by construction. It is a **local gate**: run `make -C lib/src/cli lint` before a merge (it takes about twenty-five minutes over the whole tree). CI does not run it — the `lint` job was removed 2026-09-19, the user's call: CI builds the executable for each platform and nothing else.

## Working process

Apogee is built docs-first: features are discussed in chat, written up in the planning docs, then handed to a coding session to build. Respect the flow between documents.

### Where new work is written down

- **A new feature or theme** → first a line in [ROADMAP.md](ROADMAP.md) (and an update to [SPEC.md](SPEC.md) if it changes the product's scope or principles).
- **Specced** (design decided) → its own document in [`lib/documentation/backlog/`](../backlog/README.md), one file per work item, added to the **priority-ordered index** in that directory's README (top = next to build). The backlog is the work queue — there is no separate TODO file.
- **Being built** → the agent works **straight from the backlog document** (it is the working spec); mark its index row **in progress** so parallel sessions see it's taken.
- **Completed** → recorded in [MILESTONES.md](MILESTONES.md), and the backlog document is deleted along with its index row (see **Documentation and Status** below). The backlog holds pending work only — never finished work.

### Working a backlog item

When asked to work on the next item, read the [`backlog/`](../backlog/README.md) index and take the **topmost item whose gate is satisfied** (skip gated items whose prerequisite hasn't shipped), or the specific item the user names. Read that item's document carefully — it is the working spec. Before writing any code, confirm scope and requirements with the user (the document's **Open calls** are the natural questions) — do not begin implementation until the user has answered. Complete one item at a time. When an item is finished, stop and wait for the user to explicitly ask to continue. (A bare "Continue" means: re-read this file, then take the topmost claimable backlog item.)

When applicable, also update the root `README.md` if the change affects how someone builds or installs the project.

### Versioning

Feature releases are `v0.x.0`; patch releases are `v0.x.y`. Development happens on a branch named for the release being built and merges into `stable` when that release is done — **and that merge IS the release** (user decision, 2026-09-22): once the pull request merges, the version `lib/release/VERSION` names is tagged and published, if it has not been published already, from the archives that pull request's own CI run built (2026-09-25) — so the first commit on a new release branch bumps that file (and, when the CLI changes, the CLI's own version with it), or the pull request's `version bump` check fails. The branch in development is named in ROADMAP.md's version scheme. ROADMAP.md tracks each release at the theme level; MILESTONES.md records what actually shipped in detail. **Two versions, one job each** (user decision, 2026-09-25): `lib/release/VERSION` is the **release**, and the only thing that names one; the `project(... VERSION x.y.z)` call in `lib/src/cli/CMakeLists.txt` is the **CLI's** own, which flows into `apogee version`, changes only when the CLI does, and then equals the release it ships in. A release that leaves the CLI alone carries the previous release's CLI archives, so their binaries report the older CLI version. A release is a tag and its GitHub Release, made together — the policy is [below](#release-and-install-infrastructure), the procedure is in [DEVELOPER.md](DEVELOPER.md#cutting-a-release).

## Implementing a Feature

Every change should satisfy this before merge:

- [ ] Tests for the new behavior pass, and existing tests stay green: `lib/scripts/cicd.sh --test`.
- [ ] Formatting and lint are clean: `make -C lib/src/cli format-check` and `make -C lib/src/cli lint`.
- [ ] New tests are **hermetic** — no network, no models, no writes outside the test's own temp directory. A test that needs a live provider is not a unit test; go through the injectable seam instead.
- [ ] **Real-weights checks, where an item has them, cover the model families** — Meta, Qwen, Google and OpenAI, one installed model each (its Q4_K_M build when there is one; full weights only when not), run one family at a time with its model loaded once, with each family's result recorded; never DeepSeek, nor the other models excluded there (the user's call, 2026-10-03). Optional: a family with no local model is skipped and said. The rules are in [DEVELOPER.md → On real weights](DEVELOPER.md#on-real-weights-the-model-families).
- [ ] New source files are `.h`/`.cpp` pairs, added to their module's list in its layer's `CMakeLists.txt` (`lib/src/cli/source/<layer>/CMakeLists.txt`, Architecture A4), and the test tree mirrors the package.
- [ ] **If the change touches the pipeline** (`.github/`, or a CI job's name, matrix or order): it follows [DEVELOPER.md → Changing the pipeline](DEVELOPER.md#changing-the-pipeline). Above all, once the pull request's run passes and before it merges, `lib/scripts/required-checks.py --pr <N>` shows the required checks it would set, and `--apply` sets them. `--apply` changes repository settings: an agent asks the user first. Skipped, the "Stable: CI must pass" ruleset keeps waiting for the old job names, and nothing can merge.
- [ ] **The shell's place is classified** ([ADR 0010](../adrs/cli/the-shell-is-a-mode.md)): a change that adds or alters a user-facing read or mutation places it in the full-screen shell in the same change -- drawn by a view, named for the item that will draw it, covered by the exec line, or carved out with the reason the exec line refuses it by -- in `cli/tui_parity.cpp`'s one table, which `tui_parity_test` holds to the registered commands. - [ ] **The model lists Apogee carries are current** ([ADR 0009](../adrs/cli/built-in-model-lists.md)): if the change touches a backend, the rosters, completion or model selection -- or a vendor has shipped, renamed or retired a model since a list's reviewed date -- `backends/model_roster.cpp`'s carried lists (Claude Code's Anthropic ids, the Gemini CLI's aliases) are checked against their sources and updated, the reviewed date moved, in this change. A CLI that gains a list command gets `CatalogListing` and loses its carried list. [DEVELOPER.md → Updating a carried model list](DEVELOPER.md#updating-a-carried-model-list) is the recipe.
- [ ] The affected docs are updated in the same change (see **Documentation and Status**) — run the `apogee-cli-maintenance-update-documents` skill before opening the MR; it audits every document against the branch diff and validates the system mechanically.

## Code Style

*(The two rules below are user decisions, 2026-08-24. They applied from the first line of code and are lint-enforced as of 2026-08-25 — see [⚠ Smart pointers, never owning raw pointers](#-smart-pointers-never-owning-raw-pointers) above. Formatting is settled in `.clang-format` and is never a review topic: run `make -C lib/src/cli format`.)*

- **Header/implementation split.** Every class/module ships as a `.h`/`.cpp` pair when applicable — declarations in the header, definitions in the `.cpp`. Header-only is the recorded exception, reserved for templates and trivial data-only structs. The backlog documents' **Seam + files** sections already name files as `foo.h/.cpp` pairs; follow them.
- **Smart pointers, never traditional pointers.** No raw `new`/`delete` and no owning raw pointers anywhere. `std::unique_ptr` is the default ownership type; `std::shared_ptr` only where ownership is genuinely shared (`std::weak_ptr` to break cycles); construct via `std::make_unique`/`std::make_shared`. For non-owning access, prefer references (or `std::string_view`/`std::span`) over pointers. C APIs (llama.cpp, SQLite, libcurl) hand out raw handles — wrap each in a `std::unique_ptr` with a custom deleter at the boundary class, and never let the raw handle escape it.
- _TODO:_ further naming conventions, error-handling idioms, and shared-helper locations accrete here as the first modules land.
- Match the surrounding code's conventions; when in doubt, find the closest existing analogue and follow it.

## Release and Install Infrastructure

Development happens on a version-named branch and merges into `stable` when the release is complete, **and that merge publishes the release** (user decision, 2026-09-22) — `v<VERSION>`, **from the pull request's own build, or with the CLI unchanged from the latest release's** (user decisions, 2026-09-25). Every CI build job packages its target through [`.github/actions/package`](../../../.github/actions/package/action.yml): the archive, the binary proven to run, and a `.source` record of the commit and source tree it was built from, kept as an artifact of the run. When the pull request merges, CI's `tag and release` job runs [`lib/scripts/release-from-pr.sh`](../../../lib/scripts/release-from-pr.sh), which finds the pull request's last green run; requires every archive to have been built from the merge commit's exact source **tree** — CI builds GitHub's test merge, whose tree is the merge's unless `stable` moved after the run; requires the executable to report that version — a CLI that changed ships in this release and says so; and then creates the tag `v<VERSION>` at the merge commit together with the release. When the CLI is **unchanged** since the latest release (`lib/scripts/changed.sh cli`), nothing of the pull request's is used for it: the script downloads that release's CLI archives and publishes them again as they are. Nothing is rebuilt, so what ships is byte for byte what CI tested. One consequence, recorded: `apogee version` names the commit the binary was built from, which is that test merge — the same tree as the merge commit, a different hash. A version whose tag already exists at another commit publishes nothing (the docs-or-hotfix merge); a tag already at the merge commit is an earlier attempt, which a re-run finishes.

**The re-cut** is the one other way a release is published, and it lives in the same workflow (user decision, 2026-10-04, M8, which deleted the separate manual release workflow and its `v*` tag trigger: a pushed tag runs nothing). [`ci.yml`](../../../.github/workflows/ci.yml) dispatched on `stable` with `publish` runs every job — the unit-test stage, then each of the five targets built on its own native runner **through `lib/scripts/cicd.sh`** and packaged through the same action — and once all five pass, its `tag and release` job runs `release-from-pr.sh --recut` on that run's own archives: the commit must be on `stable`, every archive's record must name its tree, the host's binary must run (and report the version when the CLI changed), and a version already released is refused. It is for a merge whose own archives cannot be used (the tree check failed, or the artifacts expired), or a deleted release cut again — and, unlike the merge path, it always rebuilds the CLI, even when it is unchanged since the latest release.

What ships: `apogee-<target>.tar.gz` for the three POSIX targets and `apogee-<target>.zip` for the two Windows ones, each containing the binary, the four completion stubs and, since 28g, `machine-schema.json` — the machine-mode protocol as a JSON Schema, printed by that very binary (`apogee __machine-schema`) as it is packaged and checked byte for byte against it. Completions ride inside the archive because they are part of the install contract, and `install.sh` / `install.ps1` fetch that one archive for the host (and install only the binary and the completions).

All five archives are always there, on both paths: CI requires every build on a pull request and the script refuses a run missing one, and a re-cut's `tag and release` runs only once all five builds pass. One gating policy, the stricter one (M8): the retired manual workflow let the two Windows targets fail and published a release with three archives.

On both paths the tag is created in the same `gh release create --target <sha>` that makes the release, so a failure strands no tag without its release. A tag made with a run's `GITHUB_TOKEN` triggers no workflow, and since M8 none listens for a tag at all — which also keeps the repo free of release secrets.

A source build can be any of three **install channels** (M10, 2026-10-04): `make install MODE=dev` or `MODE=test` installs `apogee-dev` or `apogee-test` beside the release `apogee`, each owning a data directory of its own, and `make uninstall MODE=<channel>` runs that binary's own `uninstall`. The archives, both installers, CI and `cicd.sh` are the release channel only and unchanged -- see [DEVELOPER.md → Install channels](DEVELOPER.md#install-channels).

Nothing here signs anything — macOS ships unsigned (user decision, 2026-09-01), and `apogee check` detects the quarantine attribute a browser download sets and prints the exact `xattr -d` fix.

Cutting one is therefore *merging the PR* — rehearsed first, by dispatching CI with the pull request's number (`release_rehearsal_pr`), which runs every check and publishes nothing. `make -C lib/src/cli release VERSION=x.y.z` remains the escape hatch: it preflights the tree, branch, version and tag, then dispatches the re-cut. The step-by-step procedure, the dry run, and how to re-cut a bad release are in [DEVELOPER.md](DEVELOPER.md#cutting-a-release).
