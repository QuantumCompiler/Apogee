# Apogee design — Developer Reference

How the design prototype is laid out, installed, built and checked. Its law is [the design's ADR 0001](../../adrs/design/react-design-prototype.md); how to work on it is [CLAUDE.md](CLAUDE.md). The old one-file prototype at `lib/design/spec/` keeps its own guide, [`lib/design/spec/CLAUDE.md`](../../../design/spec/CLAUDE.md), until 1t retires it.

## Install

In `lib/design/prototype/`, with Node 26 (`/opt/homebrew/bin/node` on this Mac):

```bash
npm ci                              # the packages, exactly as package-lock.json pins them
npx playwright install chromium     # once per machine: the smoke test's browser
```

The browser lands in `~/Library/Caches/ms-playwright`. Measured 2026-11-18 with Playwright 1.64.1, it downloads about 286 MiB (Chrome for Testing 185.8 MiB, its headless shell 99 MiB, FFmpeg 1.4 MiB) and takes 572 MB on disk. 1c's baseline and 1s's parity shots use the same browser.

Nothing is installed globally. A new package goes in with `npm install --save-exact <name>` (`--save-dev` for the toolchain), and its lock file change is committed with it. A package the app's source imports is a dependency; one only tests and config use is a dev dependency, and the layering check holds that.

## Develop, build and check

| Command | Does |
|---|---|
| `npm run dev` | Vite's server, with fast refresh. Open <http://localhost:5173/main.html>. |
| `npm run build` | Writes `lib/design/main.html` (and Vite's scratch copy in `dist/`). Nothing else under `lib/design/` changes. Two builds of the same tree are byte-identical. |

| `npm run test` | Every `*.test.ts(x)` in the prototype outside `tests/architecture/` and `tests/bundle/` (Vitest's `unit` project): the modules' own tests, and a script's tests beside it. One module's alone: `npx vitest run tests/presentation/<module>`. |
| `npm run layering` | The layering check and the token scan (the `layering` project, every test under `tests/architecture/`). |
| `npm run stale` | The built file's checks (the `bundle` project): staleness, one file, determinism, a recording inlined, and the tokens and fonts. |
| `npm run e2e` | The Playwright tests: the built file opened from disk. |
| `npm run check` | **The local gate:** typecheck, test, layering, stale and e2e, in that order. It never rebuilds. |
| `npm run baseline` | Re-makes the old prototype's images from `parity/baseline.json` (about 70 seconds). `npm run baseline -- --record --reason "<why>"` records a new revision. Not part of `check`: it needs the network for Google Fonts. |
| `npm run capture -- <recipe>` | Records a recipe's stream from the CLI's branch build (1u, [below](#the-capture-script)); `--binary <apogee>` names another build. Not part of `check`: it runs the binary. |

**Before a commit, run `npm run check`.** A change to anything the build reads leaves `main.html` stale, and the check fails saying so: run `npm run build` and commit the new `main.html` with its sources. CI never runs any of this ([ADR 0001 §6](../../adrs/design/react-design-prototype.md#6-the-gates-are-local)); `lib/scripts/cicd.sh`, `changed.sh` and the workflows do not name the prototype.

## The module map and the layering check

`modules.json` is `{ "modules": { "<layer>/<module>": ["<layer>/<module>", …] } }`: each key is a module's folder under `source/`, and its list is every module it may import. Its first edges copy the Mac app's Presentation edges: `styles` depends on nothing; `shell`, `session` and `compose` on `styles`; `sessions` on `session`, `shell` and `styles`; the other 13 places on `shell` and `styles`; `app` on all 18 others. The lower modules' edges (1d): `process` depends on `clock` (a preset's clock settings); `protocol` on nothing; `reads` on `process` and `protocol`; `jobs` and `session` on `clock`, `process` and `protocol`; and `app` on `process` too, for the mode rules' type. 1e's: the shell on `clock` (the toast's ticks) and `process` (the `apogee` mode's type); the monitor on `clock`, `process` and `reads`; `app` on `clock` and `reads` too. 1u's, as the Mac's `PresentationSession` imports them: `session` on `clock`, `process`, `protocol`, `reads` and `session` (Business) besides `styles`; `app` on Business's `session` too. 1v's: `session` and `app` on `jobs`, for the compact jobs on `JobStarting`. 1g's, as the Mac's `PresentationSessions` and `PresentationConsole` import their Business twins (and their previews build the stand-in): `sessions` on `clock`, `process`, `protocol`, `jobs`, `reads` and `session` (Business) besides `session` (Presentation), `shell` and `styles`; `console` on `clock`, `process`, `jobs` and `reads` besides `shell` and `styles`. 1h's, as the Mac's `PresentationModels`: `models` on `clock`, `process`, `protocol`, `jobs` and `reads` besides `shell` and `styles`. 1i's, as the Mac's `PresentationSettings` imports its Business twins and its previews build the stand-in: `settings` on `clock`, `process`, `jobs` and `reads` besides `shell` and `styles`; never `models`, whose roles it draws through the app root's slot. 1j's, as the Mac's `PresentationTraining` imports its Business twins and its previews build the stand-in: `training` on `clock`, `process`, `protocol`, `jobs` and `reads` besides `shell` and `styles`. 1k's: `business/media` on `process` (its folder reader's type) and `protocol`; `video` on `clock`, `process`, `protocol`, `jobs`, `media` and `reads` besides `shell` and `styles` -- never `compose` or `voice`; `app` on `media` too (Settings' Install… reads the install its row's remedy names). 1l's, as the Mac's `PresentationCompose` imports its Business twins: `compose` on `clock`, `process`, `protocol`, `jobs`, `media` and `reads` besides `styles` -- its one Presentation edge, so it never imports `video` (the app root's slot joins them) nor `settings` (the chosen voice is `styles`' `MediaPreferences`). 1m's, as the Mac's `PresentationVoice` imports its Business twins and its previews build the stand-in: `voice` on `clock`, `process`, `jobs`, `media` and `reads` besides `shell` and `styles` -- never `settings` or `compose`, the chosen voice being `styles`' `MediaPreferences`.

The check reads the map, `package.json` and every file in the prototype, and reads imports with TypeScript's own parser (`import`, `export … from`, `import()`, `require`, `import x = require` and `import('…')` types, plus each `import.meta.glob` pattern and each `new URL('…', import.meta.url)`, Vite's other ways of pulling a file into the build; a computed `import(`…${x}…`)` is read as its fixed head and `*`, the glob Vite makes of it), and each `.css` file's `@import`, `url()` and `image-set()` (1e: each `image-set()` candidate's path as Vite reads and inlines it, a string or a bare path; its comments, `data:` URIs, gradients and `#fragment`s left out; a path is relative only when it starts with `./`, `../` or `/`, and anything else names a package, as in an import). Each rule fails with one sentence naming the file or module:

1. **An empty map** is refused, and so is one with no entry at `source/<layer>/<module>/`.
2. **Folders.** Each map entry is one folder; every folder under `source/<layer>/` is an entry; `source/` holds only the four layers and the entry point; a layer's folder holds only its card and its modules' folders.
3. **Placement.** A module sits at `source/<layer>/<module>/`.
4. **Nothing from outside.** A package is one `package.json` lists. `source/` imports only dependencies: no dev dependency, no Node built-in. Tests, scripts (`scripts/`, 1c) and config may use both. No relative import, glob or `new URL` leaves `lib/design/prototype/`. **The fixture roots** (1d) are the one way past it: `@recorded/…` (Vite's alias for `lib/src/darwin/tests`) and `fixtures/` are reached only from a Presentation module's `Previews/` and from the tests (a file under `tests/` or `e2e/`, or a `*.test.*` or `*.spec.*` file outside `source/`, where a test-named file is source like any other), never from Infrastructure, Data or Business, which are handed their rules. Each recording is named in full, in a `Fixtures/` folder of `@recorded` or under `fixtures/`, and imported with `?raw`. A glob over either root fails, and so does a computed `import(`…${x}…`)`, which the check reads as the glob Vite makes of it. **The tokens root** (1e) is the one way to `tokens.json`: `@tokens` (the typed module), `@tokens/themes.css` (its CSS) and `@tokens/tokens.json` (the file, for the declaration's types) and nothing else under it, reached only from `presentation/styles` and the tests. **A `.css` file** is held to this rule as code is, and a remote `url()`, `@import` or `image-set()` candidate (`https://…`, `//…`) fails: the built file loads nothing from the network.
5. **Edges.** A dependency on a higher layer is an `upward edge`. A map entry naming no module fails, and so does a file importing a path in no module (`source/main.tsx`, `tests/`, a file loose in a layer). A file importing a module its own module does not declare fails. `styles` leans on no sibling, and the shell depends on no place, even when declared.
6. **React** (`react`, `react-dom`, `react-*`, `@react-*`, and any `.tsx` file) stays in Presentation, and out of every `ViewModels/` file.
7. **MVVM shape.** Every Presentation module but `styles` has `Views/` and `ViewModels/` with a file in each, and no file at its root.
8. **The entry point** is one file, `source/main.tsx`, importing only `presentation/app`.
9. **Mirror tests.** Every module has a test in `tests/<layer>/<module>/`.
10. **Schemes** do not apply: there is no Xcode. Vitest runs one module's tests by path.
11. **Previews.** Every component a Presentation module's `Views/` or `Components/` exports (a capitalized function, class, or constant holding a function or a `memo`/`forwardRef` call; a renamed default, `export { View as default }`, by its own name) is drawn, as `<Name`, by some file in its `Previews/`.
12. **Layer cards.** Each layer's `source/<layer>/CLAUDE.md` has a **Modules:** line whose backticked words are exactly its modules. A layer with none says so in words, with no backticks on that line.

`layering.test.ts` runs the check on the real tree, plants a dependency in the real map, and plants one violation per rule in a clean miniature, expecting its exact sentence.

**Adding a module:** its folder under `source/<layer>/`, its entry in `modules.json` with what it may depend on (and `app`'s entry gaining it, for a Presentation module), a test in `tests/<layer>/<module>/`, its name in backticks on its layer card's **Modules** line, and, in Presentation, `Views/` and `ViewModels/` with a preview in `Previews/` for every view it exports.

**A preview** is a named export in `Previews/<View>.preview.tsx` that draws one view over a view-model built on fakes, one export per state a person sees differently, as the Mac app's `#Preview`s are ([darwin ADR 0004](../../adrs/darwin/module-schemes-and-previews.md)).

**A preset** (`Preset`, in `infrastructure/process`, so a place's `Previews/` can name one) is:
- `rules`: four tables, `reads`, `commands`, `jobs` and `chats`, as `PreviewRunner` keeps reads and commands apart. A rule is an argument prefix (the arguments after `apogee` as the caller gives them, a read's without its `--output-format`) and its `answer`: `stdout`, `stderr`, `exit` (0 unless named; a recorded `.exit` read by `recordedExit`) or `timedOut`, and the replay rules (1v, [below](#how-a-job-and-a-chat-replay)): `exitAfter`, `freeze`, `continuations` and `cancelled`. A list of answers comes one a call, the last repeating: an install that fails, then succeeds; a chat's second launch, its restart. A rule may wait on another call (`until`, 1k, below);
- `route`: a plain string, the old prototype's `start`, which the page names in its query or hash (1e, [below](#styles-the-shell-and-the-first-screen));
- `clock`: its start ticks, `still`, its "now" and its pace;
- `apogee`: `installed`, `missing` or `config-typo`;
- `folders` (1k): the folders the CLI wrote into, each folder's files by name, a record's text beside its clip's (`StandInFolders`). No CLI verb lists the clips it made -- `video generate` writes each clip's `video.generation` record beside it as `<clip>.json`, and the Mac app's `MediaLibrary` scans those files -- so a preset hands them in as it hands the child its rules. The folders are the person's files: they read the same in every mode. Every preset carries `~/Movies/Apogee`'s five records unless it names its own ([below](#the-video-place-and-the-runtime-consent)), and `~/Music/Apogee`'s two recorded speeches (1m, [below](#the-voice-place)).

**How a call is answered.** The longest prefix wins; of two as long, the later rule (`PreviewStore`'s rule). A rule marked `exact` (1h) answers its arguments whole and no longer line, so a recording of `models quantize <h>` never answers `models quantize <h> -t Q8_0`. A rule with `until: { ran, answer }` (1k) waits on another call of its kind: until a call of `ran` has been answered with a success (exit 0, in time), every call is answered by `answer` -- the CLI's refusal, nothing counted -- and the rule's own answers play only after it, from its first; a job stopped by its Stop before its end tells the child (`stopped`), so it is no success and the rule waits again. So rain's generate is refused for peft until `train setup --with video` has gone in, however often Generate is pressed and whoever ran the install. A read nobody answered is `.couldNotStart`, naming its arguments ("no recorded answer for apogee system"), and so is a command, a job or a chat. Each one is logged in the child's `unanswered`, which a per-preset test holds empty; every call that ran is in `calls`, with its input.
- `missing`: no binary is found (`locateBinary()` is `notFound`), and nothing runs: every call is "apogee is not installed".
- `config-typo`: the binary is found, and every call exits 1 with the recorded refusal (`agents-list-bad-config.err`), its verb swapped for the call's first word, as the old prototype's `cfgRefusal` does. A read's failure then reads word for word as the old prototype's line. The refusal comes from the shared mode rules, `presentation/app/Previews/ModeRules.ts`.

**How a job and a chat replay.** A job's stdout plays one line a tick: an event of the 52b stream when it was started `streaming`, a said line otherwise. `.ended` follows on the next tick, with the rule's exit and stderr. `stop()` ends it at once, interrupted, exit 130. A chat's recording is cut where the binary waited for input: the opening (the `session` line and the lines with no turn before the first turn's), then one turn per `send`, a line with no turn going with the turn before it. A turn waits at each `question` until `answer` has answered its every item, and an answer written ahead is read when its question asks. Every line written is kept in `written`; the replay goes on as recorded (a set or an attach changes nothing a recording did not record, and a cancel only what its `cancelled` rule, below, says -- or, where the recording itself ends the turn there, its recorded result plays, as `question-cancelled.jsonl` and `permission-cancelled.jsonl` recorded it). `close()` ends it finished; `stop()` writes a cancel only while a turn is in flight, counted from the protocol's events as the Mac app's `TurnTracker` counts it (sent, until its `result` or `error`), then closes; `terminateNow()` ends it stopped; a rule with a non-zero exit (a refused launch, or a child dying mid-answer) ends failed once its lines are out; a `session` line of another protocol version is refused.

**The replay rules** (1v), each a field of a rule's answer, each tested against a recording in `MachineSession.test.ts` and `SupervisedJob.test.ts`:
- **`freeze`, a named event:** `{ name, event, nth }`, the `nth` line of type `event` counted from the recording's start. A still frame stands right after it, however few its start ticks, and after any `advance`; a live clock plays straight to it on its first tick, then on at its pace. `chat`, `monitor` and `chat:compacting` stand mid-reasoning this way (`streamingFrames`).
- **`exitAfter`, ticks:** a chat's child exits that many ticks after its input closes -- taking no line meanwhile (a write throws `SessionError`: Not sent), while what it had already written drains, one line a tick -- so a still frame can stand between a stop and the next child (Restarting). A job's `.ended` comes that many ticks after its next tick, so a still frame can stand mid-job (`chat:compacting`). 0, at once and the next tick as before, unless named. **`holdAt`** (1k) moves a job's wait to after that many of its stdout lines, the rest played after it and its end the tick after them -- never past the hold in one tick, whatever the pace -- so a run rests on a line mid-way: the install that goes in rests on its `installing …` line while pip runs, its `installed` and where it went said only at its end, as the old card does. All its lines unless named.
- **A restart is the rule's next answer:** a second launch (`--resume`, and `--suite` after a move) replays the list's next recording.
- **`continuations`, a choice point:** `{ after, nth?, by }`. Once the `nth` (first) line of type `after` has played, the first answer, turn or setting written picks the branch `by` names it -- an answer by its text (`yes`, `Per host`, `''` for Skip), a turn as `user` (a retry), a setting by what it sets (`set model=claude`, `set temperature=0.4`: each field `key=value` in the line's order, a text unquoted). Each branch is a whole recording sharing the main one's lines up to there (its own capture from the same opening turn, or hand-made), played from the line the replay has reached: what the turns sent so far released of it, past the lines played, is queued, and its later turns wait for their sends. A choice no branch names is noted in `unanswered` (`chats: answer maybe after the question of apogee chat …`, `chats: set temperature=0.4 after the error of …`) and the replay goes on as recorded.
- **`cancelled`, Stop:** a recording of the same session whose turn a `cancel` ended (a capture with the recipe's `cancel`). A cancel written while a turn is open drops that turn's unplayed lines and plays this recording's ending of the same turn in their place -- its `result` with `finish_reason: "cancelled"`, and the calls reported `failed` just before it -- so Stop works at any line, mid-reasoning or while a card stands. Where the recording itself ends the turn right there (its `result` next, past only `tool_call` lines), that end plays instead. A cancel nothing recorded is noted (`chats: cancel during turn 1 of …`); one with no turn open is ignored, as the binary ignores it. A cancel that ends a turn at a choice point spends it.
- **`busy`, a job's stderr as it runs** (1j): the answer's stderr plays a line a tick as the job's busy line (`JobUpdate.busy`), before its stdout's lines, then its end, the whole stderr its tail -- as the Mac samples stderr's last line while a run goes: `train run`, which takes no machine stream, says its progress there (`train-run.err`), and a promote narrates there before its result. Unless named, stderr is only the tail at the end (1d's). Tested in `SupervisedJob.test.ts`.
- **`writes`, files a job writes as it plays** (1l): `{ after, folder, file, stopped? }`, each written into the child's folders (`StandInChild.folders`, made from the preset's) once `after` of the job's stdout lines have played -- the project the composer saves beside its video after every step, which the screen reads there, as the Mac does; a write `after: 0` lands as the job starts (a new render's first project, nothing made, so it is beside its video from Render on), except on a resume, whose own write comes after its first line. A Stop writes the last write's `stopped` file (the project saved `cancelled`, its finished scenes kept), and the child remembers that write (`stopped(kind, args, lastWrite)`): the same command next plays its first line, then on from that write, its file written again first -- so a resume renders only what the project lacks, wherever it stopped. Tested in `SupervisedJob.test.ts`.

**When the clock starts.** On a live clock, the start ticks reach only the jobs and chats open at `start()`: one opened later starts at its first line. A still frame catches a later one up, so a job a view-model opens after an awaited read is the frame's ticks in all the same. A chat opens with no turn sent, so its catch-up plays only its opening; a `send()` written after `start()` plays only on later ticks, which a still frame never has, so a still chat preset writes its sends before `start()`. `AppViewModel.start()` awaits a chat preset's setup -- the binary located, the chat opened, its sends written -- before it starts the clock (1u). A send to a child that refused its launch (a non-zero exit, as `launch-refused-*.err` records it, and the `config-typo` mode) is never logged as a turn past its recording: that child exits without reading its input (1u).

**Building one, in a test** (a place's `Previews/` builds it the same way, but may not import `app`, so it imports `agents-list-bad-config.err` itself for the mode rules):

```ts
import agentsList from '@recorded/business/reads/Fixtures/agents-list.json?raw'
import { modeRules } from '../../../source/presentation/app/Previews/ModeRules'
const preset: Preset = { rules: { reads: [{ arguments: ['agents', 'list'], answer: { stdout: agentsList } }] }, route: 'library', clock: { still: true }, apogee: 'installed' }
const child = new StandInChild(preset, modeRules)
const clock = new Clock(preset.clock)
const reads = new ReadRunner(child) // and new JobStarter(child, clock), new ApogeeClient(child, clock)
clock.start() // a still chat preset's sends are written before this line
```

A view-model takes the interfaces (`CommandRunning`, `JobStarting`, `ChatStarting`) and never the stand-in.

### Where a recording lives

- **The Mac app's recordings are read in place:** every file in the 8 `Fixtures/` folders under `lib/src/darwin/tests/` (613 files on 2026-11-18). A preset imports each by its full name through the `@recorded` alias, with `?raw` so its text stays byte for byte: `@recorded/business/reads/Fixtures/agents-list.json?raw`. Never a glob: the build bundles only what a preset names. A recording re-recorded there reaches the next build, and the staleness check says when.
- **Only a Presentation module's `Previews/` and the tests import a recording** (rule 4). The stand-in is handed its rules, as `PreviewRunner` is.
- **A state nobody recorded** gets a hand-made file in the CLI's exact shape, named `*-handmade*`, in the design's own `fixtures/`, laid out as the Mac app's tree (`fixtures/business/reads/…`). A new recording goes there too, captured with the repository's capture scripts in a throwaway `APOGEE_HOME`. The Mac app's folders gain only what its own tests read.
- **A document that exists only as a Swift literal** is extracted to a fixture file by the change that first needs it: into the test's own module `Fixtures/` folder beside its siblings, the Swift test reading the file and behaving the same, the preview's copy kept with a comment naming the file, and named `*-handmade*` when the literal was written by hand. It must have the CLI's exact shape: a literal that lacks fields the CLI always prints is not extracted where a recording answers (1d left Monitor's `system` literal alone, since `business/reads/Fixtures/suites-system.json` records it whole).
- **The decode check** reads every recording from both roots at test time, with Node: each `.json` decodes to one document, and each line of each `.jsonl` to an event, an unknown one kept (`tests/data/protocol/decode.test.ts`).

## Styles, the shell and the first screen

The Presentation layer's foundation and the first screen ported end to end (1e): the tokens, the appearance, the shell and its hosts, the composition root, and the system monitor.

**The tokens.** `lib/design/spec/json/tokens.json` is the one place a color, type size, font, radius, layout size, motion or fixed value is written; 1t moves it beside the built file, changing the two lines that say where it is: `tooling/tokens.ts`'s `tokensRoot` and `tsconfig.json`'s `paths` entry for `@tokens/tokens.json` (everything else, the Playwright tests too, reads it through `tokensFile`). The build reads it through the named root `@tokens` (`tooling/tokens.ts`, a Vite plugin the build and Vitest both use) and generates two modules, never written to disk:
- `@tokens`, the typed tokens module: tokens.json as one value. `tsc --noEmit` runs before any build, so its types are declared in the committed `source/presentation/styles/Tokens/TokensModule.d.ts`, which takes them from tokens.json itself through `tsconfig.json`'s `paths` (`@tokens/tokens.json`): a color name, theme, type step, text size or font that tokens.json lacks does not compile.
- `@tokens/themes.css`, the custom properties: a shared block on `:root` (`--layout-*`, `--radius-*`, `--control-*`, `--t-*` at the medium size, the default `--font-ui` and `--font-mono`, `--scrim-modal`, `--shadow-menu`, `--shadow-dialog`, `--shadow-toast`, `--window-close`, `--window-minimize`, `--window-zoom`, `--caption-fill-opacity`, and the motion: `--motion-chevron`, `--motion-caret` and `--motion-pulse`), then one block per theme, `[data-theme="dark"]`, `"light"` and `"contrast"`, each with its 25 colors in tokens.json's letter case and its `color-scheme`.

Only `presentation/styles` imports `@tokens` (rule 4); `styles/Tokens/Tokens.ts` re-exports it with each kind's names in tokens.json's order (`themeIds`, `colorNames`, `typeSteps`, `textSizes`, `uiFonts`, `codeFonts`, `layout`). The build leaves CSS unminified, so the built file carries the generated blocks as written, and **the token check** (`tokenCheck`, in `tooling/tokens.ts`) holds both the generated CSS and the built file's to tokens.json, value for value (`tests/presentation/styles/Tokens.test.ts`, `tests/bundle/tokens.test.ts`). tokens.json's `motion` entries are partly words (`"1.4s ease-in-out, opacity 1 to 0.3"`), so each `--motion-*` variable is its entry's leading duration and timing function (`150ms ease`, `1.1s steps(1)`, `1.4s ease-in-out`; `motionValue`), and an entry with no CSS at its head fails the build rather than reach a stylesheet. The words' rest (the blink, the fade to 0.3, reduced motion stopping both) is the helmet's keyframes and media query.

**The appearance** (`styles/Appearance/Appearance.ts`): the old prototype's appearance state as one value, `Appearance` (`themeChoice` or `auto` with its `autoLight` and `autoDark` picks, each theme's `overrides`, `uiFont`, `codeFont`, `textSize`), and its theme machinery as pure functions over it: `themes()`, `colorGroups()`, `lum()`, `ratio()`, `contrastOf()` (a row's contrast by its rule), `contrastBadge()` (1i: under 3:1 `too low`, under 4.5:1 `low`, a border none; shared with 1q's color page), `effectiveTheme()` (automatic draws its light-uses pick on a light system and its dark-uses pick on a dark one, 1i; unsaid, dark, as the old `effTheme()` does), `colorsOf()`, `withOverride()`, `typeSizes()`, and `rootVars()`, the window's inline variables, word for word the old one's but for the hex's letter case (`rootStyle()` is the same as a React style object). `ThemeService` holds the value for the window, and the viewer's light or dark setting (`system`, which the shell's view reads from `prefers-color-scheme`, 1i) unless it is pinned (`pin`): the composition pins it to dark on every preset, as the old prototype draws Automatic, so frames match the baseline. The shell's view puts `data-theme` and the service's `style` (`rootStyle()` at that setting) on the window, so a change restyles everything at once. Settings › Appearance (1i, `ThemeSettings`) changes it through the service and keeps nothing of its own but the hex fields' drafts. The parity tests read the old prototype at its frozen revision from git (`tests/presentation/styles/Frozen.ts`, never the working tree): `rootVars()` for 3 themes × 4 sizes × 3 interface fonts × 3 code fonts, `ratio()` for all 25 rows in each theme, `withOverride()`, and tokens.json's 75 colors against the frozen `themes()` and `colorGroups()`.

**Observation** (`styles/Observation/`): Swift's Observation, which TypeScript lacks. A view-model extends `Observable` and calls `changed()`; a view calls `useObserved(model)`, React's `useSyncExternalStore` over it.

**The stylesheets** (`styles/Stylesheet.ts`, imported by `app`'s view alone): `Fonts.css`, the ten faces the old Google Fonts link loads (IBM Plex Sans 400, 500 and 600, IBM Plex Mono 400, 500 and 600, Atkinson Hyperlegible 400 and 700, JetBrains Mono 400 and 500), latin, woff2, from the `@fontsource/*` packages, inlined by the build; the generated `@tokens/themes.css`; and `Helmet.css`, the old helmet's shared classes under `.ap`. A media query cannot read a custom property, so the helmet's two width breakpoints are `.ap[data-collapsed]` (900 px or less: the sidebar a 56 px column of icons) and `.ap[data-narrow]` (600 px or less), set by the shell's view-model from tokens.json's `collapseBelow` and `narrowBelow`, at or below each, as `max-width` is.

**The token scan** (`tests/architecture/tokens/`, run by `npm run layering`) holds the design's rule "every color is a token" and its siblings over every `.ts`, `.tsx` and `.css` file in `source/`: no hex, `rgb()`, `hsl()` or other color function but tokens.json's fixed values (the scrim, the shadows, the window controls, in either spelling); every `font-size` a `var(--t-…)` (or a relative `em` or `%`); every `font-family` `var(--font-ui)` or `var(--font-mono)` (or `inherit`); every `@font-face` family one that tokens.json's font stacks name; and no time (`.15s`, `150ms`) in a `transition` or `animation` property, in CSS or a style object: motion is a `var(--motion-…)`. It reads strings, templates and JSX text in TypeScript, and declarations in CSS, never a comment. One-off geometry, such as a padding, a gap or a grid column, is written as the old prototype writes it; the sizes tokens.json names (the sidebar, the header, the monitor's width, the radii, the control heights) come from it.

**The shell** (`presentation/shell`), the Mac app's names:
- `ViewModels/Destination.ts`: the 11 places in `Destination.swift`'s order and names, and each unported place's placeholder, the design item that ports it (each feature item takes its own line out); `Overlay` is `monitor` or `console`, one at a time.
- `ViewModels/KeyMap.ts`: the shell's keys (⌘1–⌘9, ⌘0, ⇧⌘R, ⇧⌘L, ⌥⌘M, ⇧⌘K, ⌃⌘S, ⌘,) and the design's 23-line keyboard list, as data; `BoundKey` (a chord and its words, a place's binding among them: Sessions' five carry theirs, 1i), `chordsNamed` (the chords a line names, `⌘1 – ⌘9, ⌘0` each of its ten) and `keyboardLines` (the list Settings › Keyboard draws: the design's lines, then a line for each bound key none names, 1i). ## The built file

- **One file.** `vite-plugin-singlefile` inlines the code and styles, and the ten web fonts as `data:` URIs (1e; 193,972 bytes of woff2, about 259 KB as base64), and `tooling/oneFile.ts` fails the build if Vite emits anything but `main.html`. The `bundle` project's one-file test holds the committed file to no `<script src>`, no `<link href>` but a `data:` one, and no chunk `import()`; the smoke test holds it to loading nothing but itself.
- **Staleness by hash.** The build takes a SHA-256 over every input, sorted by path: `main.html`, `package.json`, `package-lock.json`, `tsconfig.json`, `vite.config.ts`, and every file under `source/`, `tooling/` and `fixtures/`, plus each recording a file under `source/` names as `@recorded/…` (hashed as `@recorded/<path>`, 1d), and `tokens.json` (hashed as `@tokens/tokens.json`, 1e), so a token edit stales the build. Dot files are left out. The Swift tests beside the recordings, and a recording only a test reads, are not inputs, so another session's Swift edit never stales the build. It writes the hash into the page's `<meta name="apogee-design-sources">`. The staleness test recomputes it and, on a mismatch, fails naming `lib/design/main.html` and `npm run build`.
- **Determinism.** The determinism test runs two production builds into a scratch folder (`APOGEE_DESIGN_OUT`, never over the committed file) and compares them byte for byte.

## The old prototype's baseline

The old prototype (`lib/design/spec/`) is frozen at one recorded revision, and its look at that revision is the reference 1s checks the port against. The images are never committed. `scripts/baseline.ts` re-makes them from git history, so they outlive 1t's deletion of the old files.

- **`npm run baseline -- --record --reason "<why>"`** refuses while `git status` shows anything under `lib/design/spec`, naming the files. Otherwise it takes the newest commit touching `lib/design/spec`, runs [the 30-tick check](../../../design/spec/CLAUDE.md#checking-a-change) there in all three `apogee` modes, shoots it, and writes `parity/baseline.json`, adding the reason to its history. Record only at a committed fix to the frozen prototype.
- **`npm run baseline`** (capture) reads `baseline.json` and re-makes its images. It refuses a revision this repository does not hold, a tree hash or preset list that is not the revision's, a different Playwright version, and any image that draws `support.js`'s error box. It fails when the modes kept are not the recorded ones, or when an image differs from the last run's hash list.
- **What it shoots.** Git is only read. `git archive` copies the revision's `lib/design/spec` into a temp folder: no checkout, no worktree, no optional lock on the shared index. That `html/` folder is served by `python3 -m http.server`, as [`spec/README.md`](../../../design/spec/README.md#opening-it) opens it. Then:
  - every start preset in the revision's `data-props`: `main.html?start=<preset>&still=true&apogee=installed`, at 1440 × 900;
  - the same preset at `missing` and `config-typo`, kept only where the image's hash differs from `installed`;
  - the 15 other boards, full page at their `canvas.json` size, once per value of their prop menus. `App.dc.html` is the canvas's alias for `main.html`, so its frames are the presets.

  At `b375fac9` that is 78 presets, 19 more images in another mode (12 presets), and 32 board images: 129 in all.
- **Two runs draw the same pixels.** Each of these was needed, measured 2026-11-18:
  - the clock is fixed at `2026-11-14T09:41:00Z`, in UTC and `en-US`, and `Math.random` is seeded;
  - each image is shot in a page of its own, on its second load, once its fonts are in the context's cache. A first, cold load draws differently (`chat` kept two extra modes that way);
  - Chromium rasterizes on one thread (`--num-raster-threads=1`). With several, tiles race to cache a glyph, and Inspector's Geist Mono came out differently in about one launch in four;
  - each Google Fonts stylesheet is held to the one recorded. The same URL is sometimes answered with dynamically subset faces (`fonts.gstatic.com/l/font?kit=…`) instead of the static versioned files (`/s/<family>/v<N>/…`), which draw differently (one fetch in eight). A capture that gets a subset tries again in a fresh context, up to 10 times. `baseline.json`'s `fonts` holds each static stylesheet's SHA-256, and a capture refuses one that changed.
- **It needs the network for Google Fonts** (every old board links `fonts.googleapis.com`). If a font does not load, the run is refused, never recorded in fallback fonts.
- **The output**, in `.parity/baseline/<revision>/`: `screens/<preset>@<mode>.png` (`:` written `_`), `boards/<Board>@<prop>=<value>.png`, `hashes.txt` (`shasum -a 256 -c hashes.txt` checks it there), and `index.html`, a contact sheet of every image. A run compares itself with the last run's `hashes.txt`, and removes any `.png` it no longer writes.
- **`parity/baseline.json`** holds the full revision hash, the commit's date, the tree hash of `lib/design/spec` at it, the preset list, the modes kept per preset, the 30-tick result per mode, the Playwright version, the viewport, the fixed clock, time zone, locale and seed, the pinned stylesheets, and the history of records with their reasons. A test beside the script holds its preset list to the revision's `data-props` and its tree to the revision's.
