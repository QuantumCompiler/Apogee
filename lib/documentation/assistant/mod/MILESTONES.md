### 2026-11-21 — `mod-tools-and-commands` (backlog item 1b): Apogee's tools, the `/apogee` set and the status line

**Why.** Measured 2026-11-21 at `20a234d3`: the scaffold found the binary and said nothing else. Claude had no Apogee tool, the person no command, and nothing showed the backend, its version or a run. This item gives the mod its working surfaces over the contracts the spike measured and the CLI's 54a and 54b shipped: Apogee's served tools and a local completion for Claude, the `/apogee` set, and a status line, with anything long under the async law.

- [x] **Apogee's served tools, registered into the session** (`src/business/served/`, `src/business/surfaces/`, `src/presentation/tools/tools.ts`). At the session's start the found binary's `apogee mcp serve` is listed once (10 s): the handshake (`initialize`, `notifications/initialized`) and `tools/list` written to its stdin, the reply read back from its stdout. Every tool it lists but `complete` is registered with `$.tool.register` under its own name, description and schema: 22 on apogee 0.2.0, the 17 native reads and the five status reads, as `mcp__apogee__<name>` behind ToolSearch. A call is one run of `<binary> mcp serve` with the handshake and that `tools/call` on its stdin, a read tool's within 120 s (the CLI's own client's bound, `mcp_serve_client.py`). The answer is the server's text, a status read's document byte for byte; an error result is the call's error in the server's words; a server that cannot run or answers no reply is said with why, its exit status and last stderr line. Each tool is registered on its own, so one the engine refuses never drops those after it. What the engine took is kept in `$.state` once registering is done (`apogee.tools`, shape `tools-2`): the names registered, and each refusal in the engine's words, which `/apogee` says. The root's `tool.run` hook answers those names alone, passing any other `mcp__apogee__` name on.
- [x] **`apogee_complete`** (`src/business/complete/`, `src/presentation/tools/complete.ts`), offered only for a local, unmetered backend and saying so. Where the listing names the served `complete` (the person's config lists it under a backend's `mcp_serve:`, 54b), that tool is its plumbing: its backends are the schema's `enum`, each at the bound the server's description says for it (`<name> (at most N tokens)`), since the schema's `maximum` is only the widest. A backend the description does not bound is offered at the widest, its own bound said as unsaid. A bound the model leaves out is never sent, so the server holds each backend to its own, and `models list` is not read. Otherwise the CLI path: the configured `llamacpp` and `mlx` backends `models list` shows that chat (a row with no kind, or an MLX one of kind `chat` or `vision`). It is offered only where `models status` names no active suite and a utility model that is unset or local and unmetered, since the one-shot calls those models and the served `complete` never does. Each backend is held to its own bound, 1024 or its entry's `max_tokens` when lower (`config get backends.<name>.max_tokens`, one read a backend; a read that fails keeps 1024), and run as `<binary> complete -m <backend> -n <bound> --rag "" -- <prompt>`. A call runs within ten minutes on either path. The served `complete` is never registered under its own name. The description says what one call is, each backend and its bound, that a call spends this machine's time and never money, that `max_tokens` asks for fewer and never more, what a slow answer does, and why it is offered. A request is checked before anything runs: a prompt, a backend offered, a bound in range. With no such backend it is not registered, and `/apogee` says why.
- [x] **The async law** (`src/business/jobs/`). A completion gets a 30-second window on `$.clock`. If it ends inside it, it answers there.
