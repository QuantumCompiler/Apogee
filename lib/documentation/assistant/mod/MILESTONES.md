- [x] **The four layers**, one package each, every package with its tests under `tests/<layer>/<package>/`:
  - `src/infrastructure/discovery/` (155 lines): the macOS app's ladder mirrored. It tries the `binary` override first, then the channel's places in `~/.local/bin`. The release channel tries `apogee`, `apogee-dev` and `apogee-test`. The dev channel tries `apogee-dev` alone, never the release binary (GUI M18's rule). A place that does not exist is `not installed` and is never run. One that cannot be looked at is passed over with `could not be looked at: …` and the ladder goes on: `$.fs.exists` rejects for a network location, and an `fs.*` hook may refuse it. Each candidate that exists is run as `<candidate> version`, bounded by 10 s, the app's timeout. Its first line must read `apogee <version> …`, and a `channel:` line is taken when present. A failed run is passed over with what it said: `could not run`, the exit status with the last stderr line, or the line printed. With HOME unset or empty, each channel place is passed over with `HOME is not set`, and the override is still tried. The home folder comes from `$.env.get('HOME')`, files from `$.fs.exists` and runs from `$.process.run`, since a hooks module has no Node.
  - `src/data/state/` (30 lines): the one `$.state` atom, `apogee.binary`, shape `binary-1`, through `update` from the atom library: `recordBinary` keeps what discovery found, and `markAbsenceSaid` marks the absence said, answering true exactly once.
  - `src/business/binary/` (20 lines): `findBinary`, which runs discovery, keeps its answer, and decides whether the absence is said now: once a session, then quiet, even when a replaced hooks copy starts the session again.
  - `src/presentation/notices/` (29 lines): `findAndSayAbsence`, the scaffold's one visible behavior. When none answers, it raises one toast for 10 s: `Apogee is not installed where the mod looks: ~/.local/bin/apogee (not installed), … Install Apogee with: curl -fsSL https://raw.githubusercontent.com/QuantumCompiler/Apogee/stable/lib/scripts/install.sh | bash`. - [x] **The layering check**, `tests/architecture/layering/` (`check.mjs` 354 lines, `layering.test.mjs` 289, `tree.mjs` 42, `main.mjs` 12): ADR 0001's teeth, over the TypeScript compiler API with its type checker. It refuses an empty graph. It holds every file of `src/` at `src/<layer>/<package>/`, requires every layer to have a package and every package to have its mirroring tests, and fails an upward or undeclared edge by name. Every file of the plugin has a place it holds: `hooks/` holds `hooks/register.tsx` alone and `types/` holds declarations (`.d.ts`) alone, so code anywhere else fails by name. A layer's file that is not TypeScript fails too, since the engine loads `.js`, `.jsx`, `.mjs` and `.cjs` and the check cannot read them. The contract's declarations are read like the rest: they import nothing of the mod but each other, so no edge is laundered through them, and they reach no noun. Imports, re-exports and type-level imports all count, and so does an import of the composition root. Nothing but `'claude-code'` comes from outside the mod: `'claude-code/testing'` and the tests stay out of the plugin, and `import()` is refused because the engine will not load it. The engine's nouns are held to their layers: `process`, `fs` and `env` to Infrastructure; `state`, `store` and the atom library to Data; `ui`, `command` and `tool` to Presentation. The atom library counts however it is taken outside Data: imported or re-exported by name, or `'claude-code'` taken whole (`import * as`, `export *`, `export * as`); a type-only take passes. `http` belongs to no layer, and the root reaches no noun. A noun is caught however the engine is named, destructured or indexed. On the tree: `layering: 6 files and 18 imports hold ADR 0001` (the four layers' files, the root and the contract).

The run's own decisions (2026-11-21), each flagged for your veto:
- **The engine floor is Claude Code 2.1.326.** Validate follows `$` past an import only into a function declaration, so every function that takes `$` across files is one, and that holds on 2.1.326. The installed 2.1.289 refuses `$` across any import and does not load the module: its error reads `$ is followed only into a function declared in this same file, never across an import`. It also does not know `engines`. The only shape 2.1.289 loads spells every `$` call in `hooks/register.tsx`, which would leave the layers empty and the composition root holding everything. So the plugin states `engines: { "claude-code": ">=2.1.326" }`, the build the types came from and the desktop app's engine.
- **The API declarations are vendored unmodified** at `vendor/claude-code/index.d.ts` and included by the mod's own tsconfig, never through `paths`, since the file declares the module ambiently. The engine's per-load `.claude-plugin/types/` is git-ignored and never included, which keeps the two copies from colliding. **1d inherits:** `npm ci && npm run typecheck` on a runner needs no engine and no load. When the engine floor moves, the vendored file is replaced whole, from the new build's `claude-code.d.ts`, and its first line says which build wrote it.
- **The nouns' layers.** ADR 0001 names `$.process` (Infrastructure), `$.ui` (Presentation), atoms (Data) and slash registration (Presentation). This item adds `fs` and `env` to Infrastructure, since they reach the host as `process` does and discovery needs both. It adds `store` to Data, beside `state`. It adds `tool` to Presentation, since "Presentation registers, Business decides". And it refuses `http` in every layer: that is the client invariant's mod-side teeth, which `CLAUDE.md` gives to the layering check. A noun the table does not name is unconfined until an item that uses one declares its row.
- **The override is a plugin option, not an atom.** The item names "an override atom", as the macOS app keeps its override in its settings. A `$.state` atom lasts one session. A `userConfig` option persists, is a row in `/config`, and is read once at load and handed down from the composition root, so nothing below it reads a setting.
- **The dev channel** is the plugin's `channel` option, `release` (the default) or `dev`, beside its `binary` override. `dev` looks at the override and `apogee-dev` alone, so a development load never drives the production install. A load from `--plugin-dir` keeps its options under `apogee@inline`, apart from an installed `apogee@<marketplace>`, so setting `dev` there leaves the production install's options alone. The found binary also keeps the channel it reported (`channel: dev`), for 1b's surfaces to say.
- **plugin.json states version 0.2.1, an author and the license.** Version 0.2.1 is the release the mod first ships in, as the CLI keeps its own version bumped to the release it ships in. The license is the repository's MIT. With these, `validate --strict` is clean; without them it warned on version and author. Whether `version bump` holds the mod's version is 1d's call.
- **The composition root is `hooks/register.tsx`,** as ADR 0001 and `CLAUDE.md` name it and `hooks.json`'s `./register.tsx` resolves. The item's Technical approach row `lib/src/mod/register.tsx` was read as that file.

No `@types/node`: the network answer covered TypeScript and the plugin API's types. So the node-side checks are plain `.mjs`, outside the tsconfig and untyped, and are proven by their own tests and the mutation pass.
- **The binary is kept in `$.state`,** one atom with a shape tag, declared in the contract. "Once" means once a session, and the atom holds it, so a hooks copy the engine replaces mid-session does not say it again. Discovery runs awaited in `session.start`, after the engine's own start, so 1b's registrations can stand on its answer by turn one.

No test covered `changed.sh` before, the CLI's script tests run under its CMake build, and the run must not build the CLI. - **No layer cards** (`src/<layer>/CLAUDE.md`). The item names none, and the codebase maps in `CLAUDE.md` and `DEVELOPER.md` are the map.
- **Code outside a layer is refused, not read; JavaScript too** (taken at the review, 2026-11-21). `hooks/` holds `hooks/register.tsx` alone and `types/` holds `.d.ts` files alone, so the root and the contract cannot launder a noun or an edge through a helper beside them. **1b inherits:** when `register.tsx` grows, what it hands off goes into a layer's package (Presentation's, for registrations' handlers), never into a second file of `hooks/`. A JavaScript file in a layer is refused by name rather than read with `allowJs`. In untyped JavaScript the type checker finds the engine only where it is spelled `$`, so a renamed engine would pass unseen. The mod is TypeScript, and refusing is the narrower law.
