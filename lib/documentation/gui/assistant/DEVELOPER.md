# Apogee GUI — Developer Reference

The package-by-package architecture reference for the GUI applications: every directory, file, interface, and build/test command. The contributor entry point is [CLAUDE.md](CLAUDE.md); the product spec is [SPEC.md](SPEC.md). The CLI's own reference — including the machine-mode protocol the GUI is built against — is [`cli/assistant/DEVELOPER.md`](../../cli/assistant/DEVELOPER.md) and [`cli/reference/machine-mode.md`](../../cli/reference/machine-mode.md).

---

## Layout

Each application is self-contained, owning its build, with `source/` and `tests/` at its first level. Each is four layers — Infrastructure, Data, Business, Presentation — with dependencies pointing down, regardless of its language and framework ([ADR 0001](../adrs/layer-enforcement.md)): `source/<layer>/<package>/`, tests mirroring. Presentation modules keep the MVVM shape — `Views/`, `ViewModels/`, module-specific extras — with shared typography, colors and common components in the one `styles` module ([ADR 0002](../adrs/presentation-mvvm.md)).

```
lib/src/darwin/                 the macOS application (1a, 2026-10-20)
├── Apogee.xcodeproj/           the Xcode project -- the module map
│   ├── project.pbxproj         every target, its folder, dependencies, links and embeds
│   └── xcshareddata/xcschemes/Apogee.xcscheme
│                               the shared scheme: builds the app, runs every test bundle
├── scripts/build.sh            the one build entry from outside (cicd.sh calls it)
├── scripts/capture-fixture.sh  refreshes the recorded protocol fixture from a real binary
├── source/
│   ├── main/                   the application target `Apogee`: the entry point alone
│   ├── infrastructure/         CLAUDE.md (the layer's card) · process/
│   ├── data/                   CLAUDE.md · protocol/ · preferences/ · discovery/
│   ├── business/               CLAUDE.md · session/ · reads/
│   └── presentation/           CLAUDE.md · styles/ · shell/ · session/ · app/ (each Views/, ViewModels/)
├── tests/                      mirrors source/'s modules, one unit-test bundle each
│   └── architecture/layering/  the layering check
└── build/<target>/             output (ignored): xcode/ derived data, Apogee.app
lib/src/linux/                  the Linux application -- not yet started
lib/src/windows/                the Windows application -- not yet started
```

### `lib/src/darwin/` — the macOS application

**An Xcode project, and the project is the module map** (1a; an Xcode project rather than a Swift package is the user's call, 2026-10-20). A module is a **framework target** building one folder, `source/<layer>/<package>/`, as a file-system synchronized group — a file added to the folder is compiled into the target with no project edit — named `<Layer><Package>` (`DataProtocol`), so its folder is its layer's declaration and every `import` names the layer it reaches. Its **dependencies and links are its edges**. Each module has an **unhosted unit-test bundle** at `tests/<layer>/<package>/`, `<Layer><Package>Tests`, in the shared scheme. The **application target `Apogee`** builds `source/main/` — `ApogeeMain`, which starts `PresentationApp`'s `ApogeeApp` and nothing else, the composition root as the CLI's `source/main.cpp` is — links `PresentationApp`, and embeds every framework that reaches. Project-wide: Swift 6 language mode, macOS 27.0 deployment target, `arm64` only, `CODE_SIGN_IDENTITY "-"` (ad hoc, the user's call, 2026-10-20), no hardened runtime, no package references, and **no code coverage** (`ENABLE_CODE_COVERAGE`, `CLANG_ENABLE_CODE_COVERAGE`, `CLANG_COVERAGE_MAPPING` all `NO`, the scheme's `codeCoverageEnabled = NO`): left to Xcode 27's scheme default, every build -- the Release app included -- was instrumented and wrote `default.profraw` wherever it ran.

| Module | Layer | Files | What it is |
|---|---|---|---|
| `InfrastructureProcess` | Infrastructure | `ChildCommand.swift`, `RunningChild.swift`, `ProcessSpawner.swift`, `CapturedRun.swift`, `LineFramer.swift`, `BoundedTail.swift` | `ChildCommand`: a child to spawn -- an absolute executable (a `.app` inherits no shell `PATH`), arguments, variables laid over the parent's environment, a working directory. `RunningChild` (`lines`, `stderrTail`, `write`, `closeInput`, `terminate`, `kill`, `waitForExit`) and `ChildSpawner`; `ProcessSpawner` makes `FoundationChild`: a `Process` with three pipes, its state behind one `Mutex` -- stdout through `LineFramer` (whole lines, UTF-8 once whole, U+FFFD for bytes that are not), stderr into an 8 KiB `BoundedTail`, `F_SETNOSIGPIPE` on stdin so a write to a dead child throws `ChildError.inputClosed`, and an exit awaited until stderr closes too (or two seconds after the exit). `capture(_:timeout:stdoutLimit:)` runs a one-shot child whole: input closed, SIGTERM past its time and SIGKILL two seconds later, stdout cut at its limit. |
| `DataProtocol` | Data | `MachineProtocol.swift`, `JSONValue.swift`, `ProtocolEvent.swift`, `EventDecoder.swift`, `DriverLine.swift`, `ReadDocument.swift` | The protocol as types. `ProtocolEvent` is `kind` + `fields`: every event of machine-mode.md a typed case (`SessionInfo` with `Capabilities`, `TurnResult` with `Usage` absent when absent, `Question` with its `QuestionItem`s and permission facts, `TodoItem`s ...), `task(type:)` for a task run's events, `unknown(type:)` for anything else or a known type missing what its case needs, `unreadable(line:)` for a line that is not one JSON object with a type -- and `fields` keeps every field. `EventDecoder.decode(line:)` never fails. `DriverLine` writes `hello`, `user`, `answer`, `attach`, `cancel`, `type` first, byte-stable. `ReadDocument` keeps a read's document whole (list entries, total, problems). `MachineProtocol`: version 1, the `stream-json` word. |
| `DataPreferences` | Data | `Preferences.swift` | The GUI's own settings, never the CLI's config: `binaryOverride`, kept as a path; `route`, the place the window last showed; `sidebarHidden` (a flag kept as `true` or absent) -- in the defaults domain `com.quantumcompiler.apogee` through a `KeyValueStore` (`DefaultsStore`; `MemoryStore` for tests). |
| `DataDiscovery` | Data | `BinaryDiscovery.swift` | Finds the binary: `candidates(override:)` -- the override, `~/.local/bin/apogee` (release), `apogee-dev`, `apogee-test` -- and `locate(override:)`, each verified by `apogee version` (ten seconds, an `apogee x.y.z` first line): `found(FoundBinary, skipped:)` or `notFound(skipped:)`, every skip with its reason, and `DiscoveryOutcome.installHint`. |
| `BusinessSession` | Business | `ChatLaunch.swift`, `MachineSession.swift`, `TurnTracker.swift`, `ApogeeClient.swift` | `ChatLaunch`: `chat --output-format stream-json --input-format stream-json`, then `--tools`. `MachineSession` (an actor): `start(spawner:command:hello:)` spawns and says hello; `events` is an `AsyncStream<SessionEvent>` -- each `ProtocolEvent`, then `.ended(SessionEnd)` with its reason (`finished`, `failed`, `stopped`, `couldNotStart`, `unsupportedProtocol`), exit, stderr tail and one-line `message`; `send(user:)`, `answer(_:)`, `attach(path:graph:)`, `cancel()`, `close()`, and `stop(grace:)` -- cancel a turn in flight, close the input, SIGTERM after the grace, SIGKILL two seconds later. A session announcing another protocol version is refused, not misread. `TurnTracker`: `opening`, `idle`, `running(turn:)`, `asking(turn:unanswered:)`, `over`, from the events alone. `ApogeeClient`: `locateBinary()` with the stored override, `startChat(binary:launch:folder:environment:)` in the user's home unless given a folder. |
| `BusinessReads` | Business | `ReadRunner.swift` | One read, `apogee <arguments> --output-format json`, captured (sixty seconds): `ReadOutcome` -- `document`, `failed` with the stderr tail, `undecodable`, `timedOut`, `couldNotStart`. |
| `PresentationStyles` | Presentation (the floor) | `Palette.swift`, `Typography.swift`, `Metrics.swift`, `Components/EmptyState.swift` | The shared vocabulary: `ColorToken`s (surfaces -- window, sidebar, inspector, card, control, selection, code -- lines, text, status and the three model kinds) from the design's Graphite Light/Dark themes (`lib/design/spec/json/tokens.json`, copied) resolved against the window's appearance through a dynamic `NSColor`; `TypeScale` and `Font.apogee*` in the system fonts; `Spacing`, `Radius`, `Layout`; `EmptyState`, a centered symbol, title and message. Leans on no sibling. |
| `PresentationSession` | Presentation | `ViewModels/Transcript.swift`, `ViewModels/SessionViewModel.swift`, `Views/SessionWindow.swift`, `Views/TranscriptRow.swift`, `Views/QuestionCardView.swift`, `Views/PermissionCardView.swift`, `Views/InputBar.swift`, `Components/Card.swift` | One chat session. `Transcript`: a pure reducer -- `apply(SessionEvent)`, `userSent`, `answered`, `cancelling` -- into `TranscriptItem`s (user, the turn's `Activity` section, `Answer` as its deltas joined, notice, `QuestionCard`, `PermissionCard`, error, stopped, todo in place, the quiet unknown row, `Ending`) and a `Status` from events alone. `SessionViewModel` (`@MainActor @Observable`, no SwiftUI): `connection` (`idle`, `locating`, `missing(hint:places:)`, `connected`), `transcript`, `draft`; `start`, `submit`, `answer(_:with:)`, `cancel`, `shutDown`, over an `any ChatStarting`, every outbound line through one ordered outbox. The views bind to it: the window (starting, not found, the conversation), the rows, the cards, the input bar (Send ⌘⏎/⏎; Stop ⌘./Esc via `onExitCommand`). |
| `PresentationShell` | Presentation | `ViewModels/Destination.swift`, `ViewModels/KeyMap.swift`, `ViewModels/ShellViewModel.swift`, `Views/ShellView.swift`, `Views/Sidebar.swift`, `Views/ShellCommands.swift` | The window around every screen (1e). `Destination`: the design's seven places in its order -- `title`, `symbol`, `key` (⌘1–⌘7), and for an unbuilt one a `Placeholder` (what will be there, and today's command); `Overlay` (the monitor). `KeyMap`: `KeyChord` (`symbols` in the menus' ⌃⌥⇧⌘ order), the shell's `KeyBinding`s over `ShellCommand` (`go`, `modelsLibrary`, `toggleMonitor`, `toggleSidebar`, `openSettings`), and `reference`, the design's twenty-line keyboard list. `ShellViewModel` (`@MainActor @Observable`, no SwiftUI): `route` (kept in `Preferences`, an unknown one opening Sessions), `overlay`, `sidebarHidden`, `width`, `toast` (`say`, `dismissToast`; five seconds), `perform(_:)`, and `layout` -- `ShellLayout`, the window law: below `collapseBelow` (900) the sidebar is `.icons` and `sidePanes` is false; hidden is `.hidden` at any width. | `Apogee` (application) | -- (`source/main/`) | `ApogeeMain.swift` | The entry point: `@main`, `ApogeeApp.main()`. |

**The layering check** (`tests/architecture/layering/`): `ModuleMap` reads `project.pbxproj` with `PropertyListSerialization` (it is an old-style property list) -- each target's product type, synchronized folder (its whole path walked up the groups), target dependencies, linked and embedded products, and the build settings that would reach outside the project -- and the shared scheme's testables; `SourceTree` is the files, on disk or planted; `LayeringCheck` holds them to the rules its header lists (ADR 0001's layers and edges, nothing from outside the project, declared imports, UI frameworks in Presentation and never in `ViewModels/`, the MVVM shape, `styles` as the floor, the application's one file and exact embeds, mirrored tests, the scheme running every bundle, the layer cards). `LayeringTests` runs it on this project, plants each violation in a miniature, and plants one dependency into the real project file's objects.

**The window's tests** need no window and no process (`tests/presentation/session/`): `TranscriptTests` folds scripted event sequences -- the recorded mock-actor stream among them -- and pins the rows and each status; `SessionViewModelTests` drives the view-model over `ScriptedSession`/`ScriptedStarter` (`Scripted.swift`), which record every line asked of them, and once over a real `MachineSession` fed by `ReplayChild`, an in-memory `RunningChild` replaying the recorded stream (pausing after `session` for a `user` line and after each `question` for an `answer`) whose written bytes are checked exactly.

**The shell's tests** (`tests/presentation/shell/`): `ShellViewModelTests` drives the view-model over a `MemoryStore` -- every place gone to and restored by a fresh view-model, each command, overlays, the window law's threshold, the toast -- and `KeyMapTests` holds the keys to the design's list.

**The client core's tests** run real processes and nothing else: `/bin/sh` scripts for the spawner, the discovery table and the reads; and for the session **a scripted fake `apogee`** (`tests/business/session/FakeApogee.swift`: a Python program written to a temporary directory, speaking the protocol by `FAKE_SCENARIO` -- `conversation`, `slow`, `dies`, `unknown`, `protocol2`, `stubborn` -- and logging every line it reads to `FAKE_LOG`). **The recorded fixture** (`tests/data/protocol/Fixtures/mock-actor.jsonl`) is the real binary's stdout for the mock-actor conversation; `scripts/capture-fixture.sh [binary]` records it again in a throwaway `APOGEE_HOME` on the CLI's mock backend, and a vocabulary change in a new CLI then fails `EventDecoderTests` rather than passing silently. **`RealBinaryTests`** drives an installed `~/.local/bin/apogee` (or `-dev`, `-test`) through the same conversation in a throwaway `APOGEE_HOME`, never `~/.apogee`, and is skipped -- the reason printed -- where there is none.

**Adding a module:** the folder `source/<layer>/<package>/` (Presentation: with `Views/` and `ViewModels/`); in Xcode, a macOS framework target named `<Layer><Package>` whose synchronized folder is that directory, linking only its own layer or below; its test bundle `tests/<layer>/<package>/` (`<Layer><Package>Tests`, no host application) added to the shared scheme's tests; its name on its layer card's **Modules** line; and, when the app comes to reach it, the application target's Embed Frameworks. The layering check names whichever of these is missing.

## The contract the GUI builds against

- **The protocol:** [`machine-mode.md`](../../cli/reference/machine-mode.md) — the JSONL events, the driver's stdin lines (including `cancel`), the reads' `--output-format json` documents, task and play narration.
- **The schema:** `machine-schema.json` — printed by the binary (`apogee __machine-schema`), shipped in every CLI archive, and pinned to the doc and the implementation by `cli.machine_schema_conformance`.
- **Getting a CLI to drive:** a release install (`install.sh` / `install.ps1`), a source build (`make -C lib/src/cli install`, channels per the CLI docs), or CI's `apogee-<target>` artifacts.

## Build & test

```bash
lib/scripts/cicd.sh --test                    # every application, host-native -- the gate
lib/scripts/cicd.sh --app darwin --test       # the macOS app alone: build, bundle, suite
lib/src/darwin/scripts/build.sh test          # its suite alone (Debug)
lib/src/darwin/scripts/build.sh build         # Release Apogee.app, version stamped, signed ad hoc, verified
lib/src/darwin/scripts/build.sh open          # build, then open the app
```

Or open `lib/src/darwin/Apogee.xcodeproj` in Xcode: the shared scheme `Apogee` runs the app and the tests (Cmd-U) with the same settings; a build from Xcode carries no version and says "Development build".

**A tool that writes bare modules into Xcode's derived data breaks it.** SweetPad's build server (`sweetpad bsp`), left at its default, "prepares" each target by writing `<Module>.swiftmodule` (with `.abi.json`, `.swiftdoc`, `.swiftsourceinfo`) straight into the shared `~/Library/Developer/Xcode/DerivedData/Apogee-*/Build/Products/Debug/`. A build puts that folder on the compiler's `-I` path, where a bare module wins over the framework's own, so once the source moves on, every build compiles against the stale interface -- on 2026-10-20 a Debug build failed to link `PresentationApp` on a 12:10 copy of `BusinessSession`'s. The cure is Product -> Clean Build Folder (or removing those bare files); the prevention is giving the tool a derived-data path of its own. `scripts/build.sh` is immune: its derived data is `build/<target>/xcode/`.

`scripts/build.sh` drives `xcodebuild` over the shared scheme for `platform=macOS,arch=arm64`, its derived data in `build/<target>/xcode/`, `-quiet` so the log keeps warnings, errors and the tests' output. `build` passes `lib/release/VERSION` as `MARKETING_VERSION`, copies the Release product to `build/<target>/Apogee.app` and runs `codesign --verify --deep --strict` on it. `test` writes `build/<target>/tests.xcresult` and, on a failure, prints every failed test with its messages from it. It builds macos-arm64 on an Apple-silicon Mac only. `cicd.sh` calls it -- `build`, then `test` under `--test`; `test` alone under `--unit-tests`; `clean` under `--clean` -- and knows nothing else of how the app compiles: `APPS=(cli darwin)`, darwin built for macos-arm64 only, deferred to CI on another host (refused there under `--no-defer`), and `--app` picks applications (every one by default; the CLI pipeline passes `--app cli`). `lib/scripts/changed.sh gui-darwin` declares what the app is built from: `lib/src/darwin/`, `cicd.sh`, `changed.sh` and `lib/release/VERSION`. The repo-wide release law is in the [CLI docs](../../cli/assistant/CLAUDE.md#release-and-install-infrastructure).

### CI: `.github/workflows/darwin.yml`

The app's own pipeline, beside the CLI's `ci.yml` (1d, 2026-10-20), on every pull request into `stable` and on request:

- **`what changed (darwin)`** (Ubuntu): `lib/scripts/changed.sh gui-darwin <latest release's commit> HEAD` on the pull request's test merge -- the CLI pipeline's own question, against the latest release -- or "everything runs" on request. If it fails, the build is skipped and its required check never reports: fail closed.
- **`build darwin`**: when the app changed, on GitHub's **`xcode-27`** image (macOS 27, Xcode 27 -- the macOS 27 SDK the app needs; a preview image since 2026-07-16), `lib/scripts/cicd.sh --app darwin --platform macos-arm64 --test --no-defer` (the Release app built, signed ad hoc and verified, then the whole suite, the real-binary pass skipped there), then `lib/src/darwin/scripts/build.sh package`, and the zip uploaded as the artifact **`apogee-gui-darwin`**. When it did not, the job runs on a Linux runner with every step skipped and passes under its name -- the required-names pattern, without a Mac runner for nothing. The job's runner is an expression of the gate's answer; a required job never gets a job-level `if:`.
- **The artifact**: `Apogee-<version>/Apogee.app` and `README.txt` (what it is, the CLI it needs and the installer's one-liner, the ad-hoc signature's Gatekeeper cost -- right-click -> Open the first time -- and the commit it was built from); `package` re-verifies the signature on the app unpacked from the zip. No release carries it yet.
- **Rehearsed** on the dev host by the same commands (the 1d item's way; `make pr-ci` covers the CLI pipeline only): `lib/scripts/cicd.sh --app darwin --platform macos-arm64 --test --no-defer`, then `lib/src/darwin/scripts/build.sh package`.
- **Required checks**: its two job names join the "Stable: CI must pass" ruleset through `lib/scripts/required-checks.py --pr <N> --apply` once a pull request's run has passed, before it merges (the CLI docs' [Changing the pipeline](../../cli/assistant/DEVELOPER.md#changing-the-pipeline)) -- `--apply` changes repository settings, so it is the user's to run.
