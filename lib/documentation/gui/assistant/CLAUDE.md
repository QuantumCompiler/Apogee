## What this is

The Apogee GUI: one native desktop application per platform (`lib/src/darwin/`, `lib/src/linux/`, `lib/src/windows/`), each a graphical front end that **drives the `apogee` CLI over its stdio machine mode** — the harness's capabilities rendered, never reimplemented. See [SPEC.md](SPEC.md) for scope and principles, and [MILESTONES.md](MILESTONES.md) for what has shipped -- since 2026-10-20 the macOS application and its session window (Milestone A) and every screen of the design (Milestone B): track 1, complete in v0.2.0.

## Stack & environment

- **Language / frameworks:** **Swift and SwiftUI** for the macOS application (the user's call, 2026-10-20, with the first spike); an **Xcode project** as its build (the user's call, 2026-10-20, at 1a's build, over the SwiftPM default it was groomed with), Xcode building and **ad-hoc signing** the `.app` itself (same date). The linux/windows apps' stacks are still open — decided when their work opens.
- **Key dependency:** the `apogee` binary and its machine-mode contract — [`machine-mode.md`](../../cli/reference/machine-mode.md) and `machine-schema.json` (shipped in every CLI archive, printed by the binary itself). A development GUI can take the CLI from a release install or from CI's `apogee-<target>` artifacts.
- **Platforms:** macOS (Apple silicon), Linux (x64/arm64), Windows (x64/arm64) — the CLI's five targets. Primary dev host is macOS. **macOS is built first** (the user's call, 2026-10-20): macOS 27+, Apple silicon only, matching the CLI's `macos-arm64` target.
- **Build:** each application under `lib/src/<app>/` is self-contained and owns its own build. The macOS app is an Xcode project (`lib/src/darwin/Apogee.xcodeproj`, Swift 6, macOS 27 and later, Apple silicon) driven by `xcodebuild` through its shared scheme `Apogee`, whose one entry point from outside is `lib/src/darwin/scripts/build.sh`; it is in `cicd.sh`'s `APPS` as `darwin` (built for macos-arm64 on an Apple-silicon Mac, deferred elsewhere), `lib/scripts/changed.sh gui-darwin` declares what it is built from, and its own pipeline, beside the CLI's, is `.github/workflows/darwin.yml` (1d): built and tested on GitHub's `xcode-27` image through `cicd.sh`, packaged as the run artifact `apogee-gui-darwin`.

## ⚠ The GUI is a machine-mode client

**The rule.** Every capability reaches the GUI by driving the `apogee` binary as a child process over the stdio machine mode. The GUI never links the CLI's libraries, never calls a provider itself, never reimplements a capability the CLI owns, and never opens a listening socket for local work.

Why this is non-negotiable: "parity is the product" is the repo's founding law — every capability reaches every surface through one shared core. The moment a GUI grows its own path to a provider or its own copy of a capability, the surfaces drift apart and the CLI's test suite stops vouching for what the GUI does. The stdio contract is also the recorded product shape: local front-ends are pipes; `apogee serve` exists solely for remote deployments.

- Build against the protocol as the schema states it: `machine-schema.json` rides in every CLI archive, and the session's `capabilities` line announces what the binary speaks.
- The protocol grows **additively** (the CLI's ADR 0006): a GUI must tolerate events and fields it does not know, and must never require a protocol change that breaks an older front end.
- The CLI child's stderr is captured, never surfaced raw; cancellation is the protocol's `cancel` line, never a kill as the first resort.
- Secrets never pass through the GUI: keys are entered through the CLI's own flows, and the protocol carries no key fields by construction (the CLI's secrets invariant).

Enforced by: the contract side is test-locked in the CLI (`cli.machine_schema_conformance` pins the doc, the schema and the binary to each other; `cli.machine_mode` drives the real binary). On the GUI side, the link-policy analog exists since 1a: the darwin layering check (`lib/src/darwin/tests/architecture/layering`) fails any package dependency, product, `unsafeFlags` or `linkedLibrary`, so nothing of the CLI's can be linked. Since 1b the client side is test-locked too: the decoder is held to a stream recorded from the real binary (`tests/data/protocol/Fixtures/mock-actor.jsonl`, refreshed by `scripts/capture-fixture.sh`), unknown events, fields and lines flow through by test, the child's stderr is a bounded tail by test, `cancel` is a protocol line and termination only `stop`'s escalation by test, and a pass drives the installed binary itself when there is one. The rest is held by review.

## Working process

The GUI is built docs-first, the same lifecycle as the CLI's. Where new work is written down, how a backlog item is worked, and the bare-"Continue" convention are exactly the CLI docs' rules — read [Working process](../../cli/assistant/CLAUDE.md#working-process) there. The GUI's deltas:

- GUI work lands in **this** tree's ROADMAP/backlog/MILESTONES, never the CLI's; an item that needs a CLI change (a new protocol event, a new read) gets a sibling item in the CLI's backlog, gated both ways.
- **Versioning is repo-wide** (the release, `lib/release/VERSION`, the merge-is-the-release law — the CLI docs record it). The GUI ships inside those releases once it exists; its pipeline joins CI beside the CLI's.

## Implementing a Feature

Every change should satisfy this before merge:

- [ ] Tests for the new behavior pass, and existing tests stay green: `lib/scripts/cicd.sh --test` (every application), or `lib/scripts/cicd.sh --app darwin --test` for the macOS app alone. They are hermetic: scripted fakes, no network, no `apogee` binary, no window.
- [ ] The machine-mode invariant holds: no linked CLI, no second capability, unknown protocol events tolerated.
- [ ] **The four-layer law holds** ([ADR 0001](../adrs/layer-enforcement.md)): a new package declares its layer, dependencies point down, the UI framework's types stay in Presentation — whatever the language.
- [ ] **Presentation keeps the MVVM shape** ([ADR 0002](../adrs/presentation-mvvm.md)): `Views/` and `ViewModels/` per module (view-models SwiftUI-free), shared visuals and common components in the one `styles` module, never duplicated.
- [ ] **Every view can be seen on its own** ([ADR 0004](../adrs/module-schemes-and-previews.md)): a new view has a named `#Preview` in its file for each state a person sees differently, inside `#if DEBUG`, over its module's `Previews/` fakes and the binary's recorded documents -- never the binary, `~/.apogee` or the network; a new Presentation module has its shared scheme.
- [ ] **Every CLI command has its place** ([ADR 0003](../adrs/parity.md)): a CLI command added or removed is classified in `ParityTable` in the same change -- a screen, the console, a queued item, or a carve-out with its reason -- and `scripts/refresh-parity-fixture.sh` re-run against that CLI.
- [ ] The affected docs are updated in the same change (see **Documentation and Status**).

## Code Style

- **Swift 6, strict concurrency, warning-free.** The project builds in the Swift 6 language mode; a warning is fixed where it is raised.
- **The project file is edited in Xcode or by hand, and the layering check reads it.** A file added to a module's folder needs no project edit (synchronized groups); a new module is a framework target, its test bundle and its line in the shared scheme together (in Presentation, its own shared scheme too), and the application target embeds what it newly reaches.
- **One type per concern, named for what it is**, a doc comment on every public declaration saying what it is for -- and, where a rule of the protocol or an ADR is why it is shaped so, which rule.
- **A target's name states its layer** (`DataProtocol`, `BusinessSession`), so every `import` says which layer it reaches; a new package is a directory, a target, a mirroring test bundle and a line on its layer card, together.
- **A public declaration's default arguments name only its own module and the system's** (2026-10-20). Swift compiles a default argument into the caller, so `init(spawner: any ChildSpawner = ProcessSpawner())` makes every caller reference `InfrastructureProcess` -- a module it may not link. Give the defaulted form its own overload inside the module instead (`ApogeeClient.init(identity:)`), as the `PresentationApp` link failure that taught this now does.
- **View-models are `@MainActor @Observable` classes importing Foundation and Observation only**; the views bind to them and to `styles`, and nothing else.
- **Tests use Swift Testing** (`@Suite`, `@Test`, `#expect`), each named for the behavior it pins.
- Match the surrounding code's conventions; when in doubt, find the closest existing analogue and follow it.

## Release and Install Infrastructure

Repo-wide and recorded in the CLI docs ([Release and Install Infrastructure](../../cli/assistant/CLAUDE.md#release-and-install-infrastructure)): a merge into `stable` publishes the release `lib/release/VERSION` names. The GUI's own packaging, install path and pipeline join that machinery application by application — each app gets its own `changed.sh` entry and its own pipeline, and can take the CLI from the run's `apogee-<target>` artifacts. The macOS app has its entry (`gui-darwin`) and its ad-hoc-signed, verified `Apogee.app` (`scripts/build.sh build`) since 1a, and its pipeline (`.github/workflows/darwin.yml`) since 1d, which keeps the app zipped with its README (`scripts/build.sh package`) as the run artifact `apogee-gui-darwin`. Its place in a release is later work (the user's call, 2026-10-20: a CI artifact until the session window ships -- which it now has; the wiring is its own item).
