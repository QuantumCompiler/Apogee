# v0.3.0: macOS, iPadOS and iOS whole

**What / why.** The user's vision, 2026-11-07: Apogee is a private, self-hosted harness that feels like Claude on every device the person owns, with one strong machine of theirs (for example 512 GB of memory and a finely tuned large model) serving their own desktops and phones. v0.3.0 is the release where that works on the Mac, the iPad and the iPhone, the foldable iPhone included (GUI SPEC → [One-liner](../../assistant/SPEC.md#one-liner)). The items before this one build the pieces: the server's side (CLI [59a](../../../cli/backlog/v0.2.3/paired-devices.md)–[59e](../../../cli/backlog/v0.2.3/tasks-outlive-the-connection.md), [60a](../../../cli/backlog/v0.2.4/one-tool-definition.md), [60b](../../../cli/backlog/v0.2.4/device-tools.md)), the app's connection and places ([7a](../v0.2.4/app-connection-local-or-server.md)–[7c](../v0.2.4/every-place-against-a-server.md)), the iOS build, the iPad and distribution ([8a](../v0.2.5/app-builds-for-ios-and-ipados.md)–[8c](../v0.2.5/iphone-and-ipad-distribution.md)), and the iPhone and the foldable ([9a](iphone-app.md), [9b](foldable-iphone.md)). This item adds no capability. It is the release's proof: it shows every capability on every Apple platform, it checks the anti-goal, and it ships the release with the docs that say how to pair.

It closes **the release goal**: every capability on every Apple platform, with the Mac and the CLI still complete alone. Measured at HEAD (`4f92316d`) on 2026-11-07, five things stand between the pieces and that release:

1. **The parity table knows one platform.** `ParityTable.places` (`lib/src/darwin/source/presentation/shell/ViewModels/Parity.swift:52-90`, 32 rows) gives each command one place, for a local binary on a Mac. 7c adds a remote meaning to each row (`onServer`, `onServer(here:)`, `notRemote(reason:)`), but nothing says what a row means on an iPad or a phone. A place awkward on a phone could quietly have no way in, and no test would fail. The table is also behind the binary today: `apogee __complete ""` on the branch binary (a scratch `APOGEE_HOME`) answers 30 top-level words, while the recorded `tests/presentation/shell/Fixtures/command-words.txt` holds 29 (`acp` is 5a's).
2. **No test drives the app whole.** The suite is per module. `ScriptedRunner` is defined in 14 test files and `ScriptedJobs` in 11, one per module's bundle. The session's tests replay the recorded `tests/data/protocol/Fixtures/mock-actor.jsonl` through a scripted child (`tests/presentation/session/Scripted.swift`). `tests/presentation/app/` holds `AppViewModelTests`, `CapabilitiesFromLaunchTests`, `ChildrenSeenTests` and `TerminationTests`, and none of them carries one conversation across the composed places. Nothing scripted plays a server. `tests/business/session/RealBinaryTests.swift` drives the installed binary, which is local and not hermetic.
3. **The anti-goal is held on the CLI's side only.** The CLI pins never-listens by symbol scan and by process: `cli.no_listen_symbols` (`lib/src/cli/tests/CMakeLists.txt:561-644`) and `cli.complete_opens_no_listening_socket` (`:882-892`). The app has no network code today, so nothing can reach a server. Once 7a adds a transport, nothing in the app's suite fails if a Mac with no server configured opens a connection, or if a local place starts depending on one.
4. **A release carries the Mac app and nothing else.** `release-from-pr.sh` attaches `apogee-gui-darwin.zip` (`:17`, `:84`, `:421-488`, GUI M17), and `build.sh` builds one target (`TARGETS=(macos-arm64)`, `:49`). Getting the iOS app onto a device is 8c's path, and 8c's default is that a release asset carries no iOS build.
5. **No document says how to pair, and the public ones lag.** A search for `pair` in the root `README.md` and the GUI `DEVELOPER.md` finds `check --fix`'s "repairs" (`README.md:37`) and the Models place's drafter pairing and `repair` (`DEVELOPER.md:53`), and nothing about pairing a device. `README.md:80` still says the macOS app "is not yet part of a release", which has been stale since M17. The app's zip README (`build.sh:163-177`) calls it "the desktop app, in development" and names only the local CLI. `apogee serve --help` names no pairing or device flag (a search for `pair|device` returns 0). The release-notes skill lists "TLS on `serve`" among the known limitations a release must re-check (`.claude/skills/apogee-maintenance-summarize-release/SKILL.md:74`); 59a makes every non-loopback bind speak TLS, with `--tls off` for an operator's own proxy, so v0.3.0's notes must say so.

This item delivers:
- **Every command classified per platform.** The parity table gives each command a place on the Mac with no server, on the Mac against a server, on the iPad and on the iPhone. The suite fails the day a row has no place on a platform, or a reasoned carve-out loses its reason.
- **An end-to-end hermetic pass per platform.** One script of acts runs through the composed app against a scripted server: pair, list, open, a turn with its question and permission cards, a read in every place, a job, a task followed across a dropped connection, and on the Mac a device-tool call. It runs on macOS, on an iPad simulator, on an iPhone simulator, and in the foldable's folded and unfolded traits.
- **The anti-goal checked.** A Mac with no server configured goes through every place and a whole local conversation over its child process. A tripwire fails the test if any remote transport is built.
- **The v0.3.0 release.** It carries the macOS app as today. The iOS and iPadOS build reaches the person's devices by 8c's path. The release notes and the docs say how to pair.

**Core constraint(s).**
- **Anti-goal: nothing here may make standalone use need a server** (GUI SPEC → [No server requirement](../../assistant/SPEC.md#non-goals); the user's call, 2026-11-07). The CLI alone, and the Mac app over pipes to its local CLI, stay complete and the default. This item is where that is proven for the release. The standalone pass runs every place of the Mac with no server configured and no network. The macOS zip still opens on the local CLI with nothing paired. The release notes call pairing optional, and the Mac's install steps need no account, no server and no Apple membership.
- **Never-listens; serving = server** (the CLI's [never-listens rule](../../../cli/assistant/CLAUDE.md); GUI SPEC → *No HTTP path for local work*). No app opens a listening socket. The iPad and iPhone connections are outbound, and on a Mac with Apogee installed the app never connects to a server on its own machine. The CLI's `cli.no_listen_symbols` and `cli.complete_opens_no_listening_socket` stay green.
- **The machine-mode client rule, as amended 2026-11-07** ([GUI CLAUDE.md](../../assistant/CLAUDE.md)): one protocol over two transports, stdio locally and the authenticated connection remotely, decoded with the same tolerance. The scripted server speaks exactly what 59b's transport carries, recorded from the real `apogee-dev serve`, never a dialect of the app's own.
- **Secrets are unleakable** (the CLI's invariant). No pairing credential, admin token or provider key appears in a recorded fixture, a preview, a log line, the release notes or the docs. The pairing steps say where a credential is made and kept, never a value: `apogee devices pair` on the server prints a one-time code, the device trades it once for its own token (59a), and the device keeps that token and the server's pin in its Keychain (7a).
- **Additive protocol** (the CLI's [ADR 0006](../../../cli/adrs/backwards-compatibility.md)). A v0.3.0 app meets an older server, and a v0.3.0 server meets an older app (a TestFlight build stays installed for up to 90 days, per 8c). The whole pass includes an older server's recorded capabilities, and every place shows the "not on this server" state (7c) instead of failing.
- **Parity** (the CLI's [ADR 0002](../../../cli/adrs/mode-parity.md); the GUI's [ADR 0003](../../adrs/parity.md)). There is one table for every platform, and a platform drops a command only with a stated reason. At the release no row is a gap that names a queued item on any Apple platform.
- **The layers and MVVM** ([ADR 0001](../../adrs/layer-enforcement.md), [ADR 0002](../../adrs/presentation-mvvm.md), [ADR 0004](../../adrs/module-schemes-and-previews.md)). The platform column is a value in the shell's view-model (SwiftUI-free). The whole pass drives view-models through the composition root, not views. The layering check stays green on the macOS and iOS targets.
- **The dev channel** (the CLI docs' [Development runs on the dev channel](../../../cli/assistant/CLAUDE.md#development-runs-on-the-dev-channel); GUI M18). Fixtures are captured from `apogee-dev serve` over a temp `APOGEE_HOME` with the mock backend. A live pass pairs dev builds with `apogee-dev serve`, never the person's production server, the release `apogee` or `~/.apogee`. The release's own app and server change only by what the release ships.

**Seam + files.** Planned, under `lib/src/darwin/` unless named otherwise.
- `source/presentation/shell/ViewModels/Parity.swift`: `CommandPlace` gains its place per platform. `ApplePlatform` has four cases: `macLocal`, `macServer`, `iPad` and `iPhone`. A row's place on each is derived from what it already states: its local place on `macLocal`, and its 7c remote meaning on the other three. An explicit override, with its reason, is allowed only where a platform differs (Open calls). The console's refusals are read for the platform the app runs on.
- `tests/presentation/shell/ParityTests.swift`: the per-platform law. Every row has a place on each platform. Every override and every `notRemote` has a reason. No row is a gap naming a queued item at the release. Every screen place can be reached on each platform: through `CompactNavigation` (9a) on the iPhone and through the regular shell (8b) on the iPad. `Fixtures/command-words.txt` is refreshed by `scripts/refresh-parity-fixture.sh` against the release's binary.
- `tests/presentation/app/WholePass/ScriptedServer.swift` (new): a scripted fake of 7a's remote connection. It replays recorded server documents and streams for each request, answers 59a's pairing with a scripted acceptance and a scripted refusal, drops and restores the connection on cue, and fails by name on any request it was not scripted for, so a pass cannot drift off its script silently. It holds no credential: its pairing answer is a planted placeholder that the leak check looks for.
- `tests/presentation/app/WholePass/WholePassTests.swift` (new): one script of acts through `AppViewModel`. Pair. List the server's chats. Open one and draw its earlier turns. Take a turn that streams its thinking and tool narration, answer its question card and its permission card, and stop a second turn. Read every place, run one command and one supervised job. Start a task, drop the connection, and follow the task again (59e). On the Mac only, answer a device-tool call on the Mac's own files (7b, 60b). Then meet an older server's capabilities. The same script runs for each platform's trait: macOS against a server, iPad regular, iPhone compact, and the foldable's folded and unfolded traits (9b).

**Decisions made** (dated):
- 2026-11-07: Specced from the Apple-platforms spike and brainstorm. The user's calls that shape this item:
  - **The vision.** Apogee is a private, self-hosted harness that feels like Claude on every device the person owns. A strong machine of theirs serves their desktops and phones, and Apogee mimics frontier harnesses (Claude Code, Codex, Gemini CLI, Ollama, vLLM) with local models.
  - **No accounts or billing.** Paid features are a someday, not now: no customer accounts, billing or metering. The server admits the person and their devices only, so the release reaches the person's own devices, not the public.
  - **The server is an add-on, never the only way the application runs.** The CLI alone, and the Mac app over pipes to a local CLI, stay complete and the default. Anything that makes the CLI or the Mac app need a server, a network or an account to do what they do today is a failure. This item checks that for the release.
  - **The SPEC amendment is approved and written.** The GUI reaches the CLI over stdio locally, or over an authenticated network connection to the person's own `apogee serve`.
  - **iPhone and iPad are clients of the person's Apogee server only**, with no on-device core. The Mac and the CLI stay standalone.
  - **Where the work happens is C.** Server tools by default, and a connected desktop offers its own files and shell. When the Mac points at a server and is asked to change a project on the Mac, the Mac's files are the ones touched. The whole pass checks this on the Mac (7b, 60b).
  - **"iPhone duo" is the foldable iPhone.** The app adapts to its folded phone screen and its unfolded near-iPad screen, and the whole pass runs both traits.
  - **The placement.** v0.3.0 is the target where macOS, iPadOS and iOS (the iPhone and the foldable) fully work. The common tool definition (60a) lands before it, and Apogee-tuned training (61a, 61b) after it.
  - **Windows and Android follow v0.3.0** (a recorded default).
- 2026-11-07: Placed last in v0.3.0 (track 9), gated on 9b and 8c. It proves the whole, so it follows the last layout (9b, and through it 9a, 8b, 8a and 7a–7c) and the path onto a device (8c), without which "working on iPhone and iPad" would mean only the Simulator. It adds no capability, so it needs nothing the gates do not already bring.
