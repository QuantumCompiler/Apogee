# The Tasks screen tells the truth: refusals decoded and shown, a resumed task's rounds kept, the read winning once a run ends, grants drawn, every task listed, one resume per click

**What / why.** The Tasks place is where a person watches an autonomous task and decides whether to resume it. The second bug sweep (2026-10-31) found seven ways it shows something other than what the ledger holds. Each one comes back to `TaskRunState` and the detail preferring the app's own run over the read, or to a field the read carries that nothing draws. The CLI's `task status` says all of it correctly, so the app falls short of parity on the place built to show it (1j's record, [MILESTONES → Milestone B](../../assistant/MILESTONES.md#milestone-b--the-designs-screens), `MILESTONES.md:629`: "what it denied", "the grants"). Re-read at HEAD 2026-10-31:

1. **A refused tool shows as raw JSON.** `TaskView.Round.init` decodes `allowed` and `denied` with `$0.stringValue ?? $0.serialized` (`source/business/reads/Tasks.swift:75-77`, used at `:83-84`). The CLI writes each entry as an object `{tool,target,by}` (`lib/src/cli/source/business/tasks/view.cpp:17-23`, `uses_json`, emitted at `:155-156`). `JSONValue.serialized` writes an object as sorted-key JSON (`source/data/protocol/JSONValue.swift:81-83`), and `TasksScreen.swift:172-173` joins those strings. So a task with `--tools` that calls `write_file report.txt`, with nobody present to allow it, gets a Rounds row in the warning colour reading `denied: {"by":"nobody","target":"report.txt","tool":"write_file"}` where `task status` says `write_file on report.txt -- nobody present to allow it` (`task_cmd.cpp:270-281`). Probe from the sweep (mock backend, sandbox `APOGEE_HOME`), `task status <id> --output-format json`: turns -> `[(0, [], []), (1, [{'by': 'nobody', 'target': 'ls', 'tool': 'run_command'}], [])]`. The CLI's own e2e pins the object shape (`lib/src/cli/tests/scripts/sh/task_e2e.sh:217`, `:241`). `allowed` is decoded the same wrong way, but nothing draws it yet (entry 6). No test has caught this because all 18 `"denied"` arrays in `tests/presentation/tasks/Fixtures/` are `[]`.
2. **A task resumed in the app loses its plan and earlier rounds from the Rounds list.** In `TaskRunState.apply`, the `task_started` branch (`TasksViewModel.swift:538-541`) takes the event's `task` view into `view` and its checks into `checks`, but never copies its turns into `rounds`. Only an event that carries a `round` object adds to `rounds` (`:531-534`). `TasksScreen.swift:159` uses the run's `orderedRounds` whenever it is non-empty and falls back to `view.rounds` only when it is empty, and nothing ever removes a run from `runs`. So the list first shows the old rounds through the fallback. At the first `task_round` it drops to only the rounds run since the resume, and it stays that way after the run ends, until the app quits. Probe from the sweep on the built binary with the mock backend (a stalled task after plan + rounds 1-2, then `task resume <id> --output-format stream-json`): `task_started turns_in_task=3`, `task_round round=3`, `task_round round=3`, `task_finished turns_in_task=4`. The Rounds list ends showing round 3 alone, while `task status` has all 4 turns.
3. **Once the app's run has ended, its stale reason, plan, checks, rounds and grants override a fresh read.** `run(for:)` is `runs.first { $0.state.taskID == id }` with no `isRunning` filter (`TasksViewModel.swift:121-123`). The detail sets `live` only for a running run (`TasksScreen.swift:106-107`), but it reads `run` rather than `live` for the finish reason (`:132`), the plan (`:137`), the checks (`:141`), the rounds (`:159`) and the grants (`:183`). `shown` falls back to the read (`TasksViewModel.swift:133-137`), so only the header agrees with the ledger. Scenario: a task started in the app is halted after round 1 with "Stop after this round". `apogee task resume <id>` run in a terminal then finishes it done after round 3. Back in Tasks the header says `done · 3 of 8 rounds`, and beneath it the screen still shows the old "halted … after round 1" reason in the warning colour, the round-1 checks as failed, and only the rounds the app saw. A resume started from inside the app hides the problem, because it puts a newer run first.
4. **The list silently drops every task past the newest 50.** `refresh()` reads `task list` without `--all` (`TasksViewModel.swift:91`). The CLI returns only the newest `kListLimit` = 50 rows (`lib/src/cli/source/business/tasks/view.h:36`, `view.cpp:213`) and puts the full count in `total` (`view.cpp:212`, `:226`). `TaskSummary.list` reads only `data` (`Tasks.swift:29-37`). `ReadDocument.total` exists (`source/data/protocol/ReadDocument.swift:27`), but no tasks code reads it. With 60 tasks the place lists 50 and gives no sign that 10 more exist. An old halted, stalled or cancelled task that `task resume` would continue can't be opened from the app, so its Resume can't be clicked. The CLI has the flag: `--all`, "Every task, not only the newest 50" (`task_cmd.cpp:1302-1303`). Probe: `task list --output-format json` -> `{"data":[],"object":"list","total":0}`.
5. **A run or resume the CLI refuses before it starts disappears with no reason.** In machine mode a refusal writes nothing to stdout. `fail_user` writes `apogee task: …` to stderr and exits 1 (`task_cmd.cpp:61-64`). `follow()` (`TasksViewModel.swift:259-276`) has no failure path: it sets no `failure` and calls no `say`. The stderr line lands only in the run's `activity` (`:505-508`). That run never gets a `taskID` or a view, so the "Starting a task…" row (`TasksScreen.swift:46`, `$0.isRunning && $0.state.taskID == nil`) vanishes when the child exits, and `listed` and `run(for:)` (`TasksViewModel.swift:121-123`, `:163-171`) can't find it. Scenario: the person ticks "allow writes" in New task. That passes `--allow write_file --allow edit_file` (`:379`) against a config with `permissions.edit_file: deny`. The CLI exits 1 with `apogee task: --allow write_file: the config says permissions.write_file: deny -- …`. The app shows "Starting a task…" briefly, then nothing. Resume does the same where the CLI refuses on rules the app can't see: an agent or grant the config no longer allows (`task_cmd.cpp:416-426`, `:628-631`, `:760-765`), the task lock held (`:553-556`), or a conversation that can't be read (`:584-585`). Probes from the sweep in stream-json mode: `task run --tools --allow write_file --output-format stream-json -- x` gives `stdout bytes: 0` and stderr `--allow write_file: the config says permissions.write_file: deny …`; `task resume <id> --output-format stream-json` gives `stdout bytes: 0` and stderr `apogee task: task … spent its round budget (2) …`. The spent-budget refusal is not something the app can hit, since 4h has never offered Resume on an exhausted task (`Tasks.swift:122`).
6. **A task's grants and the calls they let through never show once the live stream is gone.** The detail draws grants only from `task_grant` events in a stream this app instance is following (`TasksScreen.swift:183-188`, `if let run, !run.state.grants.isEmpty`, the only source being `TasksViewModel.swift:546-550`). The read has both: `policy.grants` (`TaskView.grants`, `Tasks.swift:105`, `:139`) and each turn's `allowed` (`Round.allowed`, `:67`, `:83`). Both are parsed, but nothing in `source/presentation` reads them. So for a task run from the CLI, or any task after the app relaunches, the page says neither what the task was granted nor which calls the grants let through. `task status` says `grants: write_file` and `allowed: round 1: write_file on … -- this task's grant` (`task_cmd.cpp:239-243`, `:275-277`). This also falls short of 1j's record.
7. **Resume stays clickable while the app's own resume is starting up, so a second click starts a second resume.** `resumable(id)`'s only guard is `live(id) == nil` (`TasksViewModel.swift:156-159`). `live` finds the app's runs by `state.taskID` (`:126-128`), which only an event carrying `task_id` sets (`:529`), in practice `task_started`. The CLI takes the task lock first (`task_cmd.cpp:553`), then builds the providers (`:620`) and the MCP servers and tools (`:720-745`), and emits `task_started` only from `run_task` (`:944`). For that whole window the detail's Resume (`TasksScreen.swift:123-124`) stays enabled, and `resume(id)` (`TasksViewModel.swift:231-234`) starts a second `apogee task resume <id> --output-format stream-json`. The row menu guards against this by matching on arguments (`interrupted(_:)`, `:242-245`, GUI M16); the detail does not. The second child exits on the lock refusal (`lib/src/cli/source/business/tasks/ledger.cpp:250-252`, `task … is running (process …) -- one task runs at a time`). That run never gets a `taskID`, so its line is never drawn (entry 5). The lock prevents a double run, so the harm is a click that does nothing, with no sign a resume is already under way.

What already works: the header follows the ledger once a run ends (`shown`), Resume is offered for exactly the states `task resume` continues and runs in the task's folder (4h, [Milestone E](../../assistant/MILESTONES.md#milestone-e--the-audits-gui-findings)), a killed task's row says interrupted (M16), and halt and cancel failures already reach the "That didn't work" alert in the CLI's words (`TasksViewModel.swift:290-301`).

**Core constraint(s).**
- **The GUI is a machine-mode client** (GUI `CLAUDE.md`): the screen shows what `task list` and `task status` read and what the stream says, and infers nothing of its own. The words for a use and its authority are `task status`'s (`task_cmd.cpp:196-221`, `:270-281`), not new ones. The CLI child's stderr is never surfaced raw: a refusal is shown as the bounded tail's last line, the CLI's one sentence, as 4f's `InstallConsent` and the halt/cancel alert already do.
- **The protocol grows additively** (the CLI's ADR 0006): `allowed`/`denied` entries are decoded field by field and tolerate fields they don't know. An entry that is a bare string is kept as a tool name, never dropped and never serialized.
- **The four layers** (ADR 0001): the decode (`TaskView.Use`) stays in `BusinessReads`; the fold and the screen's choices in `TasksViewModel`; nothing below Presentation imports SwiftUI.
- **MVVM** (ADR 0002): every decision this item adds (live or ended, which view is newer, a run's target task, the list's truncation, the words for a use) lives in the view-model, where tests reach it. The view only binds.
- **Every view can be seen on its own** (ADR 0004): each new state gets a named `#Preview` over the module's `Previews/` fakes and recorded documents.
- **Development runs on the dev channel**: fixtures are recorded from `apogee-dev` over a sandbox `APOGEE_HOME` on the mock backend, never the release `apogee` or `~/.apogee`. Until M18 ships, no development build of the app is launched for a live pass (GUI `CLAUDE.md`).
- **Hermetic tests**: scripted runners and jobs, recorded documents and streams, no binary, no network, no window.

**Seam + files.**
- `source/business/reads/Tasks.swift`: `TaskView.Use` (`tool`, `target`, `by`). `Round.allowed` and `Round.denied` become `[Use]`, decoded from objects, with a string entry kept as `Use(tool:)`.
- `source/presentation/tasks/ViewModels/TasksViewModel.swift`:
  - `Run` carries the task it targets: for a resume, the id taken from its arguments; for a run, whatever `task_started` names. `run(for:)` and `live(_:)` match on it, so a starting resume is live from the click (entry 7), and a refused resume is that task's run, with its line drawn on its page (entry 5).
  - `follow()`: a run that ends without success and without `task_started` sets `failure` and calls `say` with the stderr tail's last line (entry 5).
  - `TaskRunState.apply`'s `task_started` seeds `rounds` from the view's turns, keyed by round (entry 2).
  - The detail's sources become one `TasksViewModel` answer per part (reason, plan, checks, rounds, uses, grants). A live run's state wins, and once the run has ended the newer of the read and the run's last view wins, by `updated_at` (entry 3).
  - `refresh()` reads `total` and holds `--all` once asked (entry 4).
  - The words for a use: `tool on target -- authority`, as `task status` words it.
- `source/presentation/tasks/Views/TasksScreen.swift`: the Rounds row's `denied:` in those words. A **Grants** line from `policy.grants` and an **Allowed** section from the rounds' `allowed`; the round in flight's `task_grant` lines stay until its round lands. The list's "newest 50 of 60 · Show all" footer. Resume shown as resuming while one starts. Previews for each new state (`Previews/TasksPreviews.swift`, `Previews/PreviewDocuments.swift`).
- Tests (mirroring the source tree):
  - `tests/business/reads/`: a new `TaskReadsTests.swift` for the use decode.
  - `tests/presentation/tasks/`: `TasksViewModelTests.swift` (the fold, the detail's sources, the list's truncation, the refusal) and `TaskResumeTests.swift` (one resume per click, a refused resume).
  - New fixtures under `tests/presentation/tasks/Fixtures/`: `task-status-uses.json` (a round with `denied` by `nobody` and `allowed` by `grant`, and `policy.grants`), `task-list-newest-50.json` (50 rows, `total` 60), `task-resume.jsonl` (a resume's `task_started` carrying 3 turns, then round 3, then `task_finished` with 4), each recorded from `apogee-dev` on the mock backend in a sandbox `APOGEE_HOME`.
- Docs at ship: GUI `MILESTONES.md` (the entry), `DEVELOPER.md` and `CLAUDE.md`'s codebase map (the `tasks` line: a run's target task, the detail's sources, the use words).

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item because all seven findings are one screen showing other than the ledger, through two seams: the detail preferring the app's run over the read (entries 2, 3, 5, 7) and fields the read carries that nothing draws or decodes (entries 1, 4, 6). Two of the sweep's findings were the same bug, the `denied` decode, and are merged as entry 1. Entry 6's side note found it too.
- 2026-10-31: The fixes are the app's alone. The CLI already prints every fact in `task status` and `task list`'s `total`. The CLI-side fix in this area, a halt or cancel kept while a resume starts up, belongs to the sibling 57u. This item takes that fix as given and links it.
- 2026-10-31: Gated on the CLI's 57u. Entry 7 makes the app's own resume live from the click, so the detail can offer the stops during the resume's startup window. Until 57u ships, a stop sent in that window is acknowledged and then dropped, so the stops there wait for it.

**Open calls:**
- [default: a use reads `tool on target -- authority`, in `task status`'s words: allowed by `grant` "this task's grant", `person` "the person at the terminal", `config` "the config"; denied by `config` "the config denies it", `nobody` "nobody present to allow it", `person` "refused at the prompt"; an unknown `by` is shown bare when allowed and left out when denied, as the CLI does.]
- [default: the Rounds row keeps a short `denied:` (the tools and targets) and the page gains an **Allowed** and a **Denied** section, one row per use with its round, as `task status` prints them. The **Grants** line reads `policy.grants`, or "none" with the CLI's "with nobody present, a tool that asks is denied" when the task has tools.]
- [default: the live **Let through by its grants** section is replaced by **Allowed** from the rounds' `allowed`. `task_grant` lines are kept only for the round in flight, until that round's `task_round` lands.]
- [default: once a run ends, the detail takes the newer of the read and the run's last view by `updated_at`. The run keeps only its **Activity**, its own record of what it said.]
- [default: when `total` exceeds the rows read, the list ends with "The newest 50 of 60 tasks · Show all". Show all re-reads with `--all` and stays on it for the life of the place. The CLI's default read stays the first one, as a person typing `task list` sees it.]
- [default: a refused start or resume raises the place's existing "That didn't work" alert with the stderr tail's last line, the `apogee task: ` prefix kept as the CLI wrote it, and a refused resume's line also stays in that task's **Activity**. A refused new run leaves no row, since the ledger holds no task.]
- [default: while the app's resume of a task is starting, the detail shows "Resuming…" in place of Resume (disabled). Once 57u has shipped, the detail also offers Stop after this round and Stop now in that window, sent as `task halt`/`task cancel <id>`.]
- [default: a run's target task is the id after `task resume` in its arguments, read once at `follow()`, and `task_started`'s `task_id` once it arrives. The row menu's argument match (`interrupted(_:)`) becomes a call to the same lookup.]
- (consumed decision) In machine mode a refusal before the run starts goes to stderr only: the protocol's stdout carries only protocol events (`task_cmd.cpp:61-64`, the machine-mode rule `chat` shares). The app reads it there and asks the CLI for nothing new.
- (consumed decision) A halt or cancel sent while a resume starts up is kept by the CLI. That is [57u](../../../cli/backlog/v0.2.1/task-halt-during-resume.md)'s fix, and this item's gate.

**Guardrail(s).** Each failure pinned as a hermetic test over scripted fakes and recorded documents:
- `task-status-uses.json` decodes each `denied` and `allowed` entry to its tool, target and authority, a bare-string entry kept as a tool. The Rounds row and the sections read `write_file on report.txt -- nobody present to allow it`, never a `{`.
- A resume stream whose `task_started` carries 3 turns, then round 3 alone, leaves the plan, rounds 1-2 and round 3 in `orderedRounds`, through `task_finished` and after.
- A run that ended halted after round 1, followed by a read saying done after round 3, shows the read's reason, checks and rounds. A run in flight still wins over a read it has outrun.
- `task-list-newest-50.json` (`total` 60) yields the footer, and Show all reads `task list --all`.
- A scripted job that ends with exit 1, no `task_started`, and the stderr tail `apogee task: --allow write_file: the config says permissions.write_file: deny -- …` sets `failure` to that line and calls `say`. The same for a resume leaves the line in that task's Activity.
- A read with `policy.grants` and rounds' `allowed`, with no run, draws the Grants line and the Allowed section.
- With one resume's job running and no `task_started` yet, `resumable(id)` is false and a second `resume(id)` starts no job (the scripted starter's call count stays 1).
- Named previews: a denied round, a task's grants and allowed calls, the list past 50, a refused start, a resume starting.

**Acceptance criteria:**
- [ ] A refused tool reads `write_file on report.txt -- nobody present to allow it` in the Rounds list and the Denied section, never as JSON.
- [ ] A task resumed in the app keeps its plan and every earlier round in the Rounds list, during the run and after it.
- [ ] Once the app's run has ended, a fresh read's reason, plan, checks, rounds and grants are what the page shows.
- [ ] With more than 50 tasks, the list says how many exist and Show all lists every one.
- [ ] A start or resume the CLI refuses says why, in the CLI's words, in the alert. A refused resume's line also stays on the task's page.
- [ ] A task's page shows its grants and every call they let through, for a task run from the CLI and after a relaunch.
- [ ] While a resume is starting, the page says so and a second click starts nothing.
- [ ] `lib/scripts/cicd.sh --app darwin --test` is green and the layering check passes.
