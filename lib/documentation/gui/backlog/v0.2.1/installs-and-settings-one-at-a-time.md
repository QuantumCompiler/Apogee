# One install at a time wherever it starts, and Settings recovers, queues and says what is unset

**What / why.** The app runs long or state-changing children from two kinds of place: the media places' runtime installs (Video, Voice, Compose: `apogee train setup`, and since 2026-10-31 its `--rebuild`), and Settings (Health's `check --fix` and `bootstrap`, every pane's one-line change). Each is guarded, but the second CLI/GUI bug sweep (2026-10-31) found the guards checked at the wrong moment, never released, or silently refusing. Two installs can then race on the one Python environment, a failed bootstrap greys Health out until relaunch, a permission change can be dropped without a word, and an unset address reads as blank. Paths below are under `lib/src/darwin/source/`, re-read at HEAD (`b26550bb`) on 2026-10-31.

1. **An install starts without asking whether another runs, so two `train setup` runs share one environment** (regression of 4f `media-studio-finished`'s decision "One install at a time", [MILESTONES.md:1919](../../assistant/MILESTONES.md#milestone-e--the-audits-gui-findings): "While a `train setup` or `bootstrap` runs anywhere in the app, a refusal isn't offered another"; widened by `6632a8b5`, the install sheet's rebuild, MILESTONES.md:2713). The rule is applied only when a refusal becomes a consent: `installElsewhere()` is consulted at `presentation/voice/ViewModels/VoiceViewModel.swift:264`, `presentation/video/ViewModels/VideoViewModel.swift:298` and `presentation/compose/ViewModels/ComposeViewModel.swift:322`, over the registry predicate `AppViewModel.installing(in:)` (`presentation/app/ViewModels/AppViewModel.swift:276-278`, wired at `:170-175`). It is never consulted when the install starts: `install()` guards only its own place (`VoiceViewModel.swift:294` and `VideoViewModel.swift:336`, `guard let consent, let binary, job == nil, installJob == nil`; `ComposeViewModel.swift:350`, `guard let consent, let binary, !isRunning`). It is not consulted either when a failed install raises the rebuild consent (`VoiceViewModel.swift:318`, `VideoViewModel.swift:360`, `ComposeViewModel.swift:374`, `InstallConsent(afterFailed:)`, which becomes `train setup --rebuild --yes --with <set>`, `business/media/MediaRecords.swift:264`). A consent stays on its view-model until used or declined, so one raised while nothing installed is still live when another place's install, or Settings' bootstrap, is running. Settings' `fix(["bootstrap"])` (`presentation/settings/ViewModels/SettingsViewModel.swift:623-634`) never asks the registry at all. The CLI does not stop the second run: `train setup`'s create and rebuild path (`lib/src/cli/source/presentation/cli/train.cpp:2000-2045`) works on the one `env.dir()` and takes no lock (the CLI's only `FileLock` user is the config edit, 55f, `lock_config_file`, `lib/src/cli/source/data/contracts/config_edit.cpp:3420-3432`).
   - Scenario (two installs): no environment yet. Say something in Voice: refused for its runtime, nothing installing, so the consent is raised. Go to Video and generate: refused, consent, Install, so `apogee train setup --with video` runs and creates the environment. Back in Voice, its consent is still up: Install starts `train setup --with voice` beside it. Two environment creates, two pips into one environment at once, and the record's `sets` is whatever the last to finish wrote.
   - Scenario (rebuild): Voice's install fails with M19's refusal, and the app raises `train setup --rebuild --yes --with voice` with no check. Saying Rebuild moves the environment aside while Video's install, or a running clip or composition, is still using its Python.
2. **A failed `check --fix` or `bootstrap` greys out both Health buttons until the app is relaunched.** `fix()` (`SettingsViewModel.swift:623-634`) clears `fixing` only when the run did not fail: `if case .failed(let message)? = status { failure = message } else { fixing = nil }` (`:631`). `fixing` is assigned nowhere else (`:625`, `:631`), and the guard at `:624` (`fixing == nil`) refuses every later fix. `SettingsView.swift:270` keeps both buttons `.disabled(model.fixing != nil)`, and `:271-272` keep showing the dead run's last busy line, for the rest of the session (the view-model is built once, `AppViewModel.swift:176`). The toast at `:632` says `<args> stopped` for a run that failed. No job handle is kept, so there is no Stop. Settings raises no alert: the failure is the inline red line (`SettingsView.swift:42-44`), cleared by the next `refresh()` (`SettingsViewModel.swift:300`), and nothing in Settings calls `dismissFailure()` (`:636`).
   - Scenario: Settings › Health › "Install runtimes and register providers (bootstrap)" while offline. `bootstrap` exits non-zero, which folds to `.failed`, and the toast says `bootstrap stopped`. Both "Fix what can be fixed (check --fix)" and "bootstrap" stay disabled with the old busy line under them, and neither runs again until relaunch.
3. **A Settings change made while another is running is dropped without a word.** Every pane's change goes through `change()` (`SettingsViewModel.swift:603-618`), whose first line is `guard working == nil else { return nil }` (`:604`): no toast, no `failure`. The controls are not disabled while it runs: the permission Picker (`SettingsView.swift:420-427`) calls `setPermission` (`SettingsViewModel.swift:476-479`) on every selection. The Picker's binding reads `entry.level`, so it shows the old level again once the first change's own `refresh()` ends.
   - Scenario: Permissions, set `bash` to deny, then, within the ~200 ms the first `apogee config set-permission bash deny` takes to spawn and exit, set `write_file` to deny. The second call returns at the guard: no `write_file: deny` toast, no error, and `write_file` keeps its old, more permissive level. On a security setting, the person believes a tool is gated when it is not.
4. **An unset web search address shows as blank, not "not set", and Set takes an empty field.** `value(_:_:)` (`SettingsViewModel.swift:440-445`) promises `nil` for a key the config does not set, but returns the trimmed text of any `.done`, and `config get` on an unset key prints an empty line and exits 0. So on a fresh config `webSearch` (`:329`) is `""`, and `Text(model.webSearch ?? "not set")` (`SettingsView.swift:470`) draws an empty row. `memory.recall` uses the same helper but always resolves to a value (`true`), so it is not affected. The Set button (`SettingsView.swift:479`) has no empty guard: it runs `config set tools.search.url ''`, which clears an existing address with no warning and confirms `tools.search.url is ` (`setConfig`'s `done:`, `SettingsViewModel.swift:503`).
   - Probe (the sweep's sandbox): `apogee config get tools.search.url </dev/null` printed an empty line, rc=0; `config set tools.search.url ''` printed `tools.search.url = `, rc=0. Re-run 2026-10-31 on a local build (`lib/src/cli/build/default/source/apogee`) over a scratch `APOGEE_HOME` after `config init`: `config get tools.search.url | od -c` gave `\n` alone, rc=0; `config set tools.search.url ''` printed `tools.search.url = `, rc=0.

What already works: a refusal raised while an install runs anywhere is said instead of offered, at all three places (pinned by `VideoInstallTests.installElsewhere`, `VoiceInstallTests.installElsewhere`, `ComposeStudioTests`); a place never starts a second install of its own; a successful `check --fix` or `bootstrap` clears `fixing` and reads Health again; a change that fails is said in the CLI's words.

**Core constraint(s).**
- **The GUI is a machine-mode client** (GUI `CLAUDE.md`): the app does not reimplement the CLI's environment handling or add a lock of its own to `~/.apogee`. It gates what *it* starts, through the children registry it already keeps; what `train setup` does once started stays the CLI's.
- **One install into the one environment at a time** (4f's decision, kept and now enforced): the check is made when a run *starts*, not only when it is offered, at every start: an install, a rebuild, and Settings' bootstrap. A rebuild also waits for whatever is using the environment's Python.
- **Every change the person makes is either made or said** (this item's rule): no control silently drops an input; a long fix always ends in a state from which it can run again.
- **The four-layer law** ([ADR 0001](../../adrs/layer-enforcement.md)): the registry predicates stay in the composition root (`presentation/app`), passed to each view-model as a closure, as `installElsewhere` is today; no view-model reaches the registry itself.
- **Presentation keeps the MVVM shape** ([ADR 0002](../../adrs/presentation-mvvm.md)): the queue, the guard and the unset reading live in the view-models; the views only bind (`.disabled`, Stop).
- **Every view can be seen on its own** ([ADR 0004](../../adrs/module-schemes-and-previews.md)): a state a person now sees differently (Health after a failed fix, a fix running with Stop, the address unset) has its named `#Preview` over `Previews/` fakes.
- **Development runs on the dev channel** (GUI `CLAUDE.md`): the suite is hermetic; any live pass drives `apogee-dev` over `~/.apogee-dev`, never the release `apogee` or `~/.apogee`, and until M18 ([`app-dev-channel.md`](../maintenance/app-dev-channel.md)) lands a live pass of a development build is asked of the user first.

**Open calls:**
- [default: with another install running, `install()` starts nothing: the toast says `<the running command> is already running: press Install again once it has finished`, and the consent is kept so the sheet's Install works once it has.]
- [default: a failed install's rebuild consent is raised only when nothing else installs; otherwise its command is said, as the refusal path says it today (`<command> is already running: …`).]
- [default: a rebuild consent also waits while a job in the registry runs the environment's Python (`video generate`, `video compose`, `voice say`, `train …`), refused with a toast naming it; a plain install does not wait for those (it adds packages; it does not move the environment).]
- [default: Settings' `bootstrap` asks the same registry; `check --fix` does not (it installs nothing: `apply_fixes`, `lib/src/cli/source/presentation/cli/check.cpp:2805`), and still shares Health's one `fixing` slot with bootstrap.]
- [default: a failed fix clears `fixing`, keeps the CLI's message as the red line, and toasts `<args> failed: <message>`; `<args> stopped` only for a stopped run, `<args> finished` for a done one.]
- [default: Health keeps the fix's job and offers Stop beside its busy line, stopping as the media install cards do (`grace: .seconds(10)`).]
- [default: a change made while another runs is queued and run in order, each with its own toast and read-back; nothing is disabled, nothing is dropped.]
- [default: `value()` reads an empty trimmed result as `nil` (so the row says "not set"); Set is disabled while the field is empty or whitespace. Clearing an address stays out of the pane: the CLI has no `config unset`, and `config set tools.search.url ''` remains a console command.]
- [default: no CLI sibling: a lock on the environment in `train setup` is noted for a later CLI item if wanted; this item closes the app's paths.]

**Guardrail(s).** Hermetic: scripted spawners and fakes, a scripted registry, no binary, no network.
- **Entry 1:** with `installElsewhere` true, each place's `install()` (Voice, Video, Compose) starts no job, says the running command and keeps its consent; a failed install with `installElsewhere` true raises no rebuild consent and says why; a rebuild consent with an environment job in the registry starts nothing. `AppViewModelTests`: the predicates over a registry holding `apogee train setup …`, `apogee bootstrap`, `apogee video generate …`, and Settings wired to them; Settings' `bootstrap` with an install in the registry starts nothing.
- **Entry 2:** `SettingsHealthTests`: a scripted `bootstrap` that exits non-zero leaves `fixing == nil`, `failure` set to the CLI's message, the toast `bootstrap failed: …`, and a second `fix(["check", "--fix"])` starts a job; Stop on a running fix ends it and clears `fixing`.
- **Entry 3:** `SettingsViewModelTests`: two `setPermission` calls, the second made while the first's scripted command is held, both reach the runner in order and both are said.
- **Entry 4:** `SettingsViewModelTests`: a scripted `config get tools.search.url` printing `\n` reads as `webSearch == nil`; `setConfig` with an empty value runs nothing.

**Acceptance criteria:**
- [ ] With an install running anywhere in the app, no place starts a second `train setup`, whether from a consent raised earlier, a rebuild offer or Settings' bootstrap; each says what is running.
- [ ] A rebuild never starts while a clip, composition, speech or training job uses the environment.
- [ ] After a failed `check --fix` or `bootstrap`, both Health buttons are enabled again, the toast says it failed and why, and a running fix can be stopped.
- [ ] Two Settings changes made in quick succession both land and both are said; `write_file: deny` set straight after `bash: deny` is in the config.
- [ ] On a fresh config the Web search address row says "not set", and Set does nothing on an empty field.
- [ ] The full darwin suite and the layering check are green.
