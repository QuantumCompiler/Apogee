# The Sessions place reads the binary it runs, current and in order

**What / why.** The Sessions library is where the app finds the binary, learns what it can do, and reads the list, the inspector and recall for every other place. The second bug sweep (2026-10-31) found five ways it acts on something stale. A binary that Try again finds is never adopted, so the chat works while the library and every other place stay binary-less. A failed recall read keeps the old listing, so Forget's question names summaries from an earlier read. A saved chat's Compact… is killed at 60 s though it runs a model turn. A re-ask in flight lets a second place change run ahead of it. And the inspector's Roles come from the default suite, not the session's own. Each was re-read at HEAD the same day. Line numbers are as they stand now, under `lib/src/darwin/source/` unless the path says otherwise.

1. **A binary found by Try again is never adopted.** When nothing is found at launch, `SessionLibraryViewModel.start(inView:)` (`presentation/sessions/ViewModels/SessionLibraryViewModel.swift:251-262`) takes the `.notFound` case at :258: it sets `listing = .missing`, opens a new session and returns with `found` unset. The window's Try again is `MissingBinaryView(hint:places:retry: model.start)` (`presentation/session/Views/SessionWindow.swift:21`), which is `SessionViewModel.start()` (`presentation/session/ViewModels/SessionViewModel.swift:355`). Its `connect` (:393-410) locates and connects on its own, then calls `onLocated?(located)` (:401). The library's `onLocated` (`SessionLibraryViewModel.swift:778-782`) handles only `outcome.skippedOverride`. It never adopts the binary it was handed. The chat connects and answers, but every library read and act returns silently on `guard let found`: `refresh` (:403), `readModels` (:423), `readWindow` (:442), `refreshRoles` (:461), `rename` (:926), `delete` (:955), `compact` (:1026), `refreshRecall` (:1049) and `forgetRecall` (:1109). None of them shows a toast. The list keeps saying "Apogee isn't installed, so there are no sessions to list." (:1141), and `checkBinary` (:389) does nothing. Every other place keeps the nil binary that `AppViewModel.start()` (`presentation/app/ViewModels/AppViewModel.swift:294-316`) handed it once from `sessions.binaryURL`: Models, Stored weights, Downloads, Tasks, the monitor, the console, Suites, Graph, Knowledge, Training, Library, Review, Video, Compose, Voice and Settings. A private session needs the binary too. On a binary that uses the `--no-recall` private fallback, `deletePromised(of:)` (:802-815) guards on `let found` (:803) and returns nil, so the promised delete never runs. The private chat stays on disk, and the quit log reports no failure. This lasts until the app relaunches or the window's `.task { await model.start() }` (`presentation/app/Views/ApogeeApp.swift:87`) runs again. MILESTONES 4c names this path ("A session that locates for itself reports it through `onLocated`", [MILESTONES.md:1706](../../assistant/MILESTONES.md#milestone-e--the-audits-gui-findings)) but adopts only the override. *Scenario:* launch with no `apogee` installed. Install it and press Try again. The chat answers. The sidebar still says Apogee isn't installed, Rename and Delete do nothing, and Models, Tasks and Settings have no binary.

2. **A failed recall read keeps the old listing, so Forget's question is stale.** In `refreshRecall()` (:1048-1071), `.document` sets `recallListing` and `recall`, and `.text` sets `recallListing = nil`. But `.failed(let why)` (:1065-1066) sets only `recallFailure = why`, so the last listing and count line stay. The inspector is handed both `recallFailure` and `recallListing?.summaries` (:1190-1191), and it draws the old count and the old summary list next to the new failure (`presentation/sessions/Views/SessionsScreen.swift:196`). `canForgetRecall` (:1083-1086) is `recallListing?.holdsAny ?? true`. `askToForgetRecall()` (:1091-1096) re-reads, then asks on that stale value. `forgetRecallMessage` (:1100-1103) builds "These go: …" from the same stale listing. So, if the last good read named two summaries and this read fails, the question reads `These go: 2 chat summaries: "A" and "B"`, while `--forget --yes` erases whatever recall holds now. If the last good read was empty, Forget stays disabled however many summaries exist now. Settings handles the same failure the other way: `readRecallHolds` (`presentation/settings/ViewModels/SettingsViewModel.swift:393-411`) clears both values on `.failed` (:407-409), so the two screens disagree. This is a **regression of GUI M15** (`reads-become-documents`): "With recall read as a count, Forget erased summaries no one had seen", and "Forget's question says how many and names them, and is disabled when nothing is held" ([MILESTONES.md:2608-2612](../../assistant/MILESTONES.md#milestone-e--the-audits-gui-findings)). Both hold only while the read succeeds. Low severity: the question and the list are misleading, but no wrong data is erased.

3. **A saved chat's Compact… is killed after 60 s.** For a saved chat that is not the live session, `compact(_:)` (:1025-1042) runs `chats compact <id> --yes` through the library's `runner.command` (:1032). That is `ReadRunner` with its default `timeout: Duration = .seconds(60)` (`business/reads/ReadRunner.swift:19-26`), passed to `spawner.capture` (`business/reads/CommandRunning.swift:71-80`). `CapturedRun` terminates the child at the timeout and kills it 2 s later (`infrastructure/process/CapturedRun.swift:20-36`). Compaction is a full summarising model turn over the chat's history (CLI `source/presentation/cli/chat_history.cpp:443-476`, then `compact_conversation`, :561-567, on the utility role's backend). On a local backend with a long history it can run past 60 s. The GUI then kills it and toasts `Not compacted: … it did not finish within 60.0 seconds` (`CommandRunning.swift:108`, a `Duration` said as Swift prints it). Because the CLI saves only after the compaction succeeds, the chat is left as it was. Nothing is corrupted. But a chat large enough can never be compacted from the app, and every retry fails the same way. No backlog item or MILESTONES decision covers this. The only 60 s bound the docs record is for the graph's acts, and the docs give long children to `SupervisedJob`.

4. **A re-ask in flight lets other place changes run ahead of it.** When the binary's fingerprint has changed (a `make install` under the running app), `learnCapabilities()` (:370-382) first clears `lastAccepts`, `lastEvents` and `lastSchema`, then sets `askedOf` (:375), then awaits `__machine-schema` (:376). A place change made while that read is in flight passes `checkBinary()` (:388-391) at once, because the fingerprints already match. Two things then go wrong. (a) Every place change is its own unordered `Task` (`AppViewModel.swift:213-219`), so the second change's `cameIntoView()`/`leftView()` (:218; `SessionLibraryViewModel.swift:278-304`) can run before the first change's. Example: click Sessions (task A suspends in `__machine-schema`), then Tasks within ~100 ms. Task B runs `leftView()` at once, and the session is already paused, so nothing happens. A then finishes and runs `cameIntoView()`: `inView = true` and `current.resume()` starts a session child while Tasks is on screen. Nothing pauses it until the next place change. (b) Anything that reads the flags in that window sees them as unknown (`lastSchema = nil`): `streamsJobs`, `hasTrack52`, the vocabulary, and the jobs' `streams` closures (`AppViewModel.swift:88, 157, 162, 169`). For instance, a pull started then runs without `--output-format stream-json` and shows no byte progress, though the binary streams. The intent is stated in the code at `AppViewModel.swift:215-216`: "A binary changed under the app is asked again before the place it opens reads or runs anything (GUI 4k)". This is a **regression of GUI 4k** (`settings-sessions-graph-parity`): capabilities are known from launch, and the read "runs again whenever the binary's file changes, … checked on every place change" ([MILESTONES.md:2265](../../assistant/MILESTONES.md#milestone-e--the-audits-gui-findings)). Low severity.

5. **The inspector's Roles ignore the session's suite.** `refreshRoles()` (:460-469) always reads plain `models status` (:462) and sets `roles = Field.list(from: document)`. The inspector passes those roles on (:1189), and they are drawn as the Roles section (`SessionsScreen.swift:180`). `models status --help` says: `--suite MODEL_SUITE_OR_OFF  Resolve under this suite instead of models.default_suite, or off for none`. So a session run bare (`chat --suite off`), or under a suite other than the default, is shown the default suite's roles. Since M13, the same inspector also shows the session's own Suite line (`suite: current.suiteFact`, :1193). Those two disagree on screen: `Suite: none` above Roles rows that say `(via suite duo)`. Because the JSON's `fields` include them, the default suite's `suite` and its multi-line `footprint` are drawn as Roles rows too. *Probe (sandbox, `models.default_suite = duo`, utility m2):* plain `models status` gives `utility: m2   (via suite duo)`, while `models status --suite off` gives `utility: (unset -- the chat's own backend)` and has no `suite` or `footprint` field. A session under `--suite rich` is shown duo's members in the same way.

What already works: the chat itself connects through Try again (finding 1). A successful recall read lists, names and gates Forget correctly (finding 2). A live session's Compact runs in its own session, untimed, by the protocol's `compact` line (finding 3). A place change with no binary change asks nothing and runs in order (finding 4). The Suites place already reads `models status --suite <name>` (`presentation/suites/ViewModels/SuitesViewModel.swift:126`), which is the precedent for finding 5.

**Core constraint(s).**
- **The GUI is a machine-mode client** (CLAUDE.md): roles, recall and compaction are what the CLI states, read through its own verbs and flags (`models status --suite`, `chats recall`, `chats compact`). The app never computes them itself.
- **Long children are supervised** (the Codebase Map's `jobs`: "the one supervisor of every long child"): a run that drives a model is never a bounded read. Every child stays registered in `ChildRegistry`, so the monitor sees it and quit stops it (4c).
- **Capabilities are known before a place reads or runs** (GUI 4k): no place runs on the fallback while the binary that is there can do more.
- **A private session's promise is kept** (4a): the private fallback's delete runs whenever a binary is there to run it.
- **The four layers and MVVM** (ADR 0001, ADR 0002): the fix stays in the view-models and the composition root. View-models stay SwiftUI-free.
- **Hermetic tests** (CLAUDE.md → Implementing a Feature): scripted fakes and recorded documents. No `apogee` binary, no network.
- **Development runs on the dev channel** (CLAUDE.md): any live pass drives `apogee-dev` over `~/.apogee-dev`, never the release `apogee` or `~/.apogee`. Until GUI M18 ([`app-dev-channel.md`](../maintenance/app-dev-channel.md)) ships, no development build is launched on the user's machine without asking.

**Seam + files.**
- `source/presentation/sessions/ViewModels/SessionLibraryViewModel.swift`:
  - `onLocated` adopts a found binary when the library has none, or a different one. It sets `found`, learns the capabilities, refreshes the list and the models, and hands the binary up (finding 1).
  - `refreshRecall`'s `.failed` clears `recallListing`, `recall` and `recallSelection` (finding 2).
  - `compact(_:)` runs a saved chat's `chats compact <id> --yes` as a supervised job, with no read timeout (finding 3). The library is handed the app's `JobStarter`.
  - `learnCapabilities`/`checkBinary` hold the ask in flight, so that every `checkBinary` awaits it rather than returning early (finding 4).
  - `refreshRoles` reads `models status --suite <the session's suite>` where that suite is known, and re-reads when the suite changes (finding 5).
- `source/presentation/app/ViewModels/AppViewModel.swift`:
  - a binary the library adopts later is handed to every place, by the same `connect`/`use` sequence `start()` runs (finding 1);
  - place changes are applied in order, one after another (finding 4).
- `source/presentation/settings/ViewModels/SettingsViewModel.swift`: only if Forget's question for a failed read gets shared wording. Its `.failed` handling is already the target behavior.
- Tests, mirroring the source tree:
  - `tests/presentation/sessions/` (`OverrideSkippedTests.swift`'s Try-again path, `ReadsAsDocumentsTests.swift`, `SavedChatActsTests.swift`, `CapabilitiesTests.swift`, `SuiteInspectorTests.swift`, over `Scripted.swift`);
  - `tests/presentation/app/` (`AppViewModelTests.swift`, `CapabilitiesFromLaunchTests.swift`);
  - `tests/presentation/settings/RecallForgetTests.swift`, if the shared wording lands.
- Docs: the GUI `MILESTONES.md` entry. The Codebase Map's `sessions` line, if the library takes the jobs starter.

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item, because all five are the Sessions library reading or acting on something stale (a binary it never adopted, a listing from an earlier read, a timeout meant for reads, a capability set mid-ask, the default suite's roles). All five are in one view-model and its composition root, and their tests share `Scripted.swift`.
- 2026-10-31: GUI-only. Each finding is the app's use of a CLI verb that already says the right thing: `models status --suite`, `chats recall`'s failure, and `chats compact` saving only on success. No CLI sibling is needed.

**Open calls:**
- [default: a binary found by a session's own locate is adopted whenever the library has none or has a different one. Adopting it runs `learnCapabilities`, `refresh` and `readModels`, then hands `binaryURL` to every place in `AppViewModel` through one `binaryAdopted` callback, with the same sequence `start()` runs. A private session's promised delete then runs on the adopted binary.]
- [default: a failed `chats recall` read clears the listing, the count line and the selection on both screens. The inspector shows the failure alone. Forget stays offered, because the CLI says "nothing to forget" itself, and its question says recall could not be read in place of "These go: …". The two screens use one wording.]
- [default: a saved chat's Compact… runs as a supervised job on the jobs core. It has no read timeout, is registered in `ChildRegistry`, is shown busy in the row, and can be stopped by an interrupt. Its last line or its failure is toasted, and the list and Details are read back. A longer fixed timeout was considered and rejected: no bound fits every chat and every backend.]
- [default: the ask in flight is kept as a task that every `checkBinary` awaits. Place changes are applied one after another, through a chain where each awaits the one before it, so the last change made is the one in force.]
- [default: Roles read `models status --suite <name>` for a named suite, or `--suite off` for none. The suite is the session's `runningSuite`: the `session` event's word, else the launch's flag. Plain `models status` is read only where the suite is unknown. Roles are read again when the session's suite changes (`/suite`, the header, a `session` event). The `suite` and `footprint` fields are not drawn as Roles rows, since the Suite line already says the suite.]

**Guardrail(s).** Each failure is pinned as a regression test over scripted fakes: `Scripted.swift`'s locating starter, a scripted `CommandRunning`, a scripted `JobStarter`, and recorded `chats recall` and `models status` documents. No binary, no network.
1. **Try again adopts the binary.** Launch on `.notFound`, then a session's own locate finds a binary. Pin that the list reads, rename and delete run, and every place in `AppViewModel` holds the binary. Pin that a `--no-recall` private session's promised delete runs `chats delete <id>`.
2. **A failed recall read clears the listing.** A two-summary listing, then a `.failed` read. Pin that the inspector has no summaries, that Forget's question contains no "These go", and that an earlier empty listing does not keep Forget disabled.
3. **Compact is a job.** Pin that a saved chat's Compact… starts a supervised job whose argv is `chats compact <id> --yes`. Pin that no 60 s timeout applies, and that a job stopped or failed toasts "Not compacted" in the CLI's words.
4. **Place changes wait for the ask.** A changed fingerprint whose `__machine-schema` is held open while Sessions is chosen, then Tasks. Pin that `cameIntoView` and `leftView` run in that order, that the session ends paused, and that `streamsJobs` is known before Tasks reads.
5. **Roles follow the session's suite.** A session on `--suite off`, then one on `--suite rich`. Pin that `models status --suite off` and `models status --suite rich` are read, that the Roles rows hold no `(via suite duo)`, `suite` or `footprint` row, and that a `/suite` switch reads Roles again.

**Acceptance criteria:**
- [ ] After Try again finds a binary, the Sessions list is read, Rename, Delete, Compact, Info, recall, models and capabilities all work, and every other place has the binary. A private session's promised delete runs.
- [ ] A failed recall read never leaves an earlier read's summaries on screen or in Forget's question, and never keeps Forget disabled on an earlier empty read. The inspector and Settings agree.
- [ ] A saved chat's Compact… is never killed at 60 s. It runs as a supervised job, can be stopped, and is said in the CLI's words.
- [ ] After the binary changes, a quick second place change never resumes a session off screen, and never runs a place on unknown capabilities.
- [ ] The inspector's Roles match the session's Suite line: a bare session shows no suite's members, and a session under another suite shows that suite's.
- [ ] The full suite is green (`lib/scripts/cicd.sh --app darwin --test`), and so is the layering check.

**Scope note.** Earmarked for v0.2.1 (track 6). Ungated. Out of scope: the CLI's own compaction speed; the graph acts' 60 s bound, which is recorded and stays; Settings' recall screen beyond sharing Forget's wording; and the place changes' own reads, which each place owns.
