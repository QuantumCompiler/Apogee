# A session keeps its own chat, its lines and its answers through restarts, deaths and quit

**What / why.** The second CLI/GUI bug sweep (2026-10-31) found eight places where the session window and the Sessions library lose track of what is happening when a child stops, restarts, dies or is given up on. Each one survived a three-lens skeptic panel. In each, the app says one thing and the conversation on disk or in the child says another: a session takes a chat that isn't its own (and a private one deletes it), a message is drawn as sent but never reaches a child, an answer streams forever, quit leaves a child running with no signal, and a suite switch on a new chat's first turn says the turns are lost when the CLI has saved them. Every case is on a path the app ships for an older binary or for a child that dies, and that is the path the person can least see. Re-verified at HEAD (`b26550bb`), 2026-10-31. Paths are under `lib/src/darwin/source/presentation/` unless given in full.

1. **An older binary's new or private session adopts an unrelated chat, and the private one then deletes it.** `identifyNewSession` (`sessions/ViewModels/SessionLibraryViewModel.swift:488-502`) takes the single non-empty chat that has appeared since `listedBeforeNew` as the open session's own. It runs on every `refresh()` (`:412`), including `cameIntoView` (`:278-289`), and never checks that the open session has sent or been answered. `SessionViewModel.identify` (`session/ViewModels/SessionViewModel.swift:326-333`) then keeps that id for good. Scenario: on a binary from before the CLI's M28 (any v0.1.x), press Shift-Cmd-N, so the private fallback runs `chat --no-recall`, and send nothing. In a terminal, hold a conversation with `apogee chat`, which writes chat T with turns > 0. Come back to Sessions: `appeared == [T]`, so `identify(T)` sets `chatID = T` and `isSaved = true`. T disappears from the sidebar, because `groups` filters out `current.chatID` (`:1132`). The private session's own chat P is never identified, because `chatID` is already set. A pause and resume relaunches with `--resume T --no-recall` (`SessionViewModel.swift:412`), carrying on the terminal conversation. On close, `deletePromised` (`SessionLibraryViewModel.swift:802-815`) runs `chats delete T`, the user's unrelated conversation, and P stays on disk. An ordinary new session on a pre-M28 binary gets the same wrong guess without the delete: Rename, /delete and the next launch's reopen (`preferences.openChat`, `:499-501`) all act on T. The delete happens only on binaries from before the CLI's 52d (2026-10-20), which use the `--no-recall` fallback. The wrong guess happens on any binary from before M28 (2026-10-24). It contradicts GUI MILESTONES M10's "Without `chat_id`, the guess is made right" (`MILESTONES.md:475`). No `SessionIdentityTests` case (`tests/presentation/sessions/SessionIdentityTests.swift:79-284`) covers an outside chat appearing while the session is unsent. The closest, `emptyChatPassedOver` (`:143`), covers only an empty one.
2. **A suite switch queued during a new chat's first turn says the conversation can't be carried on, and may drop it, though the CLI has saved it.** When the first answer's `result` arrives, the loop calls `heard(event)`, then `releaseHeld()`, then `observer?(event)` (`SessionViewModel.swift:456-461`). `releaseHeld` starts `Task { await moveSuite(...) }` (`:711-713`). The observer's `turnEnded()` starts the library's `refresh` as a separate `Task` (`SessionLibraryViewModel.swift:899-901`). `moveSuite` runs first, while `savedChatID` is still nil: `isSaved` is set only by `identify`, from `identifyNewSession` inside `refresh`. `hasTurns` is true, so `saysItself` (`SessionViewModel.swift:758-759`) is false, and the transcript gets "switching to suite fast -- ... the earlier turns can't be carried on: this session isn't in the saved list". `moveSuite` writes that line before any await, so it is wrong every time. `restart()` then waits for the child to stop and checks `if savedChatID == nil` (`:688`). If `chats list` hasn't come back by then, `forgetUnsaved()` and `transcript.restarted()` drop the first turn, the child relaunches with no `--resume`, and chat X, already written by the CLI, is left as an orphan in the list. This happens on M28/M29 binaries (schema `2026-10-26`) and on binaries before M28, since both learn that a chat is saved only from the list. `SuiteSessionTests.switchHeldMidTurn` (`tests/presentation/session/SuiteSessionTests.swift:139-153`) covers only a resumed chat (`ChatLaunch(resume:)`), never a new chat's first turn. Not probed live, because no live pass is allowed until M18. Regression of GUI M10 (`session-label-follows-its-chat`): "Named versus written" (a chat is saved once a turn is answered and the list says so, `MILESTONES.md:474`), and M13's suite-switch line logic (the app's line stays only "for an unsaved conversation with turns", `:2515`).
3. **A turn or line sent while a restart or pause is stopping the child is silently lost, though it is drawn as sent or applied.** `restart()` (`SessionViewModel.swift:679-694`) and `pause()` (`:538-549`) set `pausing = true` and wait in `session.stop(grace:)` for up to the 5 s grace, with no status change first. During that wait the transcript still says ready and the outbox is still there, so `canSend` (`:569-572`, `acceptsInput && outbox != nil`; `Transcript.swift:94`, `status == .ready`) keeps Send enabled (`session/Views/InputBar.swift:51`), and `takesLinesNow` (`:609-615`) still takes lines. But `MachineSession.stop` has already called `close()` (`lib/src/darwin/source/business/session/MachineSession.swift:193-197`, `inputClosed = true`), so `write` throws `notRunning` (`:224`), and `Self.write` hides the error with `try?` (`SessionViewModel.swift:497-509`). Scenario: on a 52d binary, move the open session to another suite (`moveSuite` → `restart`); on a binary without `set`, change the model; or, on a pre-55b binary, rename the open chat (`rename` → `pause`). While the old child saves and unloads, type a message and press Send. `userSent` draws the user row and the status turns working. The `user` line is dropped at the closed input, and `.ended` (pausing) then gives `paused()` and `reopening()`. The message stays in the transcript, never answered, with no error. An attach in that window shows a chip for a file the model never got. A detach removes a chip while the resumed child still holds the attachment, and `reopening()` doesn't put the chips back, so it can't be detached again. A `set` is the exception: `sendLine` merges it into `launch.settings` (`:824-828`) before `beginLaunch`, so the relaunch carries it.
4. **Quit gives up at 5 s just before the stop's own SIGTERM, so a child that won't end usually gets no signal before the app exits.** `quit()` (`SessionLibraryViewModel.swift:332-339`) waits for `session.shutDown()` with `finishes(within: SessionViewModel.grace)`. `finishes` (`:343-357`) starts its timer `Task` (`clock.sleep(for: limit)`) before the work `Task` that calls `shutDown`. `shutDown` (`SessionViewModel.swift:515-521`) then starts `session?.stop(grace: Self.grace)` (`grace` = 5 s, `:150`). `MachineSession.stop` (`MachineSession.swift:202-213`) computes its own 5 s deadline only when it runs, and `ends(within:)` (`:215-221`) checks it in 20 ms sleeps before `child.terminate()`. So the library's timer always fires first. Scenario: a turn is running on a local model that doesn't respond to cancel or EOF promptly, for example during prompt processing. Press Cmd-Q. Cancel is written and stdin closed. At t = 5.000 s the library's timer gives up. For a non-private session, `deletePromised` returns without suspending. `Termination` (`app/ViewModels/Termination.swift:86-99`) logs "given up so the app can quit -- its stop still escalates", and with no jobs `stopping` is already true, so it calls `answer()` at once and AppKit exits within milliseconds. The actor's check would reach its deadline only at about 5.0–5.02 s. The child, and its process group holding gigabytes of model memory, is left running with no signal. The race is lost only when quit has nothing else to wait on: a private session's `chats delete`, or running jobs (`stopJobs`, `jobGrace` 3 s, `Termination.swift:37`), give the actor time to send the SIGTERM. That leaves the common case, an ordinary session with no jobs. Regression of GUI MILESTONES 4a (`private-sessions-survive`), whose decision reads "A child still alive at 5 s gets its escalation's SIGTERM" (`MILESTONES.md:1610`).
5. **An answer whose child dies mid-stream shows as streaming forever, so its held-back last line never shows.** `Transcript.apply(.ended)` (`session/ViewModels/Transcript.swift:317-323`) and `paused()` (`:165-170`) never call `finishAnswers` (`:562-571`). An answer still open when the child dies keeps `finished == false`, and `TranscriptRow` (`session/Views/TranscriptRow.swift:29`) keeps drawing it with `streaming: true`. That breaks the promise in `MarkdownDocument` (`styles/Components/MarkdownDocument.swift:31`, "never past its next line"). Scenario: a local model streams `Totals:\n| Q1 | 42 |`, and the child crashes, is OOM-killed, or is killed when a Stop's grace runs out. No `result` or `error` arrives, only `.ended`. The window shows only "Totals:", and the row the model wrote stays hidden for the rest of the session, including after a resume, which opens a new range, because a live row is never read again from history. Probed by compiling `MarkdownDocument.swift` into a harness: `S: "Totals:\n| Q1 | 42 |" => "P(Totals:)"`, and `The steps:\n1.` gives `P(The steps:)`. Only a little is hidden. A last line made only of markers (`1.`, `---`, a fence, `#`) is held back, and so is a last line that starts with a pipe. The pipe-led row is the real content lost. Regression of GUI 4d (`markdown-code-edges`): "Hold-back is bounded, streaming only" (`MILESTONES.md:1764-1774`), where any next line ends the hold (`:1772`) and the code promises "never past its next line" (`MarkdownDocument.swift:31`).
6. **Lines held for a turn that ends in the child's death keep saying "Sent when this turn ends", and Start again drops them without a word.** `releaseHeld` (`SessionViewModel.swift:704-714`) has `guard !held.isEmpty, takesLinesNow`. `Transcript.apply(.ended)` has already set the status to ended, and the loop then sets the outbox to nil (`:463-464`), so a death mid-turn never releases what was held. The strip (`session/Views/SessionExtras.swift:127-129`) and the settings sheet's starting values (`intendedSettings`, `:619-623`) keep showing those lines. The ended card's Start again / Try again calls `start()`, which sets `held = []` (`:367`) and relaunches on `launch.settings`, which a held `set` never updated. Scenario: while a turn runs, switch the model to X in the settings sheet. The strip says "Sent when this turn ends: model X". The child dies mid-turn. Press Try again: the conversation goes on with the old model while the person believes X was applied. Pause/resume and `restart()` keep `held` and release it on the new child, so only `start()` loses it. GUI MILESTONES 4b says held lines "go in order once the status is ready" (`MILESTONES.md:1645`).
7. **A rename made while a close is in flight runs `chats title` while the old child is still alive, so a pre-55b binary writes its own title back.** `rename` (`SessionLibraryViewModel.swift:924-945`) computes `pauses = chat.id == session.chatID && session.isLive && !keepsOutsideRenames` (`:928`), then calls `await session.pause()`, then `chats title`. `pause()` (`SessionViewModel.swift:538-539`) says it "Returns once the child has gone", but it begins `guard !isShutDown, ...`. Once `shutDown` (`:515-521`) has set `ending`, `pause()` returns at once, and `isLive` (`:528`) stays true while `session != nil`. Scenario: on a pre-55b binary (schema before `2026-10-25`), rename the open chat mid-turn. `renameWhenIdle` is set and the app says "Renaming when this turn ends". Then click another chat and confirm "Stop the turn and switch". The cancelled turn's `result` calls `turnEnded`, which runs the waiting rename after `refresh` (`SessionLibraryViewModel.swift:899-906`). `session` is still `current`, because `replace` is waiting in `closeCurrent` (`:706-712`), so `pauses` is true. `chats title` lands while the child is still in its exit save: `title.settle` then `save_if_changed()` (`lib/src/cli/source/presentation/cli/chat_session.cpp:1815-1816`), which older binaries ran as an unconditional `logger::save`. The child's save puts back the old title. The toast says "Renamed to X", and the next list read shows the old name. A rename from the sidebar made just after confirming a switch does the same. Regression of GUI MILESTONES 4b (`session-lines-honest`): "A rename sticks ... An older binary: the open session is paused, renamed and resumed" (`MILESTONES.md:1652-1654`).
8. **Quit deletes the `--no-recall` private chat while a child it gave up on may still be running, and that child can write the chat back on its exit.** `quit()` (`SessionLibraryViewModel.swift:335-336`) runs `deletePromised` straight after `finishes` returns, even when `ended == false`. `closeCurrent` (`:791-796`) waits for the whole `shutDown` first. The actor's SIGTERM can come up to about 20 ms later (finding 4), and the delete takes about 10 ms. Fallback binaries date from before 52d, so also from before 55b. Such a binary saves on a cancelled turn's rollback (`cancelled_result`: `session = before; logger::save(session)`, `chat_session.cpp:1716-1718` in today's form, before the `result` is sent) and recreates a deleted chat (CLI MILESTONES 55b). Scenario: on a pre-52d binary, a private session runs a slow local turn. Press Cmd-Q. Cancel and EOF are sent, the child is still busy at 5 s, quit gives up, `chats delete <id>` succeeds, and the app exits. The child finishes rolling back the cancelled turn, saves its chat and exits. The private conversation is back in `chats list`, the quit log reported success, and nothing is left to delete it. The window is narrow: the child must save between the delete and the SIGTERM, or the app must exit before the SIGTERM check runs (finding 4 makes that the usual outcome). A SIGTERM that lands kills the child without a save. The window still says "deleted when you close it" (`SessionViewModel.swift:318`).

What already works: a session that names its chat (`chat_id`, M28 on) is identified by that id and never by a guess (`namedAtOnce`). Pause/resume and `restart()` keep held lines and release them on the new child. A held `set` made before a restart reaches the relaunch through `launch.settings`. Quit is bounded by the session's grace and the backstop (`Termination.swift:32`). An `answerEnd`, `result` or `error` finishes the turn's answers (`Transcript.swift:431`, `:445`, `:468`).

**Core constraint(s).**
- **The GUI is a machine-mode client** (GUI `CLAUDE.md`): cancellation is the protocol's `cancel` line, and termination happens only through `stop`'s escalation, never as a first resort. Finding 4's fix makes sure the escalation actually runs before the app exits. It does not add a new kill path. The app never infers what the CLI saved: M10's rule stands, "learned from the list, not inferred".
- **Older binaries are driven as faithfully as current ones** (the protocol grows additively, the CLI's ADR 0006). Every fix here is on an older binary's path or on a dead child's path. A current binary's behavior stays the same.
- **One live child** (GUI 4a): a session's child and the next one never overlap. Holding lines across a stop must not open a second child.
- **The transcript says what happened** (GUI 4b): a line drawn as sent was sent, or the transcript says it was not; the held strip shows only what will still be sent.
- **The four layers** (ADR 0001) and **MVVM** (ADR 0002): the fixes live in `SessionViewModel`, `SessionLibraryViewModel`, `Transcript` and `MachineSession`, and the view-models stay SwiftUI-free.
- **Development runs on the dev channel** (GUI `CLAUDE.md`): any live pass drives `apogee-dev` over `~/.apogee-dev`, never the release `apogee` or `~/.apogee`, and until M18 ([`app-dev-channel.md`](../maintenance/app-dev-channel.md)) lands, no development build of the app is launched for a live pass without asking the user. The guardrails are hermetic.

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item, because the eight findings share one seam and one failure shape: the session's lifecycle across a stop, a restart, a death or quit (`SessionViewModel`'s stop paths, the library's identify, close and quit, the transcript's end), where the window or the list goes on stating something the child or the disk no longer matches. Built together, they share one set of scripted-session fixtures (a slow stop, a death mid-turn, an outside chat appearing).
- 2026-10-31: All eight are the app's own: the CLI's behavior on each path is what its older binaries do and will keep doing, so none needs a CLI sibling. Findings 1, 7 and 8 matter only on binaries from before M28, 55b and 52d. They are fixed anyway, because the app supports those binaries (each guess and pause exists for them).

**Open calls:**
- [default: finding 1. On a binary without `chat_id`, the library guesses only once the open session's own turn has been answered (a `result` heard on it), and only a chat that appeared since then whose `turns` equals the turns the session has had answered. An outside chat that appears while the session is unsent, or doesn't match, is passed over, and two candidates still name none.]
- [default: finding 2. The held suite move decides "carried or not" only after the library's post-turn `chats list` read has run its identify: `releaseHeld` hands the move to the library, which runs it after `refresh`. Nothing is inferred from the `session` event's `chat_id` alone.] (consumed decision: M10's "learned from the list, not inferred" stays.)
- [default: finding 3. `pause()` and `restart()` set a stopping status before they wait. Send turns off and the input says the session is restarting. An attach, detach, set or compact made in that window is held and released on the new child, as a line held mid-turn is. A `user` write that fails anyway is shown as not sent, with Retry offered, instead of being hidden by `try?`.]
- [default: finding 4. On giving up, quit has the stop's escalation send its SIGTERM at once (a `MachineSession` call that runs the escalation's terminate step now, the same step `stop` would take at its deadline), and `Termination` replies only after it. The 5 s bound and the decision not to wait for the 7 s SIGKILL (4a) stay as recorded.] (consumed decision: 4a's quit bound.)
- [default: finding 5. `.ended` and `paused()` mark every open answer finished, in every range, so the held-back last line is drawn.]
- [default: finding 6. `start()` keeps `held` and releases it on the new child's ready, as resume and restart do. A held `attach` whose path is no longer there is said in the CLI's words when it is sent.]
- [default: finding 7. `pause()` on a session already shutting down waits for its `ending` (the child gone) instead of returning at once, so a rename made during a close lands after the child's exit save.]
- [default: finding 8. Quit runs the promised delete only after finding 4's SIGTERM. When the child had not ended at the give-up, the quit log says so ("the private session was deleted while its child was ending; an older apogee may write it back"). Keeping the id for a delete on the next launch is out of scope unless a pass shows the write-back happens.]

**Guardrail(s).** Each finding's failure is pinned as a regression test over scripted sessions and runners and recorded documents: no binary, no network, no window.
- Finding 1: an unsent pre-M28 session, plain and private, with an outside chat with turns appearing in `chats list`. The session stays unidentified, the chat stays listed, and the private close deletes only its own chat (found once it appears), never the outside one.
- Finding 2: a new chat's first turn under a suite, with the switch held until `result`. No "can't be carried on" line, and the relaunch carries `--resume` with the chat the list names, including when the list read answers after the child has stopped.
- Finding 3: a scripted child whose stop takes a moment. During it, `canSend` is false and the status says stopping. An attach, detach or compact made then reaches the second child, and no user row stays unanswered without a "not sent" mark.
- Finding 4: a child that ignores cancel and EOF, with no jobs and a non-private session. The give-up's SIGTERM is recorded before `Termination` replies (`MachineSessionTests`, `TerminationTests`).
- Finding 5: an answer streaming `Totals:\n| Q1 | 42 |`, then `.ended` with no `result`. The answer is finished and the row is drawn. Likewise for `paused()`.
- Finding 6: a `set` held mid-turn, then a death, then Start again. The new child is sent the change (or launched with it), and the strip is empty once it is sent.
- Finding 7: a pre-55b schema, a rename waiting on a turn, and a switch confirmed. `chats title` runs only after the old child's stop has returned.
- Finding 8: a pre-52d private session given up on at quit. `chats delete` runs only after the SIGTERM.

**Acceptance criteria:**
- [ ] A new or private session on an older binary never takes as its own a chat written elsewhere. The private session's close deletes only its own chat.
- [ ] A suite switch held over a new chat's first turn carries the conversation on and says so. The CLI's saved chat is never left as an orphan.
- [ ] While a pause or restart stops the child, Send is off and the window says why. A line made then reaches the new child, or the transcript says it was not sent.
- [ ] Quit never exits with a given-up child left unsignalled. The 5 s bound holds.
- [ ] A child's death mid-answer leaves the answer finished, every line the model wrote drawn.
- [ ] A line held when the child dies is sent on Start again, never dropped silently. The strip shows only what will still be sent.
- [ ] On a pre-55b binary, a rename made while a close is in flight sticks.
- [ ] Quit's promised delete of a private chat runs only once the child has gone or been signalled.
- [ ] The full suite is green (`lib/scripts/cicd.sh --app darwin --test`).

**Scope note.** Earmarked for v0.2.1 (track 6). Ungated. Out of scope: the CLI's own close paths (57a), the SIGKILL step after quit (4a's recorded bound), a next-launch retry of a private delete (see the finding 8 default), and the Sessions screen's other reads (6b).
