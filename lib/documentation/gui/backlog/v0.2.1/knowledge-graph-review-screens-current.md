# Knowledge, Graph and Review show what they were asked about: a node gone after Rebuild, results per collection and branch, a slow skill reply, a vectorised collection said vectorised

**What / why.** The Knowledge, Graph and Review places each pair a selection (a node, a collection, a branch, a skill) with what was read for it. The second bug sweep (2026-10-31) found five places where the two come apart. A node that a Rebuild removed turns the whole Graph canvas into an error. One collection's search results show under another after an ingest. The Records' answers stay filtered by a branch the picker no longer shows. A slow `review skills show` reply lands under another skill. And every vectorised collection is said to be "a text index only", because the app reads `embed info`'s `vectors` object as a number. Each was re-read at HEAD the same day. Line numbers are as they stand now, under `lib/src/darwin/source/` unless the path says otherwise.

1. **Graph: a node gone after Rebuild replaces the whole canvas with an explain error.** `GraphViewModel.refresh()` (`presentation/graph/ViewModels/GraphViewModel.swift:117-148`) re-runs the search (:146) and then explains the kept `selected` again (:147, `if let selected { await explain(selected) }`). It runs after every supervised job (`run`, :250: Rebuild's `graph update`/`graph build` at :222, communities, dedupe), after every `change` (:363: export at :270, report save at :277, delete), and on every appearance (`appeared()`, :111-113, from `AppViewModel.swift:225`). When the node is gone, `explain(_:)` (:186-197) sets `explain = nil` and the screen-wide `failure` (:194-195). `emptyText` returns that failure before anything else (:382), and `GraphScreen` draws an `EmptyState` whenever `emptyText` is set (`presentation/graph/Views/GraphScreen.swift:79-81`). So the search that was just re-run successfully is hidden behind the CLI's error. Only `choose(_:)` (:153), `clearSelection()` (:210) and `confirmDelete()` (:350) clear `selected`. Neither `refresh` nor a failed explain does, so the error comes back on every later refresh until a search succeeds and another node is explained. `clearSelection()` does not clear `failure` either. *Scenario:* search `helper`, click `m.helper`, rename the function in the source, click Rebuild (`graph update`). The search re-runs, then `graph explain -- m.helper` exits 1, and the canvas reads `apogee graph: no node named 'm.helper' in graph 'cg' -- near matches: ...` until the person searches again. *Probe:* `graph explain --graph cg --output-format json -- m.gone` -> `apogee graph: no node named 'm.gone' in graph 'cg' -- near matches: ...` rc=1 (the CLI's message, `cli/source/business/graph/navigate.cpp:256`).

2. **Collections: one collection's search results show under another after an ingest.** The ingest's completion (`presentation/knowledge/ViewModels/CollectionsViewModel.swift:178-199`) sets `selected = name` (:190) and calls `refresh()`. Nothing there touches `results` or `info`. `refresh()` (:88-103) clears them only when the selection has vanished from `embed list` (:97-101), and `select(_:)` (:105-111), which does clear them, is never called. `CollectionPage` renders `model.results` under whatever collection's page is shown (`presentation/knowledge/Views/KnowledgeScreen.swift:363`). *Scenario:* collection A is selected and searched, so A's scored lines are shown. The person clicks New ingest, names a new collection B and ingests a folder. When the job ends, the page switches to B's info but still shows A's search results beneath B's search box. It shows only when the ingest targets a different collection that exists when the job ends: a new or existing B that finishes done, or one stopped partway with the collection created. A failed ingest of a new name creates nothing, so `refresh()` finds B missing and clears everything. An "Ingest more…" into A itself keeps only A's own older lines, which is not wrong. There is also a short window between :190 and `readInfo(B)` finishing, during which `info` is still A's while `selected` is B: the page heading reads A, and a search submitted then runs `embed query B`. *Probe:* `embed ingest notes2 <dir>` succeeds and `embed list` lists both collections, so the path is reachable.

3. **Records: question results stay filtered by the old branch after the Branch picker changes.** `RecordsViewModel.search()` (`presentation/knowledge/ViewModels/RecordsViewModel.swift:203-214`) fixes the branch into the stored `query` when it runs (`["knowledge", "query", "--status", branch ?? "", "--json"]`, :206). `branch` (:68) has no observer, and `RecordsView` has no `onChange` on its picker (`KnowledgeScreen.swift:94-98`). It renders `model.query`'s matches whatever branch is picked now (:107-114). *Scenario:* with `shipped` chosen, the person asks "which store?" and sees 3 matches. They switch the picker to Every branch (or `rejected`). The list still shows the 3 shipped-only matches, so the rejected records that answer the question never appear unless the question is submitted again. *Probe:* `knowledge query --status "" --json -- SQLite` returns the record, so the filter does change the answer. Low severity: the display is misleading, but nothing is lost.

4. **Review Skills: a slow `review skills show` reply lands on another selected skill.** `ReviewViewModel.show(skill:)` (`presentation/review/ViewModels/ReviewViewModel.swift:246-255`) sets `selectedSkill = name` (:247), awaits `review skills show <name>` (:249), then sets `shownSkill` (:251) or `failure` (:253) without checking that the selection is still the same. Each click starts its own `Task` (`presentation/review/Views/ReviewScreen.swift:363`). *Scenario:* the person clicks `security`, then `ai-ml` before the first read returns. If the `security` read finishes last, the list highlights `ai-ml` (`selectedSkill`, :370) while the detail panel shows security's heading, description and prompt (`shownSkill`, :388-394). A stale failed read can likewise raise `failure` for a skill no longer selected. Graph explain (`GraphViewModel.swift:189`) and the collections reads (`CollectionsViewModel.swift:116`, :144) already re-check their selection. This is the bug class GUI 4h's "Async results land where they started" fixed for plays and the collections search ([MILESTONES.md:2059](../../assistant/MILESTONES.md#milestone-e--the-audits-gui-findings)), but that entry does not cover Review's skills: a gap, not a regression. Low severity.

5. **Collections: a vectorised collection is shown as "none -- a text index only".** `CollectionInfo` (`business/reads/Knowledge.swift:96-116`) declares `vectors: Int?` (:103) and reads it with `v["vectors"]?.intValue` (:113). `JSONValue.intValue` is non-nil only for a number (`data/protocol/JSONValue.swift:56-62`). The CLI's `embed info --output-format json` has always sent an object or null: `collection_info_document` (`cli/source/presentation/cli/embed.cpp:574-596`) builds `vectors = {{"chunks", …},{"dimension", …},{"widths", …}}` plus `model` when one is bound (:580-587), null for a text-only collection, as documented (`lib/documentation/cli/reference/machine-mode.md:1261`, `"vectors":{…}|null`). So `CollectionsViewModel.vectors(_:)` (`CollectionsViewModel.swift:129-131`) always returns `"none -- a text index only"`, and the page's Vectors fact (`KnowledgeScreen.swift:354`) says it for every collection. The only fixture is the null case (`tests/business/reads/Fixtures/collection-info.json:14`, read at `tests/business/reads/KnowledgeTests.swift:39-40`, and `tests/presentation/knowledge/KnowledgeViewModelTests.swift:123`), so the object shape was never tested. *Scenario:* ingest a collection with `--retriever vector`, open Knowledge › Collections and select it. The page says "none -- a text index only" though every chunk carries a vector, so the person may re-ingest, or pick lexical, for no reason. This is a **regression of GUI 2c** (`knowledge-collections`): "a collection's `embed info` (chunks, the text index's health, its vectors or \"a text index only\", its sources)" ([MILESTONES.md:903](../../assistant/MILESTONES.md#milestone-c--cli-parity)). Medium severity.

What already works: a node explained by a click while the graph holds it (finding 1); a collection chosen by a click clears the old page and re-checks the search (`select(_:)`, :105-111; finding 2); a question asked under the branch already picked (finding 3); a skill read that returns before the next click (finding 4); a text-only collection said text only (finding 5).

**Core constraint(s).**
- **The GUI is a machine-mode client** (CLAUDE.md): what a place shows is what the CLI's own read said, for the selection it was asked about. The app reads `embed info`'s `vectors` as the CLI states it; it never computes vectors itself.
- **The protocol grows additively** (CLAUDE.md, the CLI's ADR 0006): `CollectionInfo` tolerates fields it does not know in `vectors` (a later key), and a null stays "a text index only".
- **Async results land where they started** (GUI 4h): a reply is applied only if its selection, branch or question is still the one asked; the same discipline the graph explain and the collections search keep.
- **The CLI's words** (ADR 0002 as the GUI applies it): the failure a node's explain gets is shown verbatim, in its place, never as the whole canvas's state.
- **The four layers and MVVM** (ADR 0001, ADR 0002): the fixes stay in the view-models and the Business read. View-models stay SwiftUI-free; the view binds the picker and calls the view-model.
- **Every view can be seen on its own** (ADR 0004): the vectorised Collections page gets a named `#Preview` over a recorded document.
- **Hermetic tests** (CLAUDE.md → Implementing a Feature): scripted fakes and recorded documents. No `apogee` binary, no network.
- **Development runs on the dev channel** (CLAUDE.md): any live pass or fixture recording drives `apogee-dev` over a sandbox `APOGEE_HOME`, never the release `apogee` or `~/.apogee`. Until GUI M18 ([`app-dev-channel.md`](../maintenance/app-dev-channel.md)) ships, no development build of the app is launched on the user's machine without asking.

**Open calls:**
- [default: an explain failure never sets the canvas's `failure`. When `refresh()` re-explains a node the graph no longer has, the selection and the explain card are dropped, the re-run search stays on the canvas, and the CLI's line (`no node named 'm.helper' in graph 'cg' -- near matches: ...`) is said once as a toast (`say`). When a click's explain fails, the line is shown in the existing `problem` alert and the canvas is kept. `clearSelection()` clears either.]
- [default: when the ingest's collection differs from the one selected before it, the completion clears `info` and `results` before `refresh()`, exactly as `select(_:)` does. An "Ingest more…" into the same collection keeps its results, since they are that collection's own.]
- [default: a Branch change while a question's matches are showing asks again under the new branch (`--status <branch>`, or `""` for every branch), clearing the old matches first; with no question showing, the list just filters as today. A reply is applied only while the branch and the question are still those it was asked with.]
- [default: a new skill click clears `shownSkill` at once, as the collections' `select(_:)` clears `info`, so the detail never shows the previous skill while the new one is read; the reply, or its failure, is applied only while `selectedSkill` is still its skill.]
- [default: the Vectors line follows the CLI's text mode: `<chunks> of <total> chunks, <dimension>-d [<model>]`, with `[model not recorded -- re-ingest to bind]` when no model is bound and ` -- MIXED: <widths> widths` when `widths` > 1. A null or absent `vectors` stays "none -- a text index only". No older binary sent a number (the object shape dates from the CLI's v0.1.6, before 2c), so no number fallback is kept.]
- [default: the new fixture `collection-info-vectors.json` is recorded from `apogee-dev embed info <name> --output-format json` over a sandbox `APOGEE_HOME`, a collection ingested with `--retriever vector` on the mock embedding backend (`MockEmbeddingProvider`), its path scrubbed as `collection-info.json`'s is.]

**Guardrail(s).** Each failure is pinned as a regression test over each module's `Scripted.swift` (a scripted `CommandRunning` and `JobStarting`) and recorded documents. No binary, no network.
1. **A gone node never takes the canvas.** A search and an explained node, then a Rebuild job whose re-explain exits 1 with `no node named 'm.helper' in graph 'cg' -- near matches: ...`. Pin that `emptyText` is nil, `result` is the re-run search, `selected` and `explain` are nil, the CLI's line was said once, and a second `refresh()` explains nothing. Pin that a click's failed explain sets `problem`, not `failure`, and that `clearSelection()` clears it.
2. **An ingest into another collection drops the old results.** A selected, searched A, then an ingest job into B that ends done. Pin that `results` is nil and `info` is B's once it ends, and that no moment of the completion holds A's `info` with `selected == B`. An ingest into A itself keeps A's results.
3. **A branch change re-asks.** A `shipped` question showing 3 matches, then the branch set to every branch. Pin that `knowledge query --status "" --json -- <question>` runs, the matches are the new reply's, and a reply held open past a second branch change is dropped.
4. **A slow skill reply is dropped.** `security`'s read held open, `ai-ml` clicked and answered, then `security`'s released. Pin that `shownSkill` is ai-ml's, that a released failure for `security` sets no `failure`, and that `shownSkill` is nil between the click and ai-ml's reply.
5. **A vectorised collection is said vectorised.** The recorded `collection-info-vectors.json` read through `CollectionInfo`: pin `chunks`, `dimension`, `widths` and `model`, and that `vectors(_:)` reads `N of M chunks, D-d [model]`. The null fixture still reads "none -- a text index only".

**Acceptance criteria:**
- [ ] After a Rebuild that removes the explained node, the canvas shows the re-run search, the explain card is gone, and the CLI's line is said once. No refresh brings the error back.
- [ ] After an ingest into another collection, its page never shows the previous collection's results or heading.
- [ ] After a Branch change, the question's matches are the new branch's, or the question is asked again; never the old branch's under the new label.
- [ ] The Review Skills detail always shows the highlighted skill, or nothing while it is read.
- [ ] A collection ingested with vectors shows its vector count, width and model; a text-only collection still says "a text index only".
- [ ] The full suite is green (`lib/scripts/cicd.sh --app darwin --test`), and so is the layering check.

Out of scope: the CLI's own messages and reads, which already say the right thing; re-running a collection's search automatically after an ingest into it; and a graph's near-match suggestions as clickable nodes, which would be a feature, not this fix.
