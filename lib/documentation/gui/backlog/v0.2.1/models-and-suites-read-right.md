# Models and Suites read right: a failed quantize beside a sibling says so, Stop before a store job starts stops it, a described default suite is recognised, and Roles shows only roles

**What / why.** The Models place's Jobs tab and the Suites place both show the person what the CLI did, and in four cases they show something else. A failed quantization can show its step ticked and open another job's GGUF. A Stop pressed in the first second of a store job is ignored, and the job then runs anyway. A default suite with a description is never recognised as the default. And Models › Roles draws the suite and its footprint as two more roles, whose pickers run commands the CLI refuses. Each one tells the person something false about their store or their configuration: a conversion they cancelled writes a GGUF, a default they set looks unset, a picker offers a change that cannot happen. Found by the second bug sweep, 2026-10-31, and re-read at HEAD (`b26550bb`) the same day. Paths below are under `lib/src/darwin/` unless they say otherwise.

1. **A failed quantize next to a sibling quantize of the same model shows its step ticked, and Show the weights opens the sibling's GGUF.** A store job's set-making step is done once as many sets have landed as steps before it (`source/presentation/models/ViewModels/DownloadsViewModel.swift:111-112`: `if kind == .quantize && made != nil { return true }` and `return steps[..<index].filter(\.makesSet).count < landed.count`). `landed` is every name new since the job's own `before` that sits in the job's model folder (`readBack`, `:440-443`), and `made`, the set the job's own run named, stays `nil` until `identify` runs after a successful end (`:341-346`, `:359-366`). So `landed` counts a sibling's set in the same folder. Show the weights takes `made ?? landed.first { $0.contains("/") } ?? landed.first` (`:117`) and is offered on any ended store job but a check (`source/presentation/models/Views/DownloadsView.swift:123`). Scenario: quantize Llama F16 to Q4_K_M and to Q8_0 at once. Both read the store before either lands. Q4 finishes. Q8 then fails, say because the disk fills. At Q8's final read-back the Q4 handle is new in Llama's folder, so `landed` = [the Q4 handle]. Q8's "Quantize to Q8_0" step shows done on a failed job, and Show the weights on the failed Q8 card opens the Q4 set. The same wrong tick shows while Q8 is still running: once Q4 lands, the read-back on each `.said` line (`:334`) puts it in Q8's `landed`. Run again on the failed Q8 carries the first run's `before` and `landed` (`rerun`, `:280-284`), so the new card starts with the step already ticked. The wrong registration that 4e fixed does not happen here, because `register` uses what `identify` named. Only the step ticking and Show the weights are affected. The existing test (`tests/presentation/models/JobIdentityTests.swift:67`, "two quantizations at once") quantizes two different models, in different folders, so it never meets this. This is a regression of GUI 4e `downloads-and-store-jobs`, whose rule is "What a job registers or shows is what its own run says it made, never the store's difference, which another job's sets and backends are part of" (the class doc, `DownloadsViewModel.swift:17-20`).

2. **Stop on a store job does nothing while its first store read runs, and the job then starts anyway.** `startStore` puts the card on the list, and on a first run, where `before` is `nil`, it reads `models list --all` in a `Task` and then calls `launch` (`DownloadsViewModel.swift:291-318`, the read and launch at `:308-312`). Nothing checks whether a stop was asked for in between. During the read the card counts as running, because `JobProgress.status` starts as `.running` (`source/business/jobs/JobProgress.swift:69`), and `isRunning` is `progress.status == .running` (`DownloadsViewModel.swift:122`). So the card shows Stop and not Dismiss (`DownloadsView.swift:83-92`). But `stop` is `await download.job?.stop(grace: .seconds(10))` (`DownloadsViewModel.swift:458-460`), and `job` is still `nil`, so nothing records the press. When the read answers, `launch` (`:321-325`) starts the child. Scenario: Stored weights › Quantize… (or Convert…, or Check the files: every job that goes through `startStore`) on a large store, where `models list --all` loads the config and walks the store for a few seconds. Press Stop on the new Jobs card at once. Nothing happens. When the read returns, `models quantize` starts and writes the GGUF the person tried to cancel, for minutes if it is a conversion, and Dismiss stays unavailable until then. The window exists only on a first run: Run again and the named resume go through `rerun`, which passes the saved `before`, so `launch` runs at once (`:304-306`). This breaks 4c's "Stop always ends a job" (`lib/documentation/gui/assistant/ROADMAP.md:67`) and 2i's "Stop is the interrupt" (MILESTONES, 2i).

3. **The Suites screen never recognises a default suite that has a description.** When a suite is active, `models status` opens with `out << "suite: " << suite_name << (suite->description.empty() ? "" : "   (" + suite->description + ")")` (`lib/src/cli/source/presentation/cli/models.cpp:2290-2291`), and the JSON document's fields carry that line word for word. The sweep's probe of `models status --output-format json` in the sandbox returned `{"field":"suite","value":"duo   (two)"}`, and the same document's typed `footprint.suite` was the bare `"duo"`. `SuitesViewModel` stores the raw value, `defaultSuite = Field.list(from: status).first { $0.label == "suite" }?.value` (`source/presentation/suites/ViewModels/SuitesViewModel.swift:115`), and `SuitesScreen` compares it to `suite.name` (`source/presentation/suites/Views/SuitesScreen.swift:34`, the "default" badge; `:85`, the choice between "Stop using it by default" and "Use for new sessions"). Scenario: `apogee config add-suite duo --chat m1 --utility m2 --description "two"`, then click "Use for new sessions" on duo, which runs `config set-default-suite duo` and succeeds. After the refresh `defaultSuite` is `"duo   (two)"`, which is not `"duo"`. The badge never appears, the button still says "Use for new sessions", and "Stop using it by default" is never offered. The person reads the change as having failed. Meanwhile the Sessions place reads `config get models.default_suite` (`source/presentation/sessions/ViewModels/SessionLibraryViewModel.swift:629`), the bare `duo`, so the two places disagree. No test covers the decorated form: the view-model test feeds a hand-written undecorated value (`tests/presentation/suites/SuitesViewModelTests.swift:18`, `"value":"coding"`), and every recorded `tests/business/reads/Fixtures/suites-models-status*.json` uses a suite with no description (values `fast`, `pair`, `cloud`, `shared`, `vast`, `partial`). This is a regression of GUI 1k `monitor-suites`, which records the default as read from "`models status`'s `suite` field" (MILESTONES, 1k).

4. **Models › Roles shows `suite` and `footprint` as roles when a default suite is set, and their pickers run commands the CLI refuses.** With `models.default_suite` set, `models status` adds a `suite` field first and a multi-line `footprint` field last. The footprint's first line is `"footprint: suite " + footprint.suite` (`lib/src/cli/source/presentation/cli/suite_residency.cpp:150`), and the field is written at `models.cpp:2405-2412`. `RoleAssignment.list` makes a row of every field (`source/business/reads/Models.swift:377-379`: `Field.list(from: document).map { RoleAssignment(role: $0.label, said: $0.value) }`), and `verb` builds `config set-default-\(role)` for any label but `chat` (`:373-375`). `RolesView` draws every `model.roles` entry with a picker that calls `model.assign` (`source/presentation/models/Views/ModelsScreen.swift:499-525`). `assign` runs `role.verb + [backend]` (`source/presentation/models/ViewModels/ModelsViewModel.swift:575-577`), and `choices(for:)` offers every configured backend to any role that is not chat (`:651`). Scenario: with `models.default_suite = duo`, open Models › Roles, and two extra rows appear. The first is "Suite", whose verb reads `config set-default-suite <backend>` and whose picker is set to `duo`, which is not one of its tags. The second is "Footprint", whose verb reads `config set-default-footprint <backend>`, whose picker is set to `suite` (the first word of the footprint text, `Models.swift:363-366`), and whose "what the CLI says" line is the footprint's multi-line text. Both rows have an empty description, because `ModelsViewModel.about` returns `""` for any label it does not know (`:630`). The sweep's sandbox probes: choosing m1 in the Suite row runs `apogee config set-default-suite m1`, which exits 1 with `no suite named 'm1' (configured: duo, rich)`. Choosing m1 in the Footprint row runs `apogee config set-default-footprint m1`, which exits 106 with `A subcommand is required`. The app then reports the failure. No Roles test feeds a `models status` document that has a suite.

What already works: a quantization registers only the GGUF its own run named (4e). A Stop pressed once the child is running interrupts it (4c). The Suites fit and footprint come from the typed `footprint` object (M15). Roles under no suite shows the six roles.

**Core constraint(s).**
- **The GUI is a machine-mode client** (the GUI's CLAUDE.md): the app shows what the CLI said and decides nothing the CLI owns. The default suite is the one the CLI resolves. The roles are the ones `models status` resolves (`models.cpp:2293-2298`: chat, embedding, extraction, vision, transcription, utility). A job's work is what its own run named.
- **The protocol grows additively** (the CLI's ADR 0006): a field the app does not know, such as `suite` or `footprint` in Roles, is tolerated and never turned into a control.
- **Store jobs keep their identity** (GUI 4e): what a job ticks or shows is what its own run made, never the store's difference.
- **Stop always ends a job** (GUI 4c): a Stop pressed at any moment a card shows it ends that job, and nothing starts after it.
- **Presentation keeps the MVVM shape** (ADR 0002) and **the four layers** (ADR 0001): the role filter is a Business read (`BusinessReads`); the job and suite logic stay in their view-models, SwiftUI-free.
- **Every view can be seen on its own** (ADR 0004): a state a person now sees differently (Roles under a suite) gets its named `#Preview` over recorded documents.
- **Development runs on the dev channel** (the GUI's CLAUDE.md): a fixture recorded for this item comes from `apogee-dev` over a sandbox home, never the release `apogee` or `~/.apogee`, and no development build of the app is launched for a live pass until M18 ships.
- **Hermetic tests**: scripted fakes and recorded documents, no binary, no network.

**Seam + files.**
- `source/presentation/models/ViewModels/DownloadsViewModel.swift`: `Download.isDone`, so that a quantization's set-making step ticks on `made` alone, and `firstLanded`, so that a quantization's card offers `made` alone. A stop asked before the job exists is recorded on the `Download`, and `startStore`'s read `Task` honours it: it ends the card stopped and never calls `launch`. `stop` and `dismiss` are updated to match.

- `source/presentation/suites/ViewModels/SuitesViewModel.swift`: `defaultSuite` read from the typed footprint (`SuiteFootprint(document:)`, `source/business/reads/System.swift:206-213`), else from the `suite` field matched against the suites just read.
- `source/business/reads/Models.swift`: `RoleAssignment.list` keeps only the CLI's roles. The suite the roles resolve under is exposed as its own value for Roles to show.
- `source/presentation/models/ViewModels/ModelsViewModel.swift` and `source/presentation/models/Views/ModelsScreen.swift` (`RolesView`): the suite line above the rows. Previews in `source/presentation/models/Previews/`.
- Tests: `tests/presentation/models/JobIdentityTests.swift` (findings 1 and 2), `tests/presentation/suites/SuitesViewModelTests.swift` (3), `tests/business/reads/ModelsTests.swift` and `tests/presentation/models/ModelsViewModelTests.swift` (4). New recorded documents go in `tests/business/reads/Fixtures/`: `suites-models-status-described.json` and its `-typed` twin.

**Reference.**
- GUI 4e `downloads-and-store-jobs` (MILESTONES, Milestone E): steps tick on the job's own work, and a quantization registers the GGUF its run named. Finding 1 extends that rule to a sibling in the same model folder.
- GUI 2i `convert-quantize-jobs` and 4c `children-end-cleanly` (MILESTONES): Stop is the interrupt, and Stop always ends a job. Finding 2 closes the one window before the child exists.
- GUI 1k `monitor-suites` (MILESTONES): the default read from `models status`'s `suite` field. Finding 3 is its regression.
- GUI M15 (MILESTONES): the Suites fit read from the typed `footprint`, which this item reuses for the default.
- The CLI's 27d and 27e (the active suite in `models status`, its footprint) and M31 (the typed `footprint` object): the CLI side, unchanged here.

**Open calls:**
- [default: a quantization's set-making step is done only when `made` is set, and while it runs it shows running. Show the weights on a quantization's card opens `made` alone, and is not offered when its run named no GGUF. A Run again starts with that step not done, because the new card's `made` is `nil` and `landed` no longer counts for a quantization.]
- [default: a conversion keeps ticking on sets in its own model folder. At build, check whether `models convert`'s output names each set it stores, as `models quantize`'s does (4e's probe). If it does, a conversion ticks on those names the same way. If it does not, two jobs on one model at once stays a recorded limit, stated in the class doc.]
- [default: a Stop pressed before the first store read answers ends the card stopped, with the line "Stopped before it ran: nothing ran". The read's answer is dropped and nothing is launched. The card then offers Run again and Dismiss, as any stopped store job does.]
- [default: Suites takes the default from the typed `footprint.suite` where the document carries it. Otherwise it uses the `suite` field matched against the suites just read: the name exactly, or the name followed by `   (`. It does not use `config get models.default_suite`, which is the pointer as typed and can name a suite that no longer resolves, while `models status` names only a suite that does. The Sessions place's read is left as it is.]
- [default: `RoleAssignment.list` keeps an allow-list of the six roles `models status` resolves, the same six `about()` describes. A role the CLI adds later is a CLI change that the parity work would surface. A deny-list would instead turn any new non-role field into a broken picker.]
- [default: Roles shows the active suite as one line above the rows, for example "Roles resolve under suite duo (Suites changes it)", with no picker. The footprint stays on the Suites screen.]
- (consumed decision) What `models status` prints and types, its `suite` line, its `footprint` field and M31's typed object, is the CLI's (27d, 27e, M31).

**Guardrail(s).**
- `JobIdentityTests`, same-model siblings: quantize one F16 handle to Q4_K_M and Q8_0 at once. Q4's GGUF lands and Q4 ends. While Q8 runs, its quantize step is not done. Q8 then fails: its step is not done and `firstLanded` is `nil`. Run again on it starts with the step not done.
- `JobIdentityTests`, Stop during the pre-read: the scripted runner holds `models list --all` open until the test releases it. Stop the new card, then release the read. `starter.starts` stays empty, the card is stopped, and Dismiss removes it. Run once each for Convert…, Quantize… and Check the files.

**Acceptance criteria:**
- [ ] A quantization that fails beside a sibling quantization of the same model shows its quantize step not done, and offers no Show the weights that opens the sibling's set. While it runs, the sibling's landing ticks nothing on it.
- [ ] Stop pressed on a Convert…, Quantize… or Check the files card before its first store read answers ends the card stopped, and no `models convert`, `models quantize` or `models repair` child ever starts for it.
- [ ] A default suite with a description shows its "default" badge and offers "Stop using it by default" after "Use for new sessions" succeeds, as an undescribed one does.
- [ ] Models › Roles under a default suite shows the six roles and the suite as a line, never a Suite or Footprint row, and never runs `config set-default-suite <backend>` or `config set-default-footprint <backend>`.
- [ ] The darwin suite is green (`lib/scripts/cicd.sh --app darwin --test`), and the layering check passes.
