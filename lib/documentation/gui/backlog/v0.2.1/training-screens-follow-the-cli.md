# The Training screens follow the CLI's resume and status truth: a cycle pass resumed as a cycle, the running list decoded, a stale lock recoverable, Resume naming its pipeline, an unreadable history shown

**What / why.** The Training place (GUI 2d, its Pipelines and Cycle tabs from 4j and M14) is how a person sees what training is doing and acts on it without a terminal: Resume carries an aborted pipeline on, Run one pass starts the cycle, and the Runs list shows what is running. The second CLI/GUI bug sweep (2026-10-31) found five places where those screens either pass on the CLI's wrong advice or misread a document the CLI writes correctly. Resume is offered on a cycle pass's pipeline and retrains it on the wrong data. The running list is always empty. A dead pass's lock greys out Run with no way out. Resume fails for named pipelines whose `name:` is not their key, and for every spec-file run. A damaged cycle history is drawn as no history. The CLI-side fixes belong to the siblings, [57g](../../../cli/backlog/v0.2.1/training-runs-one-at-a-time.md) (liveness: a stale lock, a live pipeline's holder) and [57h](../../../cli/backlog/v0.2.1/training-resume-and-reads-truthful.md) (what a resume continues, `cycle_error`, the pipeline document's `resume` and `spec_ref`). This item is the app's part: it stops offering what the CLI refuses, reads what those items add, and keeps a fallback for an older binary. App paths below are under `lib/src/darwin/source/`, and every citation was re-read at HEAD (`b26550bb`) on 2026-10-31.

1. **The Pipelines tab offers Resume on a cycle pass's aborted pipeline, which retrains on the spec's own dataset instead of the pass's data.** `PipelineRun.resumes` (`business/reads/Training.swift:239-241`) is true for any `aborted` or `failed` run. `canResume` (`presentation/training/ViewModels/TrainingViewModel.swift:694-696`) adds only `!isRunning && binary != nil`, and the run page's `Button("Resume…") { model.pending = .resumePipeline(run.id) }.disabled(!model.canResume(run))` (`presentation/training/Views/PipelinesView.swift:207-208`) has no filter on kind or id. So a `cycle-<id>` run is offered Resume like any other. The CLI gives the same advice: the failed pass's `gate_reason` in the recorded fixture `train-cycle-status-halted.json` reads `... Fix the data or the suite and 'apogee train pipeline resume cycle-20261026-074120', or pass --continue-on-fail to go on regardless`. `train pipeline resume` reloads the spec by `spec_name` (`lib/src/cli/source/presentation/cli/train.cpp:2978-2987`) and trains on that spec's static datasets, not the pass's `cycle/work/merged.jsonl`, and it runs outside the cycle: no dual gate, no promotion, no history entry. Scenario: a scheduled `train cycle run` is stopped, or its cumulative gate fails, leaving `cycle-20261031-…` aborted. The person opens it in Pipelines and clicks Resume…. The stage retrains on `starter.jsonl`, overwriting the failed candidate's adapter under `runs/cycle-<id>-s0`, the pipeline reads `complete`, the page then says "Each stage's run is an ordinary run: gate it and promote it from Runs." (`PipelinesView.swift:212`), and the cycle's history still shows the pass failed. Probe (sweep, mock trainer, scratch `APOGEE_HOME`): `train pipeline status cycle-20261031-201001 --output-format json` shows the stage's `"dataset":".../training/cycle/work/merged.jsonl"` and `spec_name` `nightly`, whose spec's dataset is `starter`. Probe pB.sh, the same path from the CLI: the resume printed `[train] stage 1/1 'base': mock lora on aaaaaaaaaaaa, dataset starter.jsonl`, then `pipeline complete` and `apogee train promote cycle-20261031-201133-s0 --as <backend>`; the manifest afterwards read `status complete [('passed', 'starter.jsonl')]`, and `cycle status` still showed the single fail row with `day1.jsonl` still queued. The fixture `train-cycle-run-stopped.jsonl` ends with a pass cancelled under pipeline `cycle-20261026-074122`. The panel set the app's part at medium-low: nothing reaches inference from it, and the harm is a wasted run on the wrong data and a misleading `complete`. The CLI's part ([57h](../../../cli/backlog/v0.2.1/training-resume-and-reads-truthful.md) entry 1) is high. The two findings that reported this, one from each lens, are merged here.
2. **`TrainingStatus` decodes `running` as run objects, but the CLI writes run ids, so the list is always empty.** `running = (v["running"]?.arrayValue ?? []).compactMap(TrainingRun.init)` (`business/reads/Training.swift:124`). `TrainingRun.init?` needs an object with an `id` (`:23-24`), and `JSONValue`'s subscript gives nil on a string (`data/protocol/JSONValue.swift:43-44`), so every entry is dropped. The CLI writes ids: `running.push_back(run.id)` (`lib/src/cli/source/presentation/operations/training_reads.cpp:30-34`), documented as `"running": [ids]` (`training_reads.h:23`). `TrainingViewModel.runs` (`TrainingViewModel.swift:605-607`) is then only `recent_runs`, the newest five (`kRecentRuns = 5`, `training_reads.cpp:22`). A run still training that is older than the five newest never appears in the Runs list and cannot be opened. Scenario: a long `train run` is going in a terminal while five pipeline-stage runs start after it. `train status` lists it under `running`, but the Runs tab shows only the five newer runs, and the long run's page (gate, promote) cannot be reached. Evidence: the recorded fixture `train-status-pipeline-running.json` has `"running":["pipe-20261026-074116-s1"]`; the sweep's probe printed `"running":[]` for the idle case. The only test, `TrainingTests.swift:20` (`status.running.isEmpty`), reads the idle fixture `train-status`, so it cannot catch this. The bug has been there since `b828607e` (2d, Training Studio), carried through 4h–4k, and 4j's record calls it "harmless, since `recent_runs` carries the running run" (`MILESTONES.md:2233`). That holds only while the running run is among the newest five.
3. **A cycle lock left by a dead process holds Run one pass back for good, with nothing on screen saying why or how to recover.** The CLI's `cycle_lock_held` (`lib/src/cli/source/business/training/cycle.cpp:226-229`) checks only that `cycle.lock` exists, so after a pass is killed `train cycle status` gives `active: true` and `train status` gives `cycle_active: true` (`training_reads.cpp:78`). The app's `cycleHeld` (`TrainingViewModel.swift:780-782`) is true from either, so `canRunCycle` (`:792`) disables Run one pass… (`presentation/training/Views/TrainingScreen.swift:32-33`), the State fact reads `a pass is running` (`presentation/training/Views/CycleView.swift:65`), and on a binary that keeps a halt `cycleHoldText` (`:823-831`) says nothing at all while held and not halted. The CLI's own refusal, which ends `If none is, remove the file and run again`, is never shown, because the app never runs the verb that would print it. Scenario: a pass is killed (a crash, `kill -9`, power loss). The app greys out Run one pass with no explanation until someone finds and deletes `training/cycle/cycle.lock` by hand. Probe pC2.sh (sweep): `cycle.lock` written with a dead PID (99285) after one skip pass gave `state: running now`, `active: True`, `Cycle: running now; backend nightly-model` and `cycle_active: True`. Refusing a dead holder's lock in `cycle run` is recorded design (CLI MILESTONES 27h); reporting it as a running pass is the bug, fixed in the CLI by [57g](../../../cli/backlog/v0.2.1/training-runs-one-at-a-time.md) entry 3, which adds a `stale_lock` field and makes `active`/`cycle_active` false for a dead holder. The app has to read that and show the way out.
4. **The app's Resume always omits `--pipeline`, so it fails for a named pipeline whose `name:` differs from its config key and for every run started from a spec file.** `.resumePipeline(let id): ["train", "pipeline", "resume", id]` (`TrainingViewModel.swift:244`). The CLI stores the spec's `name` in the manifest (`lib/src/cli/source/business/training/pipeline.cpp:505`) but resume looks it up as a `training.pipelines` key (`train.cpp:2980`), and a spec-file run stores the file's stem (`train.cpp:1448`), which no key matches either. `pipeline list`'s `name` is the key (`training_reads.cpp:173`) and a run's document carries only `spec_name`, so the app cannot match the two. Scenario: config `pipelines: {nightly: {name: 'Nightly SFT', ...}}`, a run aborted at stage 2. The page says `Resume from stage 2, …` and offers Resume…, which fails. Likewise a `two.yaml` run started from the console and aborted shows Resume…, which always fails: the refusal tells the user to add `--pipeline`, which the app has no way to do. Probe pA.sh (sweep): `pipeline list` showed `nightly  2  tiny`; `pipeline status` showed `spec: Nightly SFT ... Resume from stage 2: apogee train pipeline resume pipe-20261031-201124`; the resume printed `apogee train: pipeline 'Nightly SFT' is not under training.pipelines any more -- pass --pipeline <spec> to resume pipe-20261031-201124` with exit=1, and with `--pipeline nightly` it ran. [57h](../../../cli/backlog/v0.2.1/training-resume-and-reads-truthful.md) entry 2 records `spec_ref` and resolves by `name:`, and adds the pipeline document's `resume: {stage, name, pipeline}`. The same field settles what 57h's entry 3 leaves to the app: the confirm's stage. `PipelineRun.resumesAt` (`Training.swift:232-233`) is the first stage that has not passed, and `pendingTitle` (`TrainingViewModel.swift:896-898`), `resumeWords` (`:699-702`) and the button's help (`PipelinesView.swift:209`, `from the first stage that has not passed`) all say so. The CLI resumes after the last passed stage, so after `--continue-on-fail` or `gate_mode: soft` the app's `Resume <id> from stage 1, a?` trains only stage 3 (57h probe pE.sh: `Resume from stage 1:`, then `-- stage 3/3: c` and `pipeline complete`).
5. **An unreadable cycle history reads as "no history" in `train status` JSON, and the app draws the empty state and offers Run.** The CLI's `training_status_document` leaves `cycle` null whenever `load_history` returns an error (`training_reads.cpp:54-67`) and drops the error. The app reads `train cycle status` only when `status.cycle` is non-nil (`TrainingViewModel.swift:560-564`), so `noHistoryText` (`:859-861`) says `No pass has run yet, so the cycle has no history` and Run one pass is enabled. Run then fails with `the cycle history is unreadable`. `cycleHalted` falls back to `status.cycle?.halted ?? false` (`:785-787`), so a halted history that becomes unreadable shows as not halted: Halt is offered instead of Resume, and Run is enabled although `train cycle run` would refuse. A scheduled cycle fails silently while the app shows nothing wrong. Probe pG.sh (sweep): the text read was `Cycle: history unreadable -- …/history.json: cycle history: runs must be an array`; the JSON read was `cycle: None`; `cycle status --output-format json`, `cycle run` and `cycle halt` each printed `the cycle history is unreadable: …` with exit=1. The fix to the document is [57h](../../../cli/backlog/v0.2.1/training-resume-and-reads-truthful.md) entry 4 (`cycle_error`, `cycle` still null). The app has to show it.

What already works: a `running` pipeline is never offered Resume (`resumes` takes only `aborted`/`failed`), so a pipeline another process is still training is left alone; a complete run is not resumable; with no history at all the empty state is right and the read that exits 1 is never asked (`PipelineCycleTests.swift:209-216`); a pass this place started holds the cycle while it runs; and the running run is listed whenever it is among the newest five.

**Core constraint(s).**
- **The GUI is a machine-mode client** (GUI `CLAUDE.md`): whether a run can resume, what it resumes, whether the cycle's lock is live and whether its history can be read are the CLI's answers, read from its documents, never worked out by the app. The app never removes `cycle.lock` itself: the person removes it, as the CLI's recorded rule says (CLI MILESTONES 27h), and the app names the file.
- **The protocol grows additively** (the CLI's ADR 0006, GUI `CLAUDE.md`): `resume`, `spec_ref`, `cycle_error` and `stale_lock` are read when present. An older binary keeps today's behaviour, except where today's behaviour does harm on every binary (entry 1's cycle runs, entry 2's ids, entry 4's runs whose spec cannot be found).
- **A button is offered only when its verb would run.** Resume, Run one pass, Halt and the cycle's Resume are each held back when the CLI would refuse, and the screen says why in the CLI's words.
- **Presentation keeps the MVVM shape** (ADR 0002): the decisions live in the SwiftUI-free `TrainingViewModel` and the `BusinessReads` types; the views bind to them.
- **Every view can be seen on its own** (ADR 0004): each new state has a named `#Preview` over the module's `Previews/` fakes and recorded documents.
- **Hermetic tests** (GUI `CLAUDE.md`, Implementing a Feature): scripted fakes and recorded documents, no binary, no network.
- **Development runs on the dev channel** (GUI `CLAUDE.md`): new fixtures are recorded from `apogee-dev` (with 57g and 57h built) over a scratch `APOGEE_HOME`, never the release `apogee` or `~/.apogee`. A live pass of a development build waits on M18 ([`app-dev-channel.md`](../maintenance/app-dev-channel.md)) or the user's word, as that section says.

**Open calls:**
- [default: Resume is never offered on a cycle pass's pipeline, on every binary, by the `cycle-` prefix (the test 57h uses: every pass's id carries it and no other verb mints it). The page's last line says the pass's candidate is the cycle's, judged by its dual gate and discarded on a fail, and that Run one pass on the Cycle tab runs the next one, in 57h's refusal words once it ships.]
- [default: on a binary whose pipeline document carries `resume`, Resume is offered only when it is non-null, and the confirm and the line say `Resume from stage <resume.stage>, <resume.name>`. When the document names the spec the bare form cannot find, the command gains `--pipeline <resume.pipeline>`. When an earlier stage failed and stays failed, the confirm says so in the CLI's words. On an older binary, today's status rule stands, minus cycle passes, and Resume is held when the run's `spec_name` is not one of `train pipeline list`'s names, with the line `Resume needs its spec: run 'apogee train pipeline resume <id> --pipeline <spec>' in the console`.]
- [default: a running id missing from `recent_runs` is drawn as a row of its id, status `running`, with no other facts. The CLI has no per-run status read, so the app makes no extra read. An object entry in `running` still decodes by its `id`, so a later CLI that writes summaries there keeps working.]
- [default: with `stale_lock` present, the Cycle tab says the CLI's line (57g's `stopped -- cycle.lock is left by process <pid>, which is not running; remove <path> to run again`), the path selectable with Reveal in Finder; the State fact reads `stopped, its lock left behind`; Run one pass stays held, since `cycle run` refuses it, with that line as the reason. On an older binary, which reports a dead holder as active, a cycle held by another process adds the CLI's own remedy to the hold text: `If no pass is running, one that died left its lock: remove training/cycle/cycle.lock under your Apogee home.`]
- [default: with `cycle_error` present, the Cycle tab says `The cycle history could not be read: <cycle_error>` where the history is drawn, and not the no-history text. Run one pass, Halt and the cycle's Resume are held, since each refuses on it, and the line is the reason. `cycleHalted` is unknown there, not false. On an older binary, `cycle: null` stays the empty state: nothing in the document tells the two apart without the extra read `PipelineCycleTests.swift:209-216` pins as never asked.]
- [default: a pass's recorded `gate_reason` is drawn as the history keeps it, so passes recorded before 57h still carry the old resume advice. The run page of that pipeline offers no Resume (entry 1), and that is what keeps the advice harmless here.]
- (consumed decision) The fields' names and contents (`resume`, `spec_ref`, `cycle_error`), whether a cycle pass resumes, and where a resume starts are [57h](../../../cli/backlog/v0.2.1/training-resume-and-reads-truthful.md)'s. A stale lock's reading (`stale_lock`, `active`/`cycle_active` false) and a live pipeline holder's refusal are [57g](../../../cli/backlog/v0.2.1/training-runs-one-at-a-time.md)'s. The app reads them as they ship and words its lines from theirs.

**Guardrail(s).** Hermetic, over scripted runners and recorded documents, no binary, no network:
- **Entry 1.** A cycle pass's aborted pipeline (the recorded `cycle-` document): `canResume` false, no Resume line, the cycle page line shown. A `pipe-` run aborted at the same stage is still offered Resume. Both hold with and without a `resume` field.
- **Entry 2.** `train-status-pipeline-running.json`: `runningIDs == ["pipe-20261026-074116-s1"]`, listed once. A status whose running id is not among the five recent runs: the Runs list starts with that id's row, and it can be selected. An object entry in `running` decodes by its `id`.
- **Entry 3.** A `train cycle status` and `train status` with `stale_lock`: `canRunCycle` false, the hold text carrying the path and remedy, the State fact `stopped, its lock left behind`, never `a pass is running`. A live pass's lock (today's `train-cycle-status-held.json`) keeps today's words. An older binary's held cycle (no `stale_lock`, not this place's pass) shows the remedy line.
- **Entry 4.** The `Nightly SFT` run with a `resume` naming `nightly`: the started command is `train pipeline resume <id> --pipeline nightly` with the stream. The pE run: the confirm says stage 3, c, and that stage 1, a, stays failed. On an older binary (no `resume`), a run whose `spec_name` is not among the listed specs holds Resume and shows the console line, and a spec-keyed run resumes as today (`PipelineCycleTests.swift:151`).
- **Entry 5.** A `train status` with `cycle_error`: `train cycle status` not read, the error line shown, `noHistoryText` nil, Run, Halt and Resume all held. A fresh home (`cycle` and `cycle_error` both null) keeps today's empty state and controls.

**Acceptance criteria:**
- [ ] A cycle pass's aborted pipeline is never offered Resume, and its page points at the Cycle tab's Run one pass.
- [ ] A run still training that is older than the five newest is listed in Runs and can be opened.
- [ ] After a pass is killed, the Cycle tab names the lock file left behind and how to clear it. Run one pass says why it is held, and nothing says a pass is running.
- [ ] Resume on a named pipeline whose `name:` is not its key, and on a spec-file run, runs the command the CLI says will work, or is held with the console line on an older binary. The confirm names the stage the CLI resumes from.
- [ ] A damaged cycle history is shown as unreadable with the CLI's reason, never as no history, and Run, Halt and Resume are held on it.
- [ ] The full darwin suite is green (`lib/scripts/cicd.sh --app darwin --test`), with each new state previewed.
