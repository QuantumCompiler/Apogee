# Device tools: a connected desktop offers its own files and shell

**What / why.** The user's vision, 2026-11-07: Apogee as a private, self-hosted harness that feels like Claude on every device the person owns, with a strong machine serving the person's own desktops and phones. Where the work happens is the user's call C: the server's tools by default, and a connected desktop offers its **own** files and shell, as Claude Code does. When the Mac points at a server and is asked to change a project on the Mac, the Mac's files are the ones touched. The server is the brain, and the desktop's files are touched on the desktop.

**W6 — tools run where the agent loop runs, and nothing lets a connected device offer its own.** Re-verified 2026-11-07 against the branch binary (`apogee 0.2.0 (4f92316d)`, a scratch `APOGEE_HOME`, the `mock` backend):

1. **A served session's tools are the server's.** `serve --tools` builds its registry with `make_built_in_tools` (`presentation/cli/serve_cmd.cpp:256-270`), which registers the native toolsets (`presentation/cli/helpers.cpp:251-286`, `tools::register_native_toolsets`): the seven filesystem tools sandboxed to the server's `tools.fs_root` or its launch folder (`business/tools/toolsets.h:27-28`, `:69`), `run_command`, and the git tools. The probe's serve said `[tools] 25 registered`, and `check` put `fs_root` at the folder serve was started in. A file a served model reads or writes is on the server's disk, and there is no other place for it to be.
2. **The protocol has no way to offer a tool.** The chat route refuses one: a request carrying `tools` is a 400, `client-side tools are not supported: the server runs its own tool loop and returns only the final answer (tool_mode selects it)` (`presentation/httpserver/handler.cpp:648-652`; the probe got those words back). The machine mode's driver lines are `answer`, `attach`, `cancel`, `compact`, `detach`, `hello`, `set` and `user` (`apogee __machine-schema`, schema `2026-11-01`, `protocol_version` 1). None of them declares a tool or returns a tool's result. `hello` is recorded and "changes nothing" ([machine-mode.md → Introducing yourself](../../reference/machine-mode.md#introducing-yourself-hello)).
3. **Nobody on a served request can answer the gate.** `serve` passes no confirm function (`serve_cmd.cpp:273`, `make_permission_checker(config, nullptr)`; `handler.cpp:461-464`: "No AskFn, ever"), so an `ask` resolves to deny (`business/agent/tool.h:258-262`). A device's person could not approve a write on their own machine even if the call reached it.
4. **The pieces a device tool needs exist in other shapes.** A tool is a name, description and argument schema plus `writes`/`edits`/`outbound` and a `run` (`business/agent/tool.h:110-166`). The gate runs inside `dispatch`, before `run` (`business/agent/tool.cpp:249`). A call that cannot work for the rest of the turn says `unavailable` and the loop stops offering it (`tool.h:29-34`). An MCP server's tools are registered remotely-run as `mcp__<server>__<tool>`, `writes` unless the server says read-only (`business/mcp/registry.h:85-88`, `registry.cpp:96-120`). What is missing is a device on the other end of a network connection, and 60a's one definition for it to declare tools in.

This item delivers the server's half and the device's core. Over the 59b connection a device declares tools in 60a's definition: files under a folder the person granted, the shell, git. The server registers them for that session, named for the device, and its loop calls them by name. Each call goes to the device, where the device's own permission gate decides it and asks the device's own person. The device runs it and streams progress and the result back. A device that disconnects mid-call fails that call cleanly, with the uncertainty said. The Mac app's side is GUI [7b](../../../gui/backlog/v0.2.4/mac-offers-its-files-and-shell.md). It drives the device core this item ships rather than reimplementing a file tool in Swift.

**Core constraint(s).**
- **Standalone use never needs a server** (the anti-goal; the user's call, 2026-11-07; GUI SPEC → No server requirement). Device tools exist only on a 59b connection. `chat`, `execute`, `complete`, `task`, `acp` and the Mac app over pipes register, gate and run exactly what they do today. No local path links or reads the new module except the device core's own door. A machine that never points at a server never sees a difference.
- **The device's gate decides, never the server's.** A device tool is decided on the device, by the device's `permissions:`, its session mode and its person. The server may **narrow**: it can refuse to offer a device tool, as a read-only agent policy or a suite's pinned toolset drops tools today. It can never **allow** on the device's behalf. It has no checker for these calls, no `always` that writes anywhere but the device's config, and no bypass mode that reaches them. A server session in `bypass` or accept-edits mode leaves a device tool asking exactly as the device's own settings say.
- **Interactive = pipes, serving = server** (CLI CLAUDE.md → Interactive turns never open a listening socket). The device listens on nothing. It dialled the server (59b), and the server's calls come back over that same connection. The device core's local door is stdio, a child of the binary as `acp`'s sessions are. `cli.no_listen_symbols` and `cli.complete_opens_no_listening_socket` stay green with no new allow-list entry.
- **Only paired devices, only on the authenticated connection** (59a). Device tools ride the 59b session connection, never the OpenAI-compatible inference plane, which is unauthenticated by design ([http-api.md](../../reference/http-api.md)). A device's tools are offered only to the session that device drives. Another device's session never sees them.
- **Secrets are unleakable** (CLI CLAUDE.md → Secrets are unleakable by construction). A declaration, a request, a result and every log line carry tool names, arguments, the grant's folder and results. They never carry the device's pairing credential or anything from either side's `secrets/`. The device's filesystem tools are sandboxed to the grant (`resolve_in_root`, `business/tools/fs.h:29-34`), and the native tools have no `secrets/` rule of their own (a grep of `business/tools/` finds none), so a grant that holds the device's Apogee root is refused.
- **Results are the device's text.** A result is mended to UTF-8 at the one place every call already goes through (`dispatch`, `tool.h:249-252`, `tool.cpp:283`). It is bounded at the device's `read_limit` before it is sent and checked again on arrival, and it is data the model reads, never an instruction to the server.
- **Additive protocol** (ADR [0006](../../adrs/backwards-compatibility.md)). The new lines and fields join `protocol_version` 1. An older server or driver ignores them. A device that declares nothing is a session exactly as 59b ships it.
- **Parity** (ADR [0002](../../adrs/mode-parity.md); GUI CLAUDE.md, no client reimplements a capability). What a device offers are the CLI's own tools, run by the CLI's own code on the device. The Mac app bridges them (7b). It never re-implements `read_file` or `run_command`.
- **The four layers** (ADR [0001](../../adrs/layer-enforcement.md), [0008](../../adrs/module-map.md)). The remote-tool adapter and the device host are Business, beside `agent` and `mcp`. The wire lines are Presentation's. Nothing in `agent/` learns about connections.
- **The dev channel** (CLI CLAUDE.md → Development runs on the dev channel). Tests are hermetic, each side its own temp `APOGEE_HOME` under the scratchpad. A live pass names `apogee-dev` on both ends, never the release `apogee` or `~/.apogee`.

**Seam + files.**
- `source/business/devicetools/` (new module, its row in `cmake/modules.cmake`; links `agent`, `tools`, and 60a's definition):
  - `remote.h/.cpp`: the server's side. `register_device_tools(registry, device, declared, Link&)` validates each declared definition against 60a, names it `device__<device>__<tool>` (the device's paired name made a tool word, `mcp`'s rule), keeps the definition's effect hints for display, and marks the tool device-gated so `dispatch` asks no server checker for it. Its `run` sends a request over the `Link`, waits for the device's progress and result, and maps a dropped link to the failure below. `Link` is an interface 59b's connection implements and a test scripts.
  - `host.h/.cpp`: the device's side. A `Host` over a grant (a folder) and the device's own config. It registers the native toolsets the declaration names (`register_fs_tools` rooted at the grant, `register_shell_tool` with the grant as its working directory, `register_git_tools`; `business/tools/fs.h:41`, `shell.h:50`, `git.h:63`), less the device's `tools.disabled`. It declares them in 60a's definition and runs each request through the device's own `dispatch`, with the device's checker and the device's confirm. The confirm is the device's driver's `question` on the stdio door, or the CLI client's own prompt.
- `source/business/agent/tool.h/.cpp`: a device-gated flag on `Tool` that `gated()` (`tool.cpp:86-88`) answers false for, with a note that the gate is the device's. It keeps `writes`/`edits`/`outbound` true, so a read-only policy still drops a device's writer.
- `source/presentation/machine/protocol.cpp` and `json_reporter.cpp`: the lines, in 59b's protocol on both transports:
  - device to server: `tools` declares the set, each a 60a definition, with the grant's folder named.
  - server to device: `tool_request` carries `call_id`, `name`, `arguments`, and the server's `detail` for the prompt.
  - device to server: `tool_progress` (`call_id`, `text`, droppable) and `tool_result` (`call_id`, `content`, `is_error`).
  - server to device: `tool_cancel` (`call_id`) when the turn is cancelled.
  - Additive fields: the `tool_call` event's `device` (where the call ran), and `capabilities.device_tools`.
- `source/presentation/cli/device_tools_cmd.cpp`: the device core's local door. A hidden plumbing verb, `apogee __device-tools --grant <folder>`, speaking those lines on stdio and asking its own driver through the existing `question` kind `permission`. It is what 7b's Mac app runs as a child and bridges to its server connection. Where 59b ships a CLI client of a server, that client hosts the same `Host` in-process.
- `lib/documentation/cli/reference/machine-mode.md` (a "Device tools" chapter: the lines, the gate's home, disconnect), `machine-schema.json` (regenerated), `tools.md` (a device's toolset, its names), `http-api.md` (the session connection carries device tools; the inference plane still refuses client `tools`).
- Tests (hermetic: temp `APOGEE_HOME` per side, the `mock` backend's scripted tool calls, `data/backends/mock.cpp:93-137`):
  - `tests/business/devicetools/remote_test.cpp`: the namespaced names; a declared definition 60a refuses is set aside with a notice; a call goes out and its result returns; the server's checker is never consulted (a checker that fails the test if called); the server can narrow (a read-only policy drops the device's writers); the disconnect, late-result and cancel cases; the result bound.
  - `tests/business/devicetools/host_test.cpp`: only the declared toolsets under the grant; a path outside the grant refused by `resolve_in_root` (`fs.h:33`); the device's `ask` asks a scripted confirm; `always` writes the device's own config and never the other home; a grant holding the device's Apogee root refused.
  - `tests/presentation/machine/machine_mode_test.cpp`: the lines' shapes against the schema, `capabilities.device_tools`, the `tool_call` event's `device`.
  - `cli.device_tools` (`tests/scripts/sh/device_tools_e2e.sh`): a server home and a device home, the device's grant holding a file. A scripted mock turn calls `device__<dev>__read_file` then `device__<dev>__write_file`. The device's file changes, the server's launch folder does not, and the device's prompt was the one asked. Then the device is killed mid-call and the turn ends with the call `failed` and the session alive. POSIX; Windows a recorded skip where 59b's transport is.

**Decisions made** (dated):
- 2026-11-07: Specced from the Apple-platforms spike and brainstorm. The user's calls: the vision (a private, self-hosted harness, Claude-like on every device the person owns, a strong machine serving the person's own desktops and phones; no customer accounts, billing or metering, the server admitting the person and their devices only); where the work happens, C (server tools by default, a connected desktop's own files and shell offered as Claude Code's are, the Mac's files touched when the Mac asks); remote mode an add-on, never the only way the application runs, a failure being anything that makes the CLI or the Mac app need a server, a network or an account; iPhone and iPad clients of the person's server only (they offer no device tools); the SPEC amendment already written (CLI SPEC → `apogee serve`: "the tools a connected desktop offers (its own files and shell)"). Track 60, v0.2.4.
- 2026-11-07: In v0.2.4, after v0.2.3's connection (59a, 59b) and beside 60a. The user's placement puts the common tool definition before v0.3.0, and device tools are its first remote consumer. 7b, the Mac's side, needs it in the same release, so a Mac pointed at a server in v0.2.4 can change a project on the Mac.
- 2026-11-07: The device's tools are the CLI's own, run by the CLI on the device. The Mac app bridges `apogee __device-tools` and implements no tool, by the GUI's law that no client reimplements a capability it owns. iPhone and iPad have no on-device core and offer nothing.

**Open calls:**
- [default: device tools are named `device__<device>__<tool>`, beside the server's own un-prefixed tools. The registry's environment note says where each set acts ("the server's files under …; <device>'s files under <grant>"). Both sets are offered, and the server's tools stay the default by the user's call C. A device-only session that withdraws the server's filesystem tools is out of scope until asked.]
- [default: a device declares the filesystem, shell and git toolsets only, less its own `tools.disabled`. Notes, retrieval, the graph and `fetch_url` stay server-side tools. A device's web reach is its own, and nothing in this item offers it.]
- [default: the grant is one folder per connection, named explicitly: the Mac app's chosen project folder, or `--grant`. With no grant the device declares nothing. A grant of the home folder, `/`, or any folder holding the device's Apogee root is refused with a reason. `run_command` runs in the grant, and its reach beyond the grant is the device's gate's to decide, as it is locally today.]
- [default: a device that disconnects mid-call fails the call with an error naming the device and saying the outcome is unknown ("<device> disconnected before answering; whether <target> changed is unknown"). Every tool of that device is `unavailable` for the rest of the turn, and its tools leave the session's registry. A reconnect re-declares them for the next turn. A result arriving after its call failed is dropped and logged.]
- [default: the server sets no wall-clock bound on a device call while the connection lives, because a person deciding is the device's business and the device's own timeouts (shell 30 s, `toolsets.h:34`) bound the run. The turn's `cancel` sends `tool_cancel`, and 59b's liveness check decides "disconnected".]
- [default: the lines work on both of 59b's transports, so the conformance suite drives a scripted device over stdio. A local driver offering tools to a local child is harmless and unadvertised.]
- [default: a device's tools are offered only to sessions that device drives. Driving one device's files from another device's session (the phone editing the Mac's project) is out of scope, a ROADMAP idea.]
- (consumed decision) The definition's fields and effect hints are [60a](one-tool-definition.md)'s. The device's identity, name and pairing are [59a](../v0.2.3/paired-devices.md)'s. The connection, its framing and liveness are [59b](../v0.2.3/machine-mode-over-the-network.md)'s. A task's behaviour when its device is gone is [59e](../v0.2.3/tasks-outlive-the-connection.md)'s: by this item's rule its device tools are `unavailable`, never widened by the task's policy. The Mac's grant picker, its permission cards for device calls, and its bridge are GUI [7b](../../../gui/backlog/v0.2.4/mac-offers-its-files-and-shell.md)'s.

**Guardrail(s).**
- The never-consulted server checker pins that the device's gate decides.
- The read-only-policy case pins that the server can only narrow.
- The two-home e2e pins that the device's files change and the server's do not, and that `always` writes only the device's config.
- The disconnect, late-result and cancel cases pin clean failure.
- The planted-key case pins that no credential appears in a declaration, request, result, notice or log line.
- `cli.no_listen_symbols` and the runtime socket check pin that the device listens on nothing.
- The existing machine-mode, serve and ACP conformance suites unchanged pin that local use is untouched.

**Acceptance criteria:**
- [ ] Over a 59b connection in the e2e's two homes, a device declares its grant's tools; a served turn reads and edits a file in the device's grant; the server's launch folder is untouched.
- [ ] The device's `permissions:` decide every device call: `ask` asks the device's driver, `deny` refuses, `always` lands in the device's config. The server's `bypass` changes none of it.
- [ ] Killing the device mid-call ends that call `failed` with the unknown-outcome wording; the session and its next turn live on, without that device's tools until it reconnects.
- [ ] `chat`, `execute`, `serve` without a connected device, `acp` and the machine mode over stdio behave byte for byte as before; the full suite is green.
- [ ] With 7b, `apogee-dev` on the Mac pointed at a dev-channel server changes a project on the Mac (the user's live pass, optional and said).

**Scope note.** Earmarked for v0.2.4 (track 60); 🔒 60a, 59b. Out of scope: device tools from iPhone or iPad (clients only); one device's tools driven from another device's session; notes, retrieval or web tools offered by a device; Windows and Android devices (after v0.3.0, a recorded default); the `serve` start-up summary saying `tools: fetch_url` while 25 tools register (`serve_cmd.cpp:359`), a wording drift seen in the probe and not owned here.
