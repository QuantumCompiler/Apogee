# The machine mode over the network: one protocol, two transports

**What / why.** The user's vision, 2026-11-07: Apogee as a private, self-hosted harness that feels like Claude on every device the person owns, with a strong machine serving their own desktops and phones. The SPEC now says what `serve` carries for those devices: "sessions and their events, permission questions answered on the device" ([SPEC.md](../../assistant/SPEC.md) → Core surfaces 4, revised 2026-11-07). This item is the session half of that. A paired device gets the stdio machine mode's own events and driver lines, under the same `machine-schema`, over an authenticated network connection to the person's `apogee serve`. Re-measured 2026-11-07 on the branch binary (`apogee 0.2.0 (4f92316d)`), a scratch `APOGEE_HOME` and the mock backend:

**W2: the machine mode's sessions, events and lines are stdio-only.**
1. **The session is bound to the process's own pipes.** A driven chat writes its events to `JsonReporter machine_reporter{std::cout}` (`presentation/cli/chat_session.cpp:1739`) and reads its driver from `DriverInput driver{std::cin}` (`:1785`). Both classes already take any stream (`machine/json_reporter.h:102`, `machine/driver_input.h:46`), but nothing hands them anything but stdio. The reference says so: "It opens no sockets. Not one, ever" ([machine-mode.md](../../reference/machine-mode.md):1879).
2. **`serve` has no session protocol.** The probe's `serve --port 0` answered a WebSocket upgrade on `/v1/machine` with `404 {"error":{"message":"no route for GET /v1/machine"…}}`, and one on `/v1/harness/machine` (59a's plane, not yet built) with the same `404`. A streamed `"session_id":"new"` turn came back as four OpenAI chunks and `[DONE]`: no `session`, `thinking`, `tool_call`, `question` or `result` event. The same turn over stdio produced `session` (`next_turn: 1`, `chat_id`, `protocol_version: 1`), `thinking`, `answer_start`, two `answer_delta`, `answer_end` and `result`, each after `session` carrying `turn: 1`.
3. **Nobody can answer a served question.** "Nobody can answer a permission prompt on a served request" ([http-api.md](../../reference/http-api.md):27). Client tools are refused: `client-side tools are not supported: the server runs its own tool loop…` (`httpserver/handler.cpp:651`, the probe's reply). Inference is one turn at a time behind one mutex (`httpserver/handler.h:31-34`, `:164`; http-api.md:33-34).
4. **Nothing in the stream survives a dropped connection.** Events carry `turn` and no sequence number (the probe's stream; `__machine-schema` reads `x-apogee: {protocol_version: 1, schema: 2026-11-01}`, 32 event and 8 inbound definitions, with no word for a cursor, replay or transport). Over stdio, a closed stdin with a question outstanding fails the turn (machine-mode.md:891-892). A network transport that mapped a dropped socket onto a closed stdin would lose the turn every time a phone changed networks.
5. **The pieces exist.** The pinned cpp-httplib (`v0.56.0`, `cmake/ApogeeDependencies.cmake:256-258`) has a server-side `Server::WebSocket(pattern, handler)` with ping and missed-pong settings (its `httplib.h:2189`, `:2260-2265` as fetched). It is built with OpenSSL off (`ApogeeDependencies.cmake:262-266`), so TLS is not there yet. `apogee acp` already runs each session as a captured child of the binary's own `execute` in machine mode and relays its lines (`acp/session.h:25-53`, `acp/session.cpp:116`).

This item delivers **one protocol on two transports.** A served machine session is a child `apogee chat` or `execute` in machine mode, owned by `serve` rather than by any one connection. A device starts one, attaches to it, detaches and resumes it. It reconnects after a drop and gets the events it missed, replayed from a cursor, without losing the turn. Permission and question cards are answered by whichever device is attached. With no device attached, the session waits and its question is listed. The schema and the conformance suite cover both transports.

**Core constraint(s).**
- **The anti-goal: standalone use never needs a server** (the user's call, 2026-11-07; GUI [SPEC.md](../../../gui/assistant/SPEC.md):34). `apogee chat` and `execute` over stdio, the Mac app over pipes, and `serve` with no paired device all behave byte for byte as today. Nothing in the stdio path learns about the network. The relay sits on the child's side of the pipes, so the stdio stream gains no field.
- **Interactive = pipes, serving = server** ([CLAUDE.md](../../assistant/CLAUDE.md) → Interactive turns never open a listening socket; [SPEC.md](../../assistant/SPEC.md):66, clarified 2026-11-07: "a remote device's session is a served session, on `serve`'s port, authenticated"). The WebSocket route is registered on `serve`'s own `httplib::Server`, and `httpserver/serve.cpp` stays the one object file that may reference `listen`/`accept` (`serve.cpp:215`). A session's child holds its three pipes and no socket (`infrastructure/platform/child_process.h`, Milestone L), as an ACP session's does. The relay itself is socket-free and is tested without a port, like the handlers.
- **Admitted devices only.** Both routes sit on 59a's harness plane (`/v1/harness/`), whose gate runs before routing. Nothing is upgraded, listed or answered unless that gate admits the connection, on loopback too. The inference plane is unauthenticated (http-api.md:25), so a waiting question, which can hold a path, a command or a diff, is never listed on the public `GET /v1/sessions` (http-api.md:221-223).
- **Secrets are unleakable** (CLAUDE.md → Secrets are unleakable by construction). A device credential never reaches an event, a listing or a log line. The log names the device by 59a's device name, never by its token. The relayed events are the stdio events, which carry no secret today, and the relay adds only `seq`, ids and device names.
- **Additive** ([ADR 0006](../../adrs/backwards-compatibility.md); machine-mode.md:285 "Growth is by addition only"). The new transport lines, the new events and `seq` are additions. `protocol_version` stays `1`, and `capabilities.schema` moves. A client that ignores unknown types and fields (rule 1) reads a network stream as it reads stdio. `session` still comes first, and `question` is still the only event that waits (machine-mode.md:284).
- **Parity by construction** ([ADR 0002](../../adrs/mode-parity.md); [ADR 0011](../../adrs/one-session-opening.md)). A network session is opened through `chat`'s or `execute`'s own path, as a child, never through a second session core. A tool, a slash-command door or a permission rule reaches the network the day it reaches stdio.
- **The four layers** ([ADR 0001](../../adrs/layer-enforcement.md), `cmake/modules.cmake`). The relay lives in Presentation (`httpserver`, which already links `platform`: `modules.cmake:72-74`). The child goes through `platform::start_child`. A new link is a deliberate edit to `modules.cmake`.
- **The dev channel** (CLAUDE.md → Development runs on the dev channel). The live pass is `apogee-dev serve` over `~/.apogee-dev`, never the release `apogee` or `~/.apogee`. Tests use a temporary `APOGEE_HOME` and the mock backend.

**Seam + files.**
- `source/presentation/httpserver/machine_link.h/.cpp`: `MachineLink`, the socket-free line link (send a line, receive a line, closed, the peer's device name from 59a). `serve.cpp`'s WebSocket handler implements it, and tests use an in-memory one. One WebSocket text message carries one JSONL line, with no newline.
- `source/presentation/httpserver/machine_sessions.h/.cpp`: the registry of live network sessions. Each holds its child (`platform::ChildProcess`), started the way `acp/session.cpp:116` starts one (the argv built from an allow-listed `connect`), the event log numbered by `seq`, and the attached links. It reads the child's stdout at all times, so a slow or absent device never blocks the child. It arbitrates answers and tracks state (`running`, `waiting`, `idle`) from the events it relays. A drop never closes the child's stdin. Ending a session does, as any driver ends machine mode. It is idle-evicted by `--session-ttl` (http-api.md:31), but never while a question waits.
- `source/presentation/httpserver/serve.cpp`: the `GET /v1/harness/machine` upgrade, registered behind 59a's harness-plane gate, and ping and missed-pong settings for drop detection. It stays the only file that touches httplib's socket side.
- `source/presentation/httpserver/mux.cpp`: route rows for `GET /v1/harness/machine` and `GET /v1/harness/machine/sessions` (the listing: id, command, state, attached devices, last `seq`, and for a waiting session its question's `kind`, `tool`, `target`, header and `seq`), so `cli.http_api_conformance` holds them to the reference in both directions.
- `source/presentation/machine/protocol.h/.cpp`: the schema's network definitions. Inbound: `#/$defs/net_connect`, `net_leave`, `net_end`, and an optional `line_id` on every inbound line. Outbound: `net_connected`, `net_replay_gap`, `net_answered`, `net_refused`, and `seq`, named as optional on every event. All are printed by `__machine-schema`.
- Docs: [machine-mode.md](../../reference/machine-mode.md) gets a "Two transports" chapter (connect, attach, leave, end, resume, the cursor, the gap, answers from several devices, unattended questions), and "What machine mode does not do" is re-worded for the network transport. [http-api.md](../../reference/http-api.md) gets the two routes.
- Tests (hermetic: temporary `APOGEE_HOME`, mock backend scripted by `model_path`, `delay_ms` to hold a turn open: `data/backends/mock.h:57`, `mock.cpp:113`):
  - `tests/presentation/httpserver/machine_sessions_test.cpp`: an in-memory link and a fake child. Covers replay after a cursor, the gap, a drop that leaves stdin open, `net_end` closing it, a resend deduplicated by `line_id`, first answer wins with `net_answered` to the rest, a waiting session listed and exempt from the TTL, a revoked link closed with the session running on, and the argv allow-list.
  - `tests/scripts/py/reference_driver.py` gains `--transport stdio|network`. `cli.reference_driver` runs its scenarios over both and requires the same event sequence, with `seq` and ids removed.
  - `cli.machine_network` (`tests/scripts/py/machine_network_check.py`, a stdlib WebSocket client): the real binary under `serve --port 0` with 59a's test credential. Covers a turn, a drop mid-turn and a reconnect, a permission card answered, an unattended question listed then answered by a later attach, two devices, and a refused unpaired upgrade.
  - `cli.machine_schema_conformance` extended to the network definitions, validating both transports' captured streams.
  - `cli.complete_opens_no_listening_socket`: a phase where a network session's child, across its process tree, holds no socket.

**Reference.** [59a](paired-devices.md) (the gate, the device credential, TLS), [59c](many-sessions-at-once.md) (concurrency and the shared resident model), [59d](reads-and-commands-over-the-network.md) (`chats show` and the other reads over the network), [59e](tasks-outlive-the-connection.md) (tasks on the same transport), [60b](../v0.2.4/device-tools.md) (a desktop's tools offered over this connection), GUI [7a](../../../gui/backlog/v0.2.4/app-connection-local-or-server.md) (the app's second transport, the first client). Precedents: `apogee acp` (56a, 56c). A session there is a captured child of the binary's own `execute`, and a resume is `--resume <id>`. This item moves the host to the far side of a socket and keeps the child unchanged. The served sessions of the HTTP plane (http-api.md:185-219) are a precedent too: a session is asked for, never implied, it is a saved chat file, and an unknown id is a refusal, never a silent fresh context.

**Decisions made** (dated):
- 2026-11-07: Specced from the Apple-platforms spike and brainstorm. The user's calls: the vision (a private, self-hosted harness serving the person's own devices; no customer accounts, billing or metering; the server admits the person and their devices only); remote mode is an add-on, never the only way Apogee runs; iPhone and iPad are clients of the person's server only; work happens in server tools by default, with a connected desktop offering its own (60b); successive versions toward v0.3.0. Track 59, v0.2.3.
- 2026-11-07: The SPEC amendment is approved and already written (CLI [SPEC.md](../../assistant/SPEC.md):31 and :66; GUI [SPEC.md](../../../gui/assistant/SPEC.md):11; GUI [CLAUDE.md](../../../gui/assistant/CLAUDE.md):41-46, "It is the same protocol, with the same tolerant decoding"). This item is the CLI side of that one sentence.
- 2026-11-07: Gated on 59a. Nothing may listen for sessions before devices are authenticated. It sits in v0.2.3 because GUI 7a (v0.2.4) and every Apple client after it speak this protocol, and 59e and 60b build on its transport.
- 2026-11-07: A network session is a child owned by `serve`, as in ACP, not an in-process session. The stdio session stays the only session implementation (ADR 0011), the stream is byte for byte what a stdio driver reads, and a turn outlives its connection because the child does.

**Open calls:**
- (consumed decision: 59a) The TLS stack, the certificate, the device credential and the gate. This item rides whatever connection 59a's gate admits and refuses the upgrade on any other.
- (consumed decision: 59c) How many network sessions run at once, and whether a local model is loaded once and shared across session children. [default: until 59c ships, one live network session at a time. A `net_connect` for a second new session is refused by name (`one network session at a time on this server -- attach to <id>, or end it`). Attaching to the live one always works.]
- (consumed decision: 59d) The reads over the network, `chats show` among them. A resumed session draws its earlier turns from that read, as the Mac app does over stdio (machine-mode.md:204-205). This item replays only the live session's events.
- [default: the transport is a WebSocket at `GET /v1/harness/machine` on `serve`'s port, on 59a's harness plane. It is one bidirectional, ordered connection, already in the pinned httplib. SSE plus POST is not used: it would split one session's order across two connections.]
- [default: `seq` numbers every event the relay sends, from 1 per session. It is added by the relay on the network only, so stdio bytes are unchanged. A cursor is "the last `seq` I hold": `{"type":"net_connect","session":"<id>","after":N}` replays from N+1, then goes live.]
- [default: the replay log keeps the `session` event, every event of the open turn and the most recent turns, up to 8 MiB a session. A cursor older than that gets `session`, then `net_replay_gap` (`from`, `to`, and the read that holds the turns), then the kept events.]
- [default: `net_connect` starts (`"session":"new"`, with `command` `chat` or `execute` and an allow-list of launch options: `model`, `suite`, `private`, `permission_mode`, `cwd`), attaches (a live id) or resumes (a saved chat id with no live child, started as `--resume <id>`). A chat already live is attached, never started twice. `bypass` and `--allow-bypass` are refused over the network in this item.]
- [default: `cwd` must sit under a folder `serve --workspace DIR` names (repeatable; default the folder `serve` started in). Anything else is refused by name. Server tools touch the server's files (the user's call C). A desktop's own files are 60b's.]
- [default: `net_leave` (or a drop) detaches, and the session runs on. `net_end` closes the child's stdin. These names avoid the existing `detach` line, which detaches an attachment (machine-mode.md:722).]
- [default: several of the person's devices may attach at once. Every attached device gets every event. Lines from all of them are written to the child in arrival order. A question takes the first `answer`, and the others get `net_answered` (`seq` of the question, the device name) so they close the card.]
- [default: a waiting question has no clock, as over stdio. It is listed at `GET /v1/harness/machine/sessions` and replayed to any device that attaches. It ends when answered, cancelled or ended, or when `serve` stops, where the turn is rolled back as a closed stdin does and the saved chat stays resumable. Push notifications are out (they need the Apple Developer Program, GUI [8c](../../../gui/backlog/v0.2.5/iphone-and-ipad-distribution.md)).]
- [default: an inbound line may carry a client-chosen `line_id`. The relay drops a resend of an id it has seen in that session (the last 256 ids), and strips `line_id` before the child reads the line. A client resends what it is unsure of after a reconnect.]
- [default: a private chat may run over the network. It can be attached while live and cannot be resumed (`net_refused`: a private chat is not saved), and it logs nothing of itself, as over stdio.]
- [default: a device revoked while attached (59a hands this here) is checked by the relay before every event it sends and every line it takes. Its link gets `net_refused` (`device revoked`) and is closed. The session runs on, other attached devices are untouched, and the revoked device's unsent lines are dropped.]

**Guardrail(s).** `cli.reference_driver` over both transports pins one protocol: the same events in the same order, `seq` aside. The unchanged stdio goldens (`cli.machine_mode`, `cli.reference_driver --transport stdio`) and `serve_e2e` without a paired device pin the anti-goal. The relay's unit tests pin drop, replay, gap, dedup, arbitration and unattended waiting without a port. `cli.no_listen_symbols` and the new no-socket phase pin never-listens. `cli.http_api_conformance` and `cli.machine_schema_conformance` pin the routes and the schema against the reference. A planted device credential that never appears in an event, a listing or the log pins the secrets rule.

**Acceptance criteria:**
- [ ] A paired test device starts a chat over `/v1/harness/machine`, sends a `user` line and receives the stdio stream's events (`session` first, `turn` on each, one `result`), each with a `seq`.
- [ ] A connection dropped mid-turn (a `delay_ms` mock) and reopened with `after` gets every missed event once, the turn's `result` included, and the saved chat holds the turn.
- [ ] A permission card (a scripted `write_file`) is answered `yes` and `no` from the device, with the same tool results as over stdio.
- [ ] With no device attached, a question leaves the session `waiting`, listed with its tool and target. A device attaching later sees the question, answers it, and the turn ends.
- [ ] With two devices attached, the first answer is taken and the other device gets `net_answered`.
- [ ] An unpaired connection gets 59a's `401` before routing: no upgrade, no listing. A device revoked while attached gets `net_refused` (`device revoked`) at its next event and its socket is closed, while the session runs on.
- [ ] `apogee chat`/`execute` over stdio and `serve` without paired devices are unchanged, `__machine-schema` grows only by addition, and the full suite is green.
- [ ] The user's live pass, optional and said: `apogee-dev serve` on the dev Mac, a session started from one device, the connection dropped and resumed, a permission answered.

**Scope note.** Earmarked for v0.2.3 (track 59); 🔒 gated on 59a. Out of scope: many sessions at once and a shared resident model (59c); reads and commands over the network (59d); tasks on this transport (59e); a desktop's own tools (60a, 60b); every client (GUI 7a onward); uploads of a device's files (an `attach` names a server path, as over stdio it names one on the child's machine); push notifications (8c); the OpenAI-compatible plane, whose behavior is unchanged.
