# A vendor CLI's failure says why, and a side request never takes the conversation's session

**What / why.** The vendor-CLI backends (`claude-cli`, `codex-cli`, `gemini-cli`, `ollama-cli`) each keep a resume handle for the conversation (Claude's and Gemini's session id, Codex's thread id) and turn the child's own report into the `ProviderError` every surface shows. The second bug sweep (2026-10-31) found both halves broken. A side request (a title, a tool or reasoning summary, recall, a query rewrite, a clerk or graph extraction) can leave the conversation resuming the side request's session, so the next turn answers with no history. And a failure can come back as "reported an error: error", as a turn that failed after a full answer, as the error sentence saved as content, or as half an answer kept as if it were whole. Every finding was re-verified against the source at HEAD on 2026-10-31. The probes ran a fake vendor binary on `PATH` that logs its argv and stdin, under a temporary `APOGEE_HOME`.

1. **A claude-cli side request replaces the conversation's session id.** `pump_turn` stores every `TurnComplete`'s session id on the provider (`data/backends/claude_cli.cpp:304-308`). `run_one_shot` saves and restores `framer_` and `pending_` around its `pump_turn` (`:396-402`) but not `session_id_`. So every side request (`:425-446`) and every `complete_structured` (`:557-571`) leaves the provider holding the one-shot's session. That covers the auto-title and also the tool and reasoning summaries, recall, query rewrites, media, the clerk and graph extraction (`side_request = true` at `agentloop/loop.cpp:177`, `tool_summary.cpp:59`, `recall.cpp:135`, `query_rewrite.cpp:117`, `knowledge/clerk.cpp:300`, `graph/extract.cpp:319`, and others). A live child does not notice. A respawn does. After an effort change (`:469-478`) the new child gets `--resume <side session>` (`ensure_child`, `:231`) and only the new message. After a dead child (`:515-527`) it resumes the wrong session and replays every user message. Scenario: a claude-cli chat, turn 1 "my name is Zed", then the auto-title runs, then the effort changes (driver `{"type":"set","effort":"high"}`, the GUI's effort picker, `/effort`) or the child dies. Turn 2 "what is my name?" goes to a session that never heard turn 1. Probe: turn 1 ran in session `conv-1` and the title one-shot returned `title-sess`. After `set effort high` the log shows `ARGS: -p --input-format stream-json ... --effort high --resume title-sess` and `STDIN[title-sess]: ..."what is my name?"...`. Turn 2's result: `main answer from session title-sess`.
2. **A claude-cli side request or `complete_structured` returns Claude Code's error sentence as its answer.** The side-request path throws only when the child died with no output (`claude_cli.cpp:435-439`). Otherwise it returns `final_text` or the streamed answer (`:441-443`), and it never checks `outcome.complete.is_error` or `outcome.timed_out`. `complete_structured` (`:571-585`) falls back from the structured output to `final_text`, then to the answer, under the same blind spot. So an expired login's `Failed to authenticate: …` becomes a chat's title. The auto-title's catch (`presentation/cli/chat_session.cpp:525-531`, "a failed title is cosmetic") never fires, because nothing threw. The clerk and graph extraction get prose and report a misleading schema failure. After a timeout, a partial or empty answer passes as a result. Probe: a fake `claude` whose one-shot returns `{"type":"result","subtype":"success","is_error":true,"result":"Failed to authenticate: OAuth session expired and could not be refreshed"}`. After the session, `sessions/20261031-201645-c289.json` has the title `Failed to authenticate: OAuth session expired and could not…`. This is the one-shot half of [M34](../maintenance/claude-cli-says-why.md)'s reproduction. M34 says "is_error is honored", which is true only of the main turn (`:534-540`).
3. **A Gemini result-shaped failure reads "reported an error: error".** `parse_result` keeps only `status` (`data/backends/gemini_cli_events.cpp:37-41`) and never reads the `error` object beside it. `stream_chat` then throws `the Gemini CLI reported an error: error` (`gemini_cli.cpp:366-370`). This is the shape Gemini CLI 0.46.0's `handleError` emits for every fatal error under stream-json: `status: "error", error: {type, message}` (`/opt/homebrew/Cellar/gemini-cli/0.46.0/libexec/lib/node_modules/@google/gemini-cli/bundle/gemini-YXO2QQ66.js:10059-10069`). The top-level `{type:"error",message}` event does keep its message (`gemini_cli_events.cpp:113-118`), so only this path loses it. The exit-status fallback (`gemini_cli.cpp:326-332`) never runs either, because the parsed `error_detail` is already set. The only test (`tests/data/backends/gemini_cli_test.cpp:352-361`) uses `status: quota_exceeded`, a shape the CLI does not emit. Scenario: an exhausted quota, a failed auth or a turn limit. Every surface (the terminal, machine mode's `error`, the macOS app) says `gem: the Gemini CLI reported an error: error`, and nothing says why. Probe: a fake `gemini` emitting `{"type":"result","status":"error","error":{"type":"QuotaError","message":"You have exhausted your daily quota..."}}` plus stderr. The machine event was `{"message":"gem: the Gemini CLI reported an error: error","turn":1,"type":"error"}`. M34's scope note leaves Gemini out because it "already carries its CLI's text". That premise is wrong for this path.
4. **A Gemini warning fails a turn that succeeded.** Every `type:"error"` event becomes an error `TurnComplete` with `severity` ignored (`gemini_cli_events.cpp:113-118`). `run_turn` latches `is_error` (`gemini_cli.cpp:279-282`), and the later `result` with `status: success` never clears it. So `stream_chat` throws (`:366-370`) after the answer has already streamed. Gemini CLI 0.46.0 emits `severity: "warning"` error events and then a successful result in several cases: `Loop detected, stopping execution` (`gemini-YXO2QQ66.js:10915-10923`), agent execution blocked (`:10614-10625` and `:10973-10984`), and, on the ADK path, any non-fatal error other than `RESOURCE_EXHAUSTED` (`:10630-10645`). Scenario: the user watches the answer stream, then gets `error: gem: the Gemini CLI reported an error: Loop detected, stopping execution`, and the turn is dropped from history. Probe: a fake `gemini` sending a warning event, then an assistant message, then a successful result. Output: `answer_start`, `answer_delta "Here is the answer."`, then `{"message":"gem: the Gemini CLI reported an error: Loop detected, stopping execution","turn":1,"type":"error"}`.
5. **A failed first Gemini turn leaves a session the CLI never created, and every later turn resumes it.** `run_turn` mints the session id before spawning (`gemini_cli.cpp:211-214`). Nothing clears it when the turn fails: not the result-error throw in `stream_chat` (`:366-370`), not `run_turn`'s spawn-failure throw (`:228-231`), not its timeout throw (`:294-297`). `end_session()` (`:197-199`) has no caller. In a long-lived chat (the REPL, `serve`, the app), every later turn passes `--resume <id>` with only the latest message (`prompt_for(..., true)`, `:357`). If the CLI never recorded that session, the resume is refused every time (`Invalid session identifier` / `No previous sessions found`, `bundle/chunk-MKQJU6N7.js:9881-9899`). That happens when the binary failed to spawn, or exited at an auth, quota or startup error before writing the session. The chat stays broken after the user fixes the cause, and only a new chat recovers. When the CLI did record the session before failing, resuming with only the new message is correct, so the bug is the unrecorded case. Scenario: the first turn fails while signed out or out of quota. The user signs in and asks again. Every turn fails until a new chat. Probe: a fake `gemini` whose turn 1 returns a result error and which refuses any `--resume`. argv: turn 1 `--session-id 4d7a2088-...`, then turn 2 `--resume 4d7a2088-... --prompt again` (no history). Turn 2's event: `gem: the Gemini CLI reported an error: exited with status 1: Error resuming session: No session found`.
6. **A codex or gemini side request that throws leaves the conversation on the side request's thread or session.** Both `stream_chat`s clear the handle for a side request and put it back only on the normal return (`gemini_cli.cpp:351-364`, `codex_cli.cpp:427-441`). Nothing restores it on a throw: cancellation (`gemini_cli.cpp:298`, `codex_cli.cpp:278`), the turn timeout (`gemini_cli.cpp:294-297`, `codex_cli.cpp:274-277`) or a failed spawn (`gemini_cli.cpp:228-231`, `codex_cli.cpp:218-221`). After cancellation or a timeout, the conversation resumes the side request's session (Gemini always, since the id is minted before the spawn) or its thread (Codex, once the side child emitted `thread.started`, `codex_cli.cpp:265`). The model then answers without the conversation's history. After a failed spawn, Codex is left with the thread cleared. The next turn starts a fresh thread and replays the full history, so only the resume handle is lost. Gemini is left with a freshly minted id the CLI never created, as in 5. Scenario: Ctrl-C (or a driver `cancel`) while the validate objection or a query rewrite runs on a codex-cli or gemini-cli chat, or a side request hits the turn timeout. The next turn runs `codex exec resume <side-thread>` or `gemini --resume <side-session>`.
7. **An ollama-cli turn that exits non-zero after a partial answer is kept as whole, and its error is dropped.** The failure check requires an empty answer (`data/backends/ollama_cli.cpp:243`). So a run that streams some text and then exits non-zero returns that text as a complete turn (`:249-252`, `FinishReason::Stop`), and the stderr gathered at `:233-240` is thrown away. No unit test covers a non-zero exit. Scenario: the Ollama server or a cloud model fails mid-generation. The user sees half an answer as if it were complete, the turn is saved, and the CLI's `Error:` line reaches no surface. Codex and Gemini have the same check (`codex_cli.cpp:303`, `gemini_cli.cpp:326`), but their stream events set `is_error` first.

What already works: a side request on a live claude-cli child never touches the child's stdin or framing (`claude_cli.cpp:394-402`). Codex's failed side-request spawn keeps the conversation's context. A top-level Gemini `error` event carries its message. Codex and Gemini name their CLI's text when the exit is non-zero and nothing streamed. And M34 covers the claude main turn's "reported success".

**Core constraint(s).**
- **[A child's stderr is captured, never inherited](../../assistant/CLAUDE.md#-a-childs-stderr-is-captured-never-inherited).** A vendor CLI's bounded 8 KiB tail is folded into the failure message when the child fails. Ollama's partial-answer failure is that case, and it must carry the tail.
- **[A change propagates to every mode](../../adrs/mode-parity.md)** (ADR 0002). The `ProviderError` each backend throws is what the terminal, `serve` and machine mode all show, so each fix lands at the throw, once.
- **[Older versions keep working](../../adrs/backwards-compatibility.md)** (ADR 0006). Machine mode's `error` event keeps its shape. Only its message improves.
- **[Text is UTF-8 where it enters](../../assistant/CLAUDE.md#-text-is-utf-8-where-it-enters-so-no-json-dump-can-throw-on-it).** A vendor's error text and stderr tail reach machine mode's writer, which already says invalid bytes as U+FFFD. Nothing new is dumped strictly.
- **[Development runs on the dev channel](../../assistant/CLAUDE.md#development-runs-on-the-dev-channel).** Probes and tests are hermetic: a temporary `APOGEE_HOME`, the scripted spawner, fake binaries. Any live pass names `apogee-dev`, never `apogee` or `~/.apogee`.
- The item's own rules:
  - **A side request is not a turn of this conversation** (Milestone H's titling row, and each backend's own comment). It leaves the conversation's resume handle exactly as it found it, on every exit path, thrown or returned.
  - **A failure reaches the person in the vendor's own words**, with Apogee's paraphrase only where the vendor gave none.

**Seam + files.**
- `data/backends/claude_cli.cpp/.h`:
  - `run_one_shot` saves and restores `session_id_` around `pump_turn`, beside `framer_` and `pending_`.
  - The side-request path and `complete_structured` throw on `is_error` and on `timed_out`, with the main turn's message: one function shared with M34's wording.
- `data/backends/gemini_cli_events.cpp/.h`:
  - `parse_result` reads `error.message` (and `error.type`) into the failure detail.
  - A `type:"error"` event with `severity: "warning"` becomes a `Notice`, not a `TurnComplete`.
- `data/backends/gemini_cli.cpp/.h`:
  - `stream_chat` restores the saved session on every exit (a scope guard over `:351-364`).
  - A failed Fresh turn clears the id it minted, whatever the cause: the result error, the spawn failure, the timeout, cancellation.
  - A warning `Notice` goes out through `on_status`, and the turn is kept.
- `data/backends/codex_cli.cpp/.h`: `stream_chat` restores the saved thread on every exit (the same guard over `:427-441`).
- `data/backends/ollama_cli.cpp`: a non-zero exit fails the turn whatever streamed, with the stderr tail in the message.
- Tests mirror the sources:
  - `tests/data/backends/claude_cli_test.cpp`: the session handle after a side request and after `complete_structured`. The effort respawn and dead-child resume use the conversation's session. One-shot `is_error` and timeout throw.
  - `tests/data/backends/claude_cli_events_test.cpp`, only if the event shape grows.
  - `tests/data/backends/gemini_cli_test.cpp`: the 0.46.0 result-error shape replacing the invented `quota_exceeded` fixture. A warning, then an answer, then success. A failed first turn, then a Fresh second. A cancelled or timed-out side request.
  - `tests/data/backends/codex_cli_test.cpp`: a cancelled or timed-out side request after `thread.started`.
  - `tests/data/backends/ollama_cli_test.cpp`: a partial answer, then a non-zero exit.

**Open calls:**
- [default: Gemini's result-error message is `the Gemini CLI reported an error: <error.message>`. `error.type` (e.g. `QuotaError`) is added only when there is no message, and goes in the structured log line either way. The exit-status-and-stderr fallback still applies when the result carries neither.]
- [default: a Gemini `error` event with `severity: "warning"` is a notice on the status line, and the turn stands on its `result`. A `severity: "error"` event, or one with no severity (the older shape), fails the turn as today, and a later successful `result` does not clear it.]
- [default: a failed Fresh Gemini turn clears the id it minted. A failed Resume turn keeps its id, since the CLI recorded that session and resuming with only the new message is right. No resume-refused-then-Fresh fallback is added here. If one is wanted later, claude-cli's (`claude_cli.cpp:240-250`) is its model.]
- [default: each handle is restored by a small scope guard in `stream_chat` (Codex, Gemini) and `run_one_shot` (Claude), not by catch-and-rethrow, so a new throw site added later is covered.]
- [default: a claude-cli one-shot with `is_error` throws before any structured output or prose is considered. One that timed out throws `the Claude CLI did not finish in time` even with a partial answer. The callers already handle a `ProviderError`: the titler records no title, and the clerk and extraction report the failure.]
- [default: an ollama-cli non-zero exit after a partial answer fails the turn with the stderr tail, as the empty-answer case does today. The partial text is not kept as a turn. Keeping it with a non-`Stop` finish reason is not taken: `FinishReason` has no error member, and the other backends fail the turn.]
- [default: Codex's and Gemini's own "non-zero exit with an empty answer" checks are left as they are. Their stream events set the failure first, and no finding shows them wrong.]

**Guardrail(s).** Each finding's failure is a regression test on the scripted spawner, hermetic (a temporary `APOGEE_HOME`, no real vendor binary, no network):
- claude-cli, the session handle: after a side request and after a `complete_structured`, `session_id()` is unchanged. The effort-change respawn's argv names the conversation's session, never the one-shot's. A dead-child respawn resumes the conversation's session.
- claude-cli, the one-shot failures: a one-shot `is_error:true, subtype:"success"` result throws with Claude Code's text, and the titler saves no title. A timed-out one-shot throws. `complete_structured` with `is_error` throws rather than returning the sentence.
- Gemini, the message: the 0.46.0 result shape replays as `reported an error: You have exhausted your daily quota...`, never `: error`. It replaces the invented `quota_exceeded` fixture.
- Gemini, warnings: a warning event, then an answer, then `status: success` returns the answer and emits one status notice. A `severity: "error"` event still fails.
- Gemini, the first turn: a failed first turn (a result error, a spawn failure, a timeout) leaves `session_id()` empty, and the next turn's argv is `--session-id`, never `--resume`. A failed resumed turn keeps its id.
- Codex and Gemini, a throwing side request: a cancelled or timed-out side request (Codex after `thread.started`) leaves the conversation's handle as it was. The next turn's argv resumes the conversation's thread or session.
- ollama-cli: a partial answer followed by a non-zero exit throws with the stderr tail, and no turn is returned.
- A machine-mode run over the Gemini and Claude fixtures carries the vendor's text in its `error` event.

Optional live pass, on `apogee-dev` only, with the user's own logins: a claude-cli chat survives a title and an effort change remembering turn 1, and a gemini-cli chat answers.

**Acceptance criteria:**
- [ ] In a claude-cli chat, "my name is Zed", then the auto-title, then an effort change (or a dead child), "what is my name?" is answered from the conversation's own session. No side request or `complete_structured` changes the session id.
- [ ] An expired Claude login during a side request saves no title. The chat keeps its untitled name, and no error sentence appears in `chats list` or the app's history.
- [ ] A Gemini quota, auth or turn-limit failure reads `the Gemini CLI reported an error: <the CLI's message>` on the terminal and in machine mode's `error` event, never `reported an error: error`.
- [ ] A Gemini turn with a warning event and a successful result keeps its answer, saved in history, and shows the warning as a notice.
- [ ] After a failed first Gemini turn, fixing the cause and asking again in the same chat answers. No later turn `--resume`s a session the CLI never created.
- [ ] Cancelling or timing out a side request on a codex-cli or gemini-cli chat leaves the next turn resuming the conversation's own thread or session, with its history.
- [ ] An ollama-cli run that fails mid-generation fails the turn with the CLI's `Error:` line, and the partial answer is not saved as a complete turn.
- [ ] The full suite is green.
