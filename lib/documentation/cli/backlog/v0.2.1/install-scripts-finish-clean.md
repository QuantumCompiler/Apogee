# The install scripts finish clean and uninstall takes back what they wrote

**What / why.** `install.sh` and `install.ps1` are how every user who does not build from source gets Apogee, and since 2026-10-31 they are also how the user's own production install is updated ([Development runs on the dev channel](../../assistant/CLAUDE.md#development-runs-on-the-dev-channel)). The second bug sweep (2026-10-31) found that a fully successful `install.sh` run exits 1 and leaves its download behind, that the 2026-09-06 zsh-completion fix never reached `install.sh`, and five smaller ways the two scripts and `apogee uninstall` differ from what they say. Each was re-read at HEAD the same day:

1. **A successful `install.sh` exits 1 with `tmp: unbound variable` and leaves its temp directory behind.** `tmp` is declared `local` in `main()` (`lib/scripts/install.sh:72`), set at `:82`, and the EXIT trap at `:86` is single-quoted, so `"$tmp"` is expanded only when the trap fires. On a successful run that happens after `main "$@"` (`:141`) has returned and `tmp` is out of scope. Under `set -u` (`:27`) the trap then fails, and the script exits 1. Only the `die()` paths, which exit while still inside `main`, clean up. *Scenario:* `curl -fsSL .../install.sh | bash` on a clean machine installs the binary, `check --fix` and `bootstrap` succeed, the PATH note prints, and then the last line is `tmp: unbound variable` and the pipeline exits 1. Any wrapper or CI step treats the install as failed, and `$TMPDIR/tmp.XXXX` keeps `apogee-<target>.tar.gz`, the extracted binary and `completions/`. *Probe (sweep):* in a scratch HOME, PREFIX and TMPDIR, with a stub `curl` serving a fake archive, `bash lib/scripts/install.sh </dev/null` ended with `install.sh: line 1: tmp: unbound variable` and `exit=1`. The leaked dir `/var/folders/.../T/tmp.htbn5zkpUZ` held `apogee`, `apogee-macos-arm64.tar.gz` and `completions/`. Three older leaked installer dirs on this Mac (`tmp.AXTJqR8hQN`, `tmp.Aaqn1JD8qR`, `tmp.z38bHQyk7q`) each held `apogee-macos-arm64.tar.gz`. *Re-probe (2026-10-31, the same pattern alone in a scratch script):* `tmp: unbound variable`, `exit=1`, and the directory left behind, under both Homebrew bash 5.3.9 and macOS `/bin/bash` 3.2.57. The code dates from 502e45de (v0.1.0, 2026-09-01). `cli.install_parity` only greps the script's text (`tests/scripts/sh/install_parity.sh:97-110`), so nothing runs it.
2. **`install.sh` still puts the zsh completion where zsh does not look.** This is a **regression of CLI MILESTONES.md:2256** (2026-09-06: "The installer now cross-references zsh's real `fpath`"). That fix landed only in `make install`: `lib/src/cli/Makefile:237-266` asks zsh for its `fpath`, takes the first of `~/.zfunc`, `~/.oh-my-zsh/completions`, `~/.local/share/zsh/site-functions` that is on it and writable, and otherwise prints an `fpath+=` note. Its comment at `:241-243` records why: installing to a fixed `~/.local/share/zsh/site-functions` "wrote a file zsh never reads, so completion silently did nothing". `install.sh:129-133` still does exactly that, an unconditional `mkdir -p "$HOME/.local/share/zsh/site-functions"` and `install`, with no note. Stock macOS zsh does not have that directory on its fpath. This host's `zsh -f -c 'print -l $fpath'` prints `/usr/local/share/zsh/site-functions`, `/usr/share/zsh/site-functions` and `/usr/share/zsh/5.9/functions` (re-run 2026-10-31). *Scenario:* a curl-installed user on stock macOS zsh types `apogee <TAB>` and nothing completes. `whence -w _apogee` reports `none`, the symptom MILESTONES records as fixed, and nothing tells them to extend `fpath`. *Probe (sweep):* `install.sh` wrote `home/.local/share/zsh/site-functions/_apogee` and printed no fpath note. `DEVELOPER.md:928` also says zsh is checked "autoloaded from `fpath` — how both installers place `_apogee`", which is true of the Makefile only.
3. **Both installers create completion directories for shells the user does not have, against their own stated rule.** `install.sh:121-123` says "Only where the shell already looks. Creating a config directory for a shell the user does not run is litter", but `:124-138` checks only that the stub is in the archive (`[ -f "$from/completions/..." ]`) before it runs `mkdir -p` for bash, zsh and fish. `make install`'s `install-completions` (`lib/src/cli/Makefile:226-233`) states the same rule ("A shell the user does not run gets nothing") and runs the same unconditional `mkdir -p` for bash and fish. *Scenario:* a zsh-only Mac user installs with curl and ends up with `~/.config/fish/completions/apogee.fish` and `~/.local/share/bash-completion/completions/apogee` although fish was never installed. *Probe (sweep, an empty HOME, no fish):* after `install.sh`, `find home -type f` listed `home/.config/fish/completions/apogee.fish`, `home/.local/share/zsh/site-functions/_apogee` and `home/.local/share/bash-completion/completions/apogee`. This Mac has no `fish` on PATH and has `~/.config/fish/completions/apogee.fish` (read 2026-10-31).
4. **`apogee uninstall` leaves behind completions the installers wrote somewhere other than its fixed list.** `completion_candidates()` (`lib/src/cli/source/presentation/cli/uninstall.cpp:24-42`) plans four fixed paths (`:36-41`). The zsh one is `~/.local/share/zsh/site-functions/_apogee` only, while `make install` may have written `_apogee` to `~/.zfunc` or `~/.oh-my-zsh/completions` (the loop at `Makefile:250`). The PowerShell one is `home / "Documents" / ...` (`:40`), while `install.ps1:78` writes under `[Environment]::GetFolderPath('MyDocuments')`, which is not `$HOME\Documents` when Documents is redirected (OneDrive). *Scenario:* an oh-my-zsh user runs `make install`, so `_apogee` lands in `~/.oh-my-zsh/completions`, and later `make uninstall`. The plan does not list the file, and zsh keeps loading an `_apogee` that calls a binary that is gone, on every completion. On Windows with OneDrive-redirected Documents, `apogee.ps1` survives uninstall the same way. This Mac has `~/.zfunc/_apogee` and `~/.local/share/zsh/site-functions/_apogee` (read 2026-10-31), and uninstall would plan only the second. A stale stub is left behind, but no data is lost.
5. **A version without the leading `v` asks for a URL that returns 404.** `install.sh:31,79` (`APOGEE_VERSION`) and `install.ps1:52-56` (`-Version`) put the value into `.../releases/download/<value>/<archive>` unchanged. Release tags carry the `v`, and `gh release list` shows `v0.2.0`, `v0.1.9` and so on. *Scenario:* `curl ... | APOGEE_VERSION=0.2.0 bash` fetches `https://github.com/QuantumCompiler/Apogee/releases/download/0.2.0/apogee-macos-arm64.tar.gz`, which returns 404 (checked live by the sweep; `v0.2.0` returns 200), and dies with `could not download <url>`. `install.ps1 -Version 0.2.0` fails the same way (`:55`). `lib/src/cli/Makefile:381-384` accepts both spellings (`VERSION_NUM := $(patsubst v%,%,$(VERSION))`, `TAG := v$(VERSION_NUM)`), but the installers do not. `APOGEE_VERSION` is documented nowhere: `git grep` finds it only at `install.sh:31` and in the unrelated compile definition. `install.ps1`'s help says "Release tag" (`:28`). The error does print the failing URL.
6. **`install.ps1`'s PATH advice copies the whole machine PATH into the user PATH.** The check at `install.ps1:97-98` reads the User scope (`GetEnvironmentVariable('Path', 'User')`), but the suggested command at `:101` writes `"$binDir;$env:Path"`, which is the merged process PATH (machine + user, already expanded), into the User scope. *Scenario:* a user who runs the printed line gets every machine PATH entry copied into the User PATH, and `%VAR%` user entries are frozen at their expanded values. Each new process then sees every system directory twice, and later machine-level changes (an uninstalled SDK, a moved JDK) stay behind in the user copy. The current session's `$env:Path` is not updated either, so `apogee` still does not resolve until a new shell is opened. The note prints only while `binDir` is missing from the User PATH, so a reinstall does not grow PATH by itself. It grows again only if the user re-runs the line by hand.
7. **`install.ps1` run the documented way leaves `$ErrorActionPreference = 'Stop'` and its variables in the user's session.** The documented way is `irm ... | iex` (`install.ps1:6`, `README.md:22`), which runs the script in the caller's own scope. `$ErrorActionPreference = 'Stop'` (`:37`) is never restored, because the `finally` at `:104-106` only removes `$tmp`. `$target`, `$archive`, `$url`, `$tmp`, `$binary`, `$binDir`, `$completionSource` and `$completionDir` stay defined, and `$tmp` names a folder that has already been deleted. *Scenario:* for the rest of that window, a command that would normally report an error and carry on stops at the first one. `Get-ChildItem -Recurse` over a tree with one unreadable folder halts there, and a multi-path `Remove-Item` with one missing path stops partway through.

What already works: the binary is installed and `check --fix` and `bootstrap` run on every path (`cli.install_parity` holds the order). `install.sh`'s `die()` paths clean the temp directory. `make install`'s zsh placement and note are right. `install.ps1`'s User-PATH check reads the right scope, and its `finally` removes `$tmp`. Uninstall already plans only paths in the user's home and never a package manager's.

**Core constraint(s).**
- **One layout declaration, and every install path reads it**: the scripts still create no part of `~/.apogee`. The fix touches only their own steps (the download, the completions, the PATH note), and `cli.install_parity` stays green.
- **Development runs on the dev channel**: both scripts are the release channel's installers and updaters, the user's production install's update path. No probe, test or live pass runs them against the real `HOME`, `~/.local/bin` or `~/.apogee`. A run is a scratch `HOME`, `PREFIX`, `TMPDIR` and `APOGEE_HOME`, with `APOGEE_MINIMAL_INSTALL=1` and a stub `curl` serving an archive packed from the test's own build. `~/.zfunc`, `~/.config/fish` and the other files on this Mac are read, never cleaned up by the item.
- **The release channel is byte-identical** apart from these fixes: the archives' contents, the binary's channel bake and the dev and test channels' "no completions" rule (`uninstall.cpp:25-30`) are unchanged.
- **A shell the user does not run gets nothing**, as both scripts already say: a completion directory is created only for a shell that is on PATH, and the zsh stub goes only to a directory on zsh's real `fpath`, or to the fallback with the note.
- **Uninstall removes only what Apogee's installers write** (`uninstall.cpp:19-23`): the candidate list grows to exactly the places the installers can write, all of them under the user's home or Documents folder, and never a directory a package manager owns.
- **An installer advises, it never edits the user's shell or environment setup**: no `.zshrc` and no User PATH is written. The PATH and `fpath` notes stay advice, now correct advice.

**Seam + files.**
- `lib/scripts/install.sh`: `tmp` at script scope, assigned before the trap is set. Completions gated on the shell being present (`command -v zsh` / `fish`; bash is the interpreter running the script). The zsh target picked as `Makefile:247-266` picks it (`zsh -i -c 'print -l $fpath'`, the same three directories in the same order), with the same fallback note. `APOGEE_VERSION` taking `0.2.0` or `v0.2.0`. A header line documenting `APOGEE_VERSION`.
- `lib/scripts/install.ps1`: the body after `param()` runs in a child scope (`& { ... }`). `-Version` normalised to `v<x.y.z>`. The PATH note's line built from `[Environment]::GetEnvironmentVariable('Path','User')`, prepending `binDir` to `$env:Path` too, so the line the user runs fixes both the stored PATH and the current session.
- `lib/src/cli/Makefile`: `install-completions` (`:226-235`) creating the bash and fish directories only for a shell on PATH, as `install.sh` will.
- `lib/src/cli/source/presentation/cli/uninstall.cpp` (`completion_candidates`): the zsh stub in each of the three Makefile directories, and the PowerShell stub under the Documents known folder as well as `home/Documents`. The list becomes a function of its inputs (home, Documents folder, channel), so a test can supply a redirected Documents. `lib/src/cli/source/infrastructure/platform/platform.h/.cpp` gains `documents_directory()` (`SHGetKnownFolderPath(FOLDERID_Documents)` on Windows, none elsewhere).
- Tests: a new `tests/scripts/sh/install_script_check.sh`, registered as `cli.install_script` in `tests/CMakeLists.txt` beside `cli.install_parity` (UNIX). `tests/presentation/cli/lifecycle_test.cpp` (the uninstall candidates). `tests/infrastructure/platform/platform_test.cpp` (`documents_directory()`).
- Docs: `README.md` (one line naming `APOGEE_VERSION` / `-Version`), CLI `DEVELOPER.md:928` (the "both installers" sentence made true) and the new test's paragraph beside it.

**Reference.** CLI MILESTONES.md:2256, the 2026-09-06 zsh fix that item 2 regresses: its selection and note are the code `install.sh` adopts. `cli.install_parity` (M10, 51) reads all three installers' text for the `check --fix` and then `bootstrap` order. This item adds the case that runs one. The Makefile's version normalisation (`:381-384`) is the precedent for item 5. Siblings in this sweep: [windows-text-and-console.md](windows-text-and-console.md) and [windows-filesystem-safety.md](windows-filesystem-safety.md) own the binary's Windows behaviour, and this item owns only `install.ps1`.

**Open calls:**
- [default: `install.sh` and the Makefile keep their own copy of the zsh selection (a curl-run script cannot source a repo file), and `cli.install_script` holds the two lists of directories and uninstall's candidates to the same set by reading them. Moving completion placement into the binary (a hidden verb both installers call, the way `check --fix` owns the layout) is the structural alternative, left for a later item if the copies drift.]
- [default: bash completions install whenever `install.sh` runs (bash is running it). zsh and fish install only when `command -v` finds them. Litter earlier installs left behind is not swept: uninstall already removes the stub files, and the empty directories are left alone.]
- [default: `install.ps1` runs its body in `& { ... }`. Whatever `iex` still binds in the caller's scope (the `param()` defaults) is checked on a Windows host at build and said in the record. If none is available, the PowerShell half is verified by reading, as `cli.shell_completion` already records for PowerShell.]
- [default: a version that is not `latest` and lacks a leading `v` gets one. Anything else passes through unchanged, so a bad tag still 404s, and the error keeps naming the URL.]

**Guardrail(s).**
- `cli.install_script` (new) runs `install.sh` for real in a sandbox: `HOME`, `PREFIX`, `TMPDIR` and `APOGEE_HOME` in its work dir, `APOGEE_MINIMAL_INSTALL=1`, a stub `curl` on PATH that records the URL it was asked for and serves an archive packed from the build's binary and `completions/`, and a stub `zsh` that prints a chosen `fpath`. It requires: exit 0 and an empty `TMPDIR` afterwards (entry 1). With `~/.zfunc` on the stub `fpath`, `_apogee` there. With nothing usable on it, the fallback and the `fpath+=` note (entry 2). No `fish` on PATH means no `~/.config/fish` (entry 3). `APOGEE_VERSION=0.2.0` and `v0.2.0` both request `.../download/v0.2.0/...` (entry 5). Then the installed binary's `uninstall --yes` leaves no file the script wrote (entry 4, end to end). It also reads `install.ps1` and fails on `$env:Path` in the User-scope write (entry 6), on a body outside a child scope (entry 7) and on a version passed through unnormalised (entry 5), and holds the three zsh directory lists to one set.
- `lifecycle_test.cpp`: `_apogee` in `~/.zfunc` and in `~/.oh-my-zsh/completions` is planned. `apogee.ps1` under a supplied, redirected Documents folder is planned. A file outside the candidate set is never planned. The dev channel still plans none.
- Each check is verified against the unfixed script or code it guards (the sweep's probe is the expected failure for entries 1-3).

**Acceptance criteria:**
- [ ] A sandboxed `install.sh` run that installs exits 0, prints no `unbound variable`, and leaves nothing in `TMPDIR`.
- [ ] On a zsh whose `fpath` holds none of the three directories, `install.sh` prints the same `fpath+=` note `make install` prints. With one of them on `fpath`, `_apogee` lands there, and `apogee <TAB>` completes in a fresh zsh with that fpath.
- [ ] Neither installer creates `~/.config/fish` (or a bash-completion directory) for a shell that is not on PATH.
- [ ] `apogee uninstall` lists and removes `_apogee` from `~/.zfunc` or `~/.oh-my-zsh/completions`, and `apogee.ps1` from a redirected Documents folder.
- [ ] `APOGEE_VERSION=0.2.0` and `-Version 0.2.0` install v0.2.0, and `APOGEE_VERSION` is documented in the script header and README.
- [ ] `install.ps1`'s PATH line, as printed, adds only `binDir` to the stored User PATH and makes `apogee` resolve in the current window.
- [ ] After `irm ... | iex`, `$ErrorActionPreference` is what it was before and none of the script's working variables are defined.
- [ ] `cli.install_parity` and `cli.shell_completion` stay green, and the full suite is green.

**Scope note.** Earmarked for v0.2.1 (track 57). Ungated. The installers are fetched from `stable`'s raw URL, so the fix reaches curl and `irm` users when the v0.2.1 merge lands. Deliberately out: cleaning up litter or leaked temp directories that earlier installs left on users' machines (the three leaked dirs and `~/.config/fish` on this Mac included), installing completions on the dev and test channels, writing the User PATH or `.zshrc` for the user, a PowerShell runner job in CI, and the binary's own Windows behaviour (the Windows siblings above).
