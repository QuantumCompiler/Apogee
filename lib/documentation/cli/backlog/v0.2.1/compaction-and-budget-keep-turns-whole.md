# Compaction and the context budget keep turns whole and say truly what they cut

**What / why.** Compaction and the per-request budget decide what a model is sent. Six ways they get it wrong today: one leaves a chat that fails every later request, one silently drops an attached file, and four send the model or the user something false. The chat is the worst case. A compaction after a failed or cancelled tool step keeps a tool call with no result, and every later request to Anthropic is refused. The item fixes all six in `business/agentloop/` and `presentation/cli/`, so each turn is sent whole: a tool call travels with its results, an attachment stays on its message, the user's own answers are never stubbed, and a trim notice names what it cut. Found by the second CLI/GUI bug sweep (2026-10-31). Every file:line below was re-read at HEAD `b26550bb`, and paths are under `lib/src/cli/source/`.

1. **Compaction keeps a tool-calling assistant message and drops its tool results.** `compact_history` keeps "the most recent assistant message" whatever it carries (`business/agentloop/content.cpp:159-166`). A turn that fails or is cancelled after at least one completed tool phase leaves `…, user, assistant{tool_calls}, tool` in the history. The loop rolls back only the phase that aborts (`loop.cpp:577-580`, `:716-722`). A failure in the next model step (`loop.cpp:520-525`) keeps the finished phase, and the turn's catch saves it (`presentation/cli/chat_turn.cpp:313-325`). Compaction then keeps `assistant{tool_calls}` and folds its `tool` result into the summary. The orphan sits ahead of any user message, so `drop_exchanges` never removes it (`budget.cpp:209-218`). It is sent on every later request, where Anthropic's wire makes it a `tool_use` block with no `tool_result` (`data/backends/anthropic_wire.cpp:204`, `:217-221`). A re-compaction cannot clear it: with no newer plain answer it finds the same message to keep, and with no user message it folds nothing (55b, `content.cpp:113-121`). The same function serves `/compact`, auto-compaction at 90% (`chat_turn.cpp:76`), `chats compact` (`chat_history.cpp:567`) and `serve` (`httpserver/handler.cpp:413`). Scenario: a GUI chat on Anthropic with tools. The model calls `list_directory`, and the next step fails (429/529/5xx) or the user presses Ctrl-C while the answer streams. The user then compacts, or auto-compaction fires on the next turn. Every later turn gets a 400 (`tool_use ids were found without tool_result blocks`), and the chat stays stuck. Probe (the real binary, a temp `APOGEE_HOME`, the mock `actor` as the compactor). A saved chat held `[user q1, assistant done, user 'list it', assistant{tool_calls call-A list_directory}, tool{call-A 'a.txt'}]`, the state a failed or cancelled step leaves. `apogee chats compact <id> --yes` printed `compacted ...: 5 messages into 2`, and the file then held `{role:system, 'The following is a summary...SUMMARY'}` and `{role:assistant, content:'', tool_calls:[{id:'call-A', function:{name:'list_directory'}}]}`. The result for `call-A` was gone. This is a **regression of Milestone F's loop entry** ([MILESTONES.md](../../assistant/MILESTONES.md):517, the loop "rolls the half-turn back"), since compaction recreates the state that rollback exists to prevent.
2. **`/system` and the GUI's `set system` shift every message index, but the attachment anchors are not shifted, so an inlined attachment is silently dropped.** `set_system_prompt` inserts a system message at the head when no prompt was held, and erases it when the prompt is cleared (`presentation/cli/chat_session.cpp:289-295`). Either way, every later message moves by one. The attachment anchors `Attachment::inline_at` and `map_at` are absolute message indexes, set in `for_turn` (`presentation/cli/chat_attachments.cpp:899-908`), and nothing shifts them. On the next turn the Assembler finds a message at the anchor that is not the user's, and drops the attachment as "its message is gone" (`business/agentloop/budget.cpp:140-145`). `after_turn` then resets `inline_at` for good and tells the user the file "no longer fits the conversation whole" (`chat_attachments.cpp:1022-1031`). A folder's map card is reset the same way, with its own notice (`:1000-1011`). Both doors take this path: `/system` in the REPL (`chat_session.cpp:2437`) and the machine-mode `set` line (`:1681-1682`), which the macOS app sends from its settings (`lib/src/darwin/source/data/protocol/DriverLine.swift:81`). A saved chat's `chats show` also places its attachments by the stale indexes (`data/logger/session.cpp:791`). Scenario: attach a 36-byte `notes.txt` and ask "one", and the file is inlined on that message. Then set a system prompt and ask "two". The file is no longer sent, and the user is told it no longer fits, though the window is 32k. Probe (machine mode, the mock with `--context-size 32768`; lines `attach notes.txt`, `user 'one'`, [`set system 'Be terse.'`], `user 'two'`). Without the `set`, turn 1 is inlined (`ok: --- attached file: notes.txt --- ...`) and turn 2 has no notice. With it: `notice: system prompt updated -- from the next turn`, then on turn 2 `notice 2 .../notes.txt no longer fits the conversation whole -- its excerpts are retrieved from now on`. This is a **regression of 52d's `/system` fix** (`chat_session.cpp:276-280`, "found 2026-10-20"): the prompt is now added or removed at the head without moving the anchors.
3. **The schema correction and the objection re-ask send that turn's own tool results as stubs that say "call it again".** A failed schema check pushes a correction as a user message and runs again (`business/agentloop/structured.cpp:184-185`). `run` computes the turn's start as the last user message (`loop.cpp:339`, `current_turn_start` at `budget.cpp:477-484`), so the tool results the bad answer was built on now count as an earlier turn's. They are stubbed with `kFinishedWhy`, "not kept after its turn -- call it again if you need it" (`budget.cpp:18`, `:490-506`). The objection side request does the same: it appends its question, then assembles with `current_turn_start(asked)`, and sets no tools (`loop.cpp:166-182`). Stubbing ignores the window (the Assembler always stubs before `turn_start`, `budget.cpp:134`), so this happens on every backend, even when everything would fit. On the schema path the tools are still offered, so the model can follow the stub, at the cost of a second full read. On the objection path it cannot follow it. The objection's revised answer is shown as a notice and kept in `result.answer_check`, never in history, so what is wrong is user-visible output, not saved state. Scenario: `apogee analyze` with an agent that has tools and a schema. The model reads a 40 KB file and answers with JSON that misses one required field. The corrective turn sees only a stub where the file was, so it reads the file again or makes the field up. With 27g's answer check on, an objection is answered blind.
4. **The context-window table gives `gpt-4-turbo` and `gpt-4.5` an 8,192-token window.** The table's bare `{"gpt-4", 8192}` row (`business/harness/context_windows.cpp:30-34`) is a prefix (longest match, `:59-74`). It catches `gpt-4-turbo*`, `gpt-4-0125-preview` and `gpt-4-1106-preview` (128k), `gpt-4-32k` (32k) and `gpt-4.5-preview` (128k), and gives each 8,192 tokens. The table's own comment (`:17-20`) promises "unknown" for a model it does not list. The OpenAI provider has no `ContextWindowReporting`, and `Harness::context_window_for_model` falls through to the table on the entry's model name (`business/harness/harness.cpp:830-835`), so nothing earlier in the chain corrects this. Scenario: `config add-backend gpt --type openai --model gpt-4-turbo` with no `context_size`. Within a few turns every request says `context budget: N earlier exchanges not sent`, attachments stop being inlined, and the chat auto-compacts, though the model would take 30 times more.
5. **A budget trim says "the retrieved context not sent" when what it dropped was the standing context, the review note or the plan note.** `drop_injected` pops the turn's injected messages from the end. When none are left, it always reports `the retrieved context not sent` (`budget.cpp:314-326`). In a chat turn that list also holds the session's standing context (41b), the `/branch` review note and plan mode's note at its head, plus any recalled-sessions prefix (`presentation/cli/chat_turn.cpp:249-281`). A delegate's list holds its notes (`business/tools/delegate.cpp:184-185`). A partial drop gets only the generic `N injected messages not sent`. Scenario: a chat with standing context and a review note, no RAG, and a long tool-heavy turn that overflows. The notice blames retrieved context that was never there, and does not say the standing instructions went unsent. The user goes looking at their retrieval settings while the model no longer reads the instructions. The existing tests (`tests/business/agentloop/budget_test.cpp:301-303`, `:419`) cover only lists that hold nothing but retrieval.
6. **On overflow, `stub_this_turn` replaces the user's own `ask_user` answer with a stub that says "call it again, narrower".** The candidate filter in `stub_this_turn` (`budget.cpp:256-262`) lacks the `is_answer` exception that `stub_tool_results` makes (`:497`). An answer over 512 bytes (`kStubbedAbove`, `budget.h:45`) is stubbed with `kOverflowWhy` (`budget.cpp:19-20`, `:284-291`) whenever a newer large result exists in the same turn, since the newest result is never stubbed. `encode_answers` reaches that size easily because it repeats each question's text (`question.cpp:142-156`). Scenario: a small-window local model with tools asks a multi-question `ask_user`, gets a long answer, then reads two large files. The overflow stubs the oldest of this turn's results first, which is the user's answer, and the model asks the same questions again. This breaks 26c's budget table, "Kept whole: … every `ask_user` answer" ([MILESTONES.md](../../assistant/MILESTONES.md):600).

What already works: a turn that completes ends in a plain answer, which compaction keeps harmlessly. The loop rolls back an aborted tool phase. Earlier turns' `ask_user` answers are kept whole (`budget_test.cpp:213`, `:361`). Compaction's own anchor reset (`after_compaction`, `chat_attachments.cpp:1038-1066`) is right. An explicit `context_size` and a local backend's own window both answer before the table.

**Core constraint(s).**
- **The history never holds an unanswered tool call** (Milestone F, MILESTONES.md:517): several providers reject such a history outright (`loop.cpp:717-719`). Compaction is held to the same rule as the loop's rollback.
- **The harness never includes backends**: the fix for finding 1 lives in `agentloop/`, provider-neutral. Anthropic is the strictest provider, not the only one, so `anthropic_wire.cpp` is not taught to drop orphan calls.
- **26c's budget table** (MILESTONES.md:549-617): the order of trims is unchanged, and so is what is kept whole (results of 512 bytes or less and every `ask_user` answer). Only the stub's reach and the notices' words change.
- **Persist after every turn** (`chat_turn.cpp:322-325`): a failed turn still saves, and the history it saves stays sendable.
- **A change propagates to every mode** ([ADR 0002](../../adrs/mode-parity.md)): one setter serves `/system` and the `set` line (52d), and one Assembler serves chat, `complete`, `analyze`, the delegate and `serve`. Each fix is made once, there. **Older versions keep working** ([ADR 0006](../../adrs/backwards-compatibility.md)): the `notice` event's shape is unchanged; only its text names what was cut.
- **0 means unknown, never unlimited** (MILESTONES.md:366): a GPT-4-family id the table does not know answers 0, not a guess.

**Seam + files.**
- `business/agentloop/content.cpp` -- `compact_history` keeps the most recent assistant message that carries no tool calls, or none.
- `business/agentloop/budget.cpp/.h` -- the Assembler sends an assistant message whose tool calls have no result in the request without those calls (its text kept, an empty one left out), so a chat already saved in finding 1's state works again. `stub_this_turn` skips `is_answer`. `drop_injected` names what it dropped by source. A request with no tools gets an overflow stub with no "call it again".
- `business/agentloop/loop.cpp/.h` -- `Options` gains the turn a run continues (an optional `turn_start`), which `run` uses instead of the last user message. `answer_objection` assembles with the answered turn's start, computed before its question is appended. `Options::transient_prefix` gains a label per message (standing context, review note, plan note, recalled sessions, retrieved context, delegate note).
- `business/agentloop/structured.cpp` -- the corrective attempt runs with the first attempt's `turn_start`.
- `presentation/cli/chat_turn.cpp`, `business/tools/delegate.cpp` -- each injected message labeled as it is inserted.
- `presentation/cli/chat_session.cpp` -- `set_system_prompt` moves every held `inline_at` and `map_at` by +1 on an insert and by -1 on an erase, through one helper beside it.
- `business/harness/context_windows.cpp` -- the GPT-4-family rows (open call below).
- Tests: `tests/business/agentloop/content_test.cpp`, `budget_test.cpp`, `structured_test.cpp`, `validate_test.cpp` (the objection), `loop_test.cpp`; `tests/presentation/cli/chat_test.cpp` (`/system`, beside the 52d case at `:2161`), `chat_attachments_test.cpp`; `tests/presentation/machine/machine_mode_test.cpp` (the `set` line); `tests/business/harness/harness_test.cpp` (the table, beside `:641`).

**Open calls:**
- [default: compaction keeps the most recent assistant message with no tool calls. When there is none (the whole conversation was tool work), it keeps nothing after the summary. Keeping the trailing call with all its results was weighed and rejected: those results are what the summary's stubs already condensed (26c).]
- [default: the Assembler's repair touches only the request, never the history or the saved file, and logs one Warn line per repaired message. A tool result with no call before it is left out of the request the same way.]
- [default: anchors are moved by index in `set_system_prompt`. Anchoring by a stable message identity was weighed and rejected for now: it changes the session file's `attachments` format for one setter's sake. It is the fix if a second head edit is ever added.]
- [default: the corrective schema turn and the objection treat the answered turn's results as this turn's. They are sent whole unless the overflow stubs them, and the objection request stays tool-less. In a request offering no tools, the overflow stub reads `not sent: the context window was full`, with no "call it again".]
- [default: the table gains `gpt-4-turbo` 128000, `gpt-4-0125` 128000, `gpt-4-1106` 128000, `gpt-4-32k` 32768 and `gpt-4.5` 128000. The bare `gpt-4` row becomes an exact match on `gpt-4`, `gpt-4-0613` and `gpt-4-0314` (8192), so any other `gpt-4…` id answers 0 (unknown), as the table's comment promises. The windows are checked against OpenAI's model pages at build, and the table's comment gets a reviewed date.]
- [default: the trim notice names the sources dropped, in the order dropped: `the retrieved context not sent`, `the standing context not sent`, `the review note not sent`, `the plan-mode note not sent`, `the recalled sessions not sent`, joined, with a count where one source had several messages (wording settled at build). The order of the drop (from the end, so standing context goes last) is unchanged.]

**Guardrail(s).** Hermetic: a temp `APOGEE_HOME`, the mock backend, a scripted harness reading back each request it is sent. Each finding pinned:
- Finding 1: `content_test` compacts `[user, assistant, user, assistant{tool_calls call-A}, tool{call-A}]` (the probe's history). The result holds the summary and the plain `assistant done`, and no message carries a tool call. Over `[user, assistant{tool_calls}, tool]` alone, it holds the summary only. `budget_test` assembles a history of `[summary, assistant{tool_calls call-A}, user]`, and the request holds no `call-A` and the history is unchanged. A `chats compact` case replays the probe's file: the saved result has no tool call without its result, and a next turn's request holds none.
- Finding 2: in `chat_test`, a small file inlined on turn 1, then `/system` set (an insert), then turn 2. The file is still inlined on turn 1's message and no "no longer fits" notice is said. The same after a prompt is cleared (an erase), and for a folder's map card. `machine_mode_test` replays the probe's four lines, and turn 2 has no notice. `chats show` puts the attachment on turn 1 after both.
- Finding 3: in `structured_test`, a tool phase returning a 40 KB result, then a non-conforming answer. The corrective request carries the result whole. In `validate_test`, an objection's request carries the answered turn's results whole. A forced overflow on a tool-less request gives a stub without "call it again".
- Finding 4: in `harness_test`, `gpt-4-turbo`, `gpt-4-turbo-2024-04-09`, `gpt-4-0125-preview`, `gpt-4-1106-preview` and `gpt-4.5-preview` each answer 128000, `gpt-4-32k` 32768, `gpt-4` and `gpt-4-0613` 8192, and an unlisted `gpt-4-…` id 0.
- Finding 5: in `budget_test`, an overflowing turn whose injected list is standing context and a review note, with no retrieval, says those two and never `the retrieved context`. A partial drop names the source it dropped. The retrieval-only cases (`:301-303`, `:419`) keep their words.
- Finding 6: in `budget_test`, an overflowing turn holding a 600-byte `ask_user` answer and two newer large results. The answer is sent whole, and the older large result is stubbed.
