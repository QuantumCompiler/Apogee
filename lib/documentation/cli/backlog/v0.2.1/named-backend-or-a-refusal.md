# A resumed chat or a suite member naming a backend that can't start is refused, never answered by the default

**What / why.** M29 made a named backend speak for itself or not at all: `chat -m <a backend that can't start>` is refused at launch, exit 1, instead of the default answering under the named backend's label ([Milestone AO](../../assistant/MILESTONES.md#milestone-ao--the-desktop-clients-cli-growths) → `refusals-and-suites-reach-drivers`, 2026-10-26). The fix was worded for `-m` and `task`, and two other ways a session names its backend were left out. On both, a backend that is configured but could not start is still answered by `models.default`, labelled, streamed and saved as the named backend. A driver, the macOS app included, reads the wrong model's answer under the name it asked for. Found by the second bug sweep (2026-10-31), each probe run in a sandbox home on the mock backend:

1. **A resumed chat whose saved backend can't start runs on the default under the saved name.** `chat --resume <id>`, `execute --resume <id>` and `--continue` without `-m`. The launch refusal checks only the flag: `named_backend_refusal(config, built, flags->model)` (`presentation/cli/chat_session.cpp:845`). The saved backend comes back from the session file (`chat_session.cpp:924-926`). A backend *deleted* from the config is dropped there with a note (`chat_session.cpp:929-932`), but one still configured passes. It is resolved as the chat's backend with no refusal (`chat_session.cpp:1027-1038`), and every turn then reaches `SimpleRouter::route`, which answers an unstarted name from the default (`business/harness/harness.cpp:248-251`). Probe: mock backends `good` (the default) and `other`. A chat on `other` (`chat -m other`, answer `OTHER-SAYS`). Then `other` is deleted and added back as `--type mlx` with no Python environment, so it is configured but can't start. Run `echo '{"type":"user","text":"two"}' | apogee chat --resume <id> --output-format stream-json --input-format stream-json`. Expected: refused at launch, exit 1, as `chat -m other` and `task resume` are. Actual: exit 0, `session.model:"other"`, then `{"finish_reason":"stop","model":"other","text":"GOOD-SAYS","turn":2,"type":"result"}`, stderr `apogee: summarised for recall by other`, and `chats info` still records `backend:"other"`. The text REPL `chat --resume <id>` answers `GOOD-SAYS` the same way. In the same sandbox, `task run -m other` is refused: `apogee task: backend 'other' is configured but could not be started: there is no Python environment ... (started backends: good)`. `task resume` refuses this exact case (`presentation/cli/task_cmd.cpp:621-631`: "as chat's opening holds it"), so chat's opening is the one that doesn't. The macOS app resumes with `--resume` and adds `-m` only when the person set a model (`lib/src/darwin/source/business/session/ChatLaunch.swift:108-111`). It hits this whenever a resumed chat's saved backend can no longer start, not on every resume. This is an incomplete fix of M29: task resume is refused "as chat's opening holds it", and chat's own resume never was.

2. **A suite whose chat member can't start runs every turn on the default, labelled as the member.** `chat --suite`, `execute --suite` and `task run --suite`, and a resumed session that carries the suite. `validate_active_suite` (`presentation/operations/suites.cpp:249-266`) refuses only a member the config doesn't define (`config.find_backend(...) != nullptr`, line 256). It never sees the build result, so a member that is configured but failed to start passes. The chat's opening calls it at `chat_session.cpp:984-988` (the comment: "before a turn could fall back to models.default and answer from a model nobody chose"), and `task_cmd.cpp:681` does the same. `named_backend_refusal` (`presentation/cli/helpers.cpp:93`) is called only with the flag (`chat_session.cpp:845`, `complete.cpp:724`) or with the flag or the resumed session's backend (`task_cmd.cpp:627-628`), never with a suite member. Probe: `config add-suite broke --chat mlxgone --utility good`, where `mlxgone` is an mlx backend with no Python environment. (1) `chat --suite broke --output-format stream-json`: exit 0, session `model:"mlxgone"`, `suite:"broke"`, result `{"finish_reason":"stop","model":"mlxgone","text":"GOOD-SAYS","turn":1,"type":"result"}`. (2) `execute --suite broke`: the same. (3) `task run "say hi" --suite broke --rounds 1 --output-format stream-json`: both the plan and the round results are `{"model":"mlxgone","text":"GOOD-SAYS"}`, and stderr's header reads `[task] ... · mlxgone · suite broke`. In the same sandbox `chat -m mlxgone` is refused (`backend 'mlxgone' is configured but could not be started ...`). This is an incomplete fix of M29: the bug M29 fixed (the default answering under a named backend's label, its launch-only revision of M26's "a request naming a skipped backend still falls to a default") is reached through a launch path it left out, the suite's chat member. It is not a regression of a listed checkbox.

What already works: `chat -m`, `execute -m`, `complete -m`, `task run -m` and `task resume` refuse a configured backend that can't start, in M29's words. A suite member the config doesn't define is refused by `validate_active_suite`. A resumed chat whose backend was *deleted* falls back to the default and says so.

**Core constraint(s).**
- **The item's own rule, the backend's honesty**: a session never streams, prints or saves one backend's name over another backend's answer. The refusal comes before any turn can reach the router.
- **M29's rule, extended, not restated**: a backend a session opens on (from `-m`, the saved chat, or the active suite's member) answers under its own name or the launch is refused, exit 1, nothing on stdout, nothing written. The refusal gives the backend's own reason in M26's router words and lists the started backends. That is `named_backend_refusal`'s message, reused, never rewritten per caller.
- **The launch contract** (`machine-mode.md`, ADR 0006's additive protocol): a launch refusal is stderr, exit 1, empty stdout. No new event or field.
- **The four layers** (ADR 0001): the check stays in Presentation (`cli/helpers`, `operations/suites`), reading the factory's `BuildResult`. The harness router is not touched.
- **Development runs on the dev channel**: any live pass names `apogee-dev`. Probes and tests run in a temporary `APOGEE_HOME`, never `~/.apogee` or `~/.apogee-dev`.

**Seam + files.**
- `source/presentation/cli/chat_session.cpp`: once the session's backend is resolved (`:1027-1038`), refuse a saved backend that can't start (finding 1) and a suite chat member that can't start (finding 2). Both go through `named_backend_refusal`. A resume is worded as the task's, `chat <id> cannot resume: …`, naming `-m <backend>` as the way to resume on another. The `-m` check at `:845` stays where it is. `/suite` mid-chat (`:2320`) gates through the same suite check.
- `source/presentation/operations/suites.cpp/.h`: `validate_active_suite` gains the build result (an overload, or a second function beside it). A member the config defines but the factory didn't start is refused with that backend's reason, then the existing `-- suite <name>'s <role> member; fix it with: apogee config set-suite <name> --<role> <backend>`.
- `source/presentation/cli/task_cmd.cpp`: `:681` passes `built`. `source/presentation/cli/complete.cpp:740` and `symphonies_cmd.cpp:613` do the same, since both have the build result at their check.
- `source/presentation/cli/helpers.cpp/.h`: `named_backend_refusal`'s doc comment names its callers as they become.
- Tests: `tests/presentation/cli/chat_session_test.cpp` (the `[named-backend]` cases and their `NamedHome` fixture), `tests/presentation/cli/task_test.cpp`, `tests/presentation/operations/suites_test.cpp`, and `tests/scripts/sh/suites_e2e.sh` if `cli.suites_lifecycle` covers the launch.

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item for both findings. Both are launch paths M29's named-backend refusal missed. Both are decided at the same place, the session's opening in `chat_session.cpp`, where the chat's backend is resolved after the suite. Both are pinned by the same fixture: a configured backend that can't start.
- 2026-10-31: Both are an incomplete fix of M29, not a new rule. M29's "speaks for itself or not at all" covers every name a session opens on, as its task-resume refusal already reads it.

**Open calls:**
- [default: a resumed chat or execute session whose saved backend is configured but can't start is **refused**, exit 1, nothing written, as `task resume` is (M29's recorded decision). It is not run on the default with a note. The refusal names `-m <backend>` as the way to resume on another. A backend *deleted* from the config keeps falling back with its note (M29).]
- [default: the suite check refuses **every** member of the active suite that is configured but didn't start, not only the chat member. Every role's request falls to the default the same way (`harness.cpp:248-251`). If the build shows a role that never routes by name, that role stays unrefused, recorded.]
- [default: `/suite` mid-chat refuses a suite with an unstarted member the same way, since it already gates on `validate_active_suite` (`chat_session.cpp:2320`). The session stays on its current suite.]
- [default: `serve` (`serve_cmd.cpp:183`) and `analyze` (`analyze.cpp:567`) check the suite before building providers. They keep the config-only check. `serve`'s per-request answer is M29's untouched later-request fallback, and `analyze` is outside the findings.]
- [default: the macOS app needs no change. It shows this launch refusal as it shows any other (stderr, exit 1, empty stdout).]
- (consumed decision) M29: the router's fallback for later requests (`/model`, a `set` mid-session) is untouched. This item changes only what a session opens on.
- (consumed decision, 2026-11-01) 56a revised M29's clause for the switch alone: `/model` and a `set` line's `model` naming a backend that is configured but did not start are refused in `named_backend_refusal`'s words (`switch_model`, `chat_session.cpp`), the session staying on its backend -- an ACP host's model menu is a `set` line. The router itself is still untouched, and this item still changes only what a session opens on.

**Guardrail(s).** Each finding pinned in the hermetic suite: a temporary `APOGEE_HOME` (`CliHome`), the mock backend, and `NamedHome`'s `gone` (a `claude-cli` backend whose binary is nowhere: configured, never started).
- `chat_session_test.cpp` `[named-backend]`, run for `chat` and `execute`, text and `stream-json`: a chat saved on a backend that started, then the config rewritten so that backend can't start (as the probe did), then `--resume <id>` and `--continue` are refused. Exit 1, `cannot resume` and the backend's reason on stderr, empty stdout. The session file is byte-identical (`backend` unchanged, no turn added) and no recall summary is written. The same resume with `-m root` answers `ROOT<…>`. A resume whose backend was deleted still falls back with its note.
- `chat_session_test.cpp`: `--suite` whose chat member is `gone`, for `chat` and `execute`. Refused, exit 1, with the member's reason and the `set-suite` fix line. No `result` line, and no answer under `gone`'s name. A resumed session carrying that suite is refused the same way. `/suite` to it mid-chat is refused and the session keeps its suite.
- `task_test.cpp`: `task run --suite` with an unstarted chat member is refused with nothing made (no task, no session). `task resume` of a task whose suite's member can't start is refused.
- `suites_test.cpp`: the suite check with a build result. A defined, started member passes, a defined, unstarted member is refused with its reason, and an undefined member keeps its existing words.
Each case fails first on the current binary.

**Acceptance criteria:**
- [ ] `chat --resume <id>` / `execute --resume <id>` / `--continue` on a chat whose saved backend is configured but can't start exits 1 with that backend's reason, prints nothing on stdout and leaves the saved chat unchanged. No `{"model":"other","text":"GOOD-SAYS"}`.
- [ ] `chat --suite broke`, `execute --suite broke` and `task run … --suite broke` with an unstartable chat member are refused at launch with the member's reason. No `{"model":"mlxgone","text":"GOOD-SAYS"}` and no `[task] … · mlxgone · suite broke` header.
- [ ] `-m`, task resume, a deleted backend's fallback and an undefined suite member behave as M29 left them. The full suite is green.
