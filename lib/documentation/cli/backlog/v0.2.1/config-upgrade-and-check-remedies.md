# `config upgrade` edits under the lock and adds only what is missing; `check`'s unknown-key remedy never breaks the config

**What / why.** `apogee config upgrade` and `check`'s config rows are the remedies Apogee offers for a config that has fallen behind or holds a stray key. The second CLI/GUI bug sweep (2026-10-31) found three ways a remedy leaves the config worse, or reports it wrong: upgrade can silently overwrite an edit another editor just made, it says it "added" an option the file already sets and inserts the option's example under the live key, and `check` tells the user to rename a stray key into a duplicate, after which no command loads the config. Each was probed in a sandbox and re-read at HEAD the same day. Paths are under `lib/src/cli/source/`.

1. **Upgrade writes text it read outside the lock** (regression of 55f, `config-editor-correctness`: the lock is held from read to rename so two edits at once both land). `bind_upgrade` (`presentation/cli/config_cmd.cpp:868`) reads the config at `config_cmd.cpp:876`, computes `upgrade_config_text(content, …)` at `:883-884`, and only then calls `edit_config_file(path, [&upgrade](std::string_view) { return upgrade.text; })` at `:891`. `edit_config_file` (`data/contracts/config_edit.h:493-505`) takes the lock, reads the file afresh, and hands that text to the transform, which ignores it. Any edit that lands between the unlocked read and the lock is overwritten, and both commands report success. It is the one transform in the tree that ignores its argument (a grep of `edit_config_file(` callers at HEAD). 55f carved out only `config migrate` and `config init --force`, by decision. Scenario: the GUI's Settings, serve's admin plane or a `config add-backend` holds `config.json.lock` and adds a backend; `config upgrade` starts, reads the pre-add text, waits on the lock, and writes the upgraded pre-add text when it is released. The backend is gone. Probe (`scratchpad/hold.py`): python holds `config.json.lock` and starts `apogee config upgrade` on a v0.1.9 starter config, appends backend `added_meanwhile` while holding the lock, then releases. Upgrade printed `added 5 options ...`; the result was `LOST added_meanwhile`, and `config get backends` then printed nothing. The window is narrow, but the loss is real and silent.

2. **Upgrade "adds" a commented option the file already sets as a real key, and `check` counts it as missing** (a gap in 55g's commented options, `config-reads-and-validation`). `place` (`data/contracts/config_migrate.cpp:684`) decides a file "holds it already" only by the option's first comment line, `opens` (`config_migrate.cpp:693`, `count_lines(lines, option.opens, …) > 0`). A file that writes the key itself, without the template's comment, counts as lacking it. Both callers go through `place`: upgrade's `add_commented_options` (`:992`) and `check`'s `missing_template_options` (`:967`). Scenario: a config seeded by v0.1.6 with `"models": { "default_video": "mypipe" ... }`. `apogee config upgrade` lists `models.default_video` among the options it added and inserts the commented `// "default_video": "Wan-AI--..."` example under the live key. `check` counts it among the options "not in the file (their defaults apply)" (`presentation/cli/check.cpp:425`), though the file sets it and its default does not apply. Probe (`scratchpad/u3`): upgrade printed `added 8 options ... models.default_video`; afterwards grep shows both line 23 `"default_video": "mypipe"` and line 69 `// "default_video": "Wan-AI--Wan2.2-TI2V-5B-Diffusers"`. A second upgrade run was idempotent, as were runs on the v0.1.6 and v0.1.9 templates. The only other option that is a real key, top-level `review` (declared at `config_migrate.cpp:916-918`), goes through the same rule, so a config with a real `review` key is very likely hit too. Not probed.

3. **`check`'s unknown-key remedy renames a stray key into a duplicate** (a gap in 55g's typo rows). `check.cpp:460-468` turns each `unknown_keys` entry into a warning with the remedy `rename it '<nearest>' in config.json`. It never asks whether the entry already has that key. The loader collects unknown keys at `data/contracts/config.cpp:306-311` and keeps none of the entry's other keys. Scenario: a backend entry holds both `"model": "x"` and a stray `"Model": "y"`. `check` says `unknown key 'Model' ... did you mean 'model'?` with `run: rename it 'model' in config.json`. Following that leaves `model` twice in the entry, and the JSONC loader refuses the whole file (`data/contracts/jsonc.cpp:311`, `the key "model" appears twice in one object`), so every command fails. Probe (`scratchpad/h2`): the check output shows the warn row and the rename remedy; `scratchpad/y/dup.json`, holding a duplicate `model`, makes `config get` and `check` fail with the duplicate-key error. Here the remedy should say to remove the stray key.

What already works: upgrade is idempotent on every template and inserts each block where the template puts it; the lock makes every other editor's concurrent edits land (16 of 16, 64 of 64 in 55f's runs); a typo with no real twin in its entry gets the right rename.

**Core constraint(s).**
- **One config mutation path** (⚠ invariant): the fix goes through `edit_config_file`, and the upgrade is a pure transform over the text read under the lock, never text read before it. No second writer appears.
- **The lock is held from read to rename** (55f): nothing an upgrade writes may come from a read made outside it.
- **Upgrade never rewrites what is there** (55g, `upgrade_config_text`'s contract): nothing present is reordered, rewritten or removed, and a current config comes back unchanged. A file that sets an option has it, whether or not it has the template's comment.
- **A remedy `check` prints, followed, leaves a config that loads.**
- **Loading stays tolerant** (55g's decision): an unknown key is still a warning, never a refusal.
- **Development runs on the dev channel**: the live pass is `apogee-dev` over a temporary `APOGEE_HOME` in the scratchpad, never `apogee` or `~/.apogee`.

**Seam + files.**
- `presentation/cli/config_cmd.cpp` (`bind_upgrade`): the YAML refusal and the "is current" answer may still come from a first read, but the text written is `upgrade_config_text(<the locked text>, …)`, computed inside the transform. The `added` list printed is the locked run's.
- `data/contracts/config_migrate.cpp/.h`: `CommentedOption` names the key when the option is one (`models.default_video` → `default_video` in `models`; `review` at the top level). `place` returns nullopt when the live object already holds that key. Both upgrade and `check`'s count follow from that one rule.
- `data/contracts/config.cpp/.h`: `parse_backend` keeps the keys the entry writes beside `unknown_keys`, so `check` can tell a typo from a stray twin.
- `presentation/cli/check.cpp:460-468`: when the entry already writes the nearest key, the row says so and the remedy is to remove the stray key.
- Tests: `tests/data/contracts/config_migrate_test.cpp` (`[commented]`), `tests/presentation/cli/config_lifecycle_test.cpp` (upgrade under a held lock; the count `check` gives), `tests/presentation/cli/check_test.cpp` (`[unknown-keys]`), `tests/scripts/cmake/config_e2e.cmake` (55g's section).

**Open calls:**
- [default: upgrade keeps its unlocked first read only for the YAML refusal and the "is current" fast path, which takes no lock for a read-only answer. The transform recomputes from the locked text. If that run finds nothing missing because another upgrade landed first, it returns its input unchanged, and the command says the file is current.]
- [default: no change to `edit_config_file` itself. The fix is at the one caller that ignores its argument. A source check that every transform reads its argument is not added.]
- [default: only options that are one concrete key (`models.default_video`, `review`) gain a key test. The `backends.*` examples name no one key and keep the comment-line rule.]
- [default: when an entry writes both `Model` and `model`, the row reads `unknown key 'Model' -- no backend reads it, so it does nothing; the entry already sets 'model'` with the remedy `remove 'Model' from config.json` (wording settled at build). A typo with no twin keeps today's rename.]
- (consumed decision) `config migrate` and `config init --force` stay unlocked: 55f's decision, not reopened here.

**Guardrail(s).**
- **Finding 1, the probe as a test:** the test holds `config.json.lock`, starts `config upgrade` on an older starter config, appends backend `added_meanwhile` while holding the lock, then releases. Afterwards the file has both `added_meanwhile` and the upgraded options, and it parses. The test gives the waiter its first read before the append, so it fails on the old binary.
- **Finding 2:** a v0.1.6-shaped config with a live `"default_video": "mypipe"`, and one with a real `review` key, upgraded. Neither option is in `added`, and neither example block is inserted. `missing_template_options` does not count either. The template round-trips and the idempotence cases stay green.
- **Finding 3:** an entry with `model` and a stray `Model` gets the remove remedy, never `rename it 'model'`. A lone `Model` still gets the rename. Following the printed remedy leaves a config that loads.
- All hermetic: a temporary `APOGEE_HOME`, the mock backend, no network.

**Acceptance criteria:**
- [ ] An edit that lands while `config upgrade` waits on the lock survives; `config get backends` lists it after the upgrade.
- [ ] `config upgrade` on a file that sets `models.default_video` (or `review`) as a real key neither lists it as added nor inserts its example, and `check` does not count it as missing.
- [ ] `check` never tells the user to rename a key to one its entry already has; its remedy, followed, leaves a config every command loads.
- [ ] A live pass on `apogee-dev` over a scratchpad `APOGEE_HOME` reproduces each probe's fixed result; the full suite is green.
