# The tool gate enforces what it shows: no write through a dangling link, git confined to the root, an MCP deny honored, hosts denied as they are allowed, and the write prompt names the file written

**What / why.** The permission gate and the `tools.fs_root` sandbox are what make `--tools` safe to hand a model: a write is asked about by the file it touches, a read stays inside the folder Apogee was started in, and what the user denies stays denied. The second CLI/GUI bug sweep (2026-10-31) found five places where the gate shows or accepts one thing and enforces another. Two let a turn write outside the sandbox or overwrite a file the prompt never named. One lets the git tools read any repository on the machine and run a command from a repository's own config, with no prompt. Two leave a user's explicit deny unenforced or refused. Each was probed in a sandbox and re-read at HEAD (`b26550bb`) the same day. Paths are under `lib/src/cli/source/`.

1. **`write_file` follows a dangling symlink out of the root** (regression of Milestone V, the native toolsets: "a symlink pointing out" is refused, MILESTONES.md:4701, 4708). `resolve_in_root` (`business/tools/fs.cpp:185-218`) judges a path by `std::filesystem::weakly_canonical` (`fs.cpp:204`) and `is_within` (`fs.cpp:209`). `weakly_canonical` follows only links whose targets exist. A dangling link counts as a file not yet created, and it resolves to the link's own path inside the root. `write_file`'s run (`fs.cpp:582-583`) then calls `create_directories` and opens a `std::ofstream` on that path, which follows the link and creates its target outside the root. The escape table in `tests/business/tools/fs_test.cpp:65-81` tests only a link to an existing target. Scenario: a project or a downloaded archive holds `notes.txt -> ~/Library/LaunchAgents/x.plist` or `-> ~/.zshenv`, target absent. The model calls `write_file{path:'notes.txt'}`. The prompt shows `notes.txt` as a new file inside the project, and accept-edits mode or a config `allow` approves it with no prompt at all (`write.edits = true`, `fs.cpp:551`; `presentation/cli/permissions.cpp:300`). The content lands outside the sandbox. Probe: `proj/notes.txt -> ../outside/planted.txt` (dangling), `apogee complete --tools --allow write_file` with a scripted `write_file` call. Output: `Wrote 5 bytes to .../proj/notes.txt`. `outside/planted.txt` now exists and contains `PWNED`.

2. **The git tools are never gated, read any repository and run that repository's configured commands.** `find_repo` (`business/tools/git.cpp:218-235`) returns the model's `repo` argument as given (`git.cpp:219-221`). `register_native_toolsets` (`business/tools/toolsets.cpp:79-86`) never passes `fs_root` to the git tools, only the working directory. None of `git_status`, `git_log`, `git_diff` or `git_show` sets `writes` or `outbound`, so `gated()` (`business/agent/tool.cpp:72-74`) is false and nothing prompts. `Git::invoke` (`git.cpp:109-117`) runs `git -C <repo> …`, so git reads that repository's `.git/config`, and a `core.fsmonitor` there runs as a command. A turn can read the history and diffs of any repository on the machine, including file contents `read_file` would refuse. A turn that calls `git_status` in a folder with a crafted `.git/config` runs its command, served requests included. Probe: `proj/.git/config` with `core.fsmonitor = touch $W/FSMONITOR_RAN; false`, then `apogee complete --tools` with a scripted `git_status`, then `git_show{repo:'<outside repo>'}`. `FSMONITOR_RAN` was created, and the answer printed the outside repo's commit (`outside commit`, `s.txt`). The review-mode `git fetch` (`git.cpp:148-160`) is not part of this finding: Milestone V's Decisions table records "`git_diff` with a fetch: Read-only for the gate *(default taken)*" (MILESTONES.md:4721).

3. **A deny on an MCP tool that calls itself read-only is accepted and shown as active, but the tool still runs.** `Registry::register_into` sets `tool.writes = !(read_only_hint …)` (`business/mcp/registry.cpp:104`), so a tool whose server sends `readOnlyHint: true` is ungated. `permitted` (`business/agent/tool.cpp:152-157`) returns `true` for an ungated tool before any level is read. Meanwhile `config set-permission` (`presentation/cli/config_cmd.cpp:1373-1387`) and `PUT /v1/admin/permissions/{id}` accept `deny` for it without a word. `apogee check` reports it as `ok … deny` (`presentation/cli/check.cpp:1347-1348`), though it already warns that the level "has no effect" for `fetch_url` (`check.cpp:1328-1335`). The documented rule is "Read-only tools have no level" (`reference/http-api.md:1349-1351`). In practice the server's own hint overrides the user's explicit deny, and every surface says the deny holds. Scenario: the user denies a third-party server's read tool (one that reads a private repo or a mailbox) with `apogee config set-permission mcp__srv__get_file deny`, or through the admin route. Every `--tools` session and every served request still calls it. Probe: `mcp create self --command apogee --args __mcp-tools`, then `config set-permission mcp__self__list_notes deny`. `check` printed `ok   permissions.mcp__self__list_notes  deny`. `complete --tools` with a scripted call still answered `DONE<No notes yet. Use write_note ...>`: the denied tool ran.

4. **`--deny`, `/deny` and `/revoke` refuse `localhost`, dotless hosts and IPv6 literals that `--allow-host` accepts** (regression of 26o, `session-permission-presets`: "`--deny` takes either kind", MILESTONES.md:5007; decision "Hosts on `--deny`/`/deny`: Yes", MILESTONES.md:5038). `name_gated` (`presentation/cli/permissions.cpp:412-437`) treats a name as a website only when it holds a `.` (`permissions.cpp:419`). `--deny` (`seed_approvals`, `permissions.cpp:484`) and `/allow`, `/deny`, `/revoke` (`presentation/cli/chat_session.cpp:2205`) all go through it, so `localhost`, a single-label intranet name, `[::1]` and `::1` are refused with "is not a tool this chat asks about". `--allow-host` (`permissions.cpp:476`) and the prompt's `session` answer (`remember`, `permissions.cpp:49-60`) take the same names through `canonical_host` (`data/contracts/host.cpp:68-78`), which accepts all of them. A dotted IPv6 form such as `[::ffff:127.0.0.1]` passes `--deny`. Scenario: a user who wants the model kept off local services runs `apogee chat --tools --deny localhost` (or `--deny [::1]`). The CLI exits with "--deny: 'localhost' is not a tool this chat asks about ... or name a website, like docs.python.org". In bypass mode the user has no way to deny `localhost` for the session. Once a `localhost` fetch has been answered `s`, or pre-allowed with `--allow-host localhost`, `/deny localhost` and `/revoke localhost` are both refused, so that yes can't be taken back until the process exits. Real binary: `--deny localhost`, `--deny [::1]`, `--deny ::1` and `--deny intranet` each fail with that message. `--allow-host localhost` is accepted and the run proceeds.

5. **The write prompt can name one file while another is overwritten.** The fs writers' `describe_target` (`business/tools/fs.cpp:535-539`, reused by `write_file`, `edit_file` and `delete_file` at `fs.cpp:552`, `609`, `655`) returns the model's `path` argument raw. `terminal_confirm_fn` prints it as `<tool> -> <target>` (`presentation/cli/permissions.cpp:323-324`) through `StatusLine::print_line` (`presentation/views/status_line.cpp:148-160`), which filters no control bytes. The file actually written comes from `resolve_in_root`'s `weakly_canonical` (`fs.cpp:204`), which drops a nonexistent first component followed by `/..` lexically. The detail line for a file writer is only the diff's counts (`permissions.cpp:329-332`, 52a), so nothing on screen names the real file. Scenario: the model calls `write_file` with path `x\r\x1b[2K\x1b[35m[perm]\x1b[0m write_file -> notes.txt\x1b[8m/../victim.txt`. The person sees `[perm] write_file -> notes.txt`, `+1 -1`, `Allow?` and answers `y`. `victim.txt` is overwritten, or `.git/hooks/pre-commit`, a `Makefile`, any file under the root. PTY probe in `scratchpad/probe/work2`, where `victim.txt` held `original`. Terminal bytes: `[perm] write_file -> x\r\x1b[2K\x1b[35m[perm]\x1b[0m write_file -> notes.txt\x1b[8m/../victim.txt\r\n ... +1 -1 ... Allow? ...y`. The result was `Wrote 12 bytes to .../work2/victim.txt`, and `cat work2/victim.txt` gave `overwritten`.

What already works: a link to an existing target outside the root is refused by every fs tool and by `grep_files`' walk (`fs_test.cpp:65-81`, `fs.cpp:885-886`). `fetch_url`'s target is the canonical host and its detail the rebuilt URL (`business/agent/fetch_url.cpp:304-311`), so its prompt cannot be repainted. A dotted host passes `--deny`. `check` warns that a level on `fetch_url`, or on a name that is not a native destructive tool, does nothing.

**Core constraint(s).**
- **The sandbox is a table** (Milestone V): every spelling of an escape is refused through the resolver and through each tool, a dangling link included, and the outside file is left untouched. Windows links stay 57k's (below).
- **What leaves the machine is asked about by host, and the host asked about is the host reached** (⚠ invariant): what a host is, and whether two hosts are the same, is `contracts/host.h` and nothing else. `--deny` and `/deny` take exactly the hosts `--allow-host` and the `session` answer take.
- **The gate asks about what will happen**: the target a prompt names is the file the call will write, the same on the terminal, in machine mode's `question` event and so in the macOS app ([mode parity](../../adrs/mode-parity.md)).
- **A user's deny is never looser than it reads**: no hint from a third-party server overrides an explicit `deny`, and no surface reports a level as active when it is not.
- **Read-only tools never prompt** (Milestone V's rule, `tool.cpp:153-154`): the git tools stay ungated. They are confined instead.
- **A child's stderr is captured, never inherited** (⚠ invariant): git's new `-c` options change nothing about how it is spawned.
- **Development runs on the dev channel**: the live pass is `apogee-dev` over a temporary `APOGEE_HOME` in the scratchpad, never `apogee` or `~/.apogee`.

**Seam + files.**
- `business/tools/fs.cpp/.h`, `resolve_in_root`: after `weakly_canonical`, a path that passes through a symlink whose target does not exist is judged by where that target would land. The link chain is followed with `read_symlink` from the link's parent, a bounded number of hops, and re-checked with `is_within`. Every component counts, not only the last. The resolved path returned is the final target's, so a writer never opens a link.
- `business/tools/fs.cpp`, `write_file`'s run (`fs.cpp:574-594`): writes the resolved path through `harness::write_file_atomically`, as `edit_file` already does (`fs.cpp:635`). A rename replaces whatever sits at that path and follows nothing, so a link swapped in after the check is not followed either.
- `business/tools/fs.cpp`, the writers' `describe_target`: the resolved path, labelled root-relative by `diff_label` (`fs.cpp:456-462`), the label the diff already uses. A path that does not resolve inside the root is refused unrun, with `resolve_in_root`'s message, before the gate asks.
- `business/tools/git.cpp/.h`, `GitOptions` and `find_repo`: `GitOptions` gains the effective `fs_root`. An explicit `repo` is resolved through `resolve_in_root` and refused outside it with the sandbox's own message. `Git::invoke` passes `-c core.fsmonitor=false` on every call, and the commands that diff (`git_diff`, `git_show`, `git_log` with patches) add `--no-ext-diff --no-textconv`.
- `business/tools/toolsets.cpp:79-86`: hands `effective_fs_root(options.fs_root).path` to `register_git_tools`.
- `presentation/cli/helpers.cpp:298-301` (the MCP composition, after `register_into`): an `mcp__` tool the config gives a level, `config.permissions.levels`, is gated whatever its `readOnlyHint` says, so the existing checker decides it: `deny` refuses, `ask` asks (and so denies under `serve`), `allow` runs. `business/mcp/registry.cpp:104` stays the default for an unnamed tool.
- `presentation/cli/check.cpp:1318-1349`: the `mcp__` row stays `ok … <level>`, now true. `reference/http-api.md:1349-1351` and the `config set-permission` help say that a level on an MCP tool binds even when its server marks it read-only, and that native read tools still have none.
- `presentation/cli/permissions.cpp:412-437`, `name_gated`: a name is a website when `canonical_host` accepts it and it is not tool-shaped (rule under Open calls). `seed_approvals`' `--deny` and the chat's `/allow`, `/deny`, `/revoke` follow with no change of their own.
- Tests: `tests/business/tools/fs_test.cpp` (`[sandbox]`: the dangling rows), `tests/business/tools/git_test.cpp` (confinement, fsmonitor), `tests/business/tools/toolsets_test.cpp`, `tests/business/agent/tool_test.cpp`, `tests/business/mcp/registry_test.cpp`, `tests/presentation/cli/helpers_test.cpp`, `tests/presentation/cli/check_test.cpp`, `tests/presentation/cli/permissions_test.cpp`, `tests/presentation/cli/chat_session_test.cpp`, `tests/business/tools/gate_test.cpp` (the prompt's target), `tests/presentation/httpserver/handler_test.cpp` (a served git call and a served MCP deny).

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item. All five are the same defect: what the gate shows or accepts differs from what it enforces, on the gate's own vocabulary (`resolve_in_root`, `describe_target`, `gated()`, `name_gated`). They are fixed and pinned together, in one sandbox table and one gate suite.
- 2026-10-31: Finding 5 is fixed at the target, not at the printer: the prompt names the resolved file, so the `..` trick fails on every surface, machine mode included. Neutralising the bytes printed is 57p's, and the two together close it. Neither alone is enough on the terminal: 57p alone still shows `notes.txt/../victim.txt`, and this fix alone still lets a real filename carry escape bytes.
- 2026-10-31: The review-mode `git fetch` stays read-only for the gate (Milestone V's decision) and is not reopened here.

**Open calls:**
- [default: a dangling link inside the root whose target would land inside the root is allowed, and the write lands at the target. Only a target outside the root is refused, with the sandbox's message naming the link. A link chain longer than 40 hops (POSIX `SYMLOOP_MAX`'s usual value) is refused as unresolvable.]
- [default: `write_file` writes through `harness::write_file_atomically`. A new file takes the default mode. An existing file keeps its mode, carried over as `edit_file` already does.]
- [default: without `repo`, the git tools keep today's walk to the nearest repository above the working directory. A launch in a subfolder of a checkout must still see its repository, and the tool's description already says so. An explicit `repo` must resolve inside `fs_root`.]
- [default: the git hardening is `-c core.fsmonitor=false` on every call and `--no-ext-diff --no-textconv` on the commands that diff. The tools stay ungated and are not made `writes`.]
- [default: an explicit config level on an `mcp__` tool beats the server's `readOnlyHint`, rather than `set-permission` and `check` only warning that the level does nothing. The user named that tool, and a third-party server's own say-so should not undo it. An unnamed MCP tool keeps the hint's default.]
- [default: in `name_gated`, a name that is not a gated tool is a website when `canonical_host` accepts it and it is dotted, bracketed, holds a `:` (IPv6), or is a single label with no `_`, as `localhost` and `intranet` are. A dotless name with `_` is tool-shaped and keeps today's error, so a mistyped `write_flie` is still caught. A dotless typo such as `shel` becomes a website deny, which `/deny` already reports as `website shel denied for this chat`.]
- [default: a writer whose path does not resolve inside the root is refused unrun, before the gate asks: the fs twin of "an outbound tool must name its target". The mechanism, a check in `dispatch` or the writer's own, is settled at build.]
- (consumed decision) The review-mode `git fetch` is read-only for the gate: Milestone V's Decisions table (MILESTONES.md:4721).
- (consumed decision) Neutralising control bytes in what the prompt prints is 57p's (`model-text-neutralised-at-the-terminal.md`).
- (consumed decision) Link and junction resolution on Windows, and the git tools' advertising there, are 57k's (`windows-filesystem-safety.md`). Whichever builds first lands its rows in `resolve_in_root` and the `[sandbox]` table, and the other builds on them.

**Guardrail(s).** All hermetic: a temporary `APOGEE_HOME`, the mock backend or a scripted model, fake MCP servers (the in-binary `__mcp-tools` server), and throwaway git fixtures. No network.
- **Finding 1, the probe as a test:** in the `[sandbox]` table, `notes.txt -> <outside>/planted.txt` (dangling) given to `write_file` through the resolver and through dispatch with `allow` and with accept-edits. The call is refused, the refusal names the root, and `planted.txt` does not exist afterwards. The same for a dangling directory link (`d -> <outside>/newdir`, write `d/x.txt`), and for a two-hop chain whose second hop leaves the root. A dangling link whose target is inside the root is written at its target.
- **Finding 2:** `git_show{repo:'<a repo outside the root>'}` is refused with the sandbox's message and its commit text never comes back. A fixture repo inside the root whose `.git/config` sets `core.fsmonitor` to touch a marker: `git_status` succeeds and the marker is never created. A `diff.external` or textconv driver in the fixture's config never runs on `git_diff` or `git_show`. The existing review cases stay green.
- **Finding 3:** a fake MCP server whose tool sends `readOnlyHint: true`. With `permissions.mcp__<srv>__<tool>: deny` the tool is refused unrun in a `--tools` session and in a served request. With no level it still runs unprompted. `check`'s row matches what the gate does.
- **Finding 4:** `--deny localhost`, `--deny [::1]`, `--deny ::1` and `--deny intranet` are each accepted, and a scripted `fetch_url` to that host is refused unrun, in bypass mode too. After an `s` answer for `localhost`, `/deny localhost` denies it and `/revoke localhost` withdraws the yes. `--deny write_flie` still fails with the tool error.
- **Finding 5, the PTY probe as a test:** the probe's path through the terminal confirm function over a captured stream. The printed target is `victim.txt`, and neither `notes.txt` nor the raw argument is printed. The machine-mode `question` event's `target` is the same resolved label.

**Acceptance criteria:**
- [ ] No fs tool writes outside `tools.fs_root` through any link, dangling or not. The probe's `planted.txt` is never created.
- [ ] `git_status`, `git_log`, `git_diff` and `git_show` refuse a `repo` outside the root, and no git tool runs a command from a repository's config (the probe's `FSMONITOR_RAN` is never created).
- [ ] A `deny` on any `mcp__` tool, read-only hint or not, stops it on every surface, and `check` reports only levels that take effect.
- [ ] `--deny`, `/deny` and `/revoke` take every host `--allow-host` takes, `localhost` and IPv6 literals included.
- [ ] A file writer's prompt names the file the call writes, on the terminal and in machine mode. The probe's prompt reads `write_file -> victim.txt`.
- [ ] A live pass on `apogee-dev` over a scratchpad `APOGEE_HOME` reproduces each probe's fixed result, and the full suite is green.
