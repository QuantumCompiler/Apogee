# `serve` says which tools it offers, refuses cross-origin and rebinding requests, and runs one turn per session at a time

**What / why.** `apogee serve` is the one surface that owns a port, and its inference plane is unauthenticated by design (OpenAI-client compatibility). Being on loopback by default, with `--tools` gated by `tools.allowed_hosts`, is what keeps that safe. The second CLI/GUI bug sweep (2026-10-31) found three places where that bound does not hold. Re-read at HEAD (`b26550bb`):

1. **`--tools` offers every native tool, and every text says it offers only `fetch_url`.** `serve_cmd.cpp:261-273` builds the registry with `make_built_in_tools` (`helpers.cpp:231`), the same one chat uses: `fetch_url`, `web_search` where configured, every native toolset (files under `tools.fs_root`, which defaults to the launch folder, `toolsets.cpp:50-62`; git; notes; rag/graph; delegate), the session todo, and every enabled MCP server, which it starts. It decides with `make_permission_checker(config, nullptr)`. A tool that is not gated is always permitted (`tool.cpp:152-157`), and a gated tool the config sets to `allow` runs. Four texts still say otherwise: the flag's help (`serve_cmd.cpp:125-127`, "Let the model call tools server-side (fetch_url)"), the startup summary hard-coded as `-- tools: fetch_url` (`serve_cmd.cpp:359`), the flag row in [http-api.md](../../reference/http-api.md) (line 27: `fetch_url`, and `web_search`, gated to `tools.allowed_hosts`), and the comment on `make_built_in_tools` (`helpers.h:64`, "`fetch_url` only, for now"). The behavior is by design: 25b verified `read_file` over `serve` (MILESTONES, the 25b entry), and http-api.md:1354 documents that a destructive tool runs under `serve` only when the config says `allow`. What is wrong is the text. An operator who trusts it does not know that any client of the port can have the model read `.env`, notes or git history, or run a `run_command` that an `[a]lways` in chat set to `allow`. Probe (sandbox home, mock backend, `serve --tools --port 0`): stderr said `[tools] 25 registered` and then `serving m (default m) -- tools: fetch_url`. One POST `/v1/chat/completions` with a scripted `read_file` returned `X-Apogee-Tools-Used: read_file` and `DONE<SECRET-API-KEY=abc123>` (the `.env` contents). With `permissions: run_command: allow`, a POST returned `apogee_tool_calls:["run_command"]`, and the file it touched existed on disk. This contradicts http-api.md:27.
2. **A loopback `serve` accepts cross-origin and DNS-rebinding requests.** `serve.cpp:116-123` sends every method on every path straight to `mux.dispatch`. `Mux::dispatch` (`mux.cpp:488-522`) gates only `/v1/admin/` (the bearer). No Host or Origin check exists anywhere under `presentation/httpserver/`, and `grep -iE 'access-control|origin'` there finds no Host or Origin handling (its one hit is an unrelated comment, `admin_graph.cpp:187`). `parse_object` (`handler.cpp:58-66`), which `chat_completions` calls first (`handler.cpp:641-643`), parses any body as JSON whatever its `Content-Type`. So a page the user opens can run `fetch('http://127.0.0.1:8080/v1/chat/completions', {method:'POST', mode:'no-cors', body: JSON})` with the CORS-safelisted `text/plain`, and a full turn runs: it spends the served backend's key and, with `--tools`, runs the tools in entry 1. The server sends no `Access-Control-Allow-Origin`, so a plain cross-site page cannot read the reply. A DNS-rebinding page can read it. It can also read `GET /v1/sessions` and `GET /v1/sessions/{id}` and call `DELETE /v1/sessions/{id}` (`mux.cpp:49-60`, none authenticated). Probe: `curl -H 'Content-Type: text/plain;charset=UTF-8' -H 'Origin: http://attacker.example' -H 'Host: attacker.example:PORT' …/v1/chat/completions` returned 200 and ran `run_command` (the file it touched existed). The same foreign Host on `GET /v1/sessions` returned 200. `/v1/admin/` is not exposed: it needs the bearer token, which a page does not have. No document under `lib/documentation` mentions CSRF or rebinding.
3. **Two requests on one `session_id` drop an exchange, from memory and from disk.** `plan_turn` copies the session at `handler.cpp:349` (`sessions_.get(call.session_id)`), before `run_turn` takes `turn_mutex_` (`handler.cpp:376`). The turn builds on that copy (`handler.cpp:380-381`) and commits it whole (`handler.cpp:553-558`). So a request that waited behind another on the same session runs on the history from before that turn, and its commit overwrites the other turn's commit. Probe (serve, mock backend with 1.5 s delays): created session `20261031-201450-bd9b` with 'first', then sent 'second' and 'third' at the same time. Both returned (`A2<second>`, `A3<third>`), but `GET /v1/sessions/{id}` showed `turn_count` 2 and messages `[first, A1<first>, third, A3<third>]`: the 'second' exchange was gone, and 'third' was answered without it in context. A client that retries, or sends a follow-up before the last reply arrives, hits this. Regression of [Milestone T](../../assistant/MILESTONES.md#milestone-t--the-public-inference-plane)'s Concurrency decision (MILESTONES.md:4587, "One turn at a time … a second request waiting beats a first one corrupted"): the turns do run one at a time, but the second one runs on stale history.

What already works: a non-loopback bind is refused without `--allow-remote` (`serve.cpp:80-94`). The admin plane's bearer gate runs before routing, so a page learns nothing there. A served `fetch_url` reaches only `tools.allowed_hosts`. A gated tool at `ask` is denied on a served request. A browser page with no rebinding cannot read a reply.

**Core constraint(s).**
- **Interactive turns never open a listening socket**: `serve` is the one reviewed exception, and `httpserver/serve.cpp` stays the only object that references `listen`/`accept` (`cli.no_listen_symbols`). The new checks go in the socket-free mux, where tests reach them without a port. A non-loopback bind still fails closed behind `--allow-remote`.
- **Secrets are unleakable by construction**: a refusal carries no token, key or header value back. The admin gate's loopback-peer rule (judged from `remote_address`) is unchanged. A rebinding page *is* a loopback peer, which is why the new check reads Host and Origin rather than the peer address.
- **What leaves the machine is asked about by host**: unchanged. A served `fetch_url` still reaches only listed hosts. This item changes what `serve` says about its tools, not how the tools are gated.
- **One function, three callers** (`helpers.h:62-69`): `serve --tools` keeps the registry chat and `complete` build. The startup line describes that registry; it does not narrow it.
- The item's own rules: what the operator is told matches what a client can make happen. A request a browser forged on the user's machine is refused before any route runs. A session's turns build on each other in arrival order.
- **Development runs on the dev channel**: any live check runs `apogee-dev`, never the release `apogee` or `~/.apogee`. Probes use a temporary `APOGEE_HOME` under the scratchpad.

**Seam + files.**
- `presentation/cli/serve_cmd.cpp` — the `--tools` help states the real set ("the built-in tools, as chat has them: files under tools.fs_root, git, notes, fetch_url …; destructive ones only where the config says allow"). The summary at line 359 is built from the registry, not a literal. It moves into a pure function (`serve_summary`) so it can be tested.
- `presentation/cli/helpers.h` — the `make_built_in_tools` comment says what it registers today.
- `presentation/httpserver/mux.cpp/.h` — a request gate in `Mux::dispatch`, ahead of the admin gate and routing. When the server is bound to loopback, a `Host` that is not a loopback name (`127.0.0.1`, `localhost`, `[::1]`, any port) is refused. A present `Origin` whose host is neither loopback nor the request's own `Host` is refused, on every bind. The mux learns whether the bind is loopback from the serve options.
- `presentation/httpserver/handler.cpp` — `run_turn` re-reads the session under `turn_mutex_` (`sessions_.get(plan.session->chat_id)`) and builds on that copy. A session deleted while the request waited gets the typed `session_not_found` 404.
- `presentation/httpserver/serve.cpp` — only the serve options reach the mux (whether the bind is loopback); no socket change.
- Tests: `tests/presentation/httpserver/serve_test.cpp` or a new `mux_test.cpp` mirroring `mux.cpp` (the gate matrix), `tests/presentation/httpserver/handler_test.cpp` (two concurrent turns on one session), `tests/presentation/cli/serve_cmd_test.cpp` (new: the summary and the help), and `cli.serve_lifecycle` (`tests/scripts/sh/serve_e2e.sh`) on the real binary.
- Docs: [http-api.md](../../reference/http-api.md) — the `--tools` row (line 27) names the real set and links the destructive-tools section (line 1354). A new "Browsers and DNS rebinding" note under the flags table says what is refused and why. The concurrency paragraph (lines 32-33) says that turns on one session run in order, each on the last one's history. [tools.md](../../reference/tools.md) gets a line on what `serve --tools` exposes.

**Reference.** The admin gate (`mux.cpp:494-498`, Milestone T) is the precedent for a check that runs before routing and tells a refused caller nothing about routes. [Milestone T](../../assistant/MILESTONES.md#milestone-t--the-public-inference-plane)'s Concurrency decision is the promise entry 3 restores. The 25b entry (`serve -m qwen8b --tools` answering over HTTP with `read_file`) is the shipped behavior entry 1 describes truthfully. External prior art: local servers that ship an allowed-hosts check against rebinding (Jupyter's `allow_remote_access`, Vite's `server.allowedHosts`) and refuse a foreign `Host` on a loopback bind. The divergence here: no allow-list flag until someone asks for one. Sibling items: [tool-gate-enforces-what-it-shows.md](tool-gate-enforces-what-it-shows.md) (57o) owns the tool gate's own enforcement. This item owns only what `serve` says about its tools and who may reach the port.

- 2026-10-31: One item, because all three are the same promise, that `serve` stays inside the bounds it states: what the operator is told it offers (1), who may reach it on loopback (2), and what one-at-a-time means for a session (3). Entries 1 and 2 also compound: a forged request runs exactly the tools entry 1 does not mention.
- 2026-10-31: `serve --tools` exposing the full built-in registry is the recorded design (25b; "one function, three callers"; http-api.md:1354), and the sweep's panel judged it so. The fix is to make the text true, not to narrow the set. The panel rated entry 1 as medium (security-relevant output that misleads), not high.
- 2026-10-31: The milestone entry 3 regresses is `lib/documentation/cli/assistant/MILESTONES.md:4587`, not the path the sweep first gave.

**Open calls:**
- [default: the startup summary reads `-- tools: <n> (<toolsets>, plus MCP: <servers>)` and adds `-- runs unasked: <tool>, …` for every gated tool the config sets to `allow`, or `-- runs unasked: none`. The fs root is named (`files under <path>`). The help and http-api.md say the same in prose.]
- [default: `serve --tools` keeps the full registry, as chat builds it. Narrowing it (a `--tools=fetch_url` form, or a served default set) would change product shape, and that is the user's to ask for. It is not part of this item.]
- [default: the Host check applies only when the server is bound to loopback. Under `--allow-remote`, the operator's proxy and access control own the Host, which can be any name. The Origin check applies on every bind: an `Origin` is accepted when its host is loopback or equals the request's `Host`, and a request with no `Origin` (every non-browser client) is unaffected.]
- [default: the refusal is `403` in the server's error shape, saying `request refused: this server answers only requests addressed to it on loopback (Host <h>)` or `… from a page on another site (Origin <o>)`. The refused value is echoed because a client set it; no header is echoed beyond that. The gate covers every route, `/health` included, so the rule has no exceptions to remember.]
- [default: no `Content-Type` requirement. The Origin check already refuses the cross-site `text/plain` POST, because a browser always sends `Origin` on a POST. Requiring `application/json` would break the documented `curl … -d '{…}'` examples (http-api.md:194, 199), which send form encoding.]
- [default: no CORS headers are added and no `--allow-origin` flag. A browser client served from another origin did not work before either: its preflight `OPTIONS` gets a 404. Opening that is a later item, if someone asks.]
- [default: a request that waits on a session re-reads it under the lock and continues from the turn before it. It is not refused with a 409. This is Milestone T's "a second request waiting beats a first one corrupted".]

**Guardrail(s).**
- The mux gate as a table over `HttpRequest`, with no socket. On a loopback-bound mux: `Host: attacker.example:PORT` is refused on `POST /v1/chat/completions`, `GET /v1/sessions`, `GET` and `DELETE /v1/sessions/{id}` and `/health`. `Host: 127.0.0.1:PORT`, `localhost:PORT` and `[::1]:PORT` pass. `Origin: http://attacker.example` with a loopback Host and a `text/plain` body is refused before the handler runs: the handler double records no call. `Origin: http://localhost:3000` passes. No Origin passes. On a remote-bound mux: any Host passes, and a foreign Origin is refused unless it equals the Host. The admin gate's 401 matrix is unchanged.
- Two `chat_completions` on one session from two threads, with a mock backend that blocks the first until the second is waiting: both answer, and the session holds both exchanges in arrival order, `turn_count` 3 after the create turn. The second request's outgoing messages contain the first's exchange. A session deleted while a request waits gets the typed 404.
- The summary function over a registry built in a sandbox (temp `APOGEE_HOME`, mock backend). It reports the real count and toolsets, never the literal `fetch_url` alone. With `permissions: run_command: allow`, it names `run_command` as running unasked. The `--tools` help does not say `fetch_url` alone.
- `cli.serve_lifecycle` on the real binary: a foreign `Host` on `/v1/chat/completions` gets 403 and the mock backend is not called. A foreign `Origin` with `text/plain` gets 403. The existing loopback flow is unchanged. The startup line carries the real tool count under `--tools`.

**Acceptance criteria:**
- [ ] `apogee serve --tools` says on startup how many tools it offers and which, and names every tool that will run unasked. Its help and http-api.md:27 say the same. No text says `fetch_url` is the only tool.
- [ ] The sweep's probe (`Origin: http://attacker.example`, `Host: attacker.example:PORT`, `text/plain` body) gets 403 and runs no turn and no tool. A foreign Host on `GET /v1/sessions` gets 403. Clients on loopback with no Origin (curl, OpenAI SDKs, `cli.serve_lifecycle`) are unaffected.
- [ ] The sweep's three-request probe on one session ends with `turn_count` 3, every exchange is kept on disk and in `GET /v1/sessions/{id}`, and each answer was generated with the previous exchange in context.
- [ ] `cli.no_listen_symbols` and the full suite are green.
