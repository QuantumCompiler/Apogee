# A task halt or cancel sent while a run starts is kept and honored

**What / why.** `task halt` and `task cancel` are how a person stops an autonomous run, and a run can hold write grants. The second CLI/GUI bug sweep (2026-10-31) found that a stop sent while a `task resume` is still starting up is acknowledged with exit 0 and then deleted by the run it was meant for, which goes on to run every round. The same window swallows the TUI's Ctrl-C on a new run without a word. The window lasts as long as setup does: seconds with a slow MCP server. That is much longer than the "instant a task's lock changes hands" that 27h recorded as not verified. Paths below are under `lib/src/cli/source/` and were re-read at HEAD on 2026-10-31.

1. **A stop sent during a resume's setup is acknowledged, then cleared by the run it was sent to.** `task resume` takes the task lock at `presentation/cli/task_cmd.cpp:550-556`. It then builds providers (`:620`) and composes the tools, connecting the MCP servers (`:715-745`), all before `run_task` (`:944`). The lock names the task from the start, so `request_task_stop` (`:1405`) finds it running (`tasks::running_task(root) == task.id`, `:1412`). It writes the request (`:1413`) and returns `asked task … to cancel: its turn ends now, through the loop's own cancellation` (`:1418-1421`), and `task cancel` exits 0. Then the run begins, and the first thing `Runner::run` does after `resume_refusal` is `clear_request` (`business/tasks/runner.cpp:141-143`): "A request is for a running process; one standing now was left for a process that ended before reading it, and this run is a new decision." That reasoning holds for a request left by a process that has ended. It is wrong for a request addressed to this process, which is the lock's live holder. Scenario: a task fails on a question. Its config has an MCP server that is slow to connect (probe: `mcp create slow --command /bin/sh --args -c 'sleep 6'`). `apogee task resume <id> &`, then `apogee task cancel <id>` 1.5 s later. Probe output: `asked task task-20261031-211303 to cancel: its turn ends now, through the loop's own cancellation` / `cancel_rc=0` / `ls` shows `request task.json` / then `[task] … resumed`, `round 1 of 2`, `task task-20261031-211303 done`, `resume_rc=0`, and the request file is gone. A person's emergency stop is confirmed and then ignored. `task halt` takes the same path (`:1418-1419`). So does the macOS app's Tasks screen, whose Halt and Cancel run `task halt|cancel <id>` (`lib/src/darwin/source/presentation/tasks/ViewModels/TasksViewModel.swift:282-287`).
2. **On a new run in the TUI, Ctrl-C during setup is dropped silently.** The Task view's cancel callback (`presentation/cli/tui_task.cpp:162-173`) calls the same core, `request_task_stop(id, Cancel)`, with the id `live->id` holds. On a resume that id is set from the start (`:128-131`), so the request is cleared as in entry 1. On a new run the id is set only when the first event carrying a `task_id` arrives (`:145-148`), and that event is written only once `run_task` has saved the ledger. Until then the id is empty. `find_task` (`task_cmd.cpp:343-363`) then resolves the running task through the lock (`:346-347`), which already names the new id (`task_cmd.cpp:542`, `:553`). `load_task` finds no ledger and throws, and the callback swallows the throw (`tui_task.cpp:169-171`, "Not running yet, or already over: nothing to stop"). The run then starts and runs every round. On the CLI, `task cancel` during a new `task run`'s setup fails visibly instead, with `no task '<id>'` and exit 1. That is misleading, since the task is about to run, but not silent.

The sweep's panel judged the stale-write race at `task_cmd.cpp:1423-1427` (the lock changing hands between the `running_task` read and the write) to be the instant 27h recorded, not a separate finding. This item settles which way that instant falls (Open calls). What already works: a stop sent once a round is under way ends the turn through the loop's cancellation (exit 130), or the task at the round's end, as `task_e2e.sh:417-436` pins. A stop for a task no process runs is written to its ledger under the lock (`task_cmd.cpp:1423-1458`). A request left behind by a process that ended (`kill -9` after the request was written) does not stop the next resume (`tests/business/tasks/runner_test.cpp:517-526`).

**Core constraint(s).**
- **A stop the CLI acknowledges is a stop the run obeys.** The item's own rule. A `task halt` or `task cancel` that exits 0 means the named run stops before its next model call (cancel) or before its next round (halt). The only alternative is a refusal that says why.
- **27h's recorded rule stands.** A request left by a process that has *ended* is not a decision for the next run (MILESTONES 27h; `runner_test.cpp:517`). The fix moves the point where a request becomes stale from "the run starts" to "the lock changes hands". It does not drop the rule.
- **One change, every mode** ([ADR 0002](../../adrs/mode-parity.md)): the fix sits in the one core, `request_task_stop` and the runner, which the CLI verbs, the TUI's Ctrl-C and the app's buttons all reach.
- **Older versions keep working** ([ADR 0006](../../adrs/backwards-compatibility.md)): the `request` file keeps its one-word format. The task events, ledger fields and exit codes are unchanged: cancelled is 130, halted is 1.
- **Four layers** ([ADR 0001](../../adrs/layer-enforcement.md)): ownership and the request's lifetime belong to `business/tasks` (the ledger and the runner). `task_cmd.cpp` and `tui_task.cpp` only call the core.
- **Development runs on the dev channel** ([CLAUDE.md](../../assistant/CLAUDE.md#development-runs-on-the-dev-channel)): the probe re-runs on `apogee-dev` against a scratch `APOGEE_HOME`, never `apogee` or `~/.apogee`.

**Seam + files.** Source under `lib/src/cli/source/`, tests under `lib/src/cli/tests/` mirroring it ([ADR 0004](../../adrs/tests-mirror-architecture.md)).
- `business/tasks/ledger.cpp/.h`: `TaskLock::acquire` (`:231`) clears the named task's standing `request` once the lock is its own. A request that predates this process is stale from that moment, and one written after it is addressed to this process.
- `business/tasks/runner.cpp/.h`: `Runner::run` no longer clears at its start (`:141-143`). Once the `RequestWatcher` is up and before `plan()` or the first round, it reads the standing request through `stop_if_asked`. A halt or cancel there ends the run before any model call, with a reason that says so. The clear at the run's end (`:172`) stays.
- `presentation/cli/task_cmd.cpp`: `request_task_stop` (`:1405-1421`) writes the request when the lock's live holder names a task whose ledger is not yet written, with a reply that says it stops before it starts. It keeps today's reply for a task already running. `run_task_command`'s refusals between the lock (`:553`) and `run_task` (`:944`) remove a request they never got to read, along with the then-empty task directory.
- `presentation/cli/tui_task.cpp`: the cancel callback (`:162-173`) passes the lock's task when `live->id` is still empty and stops swallowing the throw for that case. It says on the notice row when there was nothing to stop.
- Tests: `tests/business/tasks/ledger_test.cpp`, `runner_test.cpp`; `tests/presentation/cli/task_test.cpp`, `tui_task_test.cpp`; the subprocess case in `tests/scripts/sh/task_e2e.sh`.
- Docs: [DEVELOPER.md](../../assistant/DEVELOPER.md)'s `tasks/` row, where "a request a process that ended left standing cleared when a run starts" becomes "cleared when the lock is taken", plus the honored-at-start rule.

**Reference.** 27h, the task runner and its ledger ([Milestone AD](../../assistant/MILESTONES.md#milestone-ad--autonomous-tasks), MILESTONES:6826, its "Not verified" naming only the lock-change instant), is the shipped behavior this item corrects. 37e, the progress seam and the Task view ([Milestone AH](../../assistant/MILESTONES.md#milestone-ah--the-full-screen-tui)), carved `request_task_stop` as the core the TUI's Ctrl-C calls. Sibling items: the app's Tasks screen and what it says after Halt or Cancel belong to [6g](../../../gui/backlog/v0.2.1/tasks-screen-truthful.md). The cycle's halt during a pass is the training precedent: a halt taken during a pass is kept (M30, Milestone AO). [57o](tool-gate-enforces-what-it-shows.md) owns what a running task's tool gate allows, which is a separate matter from stopping it.

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item with two entries. Both are the stop core losing a request in the window between taking the lock and the run's first save. On a resume the runner clears the request. On a new run the core cannot resolve a ledger that is not yet written. One seam, the request's lifetime, fixes both.
- 2026-10-31: The 1427 stale-write race is the instant 27h recorded, not a separate finding (the sweep's panel). It is settled here as a consequence of the new clearing point, not built as its own fix.

**Open calls:**
- [default: the request turns stale when the task lock is taken (`TaskLock::acquire`), not when the runner starts. This keeps 27h's rule (`runner_test.cpp:517` stays green) and keeps every request sent to the lock's live holder. The alternative is a request that names the PID it was addressed to, kept only by that process. It needs a new file format for the same guarantee, so it is not taken.]
- [default: the lock-change instant now falls toward stopping. A stop that read the old holder as live and landed just after the new one took the lock stops the new run of the *same* task. That is the safe direction for an emergency stop: the person asked for that task to stop. The reverse, a stop silently lost, is what this item removes.]
- [default: a request standing when the run begins takes effect before any model call. The task ends `cancelled` (exit 130) with reason `cancelled by 'apogee task cancel' before round <n>` (`before the plan` when there is none), or `halted` (exit 1) with reason `halted by 'apogee task halt' before round <n>`. Wording settled at build.]
- [default: setup is not interrupted mid-step. Provider building and MCP connections run to their own bounds, and the stop takes effect as they finish, before anything reaches a model or a tool. A cancellation token threaded through `build_providers` and the MCP connect would end setup sooner. It is a wider change and not needed for the guarantee, so it is noted for later if wanted.]
- [default: a stop sent during a new `task run`'s setup is acknowledged, `asked task <id> to cancel: it stops before it starts`, and the new task's ledger records `created`, `started`, `finished` with status `cancelled`, so `task status` shows it. If the run is refused before `run_task` (a grant refusal, a backend refusal), the command removes the request and the empty directory, so `task list` sees no stray entry.]
- [default: the TUI's Ctrl-C with nothing to stop (the run already over) says so on the notice row, not silently. Ctrl-C during setup is honored through the lock's task id.]

**Guardrail(s).** Hermetic, under a temp `APOGEE_HOME`, the mock backend and scripted turns, no network:
- `ledger_test`: a request standing when `TaskLock::acquire` succeeds is gone afterwards. One written after the acquire stays.
- `runner_test`: a cancel written after the lock was taken and before `run_task` ends the run `cancelled` with zero model calls (`scripted.seen` empty) and the "before" reason. A halt there ends it `halted` with zero calls. The existing "a request a process that ended left behind does not stop the next run" case, driven through the acquire, stays `done` with two calls.
- `task_test` (presentation): `request_task_stop` while the lock names a task with no ledger yet writes the request and returns the "before it starts" line, not `no task '<id>'`. A run refused after the lock leaves no `request` file and no empty directory.
- `tui_task_test`: the cancel callback with an empty `live->id` and a live lock reaches that task's request.
- `task_e2e.sh`, the subprocess case: the probe re-run. A failed-on-question task, an MCP server that sleeps 6 s, `task resume <id> &`, `task cancel <id>` 1.5 s later. Cancel exits 0. The resume exits 130 with no round run, its reason says it was cancelled before the round, and no `request` file remains. The same case with `task halt` exits 1, `halted`.

**Acceptance criteria:**
- [ ] `task cancel <id>` during a resume's setup exits 0, and the resume then ends `cancelled` (exit 130) before any model call. `task halt <id>` there leaves it `halted` before its next round.
- [ ] A request left by a process that has ended still does not stop the next resume.
- [ ] Ctrl-C in the TUI's Task view during a new run's setup stops that run. A Ctrl-C that has nothing to stop says so.
- [ ] `task cancel` during a new `task run`'s setup is acknowledged and honored, not refused with `no task '<id>'`. A run refused before it starts leaves no stray request or directory.
- [ ] The full suite is green, and the probe re-run on `apogee-dev` against a scratch `APOGEE_HOME` shows entry 1 inverted.

**Scope note.** Earmarked for v0.2.1 (track 57); ungated.
