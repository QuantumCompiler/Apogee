# A pipeline resume continues the run it names, and training reads say when a file can't be read

**What / why.** `train pipeline resume` is the way back into a run that stopped short, and `train status` and the pipeline and cycle reads are what the terminal, `serve`'s admin plane and the macOS app all show about training. The second CLI/GUI bug sweep (2026-10-31) found that resume can run the wrong data under the wrong gate, can refuse a run its own hint names, and can start at a stage other than the one it reports. It also found that a damaged or mistyped training file is reported as an empty state, or breaks every read with a JSON library error that names no file. Re-read at HEAD (`b26550bb`):

1. **A failed cycle pass hands on the pipeline's resume advice, and following it retrains on the wrong data and skips the cycle's gate.** A cycle pass replaces every stage's dataset with its merged file (`business/training/cycle.cpp:595-601`) and runs the pipeline with `continue_on_fail = false` (`cycle.cpp:613`). When that pipeline fails, the cycle's failure reason is the pipeline's error relayed whole (`cycle.cpp:653-656`), and the gate abort's error carries the pipeline verb's door: `"Fix the data or the suite and 'apogee train pipeline resume <id>', or pass --continue-on-fail to go on regardless"` (`business/training/pipeline.cpp:249-254`). `train cycle run` has no `--continue-on-fail`. `train pipeline status` prints `Resume from stage N` for any run that is not complete (`presentation/cli/train.cpp:1430-1432`), cycle runs included. `train pipeline resume` reloads the spec by the manifest's `spec_name` (`train.cpp:2978-2987`) and trains on that spec's own static datasets, not the cycle's `merged.jsonl`. Nothing refuses a `cycle-` id (`kCycleIdPrefix`, `business/training/cycle.h:44`). The resumed stage overwrites the failed candidate's adapter under `runs/cycle-<id>-s0`, the manifest ends `complete`, and the CLI offers a promote. That skips the cycle's dual gate, its history, the breaker and queue consumption, and it contradicts training.md:818-819, "**fail** discards the candidate -- **nothing reaches inference**". Scenario: a cycle with pipeline `nightly` (stage dataset `starter`) and a directory queue. A queued file regresses, so the pass fails and leaves an aborted `cycle-<id>` pipeline. The user follows the printed hint, or clicks Resume in the app. Probe pB.sh: the failing pass printed `[train] ... dataset merged.jsonl` and then `cycle FAILED -- ... 'apogee train pipeline resume cycle-20261031-201133', or pass --continue-on-fail`. `train pipeline status` printed `Resume from stage 1: apogee train pipeline resume cycle-20261031-201133`. The resume printed `[train] stage 1/1 'base': mock lora on aaaaaaaaaaaa, dataset starter.jsonl`, then `pipeline complete` and `apogee train promote cycle-20261031-201133-s0 --as <backend>`. The manifest afterwards read: status complete [('passed', 'starter.jsonl')]. `cycle status` still showed the single fail row, and day1.jsonl was still in the queue. Severity high.
2. **Resume without `--pipeline` refuses a named pipeline whose `name:` differs from its config key, and every hint omits `--pipeline`.** The config keeps `training.pipelines` by key (`data/contracts/config.cpp:2435-2442`), but a spec's `name` is its `name:` field when written, the key only as a fallback (`config.cpp:506-508`). The manifest stores `spec.name` (`pipeline.cpp:505`), and resume looks it up as a key (`train.cpp:2980`). A run started from a spec file stores the file's stem (`train.cpp:1448`), which no key matches either. The hints in `pipeline status` (`train.cpp:1431-1432`), the gate abort (`pipeline.cpp:249-254`) and the cancel line (`train.cpp:2935-2937`) all print the bare command. `train pipeline list`'s `name` is the key (`presentation/operations/training_reads.cpp:173`), and a run's document carries only `spec_name`, so a client cannot match the two. Scenario: config `pipelines: {nightly: {name: 'Nightly SFT', ...}}`. A run aborts at stage 2. `train pipeline status <id>` says `Resume from stage 2: apogee train pipeline resume <id>`. Running that command exits 1 with `pipeline 'Nightly SFT' is not under training.pipelines any more`, although the entry is still in the config. Probe pA.sh: `pipeline list` showed `nightly  2  tiny`; `pipeline status` showed `spec: Nightly SFT ... Resume from stage 2: apogee train pipeline resume pipe-20261031-201124`. The resume printed `apogee train: pipeline 'Nightly SFT' is not under training.pipelines any more -- pass --pipeline <spec> to resume pipe-20261031-201124` with exit=1. With `--pipeline nightly` it ran. The app's Resume… sends no `--pipeline` (GUI `TrainingViewModel.swift:244`), so it fails for every such entry and every spec-file run. That part is [6i](../../../gui/backlog/v0.2.1/training-screens-follow-the-cli.md)'s. Severity medium.
3. **Resume starts after the last passed stage, and every surface says it starts at the first stage that has not passed.** `StageRunner::run` sets the resume point one past the last `passed` stage, from that stage's fused checkpoint (`pipeline.cpp:52-63`). `pipeline status` reports `first_unpassed() + 1` (`train.cpp:1430-1432`, `pipeline.cpp:350-357`), and so do the resume help (`train.cpp:2829`, "Continue a pipeline from the first stage that has not passed"), training.md:663-664, the shipped record (MILESTONES.md:5648, "`resume` continues from the first stage that has not passed, the passed ones untouched") and the app's confirm dialog (GUI `Training.swift:232-233`). Under the hard gate the two points are the same stage. After `--continue-on-fail` or `gate_mode: soft`, they are not, and both halves of the recorded promise cannot hold at once: retraining stage a would change the base that b passed on. Scenario: a 3-stage spec run with `--continue-on-fail`. Stage a fails its gate, b passes, and c's training errors. Status says 'Resume from stage 1', and the app asks 'Resume <id> from stage 1, a?'. The resume trains only stage c and reports `pipeline complete` with a still failed. Probe pE.sh: status showed `1 a failed 0% / 2 b passed 100% / 3 c failed -` and `Resume from stage 1:`. The resume printed `-- stage 3/3: c` and then `pipeline complete -- pipe-20261031-201255` with `1. a failed 0% (0/1)`. Severity medium.
4. **`train status --output-format json` reports an unreadable cycle history as no history.** `training_status_document` leaves `cycle` null whenever `load_history` returns an error (`training_reads.cpp:54-67`: `if (error.empty()) { cycle = ... }`), and drops the error. The text view says `Cycle: history unreadable -- <error>` (`train.cpp:1818-1819`), and `train cycle run` refuses every pass on it (`cycle.cpp:454`). The documented contract is that `cycle` is null only until the first cycle has run (http-api.md:1220, machine-mode.md:1583-1584). The same document is `GET /v1/admin/training` (`presentation/httpserver/admin_training.cpp:16`). history.json is written atomically (`cycle.cpp:157`), so this only happens after outside damage: a hand edit, a bad disk, or a field of the wrong type (entry 5). The app gates its `train cycle status` read on `status.cycle` (GUI `TrainingViewModel.swift:560`), so it shows the empty state and offers Run. Its `cycleHalted` falls back to `status.cycle.halted` (`TrainingViewModel.swift:786`), so a halted history that becomes unreadable shows as not halted. Halt is offered instead of Resume, and Run is enabled even though `train cycle run` would refuse. A scheduled cycle fails silently while the app shows nothing wrong. Scenario: write `{"backend":"x","runs":[` to `$APOGEE_HOME/training/cycle/history.json`. `apogee train status --output-format json` -> exit 0, `"cycle":null` (identical to a fresh install). `apogee train status` -> `Cycle: history unreadable -- .../history.json is not JSON`. `apogee train cycle status --output-format json` -> exit 1 `the cycle history is unreadable`. Probe pG.sh (`runs` not an array): text read `Cycle: history unreadable -- …/history.json: cycle history: runs must be an array`; JSON read `cycle: None`; `cycle status --output-format json`, `cycle run` and `cycle halt` each printed `the cycle history is unreadable: …` with exit=1. Severity medium.
5. **A wrongly typed field in one training file breaks every training read instead of being skipped.** The readers catch only `std::runtime_error`: `read_pipeline_manifest` (`pipeline.cpp:474`), `load_history` (`cycle.cpp:139`), the run manifest's `read_manifest` (`business/training/manifest.cpp:133`) and the version ledger's reader (`business/training/store.cpp:141`). The parsers read fields with `json.value(...)`: `pipeline_manifest_from_json` (`pipeline.cpp:395-435`), `history_from_json` (`cycle.cpp:75-111`), `manifest_from_json` (`manifest.cpp:66-98`) and `ledger_from_json` (`store.cpp:74-115`). When a field has the wrong type, `json.value(...)` throws `nlohmann::json::type_error`, which derives from `std::exception`, not `std::runtime_error`. So `TrainingStore::list_pipelines` (`store.cpp:279-296`), which skips a manifest it cannot read, never gets to skip it. The bare library message reaches the top level and names no file. Scenario: a manifest from another version, or edited by hand, has `"index": "one"` in a stage. Both `apogee train status` and `train pipeline status` fail with `apogee: [json.exception.type_error.302] type must be number, but is string`, and nothing says which file is at fault. Probe pH.sh: with history.json `{"halted": "yes"}`, `train cycle status`, `--output-format json` and `train cycle halt` each printed `apogee: [json.exception.type_error.302] type must be boolean, but is string` with exit=1. With one manifest stage `"index": "one"`, `train pipeline status`, `train pipeline status --output-format json` and `train status` each printed `apogee: [json.exception.type_error.302] type must be number, but is string` with exit=1. A second probe got the same with `"index":"0"` and with `{"backend":"x","total_runs":"3"}` as the history, where a malformed history is meant to read `the cycle history is unreadable: ...`. Severity low.

What already works: under the default hard gate, a resume of a `train pipeline run` whose spec is keyed by its own name continues from the right stage on the right data. A complete run and a spec whose stage count drifted are refused (`pipeline.cpp:520-530`). A history or manifest that is not JSON at all, or that has the wrong shape (`runs must be an array`), is caught and named. The text `train status` already says when the history is unreadable.

**Core constraint(s).**
- **A change propagates to every mode** (ADR 0002): `training_status_document` and `training_pipeline_document` are what `--output-format json`, `GET /v1/admin/training` and `GET /v1/admin/training/runs/{id}` serve. Each fix lands there once, and the text views read the same facts.
- **Older versions keep working** (ADR 0006): new fields are additive (`cycle_error`, the manifest's `spec_ref`, the pipeline document's `resume`). A manifest written before this item still resumes, and `cycle` keeps its shape: null or the headline object, never a third form.
- **The four layers** (ADR 0001): the readers' catch and the resume rule live in Business (`training/`). The verb's doors (the command to run next) live in Presentation, where the verb is.
- The item's own rules: a cycle pass's candidate is the cycle's alone. It is judged by the dual gate and discarded on a fail, and no other verb trains, overwrites or promotes it. A hint prints a command that runs. A read that cannot read a file says which file and why, and never presents the failure as an empty state.
- **Development runs on the dev channel**: any live check runs `apogee-dev`, never the release `apogee` or `~/.apogee`. Probes and tests use a temporary `APOGEE_HOME` under the scratchpad and the mock trainer.

**Seam + files.**
- `business/training/pipeline.cpp/.h`:
  - The gate abort's error carries the stage's reason only. The door moves to the verb.
  - One `PipelineRunManifest::resume_from()` names the resume point. `StageRunner::run` and every surface read it, and `first_unpassed()` is no longer used to report it.
  - The manifest gains `spec_ref`, the `--pipeline` value the run took (a config key, or a spec file's absolute path).
  - `read_pipeline_manifest` catches `nlohmann::json::exception` beside `std::runtime_error` and names the file.
- `business/training/cycle.cpp`: the cycle's failure reason no longer relays a pipeline door. Its own line says the candidate is discarded and the next `apogee train cycle run` retries, with the queue still holding its files. `load_history` catches type errors and names the file.
- `business/training/manifest.cpp`, `business/training/store.cpp`: the same catch in `read_manifest` and the ledger reader. `list_pipelines` then skips a mistyped manifest as it skips a malformed one.
- `presentation/cli/train.cpp`:
  - `pipeline resume` refuses a `cycle-` run, naming `train cycle run`. Without `--pipeline` it resolves the spec from `spec_ref`, then by key, then by the one entry whose `name:` matches.
  - The status, gate-abort and cancel hints print a command that runs, with `--pipeline <ref>` when the bare form would not find the spec, and no resume hint for a cycle run.
  - The resume help and the summary say where the resume starts and that an earlier failed stage stays as it is.
  - A single-run read of an unreadable manifest says `<path>: <reason>`, not `no pipeline run`.
- `presentation/operations/training_reads.cpp/.h`: `training_status_document` gains `cycle_error`. `training_pipeline_document` gains `resume`: null when the run is complete or is a cycle pass, otherwise `{stage, name, pipeline}`, with the stage index it starts from and the spec reference to pass. It also carries `spec_ref`.
- Tests:

  - `tests/business/training/cycle_test.cpp`: no pipeline door in a failed pass's reason; the history type-error.
  - `tests/business/training/manifest_test.cpp`, `tests/business/training/store_test.cpp`: the type-error catches, and the list skipping one mistyped manifest.
  - `tests/presentation/cli/train_test.cpp`: the refusal, the spec lookup, the hints, the help.
  - New `tests/presentation/operations/training_reads_test.cpp`, mirroring `training_reads.cpp`: `cycle_error` and `resume`.
- Docs:
  - [training.md](../../reference/training.md): the resume paragraph (lines 660-668) and the cycle's fail sentence (818-819) say where a resume starts and that a cycle pass is not resumed.
  - [http-api.md](../../reference/http-api.md):1220 and [machine-mode.md](../../reference/machine-mode.md):1584: `cycle` is null until the first cycle has run, or when the history cannot be read, and then `cycle_error` says why. The pipeline document's `resume` and `spec_ref`.
  - A dated revision under the shipped `training-pipelines` record, since its resume sentence changes meaning.

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item, because all five are the same promise: what the training verbs say about a run is what the run is. Entries 1-3 are one verb, `pipeline resume`, and they share its spec lookup, its hints and its resume point. Entries 4-5 are the same readers failing to say which file they could not read. The sweep found entries 4 and 5 twice each (once under the pipelines lens, once under the driver-reads lens). Each pair is merged into one entry here.
- 2026-10-31: Entry 4's severity is medium. The panel judged it low-medium on frequency (history.json is written atomically) and kept medium for a scheduled cycle failing behind an empty state.
- 2026-10-31: The fix to entry 4 belongs to the CLI. The app is right to trust `cycle: null`, and the document is what lies.

**Open calls:**
- [default: a cycle pass is not resumable. `pipeline resume` refuses any id with the `cycle-` prefix: `pipeline <id> is a cycle pass, and its candidate was discarded -- 'apogee train cycle run' runs the next pass`. `pipeline status` prints no resume line for it, and the document's `resume` is null. The prefix is the test, because every cycle pass's id carries it (`new_run_id(..., kCycleIdPrefix)`, `cycle.cpp:605-606`), no other verb mints it, and it covers manifests already on disk.]
- [default: the gate abort's error says only why the stage stopped. `train pipeline run|resume` add their own door, so the cycle, which reuses the runner, never relays it. The cycle's failure line ends `-- the candidate is discarded; the queue keeps its files for the next 'apogee train cycle run'`.]
- [default: the resume point stays where the runner puts it today, after the last stage that passed and from its fused checkpoint. Every surface is changed to report that point: the status line, the resume help, training.md, the document's `resume`, the summary. When an earlier stage failed and the run went past it (`--continue-on-fail` or `gate_mode: soft`), they say so: `stage 1, a, failed its gate and stays as it is`. Retraining from the first unpassed stage would discard the later stages that passed, which breaks the shipped "the passed ones untouched". Under the hard gate the two rules agree, so ordinary runs do not change.]
- [default: the manifest records `spec_ref`. Resume without `--pipeline` tries `spec_ref`, then `spec_name` as a key, then the one `training.pipelines` entry whose `name:` equals `spec_name`. It refuses an ambiguous match and names the candidates. A spec file that has gone stays a refusal that names `--pipeline`. Each hint prints the bare command when that lookup succeeds and `--pipeline <ref>` otherwise.]
- [default: `train status`'s document keeps `cycle` null when the history cannot be read and adds `cycle_error`, which is the reason `load_history` gave, or null. The `cycle` field does not become an object with an error inside, because a client reading `cycle.halted` would then see a halted loop as not halted.]
- [default: a mistyped field is reported as `<path>: <the library's message>`, with the file named and the field not named. A reader that names each field is not needed to fix the failure.]
- [default: `pipeline status <id>` and `pipeline resume <id>` on an unreadable manifest say `<path>: <reason>` instead of `no pipeline run '<id>'`. The lists skip it, as they skip a malformed one today.]
- (consumed decision) How the app draws the refusal, the resume stage, `cycle_error` and the halted state is [6i](../../../gui/backlog/v0.2.1/training-screens-follow-the-cli.md)'s.

**Guardrail(s).** Each test runs in a temp `APOGEE_HOME` with the mock trainer:
- **Entry 1.** A cycle pass whose gate fails: its stderr and record reason contain no `pipeline resume` and no `--continue-on-fail`. `pipeline resume cycle-<id>` exits non-zero naming `train cycle run`, and `runs/cycle-<id>-s0`'s adapter is byte-identical afterwards. `pipeline status cycle-<id>` prints no resume line, and its document's `resume` is null. The queue file is still queued.
- **Entry 2.** A config entry `nightly` with `name: Nightly SFT`, aborted at stage 2: the hint from `pipeline status` runs as printed and resumes. So does a spec-file run's hint. An older manifest without `spec_ref` resumes through the `name:` match. Two entries sharing a `name:` are refused, naming both.
- **Entry 3.** The pE probe's run (a failed, b passed, c errored): status, the document's `resume` and the summary all name stage 3, c, and say a stays failed. The runner trains only c. A hard-gate abort at stage 2 still reports and resumes stage 2.
- **Entry 4.** `{"backend":"x","runs":[` and a `runs`-not-an-array history: the status document has `cycle: null` and a `cycle_error` naming history.json. A fresh home has both null.
- **Entry 5.** A stage `"index": "one"` in one of two manifests: `train status` and `pipeline status` exit 0 and list the other run. `pipeline status <bad id>` names the file. `{"halted": "yes"}` and `{"total_runs": "3"}` histories read `the cycle history is unreadable: <path>: …` on `cycle status`, `cycle run` and `cycle halt`. A mistyped run manifest and ledger are skipped by their lists.

**Acceptance criteria:**
- [ ] The pB probe, replayed on `apogee-dev`: the failed pass suggests no pipeline resume, `train pipeline resume cycle-<id>` is refused naming `train cycle run`, the candidate is untouched, and nothing offers a promote.
- [ ] The pA probe: `train pipeline status <id>`'s printed command resumes the `Nightly SFT` run without `--pipeline`.
- [ ] The pE probe: every surface says the resume starts at stage 3, c, and that stage 1, a, stays failed. The resume does exactly that.
- [ ] The pG probe: `train status --output-format json` carries `cycle_error` naming history.json, and `GET /v1/admin/training` carries the same.
- [ ] The pH probe: no training read prints a bare `[json.exception.type_error…]`. A mistyped manifest is skipped by the lists and named by its own read, and a mistyped history reads `the cycle history is unreadable: <path>: …`.
- [ ] The full suite is green.
