# A direct-API or local backend's failure fails its turn, never the session or the answer

**What / why.** A network, stream or decode failure on the direct-API backends (`anthropic`, `openai`, `google`) or on llama.cpp ends today in one of three wrong ways: the whole process dies (exit 1, no `error` event, every queued line lost), the failure is said as "HTTP 0", or a blocked or cut answer is kept as if it were whole. The macOS app runs one `chat --output-format stream-json --input-format stream-json` process per session, so a wifi blip mid-answer ends the app's session. The fix makes every one of these a failed turn: a `ProviderError` that names the entry and says what happened, an `error` event in machine mode, exit 2 from `complete`, 502 `backend_error` from `serve`, and nothing kept as the answer. Found by the second CLI/GUI bug sweep (2026-10-31); every file:line below was re-read at HEAD `b26550bb`, paths under `lib/src/cli/source/`.

1. **A transport failure kills the session.** A connect, DNS or TLS failure, or a connection dropped mid-stream, throws `backends::HttpError`, a plain `std::runtime_error` (`data/transport/http_client.h:102`, thrown at `http_client.cpp:262` and rethrown on the last attempt at `:335-339`). Nothing on the way up makes it a `HarnessError`: not the providers (`anthropic.cpp:475`, `openai.cpp:331`, `google.cpp` call `client_->send` unguarded), not `Harness::chat` / `stream_chat` / `complete` (`business/harness/harness.cpp:424-484`), not the loop (`business/agentloop/loop.cpp:520-525` catches only `HarnessError`, to clear the status, and rethrows). `run_chat_turn` catches only `CancelledError` and `HarnessError` (`presentation/cli/chat_turn.cpp:313-320`), and neither call site catches more: machine mode (`chat_session.cpp:1773`) and the REPL (`:2692`). It reaches `main.cpp:33-35`, which prints `apogee: <message>` and exits 1, not 2 (`kBackendError`, `presentation/cli/helpers.h:57`). `complete` is the same (`complete.cpp:556-561` catches `HarnessError` only). In `serve`, the non-streaming path catches only `HarnessError` (`httpserver/handler.cpp:682-688`), so the failure goes to httplib's handler (`serve.cpp:135-147`) and returns 500 `server_error`, not 502 `backend_error`; the streaming path sends it in-stream as `server_error` (`handler.cpp:634-636`). The only catches of `backends::HttpError` are in `business/models/source_hf.cpp`. Probe (temp `APOGEE_HOME`; an `anthropic` entry with a fake key; `https_proxy=http://127.0.0.1:9`, so nothing reached a provider): two `user` lines in, and stdout held only `{"type":"session",...}` and `{"turn":1,"type":"thinking"}`; stderr `apogee: request failed: Couldn't connect to server`; exit=1; turn 2 never served. `apogee complete --output-format stream-json hi`: exit=1, no `error` event. This breaks [machine-mode.md](../../reference/machine-mode.md):243, "every accepted `user` line ends in exactly one `result` or one `error`" -- a **regression of Milestone M's 28f entry** ("A failed turn ends in `error`").
2. **OpenAI's mid-stream failures read "HTTP 0".** On a streamed Responses API `error` or `response.failed` event, `StreamAccumulator::handle` calls `openai::error_message(0, event.data)` (`data/backends/openai.cpp:57-59`). That function reads only a top-level `error` object (`openai_wire.cpp:302-314`: `:305` finds `error` and requires an object, `:313` returns `"HTTP " + std::to_string(status)`). The `error` event carries `code` / `message` at its top level, and `response.failed` nests them under `response.error`, so both come out as `openai: HTTP 0` -- on the terminal, in the machine `error` event and in `serve`'s error. A `server_error`, a rate limit hit mid-generation or a content-policy failure all lose the vendor's message. `openai_test.cpp` has no streamed-error case; Anthropic's suite has one (`anthropic_test.cpp:546`).
3. **A llama.cpp context or decode failure kills the session.** `LlamaCppProvider::make_context` (`data/backends/llamacpp.cpp:1036-1040`) is not wrapped, and neither are its callers -- `run_multimodal` (`:1583`), `run`'s side request (`:1653`) and session context (`:1659`) -- nor the prompt decodes (`decode_in_batches` at `:1656`, `:1712`, `:1714`, `:1719`) or the generation decode (`:1485`). `llama_real.cpp` throws plain `std::runtime_error` for a context it could not create (`:1027-1032`, "could not create a context for this model ... try cache_type: f16") and for a failed decode or missing KV slot (`:481-486`). Only `embed()` converts (`llamacpp.cpp:861-862`), and load failures are thrown as `ProviderError` (`:968`). So in `chat` and machine mode the exception reaches `main.cpp:33`: exit 1, `apogee: <message>`, no `error` event, and that turn's `logger::save` (`chat_turn.cpp:325`) skipped (earlier turns stay saved). The model loads (no context is made at load), and the first turn kills the GUI's process: a `cache_type` the user named (e.g. `q8_0`) or a `context_size` the hardware cannot allocate. `serve` survives on its catch-all (`handler.cpp:634`) but answers `server_error`, not `backend_error`. A decode that fails mid-prompt also leaves the session context's KV trimmed and half-written while `session_tokens_` (`:1721`) still records the previous prompt.
4. **A Gemini blocked prompt is a silent empty answer.** Gemini answers a blocked prompt with 200, `promptFeedback.blockReason` and no `candidates`. `google::parse_response` (`data/backends/google_wire.cpp:266-326`) reads only `candidates[0]` (`:274-276`), so the empty `finishReason` maps to `FinishReason::Other` (`:242`); the streaming accumulator (`google.cpp:45-96`, `take_response` `:98-106`) returns empty text with `Other` and raises nothing. `promptFeedback` and `blockReason` appear nowhere in `data/backends/google*.cpp`. The loop then pushes `ChatMessage::assistant(answer)` with the empty answer (`loop.cpp:537-541`) and shows nothing (`:543` skips an empty answer), and `serve` reports `Other` as `finish_reason: "stop"` (`handler.cpp:175-187`). The user sees a blank turn with no reason, an empty assistant message is saved, and an API client gets an empty answer that looks normal.
5. **A stream cut before its terminal event is kept as a complete answer.** It needs a clean early end of the body -- an HTTP/2 END_STREAM, or a proxy closing a close-delimited HTTP/1.x response; a transport-level cut inside a chunked body already throws (finding 1). Anthropic's `stream_chat` goes from `parser.finish()` (`anthropic.cpp:481`) to the error check (`:483-485`) to `merge_round` (`:489`) and never reads `saw_message_stop()`: it is set at `:212` and declared at `:37-38` / `:72`, and nothing in `source/` or `tests/` reads it. OpenAI's `stream_chat` (`openai.cpp:335-340`) handles `response.completed` / `response.incomplete` (`:120-138`) but never requires one. Both return the partial text with the default `FinishReason::Stop` (`anthropic.cpp:68`, `openai.cpp:45`), saved as a finished turn: neither the user nor a driver can tell it was cut.

What already works: an HTTP error status, an Anthropic mid-stream `error` event (`anthropic_test.cpp:546`) and a Gemini stream error all fail the turn as a `ProviderError`; `serve` stays up through every case above; earlier turns are on disk.

**Core constraint(s).**
- **A change propagates to every mode** ([ADR 0002](../../adrs/mode-parity.md)): the `ProviderError` the backend throws is what the terminal, `serve` and machine mode all show, so each fix is at the throw, once, and the surfaces' existing `HarnessError` catches do the rest -- exit 2, the `error` event, 502 `backend_error`.
- **The machine protocol's turn accounting** ([machine-mode.md](../../reference/machine-mode.md):243): every accepted `user` line ends in exactly one `result` or one `error`, and the session lives on to serve the next. **The additive protocol** ([ADR 0006](../../adrs/backwards-compatibility.md)): the `error` event's shape is unchanged; only when it is sent changes.
- **⚠ The harness never includes backends**: the transport error becomes a `ProviderError` inside `data/backends/`, never by teaching `harness/` or `agentloop/` about `backends::HttpError`.
- **⚠ Secrets are unleakable by construction**: a transport message is curl's text and a vendor's is built from the response, never from the request; the keyed-error tests (`openai_test.cpp:357`, `anthropic_test.cpp:612`) cover the new paths.
- **Development runs on the dev channel**: the live probe in the acceptance criteria runs `apogee-dev` in a temp `APOGEE_HOME`, never the release `apogee` or `~/.apogee`.
- The item's own rule, persist after every turn (`chat_turn.cpp:322-325`): a failed turn still saves the session; a failed or cut answer is never saved as an answer.

**Seam + files.**
- `data/backends/anthropic.cpp`, `openai.cpp`, `google.cpp` -- every `client_->send` turns `HttpError` into `ProviderError(options_.backend_name, e.what())` through one shared helper beside the providers; Anthropic fails a stream with no `message_stop`, OpenAI one with no `response.completed` / `response.incomplete`.
- `data/backends/openai_wire.cpp/.h` -- a stream-event error reader: the `error` event's top-level `code` / `message`, `response.failed`'s `response.error`.
- `data/backends/google_wire.cpp/.h`, `google.cpp` -- no candidates and a `promptFeedback.blockReason` fail the turn, naming it, streamed and not.
- `data/backends/llamacpp.cpp` -- `run` and `run_multimodal` convert a `std::runtime_error` that is not already a `HarnessError` into `ProviderError`; a failure on the session path clears the session's token record.
- `presentation/cli/chat_turn.cpp`, `complete.cpp` -- a `std::exception` backstop after the `HarnessError` catch.
- Tests: `tests/data/backends/anthropic_test.cpp`, `openai_test.cpp`, `google_test.cpp`, `llamacpp_test.cpp` (with a failing-context and failing-decode hook in `tests/support/fake_llama.h`); `tests/presentation/machine/machine_mode_test.cpp`; `tests/presentation/cli/chat_test.cpp`; `tests/presentation/httpserver/handler_test.cpp`; `tests/scripts/sh/machine_mode_e2e.sh` (`cli.machine_mode`).

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: Five findings, one item: each is a direct-API or local backend's failure that leaves the backend as something other than a `ProviderError` the surfaces already handle -- a raw `runtime_error`, a status of 0, or a normal-looking answer. They share the seam (the providers' throws) and the guardrail (a failed turn is one `error`, and the session lives).
- 2026-10-31: A blocked or cut answer fails its turn rather than being kept with a finish reason, because the loop saves whatever answer a provider returns (`loop.cpp:540-541`): only a failure keeps it out of history.

**Open calls:**
- [default: transport failures become `ProviderError` in the providers, at their `client_->send` calls, through one helper, keeping curl's text (`anthropic: request failed: Couldn't connect to server`). `HttpError` is not re-parented under `HarnessError`: it carries no backend name, and `source_hf.cpp`'s catches rely on it being a transport type.]
- [default: `run_chat_turn` and `complete` also catch `std::exception` after `HarnessError`, logged at Error and reported as the turn's error (`complete` exits 2), so the turn accounting does not depend on every provider being right. `serve` needs no backstop: it survives today.]
- [default: OpenAI's stream error reads `code: message` from the `error` event's top level or `response.failed`'s `response.error`; with neither, `the response stream reported a failure`, never "HTTP 0".]
- [default: llama.cpp converts at the body of `run` and `run_multimodal`, catching `HarnessError` first and rethrowing it (a `ProviderError` is a `runtime_error`), the rest wrapped as `ProviderError(options_.backend_name, e.what())`. A session-path failure clears `session_tokens_` and the context's KV, so the next turn reads its prompt again rather than trusting a half-written cache; a failed `make_context` leaves `session_` null, so the next turn tries again.]
- [default: a Gemini response with no candidates and a `promptFeedback.blockReason` fails with `google: the prompt was blocked (<reason>)`, plus `blockReasonMessage` when present. Mapping it to `ContentFilter` instead was weighed and rejected: it would still save an empty assistant turn and give an API client a 200 with no answer.]
- [default: a stream with no terminal event fails with `<backend>: the response stream ended before the answer finished`; text already shown stays on screen, and nothing is saved as the answer. Google's stream has no terminal event of its own; it is held to the rule "some chunk carried a `finishReason`" only if a recorded Gemini stream confirms the last chunk always carries one -- checked at build, otherwise left as it is and said in the record.]
- [default: the loop keeps saving an empty answer a model really gave (`loop.cpp:540-541`); only the blocked prompt stops producing one here.]
- (consumed decision) The Claude CLI's "reported success" message is CLI M34's ([`claude-cli-says-why.md`](../maintenance/claude-cli-says-why.md)); the vendor CLIs' other failures are 57b's ([`vendor-cli-failures-say-why.md`](vendor-cli-failures-say-why.md)).

**Guardrail(s).** Hermetic: a temp `APOGEE_HOME`, `FakeTransport`, the mock backend, `fake_llama.h`. Each finding pinned:
- Finding 1: per provider, a `FakeTransport` transport error on `chat` and on `stream_chat`, before and after the first byte, throws `ProviderError` naming the entry (never a bare `HttpError`). In `machine_mode_test.cpp`, two `user` lines with the first turn's provider throwing it: turn 1 ends in one `error` carrying the message, turn 2 ends in `result`, the session file holds both turns. The same with a provider throwing a bare `std::runtime_error` (the backstop). `complete` exits 2 with an `error` event. In `handler_test.cpp`, the non-streaming request answers 502 `backend_error`. `cli.machine_mode` replays the probe (an `anthropic` entry with a fake key, `https_proxy=http://127.0.0.1:9`): exit 0, an `error` and then a `result`.
- Finding 2: OpenAI's `error` event and `response.failed` event, each with a vendor `code` and `message`, throw a `ProviderError` carrying them and never `HTTP 0`; the keyed-error test runs both.
- Finding 3: the fake fails `make_context` with the `cache_type` message and fails a prompt decode: each throws `ProviderError`, and a machine-mode turn over it ends in `error` with the session alive; after a failed decode the next turn decodes its prompt from position 0.
- Finding 4: a 200 with `promptFeedback.blockReason: "SAFETY"` and no candidates, streamed and not, throws `ProviderError` naming `SAFETY`; no empty assistant message reaches history.
- Finding 5: an Anthropic stream with no `message_stop` and an OpenAI stream with no `response.completed` each throw `ProviderError`; the same streams with their terminal events still answer.

**Acceptance criteria:**
- [ ] The probe, run on `apogee-dev`'s build in a temp `APOGEE_HOME`: turn 1 ends in `{"type":"error",...}` naming `request failed: Couldn't connect to server`, turn 2 is served, the process exits 0; `apogee-dev complete` on the same entry exits 2 with an `error` event.
- [ ] `serve` answers a transport failure with 502 `backend_error`, streamed and not.
- [ ] An OpenAI mid-stream failure says the vendor's code and message; no surface ever says `HTTP 0` for it.
- [ ] A llama.cpp context or decode failure fails only its turn, in every mode; the next turn works from a clean cache.
- [ ] A Gemini blocked prompt says it was blocked and why; no empty answer is saved or served as `stop`.
- [ ] A stream cut before its terminal event is a failed turn, never a saved answer with `finish_reason: stop`.
- [ ] The full suite is green.
