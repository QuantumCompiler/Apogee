# A deleted chat stays deleted and a private chat leaves nothing, on every close path

**What / why.** Two of the CLI's promises about the session record are false on paths 52d, 55a and 55b never covered. **A deleted chat stays deleted** (55b, [MILESTONES.md](../../assistant/MILESTONES.md#milestone-ar--the-audits-cli-findings):10684: "Nothing more is saved (transcript, recall summary, model state, auto-capture), and the session says so once"). **A private chat writes nothing** (52d, MILESTONES.md:9284, 9298: its attachment index "removed with the run", "Nothing lands under the data directory"; 55a, MILESTONES.md:10638: "A private terminal session keeps no line history"). The second CLI/GUI bug sweep (2026-10-31) found both broken. A chat deleted while its session runs is still archived into knowledge, written back into recall and reported done. A private chat's attachment text, its id and its typed lines outlive it. Two smaller record faults of the same seam come with them: a cancelled driven turn throws away the chat's new title, and `/title` says "renamed" when it was not. The macOS app's Delete, Stop and private sessions all ride these paths, and the person sees none of it. Each finding below was reproduced by a probe in a sandboxed `APOGEE_HOME` on the mock backend; lines are as read at HEAD (`b26550bb`, 2026-10-31).

1. **A chat deleted while its session runs, then closed with no new turn, is captured, state-saved and reported "saved".** Regression of 55b ("A running session never overwrites an outside rename or delete"). `logger::save` is the only place `session.deleted` is set (`data/logger/session.cpp:569-575`), and the close calls it only when the session changed: `save_if_changed` (`presentation/cli/chat_session.cpp:1452-1457`) skips it for a resumed chat left as it was. So the REPL's close (`chat_session.cpp:2722-2755`) runs on with the flag still false: `recall.finish` (2729), `save_state` (2732, the backend's saved model state), auto-capture (2741-2743), and at a terminal `" saved " + session.chat_id` (2746). The driven close (1814-1822) does the same, and its `say_deleted` (1817) has nothing to say. **Scenario:** resume chat X (`chat --resume X`, or open it in the shell), delete it from another terminal or from the shell's Chats view `x`, which does not guard the shell's own open chat (`presentation/cli/tui_workbench.cpp:134`), then `/exit` with `knowledge.auto_capture` on. The deleted conversation is distilled into a knowledge record, its raw transcript is archived under `knowledge/raw/`, a llama backend's state for X is written, and the session says `saved X`. **Probe** (mock chat backend, mock clerk as utility, `auto_capture: true`): resumed chat `20261031-201806-2f51`, `chats delete` -> `deleted 20261031-201806-2f51`, then `/exit`. stderr: `[apogee] captured kr-20261031T201808Z-393a45 [shipped] -- Zebra deleted chat intent.`. `grep -rl 'first q'` (the deleted chat's own question) found `home/knowledge/raw/kr-20261031T201808Z-393a45.md`; the session file stayed gone. The same case in machine mode emitted only `session`, with no deleted notice.

2. **A chat deleted during its session's exit summary is written back into the recall index and recalled into later chats.** Regression of 55b ("a chat deleted meanwhile is skipped"; "Nothing more is saved (… recall summary …)"). `summarise_for_recall` (`presentation/cli/chat_recall.cpp:145-185`) calls the model (`agentloop::summarise_chat`, 154-155) and then `index.put` (180) without checking the chat file still exists. During that call `chats delete` or the shell's `x` can run (`delete_chat`, `presentation/cli/chat_history.cpp:665-689`, gated only by `task_holds_chat`), and its `forget_recall` (682) removes the summary that `put` then writes back. The same stale flag covers what follows the summary: `save_state` on both the REPL and the driven close, and auto-capture on the REPL's. **Scenario:** a driven or REPL chat with two or more turns and recall on. Close it, and while the exit summary is being written run `apogee chats delete <id>`. The recall index then holds the deleted chat's summary, and the next chat's turn recalls it: a `memory` event names the deleted id and its summary is injected into the new conversation. **Probe** (mock chat, a fake slow `claude-cli` utility that sleeps 3 s): `child alive at delete: True`; delete -> `deleted 20261031-201512-b969`. Then `chats recall --output-format json` -> `[{'chat': '20261031-201512-b969', 'name': 'A slow but fine summary of the talk', 'summary': ..., 'updated': ''}]`. A new chat's memory event: `{"chats":1,...,"sessions":[{"id":"20261031-201512-b969",...}],"type":"memory"}`.

3. **`chats compact` exits 0 for a chat deleted mid-compaction when the chat has an inlined or mapped attachment.** Regression of 55b ("`chats compact` … refuses a chat deleted meanwhile"). The refusal at `chat_history.cpp:647-649` asks whether `logger::save` returned `Saved::Deleted`. But with an attachment `inline_at` or `map_at`, `ChatAttachments::after_compaction` (`presentation/cli/chat_attachments.cpp:1038-1066`) saves first (1063-1065 -> `save()`, 1068-1072). That save finds the file gone, sets `session.deleted` and throws the `Deleted` result away. The verb's own save then sees `unwritten()` and returns `Saved::Unwritten` (`session.cpp:560-565`), so the refusal is skipped. **Scenario:** a chat with a small attachment inlined into its first message (a backend with a known context size). Run `apogee chats compact <id> --yes` (or the shell's Chats view `c`) with a slow utility model, and `chats delete <id>` during the summary. The verb exits 0 and reports the compaction of a chat that no longer exists. **Probe:** the control without an attachment -> `compact rc 1 ... apogee chats: 20261031-201449-5a07 was deleted while it was compacted -- it stays deleted`. The same flow with an inlined `note.txt` (`inline_at 0`) -> `compact rc 0 out: compacted 20261031-201452-3210: 4 messages into 2, by slow / compaction folded the messages the attachments rode...`, `session file exists: False`.

4. **A private chat's attachment index, holding the attachment's text, is left in the temporary directory when the process is ended by a signal.** Regression of 52d/55a ("removed with the run", MILESTONES.md:9298). `PrivateFolder` removes `apogee-private-<n>` only in its destructor (`chat_session.cpp:227-232`). No SIGTERM or SIGHUP handler is installed for a chat session. The typeahead guard's handler (`infrastructure/platform/platform.cpp:405`, 435-457) restores the terminal and re-raises the signal on its previous action, so the process still ends without unwinding. The folder and its `index.db` stay, the attachment's chunks in plain text. The ways to hit it: the macOS app's `MachineSession.stop` terminating a child still running after its 5 s grace (`lib/src/darwin/source/business/session/MachineSession.swift:202-212`), or on a protocol-version refusal (107); `kill`; closing the terminal window (SIGHUP). **Scenario:** `chat --private`, driven or at a terminal: attach a file, run one turn, then the child gets SIGTERM or SIGHUP (or SIGINT while idle at a terminal). The text stays in `$TMPDIR/apogee-private-*/index.db` until the OS sweeps its temp directory. **Probe** (`TMPDIR` in the scratchpad): clean close -> `left: []`. SIGTERM -> `signal 15 rc -15 left: [.../tmp/apogee-private-1570928751]`, and grep finds `zebra private attachment text` in its `index.db`. SIGHUP -> rc -1, the folder left. SIGINT -> rc -2, a second folder left, the same grep hit. An idle driven child ignored a single SIGINT, so the driven SIGINT path is not shown to leak. A SIGKILL (the app's escalation 2 s after SIGTERM) can be covered by no handler. `machine-mode.md` says of a private chat: its attachments are "indexed in a folder of the run's own in the system's temporary directory, removed as the run ends" ([machine-mode.md](../../reference/machine-mode.md#a-private-chat-chat---private):701-703).

5. **A cancelled driven turn erases the chat's freshly settled auto-title.** Machine mode only (the GUI's loop). The pre-turn snapshot `before` (`chat_session.cpp:1711`) is taken before `title.settle(session)` (1726), which records and saves the title asked after the previous turn (`BackgroundTitle::settle`, 536-545). Both cancel paths, a chat turn (1784-1788) and a `/play` turn (1745-1749), go through `cancelled_result`, which restores `session = before` and saves it (1717-1718), overwriting the title just saved. `BackgroundTitle::asked_` is already true (520) and the future is consumed, so the chat keeps its bare id for the rest of the process. This contradicts the 2026-09-25 entry "The wait after every chat answer" (MILESTONES.md:3510: `settle()` "waits for the title and records it"). **Scenario:** a GUI-driven new chat. Turn 1 answers and the title is asked in the background; the person sends turn 2 and presses Stop mid-stream (`cancel`). Mid-turn, the file and `chats list` show the title; after the cancel the chat is named by its id again. **Probe** (mock: an answer, `Cool Title Here` for the title call, a slow third turn): `mid-turn file title: 'Cool Title Here'`, `end cancelled`, `after cancel file title: None turns 1`. `chats list` name: `20261031-201221-64e6`.

6. **REPL `/title` after an outside rename prints "renamed", and the name typed is discarded.** The handler (`chat_session.cpp:2552-2556`) ignores what `logger::save` did. `save` takes the file's `custom_name` over the session's whenever it differs from the name this process last left there (`session.cpp:588-595`), so an outside `chats title` made since the last save wins over the `/title` just typed. That the outside name wins is 55b's recorded default ("An outside rename wins, even over one the session made meanwhile", MILESTONES.md:10683). The bug is the success message. **Scenario:** a chat running at a terminal, its title settled; another terminal or the app runs `chats title <id> 'Outside Name'`; the person types `/title Mine Later`. **Probe** (REPL on a pipe, two turns, the outside rename, then `/title`): stderr `[apogee] renamed`; `chats list`: `{"name":"Outside Name",...}`. The same handler says "renamed" over a chat deleted meanwhile, where nothing was written at all (read at HEAD).

7. **The shell keeps a private conversation's typed lines in its Up history for the next, written conversation.** Regression of 55a ("A private terminal session keeps no line history"; its check: "a later session never recalls it"). The shell has one `SessionView` for its whole run. Its line history (`State::history`, `presentation/tui/session_view.cpp:160`, appended at 775) lives in memory and is never reset: `begin_conversation` (270-284) and `SessionView::begin_session` (1047-1055) leave it alone, and nothing in `presentation/tui` knows a conversation is private. Only the shell's launched opening carries `apogee tui --private`'s flags (`presentation/cli/tui_session.cpp:423-427`); every later conversation opens through `shell_session_flags` (429-430) and is written. 55a fixed the REPL's `line_reader` and `chat_history` file, not the shell. **Scenario:** `apogee tui --private`, type `our confidential merger closes Friday`, `/exit`, open a saved or new chat from the Chats view, press Up: the private line is recalled into a chat that is saved, and sent, lands in its transcript. Nothing reaches disk on its own, and the lines die with the process. **Evidence:** read from the code (the three sites above).

8. **A private chat writes its id, time and backend to the data directory's log.** Contradicts 52d ("Nothing lands under the data directory", MILESTONES.md:9298; `machine-mode.md`: writes "**nothing**"). Every session logs `"session " + session.chat_id + " on backend " + model` under `chat` or `execute` (`chat_session.cpp:1133-1134`), private or not. That `chat_id` is the one a private `session` event deliberately leaves out (machine-mode.md:105-106). A driver's `hello` is logged the same way at 1610-1611 (read at HEAD: the macOS app sends one, so its private sessions log that line too). **Scenario:** `apogee chat --private` (driven or REPL) on a fresh home: afterwards `home/logs/apogee-2026-10-31.log` exists, a record that a private chat happened, when, and on which model. **Probe:** a file sweep before and after a private machine chat (turns, attach, compact) -> the only new file was `home/logs/apogee-2026-10-31.log`, containing `2026-10-31T20:10:14Z INFO [chat] session 20261031-201014-0b09 on backend mock`. The private REPL run showed the same. No conversation text leaked: grep for the secret found nothing.

What already works: a deleted chat that takes a new turn is caught by that turn's save and said once, on both doors; `chats compact` on a chat with no attachment refuses one deleted meanwhile (the probe's control); a private chat closed cleanly leaves no folder (`left: []`); a private chat's log holds no conversation text.

**Core constraint(s).**
- **A deleted chat stays deleted** (55b): after the file is found gone, nothing more is saved (transcript, recall summary, model state, auto-capture) and the session says so once, on every door and every close: REPL, driven, the shell, `chats compact`.
- **A private chat writes nothing** (52d, 55a): no transcript, no recall, no model state, no capture, no title, no line history, no log line naming it, and its temporary folder gone however the run ends.
- **One session writer** (55b): `logger::save` stays the one place the record is re-read and written; existence is learned through it or a helper beside it in `data/logger`, never by a second reader in Presentation.
- **A change propagates to every mode** (ADR 0002) and **the shell is a mode** (ADR 0010): the REPL, machine mode and the shell close through the same checks; the shell's history follows the REPL's rule.
- **The additive protocol** (ADR 0006): the deleted `notice` and the `result` events keep their shape; only when they are said changes.
- **Development runs on the dev channel**: probes and tests run hermetic in a temporary `APOGEE_HOME`; any live pass or try-it step names `apogee-dev`, never the release `apogee` or `~/.apogee`.

**Seam + files.**
- `data/logger/session.cpp/.h` — a helper beside `save` that re-reads only whether the file this process filed still exists and sets `session.deleted` (name settled at build), so a close that writes nothing still learns of a delete.
- `presentation/cli/chat_session.cpp` — both closes (1814-1822, 2719-2755) learn of a delete before the exit summary and again after it, before `save_state` and capture; the driven turn's snapshot taken after `title.settle` (1711, 1726); `/title` (2552-2556) says what `save` did; the private session's log lines (1133, 1610) not written; the private folder removed on a signal's end and swept when orphaned (`PrivateFolder`, 210-240, its destructor 227-232).
- `presentation/cli/chat_recall.cpp` — `summarise_for_recall` (145-185): no `index.put` for a chat whose file is gone, and the entry removed again if the file went during the `put`.
- `presentation/cli/chat_history.cpp` — `compact_saved_chat` (647-649) refuses on `session.deleted`, whatever save reported it.
- `presentation/cli/interrupt.cpp/.h` (or a sibling scope in `presentation/cli`) — SIGTERM and SIGHUP during a chat session end it as a closed input does; `infrastructure/platform/` for the Windows console's close event, if the build takes it (below).
- `presentation/tui/session_view.cpp/.h`, `presentation/cli/tui_session.cpp` — `begin_session` told whether the conversation is private; a private one's lines kept apart and dropped at its end.
- Tests, mirroring the source tree (ADR 0004): `tests/presentation/cli/chat_test.cpp` and `chat_session_test.cpp` (the closes, the cancelled title, `/title`, the private log), `tests/presentation/cli/chat_history_test.cpp` (the compaction), `tests/data/logger/session_test.cpp` (the helper), `tests/presentation/tui/session_view_test.cpp` and `tests/presentation/cli/tui_session_test.cpp` (the shell's history), `tests/scripts/sh/machine_mode_e2e.sh` (`cli.machine_mode`: the private phase under SIGTERM and SIGHUP, the log sweep, the deleted close on the real binary).
- Docs: `reference/machine-mode.md` (the between-turns rule covers a close with no turn and the exit summary; a private chat's folder removed on a signal and swept when a run was killed).

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item, because the eight findings share one seam and one promise. Each is the session record (`logger::save` and the closes around it in `chat_session.cpp`, recall, compaction, the shell's session view) saying or keeping something the person deleted, kept private or did not ask for. Findings 1-3 are the same stale `deleted` flag on three paths, 4, 7 and 8 the same `--private` audit on three surfaces 55a did not reach, and 5 and 6 the record's own title faults in the same functions.
- 2026-10-31: The outside rename winning (finding 6) stays as 55b decided. This item fixes only what `/title` says.

**Open calls:**
- [default: the close learns of a delete through the new `data/logger` helper: called before the exit summary (so `recall.finish`, `save_state`, capture and the exit line all see it) and again right after it (finding 2's window), on both doors. The delete notice is said once, as 55b's `say_deleted` already guarantees.]
- [default: `summarise_for_recall` checks the file before `index.put`, and after it removes the entry again if the file is gone, so a delete landing between the check and the write is undone.]
- [default: `chats compact` refuses on `session.deleted` after its save, rather than on the save's return alone; `after_compaction` keeps its own save.]
- [default: a chat session ends on SIGTERM or SIGHUP the way a closed input ends it: an async-signal-safe handler cancels the turn and wakes the reader, and the destructors run, the private folder's included. SIGINT outside a turn at a terminal ends through the same path. The private folder is named by the owning process id, and a private chat's opening removes any `apogee-private-<pid>` folder whose owner is gone, covering SIGKILL and power loss. The Windows console's close event joins through `infrastructure/platform/` if the build finds the seam clean; otherwise the sweep covers Windows. An in-memory index (SQLite `:memory:`) would leave nothing even under SIGKILL: the build takes it in place of the sweep if the private index is opened by one connection only.]
- [default: the driven turn's snapshot is taken after `title.settle`, so a cancel rolls back to a state that holds the title.]
- [default: when an outside name won, `/title` says so: `not renamed -- <id> was renamed outside to 'Outside Name' meanwhile; /title again to replace it` (wording settled at build). A second `/title` then wins, since `save` has recorded the outside name as the one filed. Over a deleted chat, `/title` says the deleted line instead of "renamed". Making `/title` win outright would revise 55b's recorded default and is not taken.]
- [default: the shell gives a private conversation its own Up history, starting empty and dropped when it ends; the shell's earlier lines come back for the next written conversation. This is 55a's rule for the REPL.]
- [default: a private chat writes no log line of its own: neither the `session` line nor a driver's `hello`. A turn failure's line (`chat_turn.cpp:317`, the provider's error text) is kept: it is the operational record a failing backend needs and names neither the chat nor its words. The build checks that it carries no id.]
- [default: the shell's Chats view `x` gains no guard on the shell's own open chat: deleting it is a legitimate act, and the session honouring it is the fix.]
- (consumed decision) An outside rename wins over the session's (55b, recorded 2026-10-25).
- (consumed decision) A private chat's attachments are indexed in the system's temporary directory (52d, recorded 2026-10-20).

**Guardrail(s).** Each finding's probe pinned as a hermetic test, temporary `APOGEE_HOME`, the mock backend, fakes, and failing on the unmodified code:
- A resumed chat deleted outside and closed with no turn (REPL and driven, `auto_capture` on, a fake clerk): no `knowledge/raw/` record, no knowledge record, no saved model state (a fake `save_conversation` counts zero), the deleted line at the terminal in place of `saved <id>`, and the driven close's deleted `notice`.
- A chat deleted during its exit summary (the slow `claude-cli` utility fake): `chats recall` lacks it, a new chat's `memory` event never names it, and no model state or capture follows.
- `chats compact --yes` over an inlined and a mapped attachment, deleted during the summary: exit 1 with `was deleted while it was compacted -- it stays deleted`; the no-attachment control unchanged.
- A private driven chat with an attachment, sent SIGTERM and SIGHUP while idle (POSIX, `cli.machine_mode` on the real binary, `TMPDIR` in the work dir): no `apogee-private-*` left. A planted folder whose owner process is gone is removed by the next private chat's opening.
- A driven turn cancelled after the title settled: the file and `chats list` keep the title; a `/play` cancel too.
- `/title` after an outside `chats title`: the not-renamed line, `chats list` showing the outside name, and a second `/title` winning.
- The shell: a private conversation's line never recalled by Up in the next conversation, a written conversation's line still recalled (`session_view_test`, `tui_session_test`).
- A private chat (REPL and driven, with a `hello`): the file sweep before and after finds nothing new under the home, `logs/` included.

**Acceptance criteria:**
- [ ] A chat deleted while its session runs is never captured, archived, summarised, state-saved or reported "saved", whether the session closes with a new turn, with none, or while its exit summary is written; the driven close says the deleted `notice` once.
- [ ] `chats recall` and every later chat's `memory` event never name a deleted chat.
- [ ] `chats compact` exits 1 with the deleted refusal for a chat deleted meanwhile, attachments or not.
- [ ] A private chat ended by SIGTERM or SIGHUP leaves no `apogee-private-*` folder, and one killed outright leaves none past the next private chat's opening.
- [ ] Stop on a driven turn keeps the chat's title.
- [ ] `/title` never says "renamed" when the name it was given is not the chat's name.
- [ ] Up in the shell never recalls a private conversation's line into another conversation.
- [ ] A private chat leaves the data directory byte-identical, `logs/` included.
- [ ] The full suite is green; MinGW, clang 22 and AppleClang find nothing in the touched code.
