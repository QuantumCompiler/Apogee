# Pipelines, cycle passes and promotions run one at a time

**What / why.** Training trusts its record: the pipeline manifest says which stage passed, the cycle's lock says whether a pass is running, and the version ledger says which weights a backend has served. The second CLI/GUI bug sweep (2026-10-31) found five places where two processes, or one dead one, make that record wrong. A pipeline still training in one process can be resumed in another. Two runs started in the same second share one directory. A dead pass's lock reads as a live pass everywhere. launchd's ordinary stop leaves that dead lock behind. Two promotions into one backend can drop a version from the ledger. Each is quiet: every command involved exits 0 or names a cause that is not true. Paths below are under `lib/src/cli/source/` and were re-read at HEAD on 2026-10-31.

1. **`train pipeline resume` runs a pipeline that another process is still running.** Nothing locks the pipeline run/resume path. `resume_check` (`business/training/pipeline.cpp:520-531`) refuses only a complete manifest and a changed stage count, and `resume_pipeline` (`:533-551`) then runs the `StageRunner` over the same manifest. `print_pipeline_table` (`presentation/cli/train.cpp:1430-1432`) prints the resume hint for any manifest that is not complete, a running one included. Scenario: a pass, or a `train pipeline run` from the app, is training stage 1. `train pipeline status <id>` shows the resume hint, and the user runs it. The second process retrains the same stage in the same run directory and rewrites the manifest to `complete` while the first is still training. When the first finishes, it overwrites the manifest and adapter again, so the record no longer matches the weights. Probe pC.sh: a cycle pass was held on its stream FIFO, with `cycle.lock` held and `train status` reporting `running: ['cycle-20261031-201201-s0']`. `train pipeline status` printed `base training ... Resume from stage 1: apogee train pipeline resume cycle-20261031-201201`. `train pipeline resume cycle-20261031-201201` exited 0 with `base passed 100% (1/1)`, and the manifest read `complete [('passed', 'starter.jsonl')]` while the original pass was still alive. The overlap is established from the code: no lock exists on that path. It was not reproduced as a live race. A crashed run's `running` manifest must stay resumable, so the fix has to tell a live owner from a dead one. The same read leaves `active_pipeline` in `train status` JSON (`presentation/operations/training_reads.cpp:47-52`, from the manifest's status alone) and `Pipeline: <id> RUNNING` in its text naming a crashed pipeline as running indefinitely.
2. **Two pipeline runs started in the same second get the same id and share one directory.** `new_run_id` (`business/training/manifest.cpp:139-148`) checks whether `<dir>/<prefix>YYYYmmdd-HHMMSS` exists and reserves nothing. `train pipeline run` picks its id at `presentation/cli/train.cpp:2895-2899`. The directory is created only at the first `write_pipeline_manifest` (`business/training/pipeline.cpp:445`, `create_directories`, which does not fail on an existing directory), and the manifest is written by atomic rename, so the last writer wins. Two runs then share `pipelines/<id>/manifest.json` and the stage runs `runs/<id>-s<N>`. Both exit 0, and one run's record is lost or mixed with the other's. Scenario: `apogee train pipeline run --pipeline nightly` is started twice at once, for example by a script, or by the app while a cron job fires. Both print `[pipeline] nightly as pipe-20261031-201450`, both exit 0, and one directory holds whichever process wrote last, possibly with a stage adapter from the other run. Probe pI.sh: both background runs printed `[pipeline] nightly as pipe-20261031-201450: 1 stage(s)`, both gave `exit=0`, and `ls training/pipelines` returned the single entry `pipe-20261031-201450`. The same race affects `train run` (`train.cpp:2232`, `runs/<id>`, created at `manifest.cpp:106`) and `train regime run` (`train.cpp:3372`). The cycle's own id (`business/training/cycle.cpp:605`) is picked under the cycle lock, so cycle passes cannot collide with each other.
3. **A cycle lock left by a dead process reads as "running now" everywhere.** `cycle_lock_held` (`business/training/cycle.cpp:226-229`) checks only that `cycle.lock` exists. It never asks `PidLock::holder` (`infrastructure/platform/pid_lock.h:54-55`, whose `Holder` says whether the process is running) whether the holder is alive. So after a pass is killed (kill -9, crash or power loss):
   - `train cycle status` shows `running now` (`presentation/cli/train.cpp:1559`, fed at `:3701`), and its JSON gives `active: true` (`presentation/operations/training_reads.cpp:191`);
   - `train status` shows `Cycle: running now` (`train.cpp:1839`), and its JSON gives `cycle_active: true` (`training_reads.cpp:78`);
   - `check` stays `ok` and appends `a cycle is running now` (`presentation/cli/check.cpp:2739`);
   - `train cycle halt` promises `the pass running now finishes, and keeps the halt` (`train.cpp:3732-3733`) when no pass exists.

   The HTTP `GET /v1/admin/training/cycle` reads the same `active`. Probe pC2.sh: `cycle.lock` was written with a dead PID (99285) after one skip pass. The results were `state: running now`; `active: True`; `Cycle: running now; backend nightly-model`; `cycle_active: True`; `ok   cycle history  1 run(s) ... a cycle is running now`. Probe pC.sh, after kill -9: `train cycle halt` printed `the pass running now finishes, and keeps the halt` with no process alive. Refusing a dead holder's lock in `cycle run` is recorded design (`business/training/cycle.h:146-148`; MILESTONES 27h). Reporting that dead holder as a running pass is not. In the app, `cycleHeld` (`lib/src/darwin/source/presentation/training/ViewModels/TrainingViewModel.swift:780-782`) is true from those flags, so `canRunCycle` (`:792`) disables "Run one pass…" (`TrainingScreen.swift:32-33`), and `CycleView` says `a pass is running` (`CycleView.swift:65`). The CLI's "If none is, remove the file" is never shown there. The app's part belongs to the GUI sibling, [6i](../../../gui/backlog/v0.2.1/training-screens-follow-the-cli.md); this item gives it a true field to read.
4. **SIGTERM during a pass leaves the cycle locked until the lock file is removed by hand.** launchd sends SIGTERM when a job is unloaded or the user logs out, and launchd is the documented scheduler ([training.md](../../reference/training.md) → the cycle, "Schedule it with launchd"). `InterruptScope` (`presentation/cli/interrupt.cpp:24-32`) installs a handler for SIGINT only, so SIGTERM kills `train cycle run` without the cancel and unwind path. An ordinary scheduler stop becomes the crashed-cycle case: the lock stays, the manifest stays `running`, and the next pass is refused. Not taking over a dead holder's lock is the recorded rule (`cycle.h:146-148`; MILESTONES 27h, and 48d's record that taking over a dead holder's lock is the task runner's choice, not the cycle's; `tests/business/training/cycle_test.cpp:214`), so needing to remove the file is not the bug. Losing the unwind on a routine stop is the bug, and so is the status then saying a pass is running (entry 3). Scenario: the launchd job is unloaded, or the Mac logs out, while a nightly pass trains. The process exits 143. Every following night `apogee train cycle run` exits 1 with `another cycle is already running (lock: …)`, and `train status` keeps saying `Cycle: running now` and `Pipeline: cycle-<id> RUNNING`. Probe pJ.sh: `kill -TERM` on a held pass gave `pass exit=143`. `training/cycle/` still held `cycle.lock`, and the manifest read `running`. `train status` printed `Cycle: running now ...` and `Pipeline: cycle-20261031-201531 RUNNING (0/1 stage(s) passed)`. The next `train cycle run` printed `another cycle is already running ... If none is, remove the file and run again` with `exit=1`. The same SIGINT-only scope covers all 22 `InterruptScope` sites (`train run`, `train promote`, `models pull`, …; `grep -rn 'const InterruptScope' presentation/`), so a SIGTERM to any of them skips its cleanup.
5. **Concurrent promotions into one backend can lose a version from the ledger.** `promote_run` loads the ledger (`presentation/cli/train.cpp:720-723`) and plans `version = highest + 1` (`train.cpp:747-750`; `next_version`, `business/training/promote.cpp:341-347`). It then fuses, converts, commits and edits the config, and only after all that saves the ledger (`train.cpp:861`). `save_ledger` (`business/training/store.cpp:147-159`) is a lock-free atomic overwrite. The cycle's promote callback (`train.cpp:3542-3563`) and a manual `train promote` (`train.cpp:2582`) share no lock over that window. `CycleLock` keeps only two cycles apart, and `config_edit`'s `FileLock` (`data/contracts/config_edit.cpp:3420-3432`) covers only the config edit. Two overlapping promotions into one backend both build vN+1. The second `save_ledger` drops the first's entry, and the config points at whichever process registered last. The dropped version's fused GGUF/MLX weights are committed under their own weight id (`train.cpp:740-743`), so they are not overwritten. They stay in the model store untracked by the ledger, where rollback and retention never see them. Scenario: a nightly pass passes its gate and starts promoting into `nightly-model` at about the time the user runs `apogee train promote <run> --as nightly-model`. Both read a ledger ending at v3, both build v4, and the ledger ends with one v4 entry. Evidence is a code read only, not probed: `load_ledger` at `train.cpp:722` and `save_ledger` at `train.cpp:861` sit at either end of the fuse/convert, and a grep finds no `FileLock` or `PidLock` in promote or store.

What already works: a second `train cycle run` is refused while a pass runs (the `PidLock` is created exclusively, so two schedulers cannot both win). Ctrl-C unwinds a pass or a pipeline and leaves it `aborted` and resumable. A crashed `running` manifest is resumable today. Run listings skip a directory that has no manifest (`store.cpp:262-265`, `:288-291`). The fused weights of two promotions never overwrite each other.

**Core constraint(s).**
- **One process owns a run.** A pipeline (a cycle pass's included) has exactly one live holder. A run id is reserved before anything is written under it. A crashed run stays resumable without anyone deleting a file. This item's own rule.
- **The cycle's recorded lock rule stands.** A dead holder's `cycle.lock` is still refused by `cycle run`, never taken over (`cycle.h:146-148`, MILESTONES 27h). The reads tell the truth about it and name the way out. They do not change the rule.
- **One change, every mode** ([ADR 0002](../../adrs/mode-parity.md)): the liveness answer is computed once, in Business, and read by the terminal, `check`, `--output-format json`, HTTP (`/v1/admin/training/cycle`) and so the macOS app.
- **Older versions keep working** ([ADR 0006](../../adrs/backwards-compatibility.md)): `active` and `cycle_active` keep their names and types; they only stop being true for a dead holder. Anything new is an added field.
- **Four layers** ([ADR 0001](../../adrs/layer-enforcement.md)): the locks are the platform seam's (`PidLock`, `FileLock`); training's Business modules take them; Presentation only reads.
- **Development runs on the dev channel** ([CLAUDE.md](../../assistant/CLAUDE.md#development-runs-on-the-dev-channel)): the probes re-run on `apogee-dev` against a scratch `APOGEE_HOME`, never `apogee` or `~/.apogee`.

**Seam + files.** Source under `lib/src/cli/source/`, tests under `lib/src/cli/tests/` mirroring it ([ADR 0004](../../adrs/tests-mirror-architecture.md)).
- `business/training/manifest.cpp/.h`: `new_run_id` reserves the id by creating its directory exclusively (`std::filesystem::create_directory` returning false means try the next suffix), and returns an error when it cannot. Callers: `presentation/cli/train.cpp:2232`, `:2897`, `:3372`, and `business/training/cycle.cpp:605`.
- `business/training/pipeline.cpp/.h`: a per-pipeline `PidLock` (`pipelines/<id>/pipeline.lock`, label the pipeline id, `take_stale` so a crashed run resumes) held by `run_pipeline` and `resume_pipeline` for the whole run. `resume_check` refuses while a live holder has it, naming the process. A `pipeline_holder(dir)` read returns the live holder or none.
- `business/training/cycle.cpp/.h`: a pass takes its pipeline's lock beside `cycle.lock`. `cycle_lock_held` becomes a three-way read (`idle` / `running` (pid) / `stale` (pid, path)) over `PidLock::holder`.
- `business/training/store.cpp/.h` and `presentation/cli/train.cpp` (`promote_run`): one promotion per backend, a `FileLock` on `versions/<backend>.promote.lock` held from `load_ledger` to `save_ledger`.
- `presentation/cli/interrupt.cpp/.h`: `InterruptScope` arms SIGTERM beside SIGINT, both through the one cancel path.
- `presentation/cli/train.cpp`: `print_pipeline_table` (no resume hint for a live pipeline, `running now (process <pid>)` in its place), `print_cycle_history`, `train status`'s Cycle and Pipeline lines, `cycle halt`'s notice; `presentation/cli/check.cpp:2739`'s cycle row; `presentation/operations/training_reads.cpp:47-52`, `:78`, `:191`.
- Tests: `tests/business/training/manifest_test.cpp`, `pipeline_test.cpp`, `cycle_test.cpp`, `promote_test.cpp`, `store_test.cpp`; `tests/presentation/cli/check_test.cpp`; the subprocess cases in `tests/scripts/sh/train_e2e.sh`.
- Docs: [training.md](../../reference/training.md) (pipelines: one live holder, resume refused while it runs; the cycle: SIGTERM, a stale lock's reads; promotion: one per backend).

**Reference.** `PidLock` and its `take_stale` takeover (MILESTONES 27h; `tasks::TaskLock` takes a dead holder's lock, the cycle refuses it). `CycleLock`'s exclusive create (Milestone Z) is the precedent for reserving a name with `create_exclusive_file`. `FileLock` (55f) is the precedent for a lock the system releases when its holder dies, used for the config edit. `serve`'s SIGTERM handling (`presentation/httpserver/serve.cpp:190`) shows a command treating SIGTERM as a stop. Sibling items: [57h](training-resume-and-reads-truthful.md) owns what a resume continues (a cycle pass's data and gate, the first unpassed stage) and unreadable training files. [6i](../../../gui/backlog/v0.2.1/training-screens-follow-the-cli.md) owns the Training screens' part: the stale lock made recoverable, and Resume offered only when no live holder has the pipeline (`TrainingViewModel.canResume`, `:694-696`, checks only this window's own run today).

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item because the five findings share one cause: training state that two processes, or a dead one, can both claim, with no lock or liveness read where it matters. The fixes share one seam (the platform locks, read once in Business), and the reads in entries 1, 3 and 4 are one liveness answer.
- 2026-10-31: The sweep's panel set entry 4 at low severity, since manual removal of a dead lock is the recorded rule. The bugs are the lost unwind on SIGTERM and the false "running now". The rule itself is unchanged.

**Open calls:**
- [default: the pipeline lock is a `PidLock` with `take_stale`, not a `FileLock`. A crashed pipeline then resumes with no file to delete, and `PidLock::holder` lets `status` name the live process without taking the lock. Cycle passes hold it too.]
- [default: a dead holder's `cycle.lock` reads as `stale`. Text says `stopped -- cycle.lock is left by process <pid>, which is not running; remove <path> to run again`. `active` and `cycle_active` are false, and an added `stale_lock: "<path>"` field carries the path. `check`'s cycle row becomes a warning with that remedy. `cycle halt` says nothing about a running pass when there is none.]
- [default: no new verb to clear a stale lock. The reads name the file and the remedy, the refusal's own words. A `train cycle unlock` is a later item if wanted.]
- [default: SIGTERM joins SIGINT in `InterruptScope` at all 22 sites. The first SIGTERM cancels, as the first Ctrl-C does, so the child is terminated and the run recorded `aborted`/cancelled, its locks released. A command cancelled by SIGTERM exits 143, the TUI's convention (SIGINT keeps 130). Unwinding has launchd's grace period before SIGKILL; a SIGKILL stays the crashed case.]
- [default: a second promotion into the same backend waits for the first, with a notice (`[promote] waiting for another promotion into <backend>`). The wait is bounded generously (settled at build), then refuses naming it. The alternative, refusing at once, is rejected: the cycle counts a failed promotion toward its circuit breaker (`cycle.cpp:699-701`), so a user's manual promote would halt a k=1 loop.]
- [default: a run id that cannot be reserved (the directory cannot be made) fails the command with the path and the reason before training starts. An empty reserved directory left by a command that fails before its first manifest is skipped by the listings, as today.]
- (consumed decision) What a resumed cycle pipeline trains on and gates against belongs to [57h](training-resume-and-reads-truthful.md). The app's Run/Resume buttons and the stale-lock recovery on screen belong to [6i](../../../gui/backlog/v0.2.1/training-screens-follow-the-cli.md).

**Guardrail(s).** Hermetic, under a temp `APOGEE_HOME`, the mock trainer and backend, no network:
- `manifest_test`: two reservations of one second's id return two ids and two directories. A pre-existing directory moves to the next suffix. An uncreatable directory is an error.
- `pipeline_test`: a resume while a live holder (this test process's own lock, from a second acquire) holds the pipeline is refused, naming it, and leaves the manifest untouched. A resume over a lock whose PID is dead takes it and runs. `pipeline_holder` reports each.
- `cycle_test`: a `cycle.lock` naming a dead PID reads `stale` (path and pid), and a live one reads `running`. `cycle run` still refuses the stale one, and the line 214 case stays green. The reads' JSON gives `active: false` plus `stale_lock`.
- `check_test`: the stale lock's cycle row is a warning naming the file. A live lock keeps `ok … a cycle is running now`.
- `promote_test`/`store_test`: two promotions into one backend, the second started while the first holds the promote lock, end with both versions in the ledger (v4 and v5). The waiting one emits the notice.
- `train_e2e.sh`, the subprocess cases: probe pJ re-run (a held pass on a FIFO, `kill -TERM`) leaves no `cycle.lock`, a manifest not `running`, exit 143, and a next `cycle run` that is not refused. Probe pI re-run (two `pipeline run`s started together) prints two ids and leaves two pipeline directories. Probe pC re-run (a held pass, then `pipeline status` and `pipeline resume` on its pipeline) shows no resume hint, and the resume is refused non-zero.

**Acceptance criteria:**
- [ ] `train pipeline resume <id>` while another process runs that pipeline is refused, naming the process. `train pipeline status <id>` shows `running now` in place of the resume hint. A crashed pipeline still resumes with nothing deleted by hand.
- [ ] Two `train pipeline run`s (or `train run`s, or `train regime run`s) started in the same second get two ids and two directories.
- [ ] A `cycle.lock` left by a dead process is never reported as a running pass: `train cycle status`, `train status`, `check`, their JSON, HTTP and `cycle halt` all name the stale file and the remedy, and `active`/`cycle_active` are false.
- [ ] SIGTERM during a pass unwinds it: the lock is gone, the manifest is not `running`, the exit is 143, and the next scheduled `cycle run` is not refused.
- [ ] Two overlapping promotions into one backend leave both versions in the ledger. The config points at the later one, and no committed weights are left untracked.
- [ ] The full suite is green; the probes re-run on `apogee-dev` against a scratch `APOGEE_HOME` show each inverted.
