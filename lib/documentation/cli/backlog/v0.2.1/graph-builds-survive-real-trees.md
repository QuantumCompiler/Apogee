# Graph builds survive real trees, and what they store stays true

**What / why.** A graph build is the one command that turns a tree or a collection into something a turn can walk, and a person runs it over whatever they have. The second CLI/GUI bug sweep (2026-10-31) found six ways a real tree or an ordinary sequence of commands breaks the build or leaves the graph saying something false. One non-UTF-8 file fails a whole code graph. Deep nesting crashes the parser. Entity vectors that are lost are never rebuilt, though the build says a re-run will rebuild them. A relation's weight counts extraction runs, not the chunks that state it. A named graph deleted mid-build is reported as built. A NaN dedupe threshold is accepted. Paths below are under `lib/src/cli/source/` and were re-read at HEAD on 2026-10-31.

1. **One non-UTF-8 source file fails the whole code-graph build.** Regression of CLI MILESTONES 27k (`MILESTONES.md:7066`: everything the build cannot use is "**skipped and named**, never silently and never a failure"). `build_source` checks size and binary (`business/graph/code_build.cpp:230-239`) and then parses the bytes as read. `facts_to_json` serializes the file's names with a plain `out.dump()` (`business/graph/code_extract.cpp:951-962`), and nlohmann throws `type_error.316` on a byte that is not UTF-8. The call that stores the facts (`code_build.cpp:272-279`, `set_code_file_state` with `.facts = facts_to_json(*facts)`) has no `try`, so the exception leaves the build and becomes `fail_backend("code graph build failed: " ...)` (`presentation/cli/graph.cpp:826-831`). Every other dump that can meet foreign text uses `error_handler_t::replace` (`business/graph/export_html.cpp:36`, `data/backends/provider_cache.cpp:201`). Scenario: a tree holds `m.py` with the bytes `def caf\xe9_atlas():`. `apogee graph build --source <tree> --graph code` printed `apogee graph: code graph build failed: [json.exception.type_error.316] invalid UTF-8 byte at index 8: 0x5F` and exited 2. `graph report --graph code` then said `no graph built for 'code'`. Once one such file is added to a tree, every later `graph update` fails (the app's Rebuild runs it) until the file is removed, and the app's "New graph…" job fails with the same JSON exception text. Attaching the folder in chat does not end the turn: `presentation/cli/attachment_graph.cpp:119-122` catches the exception and records the attachment graph as Failed, with the `type_error.316` text as its `absent` reason, so the folder gets no graph at all.
2. **The code parser crashes on deep nesting that holds a syntax error, and a nested Rust `use` tree takes quadratic time and then crashes too.** Both run under `graph build --source` and a chat attach of a folder.
   - `contains_error` (`business/graph/code_parser.cpp:128-142`, recursive call at `:137`, called once per file at `:308`) recurses once per tree level along any branch that carries an error, with no depth limit. Its NOLINT (`:126-127`) assumes the tree's depth bounds it. The 2 MiB cap (`kMaxSourceFileBytes`, `business/graph/code_build.h:70`) does not bound depth: a 400 KB file can be 200000 levels deep. Probe: `d.py` holding `x = ` + 200000 `(` + `1 +` + 200000 `)` (400 KB). `apogee graph build --source <dir> --graph deep` exited 139 (SIGSEGV). lldb showed `EXC_BAD_ACCESS` under thousands of `contains_error` frames, frame #3 `apogee::graph::(anonymous namespace)::contains_error at code_parser.cpp:137`, repeated. The same nesting without the syntax error exited 0, and so did 50000 levels with it.
   - `expand_use_tree` (`business/graph/code_extract.cpp:345-386`) runs `collapse()` over the remaining text on every call (`:348`) and recurses once per nesting level (`:385`), so time grows with the square of the depth and stack with the depth. Probe: `lib.rs` holding `use a::` + `{b::`×n + `c` + `}`×n. n=5000 (25 KB) took 1.0 s, n=10000 3.1 s, n=20000 (100 KB) 9.1 s, and n=100000 (500 KB) was still running after 90 s. A second run measured n=10000 at 2.2 s and n=20000 at 8.7 s, and n=40000 (about 160 KB) ran 27 s and then crashed with SIGSEGV.
   - Cancellation is checked only between files (`code_build.cpp:219-222`), so neither case can be interrupted mid-file.
3. **Entity vectors lost to a failed embed, a cancel or a dedupe are never rebuilt, though the build says "re-run to embed them".** Only `graph build`'s embed phase writes an entity vector (`update_node_embedding`, `business/graph/build.cpp:421`), and it embeds only the `mutated` set (`build.cpp:384-386`). `store_extraction` adds a node to it only when `upsert.mutated` is true (`build.cpp:135-139`). `upsert_node` (`data/embedstore/graph.cpp:299-324`) and `upsert_decision_node` (`graph.cpp:361-385`) report `mutated=false` when a node's text is unchanged, and `--force` changes the plan only (`build.cpp:274`). So a node that already has a description but no vector (`dim = 0`) is never embedded again. That covers a node left behind when the phase breaks on an embed error (`build.cpp:409-419`), when a cancellation returns early (`build.cpp:296-299`, `:318-331`, `:396-398`), or when a dedupe merged a description into it and cleared its vector (`data/embedstore/graph_dedupe.cpp:265-273`). The terminal still promises the opposite: `Warning: entity embedding stopped early (...) -- affected entities stay full-text searchable; re-run to embed them.` (`presentation/cli/graph.cpp:336-339`). The re-run prints `Nothing to extract`, `mutated` is empty, and the entities stay unembedded. Even `--force` re-extracts them and still skips them. A dedupe survivor that lost its vector is left out of every later dedupe as well, because dedupe reads only `WHERE dim > 0` (`graph_dedupe.cpp:182-185`). Communities heal the same failure on their next run: `communities.cpp:297-301` embeds every `communities_without_vectors()`, a choice recorded in `MILESTONES.md:5635` (knowledge-graph-global), and `tests/business/graph/communities_test.cpp:357-367` holds it. Entities have no such sweep, and `tests/business/graph/build_test.cpp:319-334` asserts the non-healing behavior: an "already described" Atlas seeded with no vector is expected not to be embedded (`:333`, `nodes_embedded == 1 // Vault is new; Atlas existed unchanged`). `build_test.cpp:339-350` checks the failure but never a re-run. Evidence is a code read: no mock embedder can be reached from the CLI.
4. **A relation's weight (`x<N>` corroboration) grows each time a chunk is extracted again.** An inferred edge's weight counts extraction calls, not the distinct chunks that state the relation. `upsert_edge` (`data/embedstore/graph.cpp:340-359`) sets `weight = kg_edges.weight + 1` on every conflict (`:347`) and keeps no record of which chunk an edge came from, and `store_extraction` upserts every relation of every extraction (`build.cpp:150-158`). So `graph build --force`, a file extracted again after a failed chunk, a `--limit` stop or a cancel (`build.cpp:274`, `:291` on), and a re-ingest of a changed file each add the same chunk's relations again. A relation removed from a document keeps its weight too, since reconcile never recomputes it (`tests/business/graph/graph_multi_test.cpp:151-153` holds this for a dropped member). Probe (temp home, mock extractor): two chunks each state "Atlas stores readings in Vault". After three runs of `graph build notes -m extractor --force`, `graph show notes atlas` printed `-> Vault (system) x6` with 2 supporting chunks, where the true count is 2. The weight then skews `show`'s label (`MILESTONES.md:5589`, "`x<weight>` corroboration"), community label propagation (`business/graph/communities.cpp:104-121`), neighbor ordering (`data/embedstore/graph_search.cpp:253`, `:372`), and the RAG expansion score (`graph_search.cpp:736-783`). So a relation from a document that is edited often outweighs one stated across many documents. Code-layer edges are not affected: their weight is the count of their sites in `kg_edge_sites`. `MILESTONES.md:5610` pins only the deterministic edges at weight 1 on a forced rebuild. The concurrent-build path was not checked. No data is lost and nothing crashes, but counts and rankings are wrong.
5. **`graph delete <named>` during a running build deletes the file, and the build then reports success.** The terminal verb (`presentation/cli/graph.cpp:1798-1826`) and its HTTP twin `DELETE /v1/admin/graph/{id}` (`admin_delete_graph`, `presentation/httpserver/admin_graph.cpp:684`, the unlink at `:707-718`) remove a named graph's `.db` and its `-wal`/`-shm` files. Neither takes a lock or checks for a running build, and no build takes one either: a grep of `presentation/cli/graph.cpp` and `embed.cpp` for a lock or "in progress" finds nothing. A build running in another process (a terminal `graph build`, `embed ingest --graph`, or an app build job racing a delete from the terminal) keeps writing to the unlinked file. Probe (temp home g5): a named graph `work` over `notes` was built once with a slow mock extractor. `graph build work --force` was started, and after 1 s `graph delete work` printed `Deleted graph "work": 2 node(s)...`. The build then exited 0 with `Graph build complete for "work": ... Edges upserted: 2`, but `graph stats work` said `No graph built for "work"` and `embeddings/graphs/` was empty. The app's Graph place cannot race itself, because it hides Delete while a build runs. When an app build is the one racing a terminal delete, the app says "Built" once, and the stats it then reads show the graph as not built.
6. **`graph dedupe --threshold nan` is accepted.** Regression of M31 `prose-reads-gain-json`'s dedupe contract ([machine-mode.md](../../reference/machine-mode.md), the `graph dedupe` paragraph: "A threshold outside `(0, 1]` ... exits `1`"). CLI11 parses `nan` (and `NaN`) into a quiet NaN, and the guard `d->threshold <= 0.0 || d->threshold > 1.0` (`presentation/cli/graph.cpp:1720`) is false for NaN. Probe (an ingested collection `notes`): `apogee graph dedupe notes --threshold nan --dry-run --output-format json` exited 0 with `{"code_entities":0,"code_identity_merges":0,"dry_run":true,"groups":[],"merged_nodes":0,"prose_skipped":"none of 3 prose entities has a vector -- no embedder built them","threshold":null}`. The text form also exits 0, and without `--dry-run` it runs a full (no-op) merge pass instead of refusing. The HTTP twin's guard (`presentation/httpserver/admin_graph.cpp:928`) has the same shape, but a JSON body cannot carry NaN, so changing it there is for symmetry only.

What already works: a binary, oversized, unreadable or unparseable file is skipped and named. A file parsed around a syntax error is used and named partial. A cancelled code build keeps the files already parsed. A failed embed keeps the extraction and records no embed model (`build_test.cpp:346-350`). Communities heal a missing vector on their next run. Code-layer edge weights are exact. The app never offers Delete on a graph it is building.

**Core constraint(s).**
- **Text is UTF-8 where it enters, so no JSON dump can throw on it** ([CLAUDE.md](../../assistant/CLAUDE.md#-text-is-utf-8-where-it-enters-so-no-json-dump-can-throw-on-it)): a source file's bytes are one of those entrances. They are mended once, after `member.read`, through `contracts/utf8.h`'s `valid_utf8`, not at the dump. Valid files pass byte for byte.
- **The code graph is model-free by construction** (27k; the code graph's narrower list in `tests/scripts/cmake/layering.cmake:357-382`): `graph/code_*` may include only `graph/code_*`, `embedstore/`, `contracts/sha256.h` and `contracts/cancellation.h`. Mending in `code_build.cpp` adds `contracts/utf8.h` to that list by name, and nothing else. That header reaches no model.
- **Skipped and named, never a failure** (27k, `MILESTONES.md:7066`): no single file's content can fail a build. The source tree's own files are this item's test bed.
- **One change, every mode** ([ADR 0002](../../adrs/mode-parity.md)): `graph build`, `graph update`, `embed ingest --graph`, the chat attachment, `serve`'s admin routes and so the macOS app share one build core, one delete guard and one threshold check.
- **Older versions keep working** ([ADR 0006](../../adrs/backwards-compatibility.md)): graph databases built before this item open and keep answering. A new table is an additive migration. Every JSON field keeps its name and type, and anything new is an added field.
- **Four layers** ([ADR 0001](../../adrs/layer-enforcement.md)): the graph build lock is the platform seam's (`infrastructure/platform/file_lock.h`, the one 55f's config edit takes). The operations seam (`presentation/operations/graph_sources`) takes it for every named-graph build and delete, so the terminal verbs and `serve`'s admin routes share one guard; Business and the store stay lock-free.
- **Development runs on the dev channel** ([CLAUDE.md](../../assistant/CLAUDE.md#development-runs-on-the-dev-channel)): the probes re-run on `apogee-dev` against a scratch `APOGEE_HOME`, never `apogee` or `~/.apogee`.

**Seam + files.** Source under `lib/src/cli/source/`, tests under `lib/src/cli/tests/` mirroring it ([ADR 0004](../../adrs/tests-mirror-architecture.md)).
- `business/graph/code_build.cpp` (entry 1): after the binary check, `content = harness::valid_utf8(*content)` when `!harness::is_valid_utf8(*content)` (`contracts/utf8.h`, in `data/contracts/`, namespace `apogee::harness`). The hash is taken over the bytes as read, so an unchanged file is not parsed again. The file is named in the build summary (a `mended` list beside `partial`, carried in `SourceBuild` and the JSON). `tests/scripts/cmake/layering.cmake`: `contracts/utf8.h` joins the code graph's list.
- `business/graph/code_parser.cpp` (entry 2): `contains_error` walks iteratively over a `TSTreeCursor` (or an explicit stack), so depth costs heap, not stack. The NOLINT goes.
- `business/graph/code_extract.cpp` (entry 2): `expand_use_tree` collapses the tree once and expands it over an explicit stack of (view, prefix) pairs, so the expansion runs in linear time with no recursion. Any other recursive walk in the extractor is audited the same way, at build.
- `business/graph/build.cpp` (entry 3): the embed phase runs over `mutated` ∪ `nodes_without_vectors()` and drops the `!mutated.empty()` gate. `data/embedstore/graph.cpp/.h` gets `nodes_without_vectors()`: prose entity and decision nodes with `dim = 0` and a name or description, the code layer's types left out (the same exclusion as `graph_dedupe.cpp:185-187`). After this, the warning at `presentation/cli/graph.cpp:336-339` is true.
- `data/embedstore/graph.cpp` and the schema migration (entry 4): an `inferred` edge's support is a set of (collection, chunk) rows (`kg_edge_chunks`, the prose counterpart of `kg_edge_sites`). `upsert_edge` takes the chunk and inserts its support row idempotently, and the weight is the count of the rows. `business/graph/build.cpp`'s `store_extraction` passes the chunk, and when a chunk is extracted again, its old support rows are cleared first. Reconcile prunes the support rows of chunks and members that are gone, then recounts the weights.
- `presentation/cli/graph.cpp`, `presentation/cli/embed.cpp`, `presentation/operations/graph_sources.cpp`, `presentation/httpserver/admin_graph.cpp` (entry 5): one graph build lock, a `FileLock` on `<graph db>.build.lock`, taken by every build of a named graph and by `graph delete` / `DELETE /v1/admin/graph/{id}` before they unlink the file. A delete while a build holds the lock is refused, naming the build. The lock's home is the operations seam both surfaces already share.
- `presentation/cli/graph.cpp:1720` and `presentation/httpserver/admin_graph.cpp:928` (entry 6): `!std::isfinite(threshold) || threshold <= 0.0 || threshold > 1.0`.
- Tests: `tests/business/graph/code_build_test.cpp`, `code_parser_test.cpp`, `code_extract_test.cpp`, `build_test.cpp`, `graph_multi_test.cpp`, `communities_test.cpp`; `tests/data/embedstore/graph_dedupe_test.cpp`, `graph_multi_test.cpp`; `tests/presentation/cli/graph_test.cpp`, `graph_code_test.cpp`, `attachment_graph_test.cpp`; `tests/presentation/httpserver/admin_graph_test.cpp`; `tests/presentation/operations/graph_sources_test.cpp`; the subprocess cases in `tests/scripts/sh/code_graph_e2e.sh` and `graph_e2e.sh`.
- Docs: [machine-mode.md](../../reference/machine-mode.md) (dedupe: a non-finite threshold), [http-api.md](../../reference/http-api.md) (`DELETE /v1/admin/graph/{id}`: refused while a build runs; the build summary's `mended` field), DEVELOPER.md's graph section (edge weight as distinct supporting chunks; the build lock).

**Open calls:**
- [default: a non-UTF-8 file is mended (invalid bytes become U+FFFD, the maximal-subpart policy) and used, then named once in the summary as `not UTF-8 -- N byte(s) shown as U+FFFD`. Skipping it whole is rejected: the CLAUDE.md rule says bytes that are not text are mended where they enter, and a Latin-1 comment or string should not cost a file its structure. A name that holds a replaced byte keeps the U+FFFD, which is honest about what the file says.]
- [default: no in-file cancellation. With both walks linear, a 2 MiB file finishes in well under a second (bound settled at build, measured on the probes' worst cases at the cap). Cancellation stays between files, as 27k records.]
- [default: the embed sweep covers prose entity and decision nodes only, under the embedding spend rule the build already applies (`resolve_entity_embedder`). A build with no embedder resolved embeds nothing and says so, as today. `graph dedupe` does not embed, because it has no embedder. Its survivors heal on the next `graph build`, and its text names how many survivors lost their vector.]
- [default: existing edges are migrated as they are. An inferred edge with no support rows keeps its stored weight until any chunk supports it again, and from then on its weight is the count of rows. `graph build --force` recounts every weight exactly. A one-off reset of every weight to 1 at migration is rejected, because it would lose real corroboration on graphs nobody rebuilds.]
- [default: the graph build lock is a `FileLock`, so the system releases it when the holder dies and a crashed build never blocks a delete. A delete while a build holds it is refused at once (exit 1, HTTP `409`), naming the graph: `a build of "work" is running -- stop it, or wait for it, then delete`. A build that finds a delete holding the lock waits briefly, then refuses. Collection-backed graphs delete their rows through SQLite (`store.delete_graph()`), which already serializes with a writer, so they need no lock.]
- [default: a non-finite threshold gets the existing message, `--threshold must be in (0, 1]`, with exit 1 and nothing on stdout. No new wording.]
- (consumed decision) The app's Graph screens (what they show while a build runs, and after a refused delete) belong to [6h](../../../gui/backlog/v0.2.1/knowledge-graph-review-screens-current.md). Windows' refusal to unlink an open file belongs to [57k](windows-filesystem-safety.md).

**Guardrail(s).** Hermetic, under a temp `APOGEE_HOME`, the mock backend and scripted fakes (`FakeExtractor`, a scripted `EmbedFn`), no network:
- `code_build_test`: a member holding `def caf\xe9_atlas():` beside a valid file builds, uses both, names the first as not UTF-8, and stores facts that `facts_from_json` reads back. A second build parses nothing (the raw-byte hash matches). `facts_to_json` over the mended facts does not throw.
- `attachment_graph_test`: the same folder attached yields a built attachment graph with the file named, not a Failed state.
- `code_parser_test`: 200000 nested parentheses with a syntax error parse with `has_errors` true and no crash. The same nesting without the error is unchanged.
- `code_extract_test`: a Rust `use` tree nested 100000 deep (500 KB) expands to its one leaf `a::b::...::c` within a time bound settled at build, and n=40000 does not crash. The existing leaf and alias cases stay green.
- `build_test`: an embedder that fails after one vector, then a re-run with a working one, ends with every entity embedded and the embed model recorded. A cancel mid-phase heals the same way. The seeded "already described" node with no vector is embedded (the inverted line 333). `graph_dedupe_test` plus `build_test`: a merged survivor whose vector was cleared is embedded by the next build and is a dedupe candidate again.
- `graph_multi_test` (business and embedstore): two chunks stating one relation, then three forced builds, give weight 2. Dropping one chunk's statement and rebuilding gives 1. A dropped member's support is recounted by reconcile (the inverted line 153). Code-layer edges keep their site counts.
- `graph_test`/`admin_graph_test`: a delete while the build lock is held (a second `FileLock` acquire in the test process) is refused, exit 1 / `409`, with the file still present. `--threshold nan`, `NaN`, `inf` and `-nan` each exit 1 with nothing on stdout, in text and `--output-format json`.
- `code_graph_e2e.sh`/`graph_e2e.sh`, the subprocess cases: the probes re-run. The Latin-1 tree builds and `graph report` answers. `d.py` exits 0. A slow-extractor build of `work` with `graph delete work` sent after 1 s gets a refused delete, and the build's success is backed by `graph stats work`.

**Acceptance criteria:**
- [ ] `apogee-dev graph build --source <tree>` over a tree with a Latin-1 file exits 0, names that file, and `graph report` answers. `graph update` and a chat attach of the same tree succeed. No build message carries `json.exception`.
- [ ] A 400 KB file 200000 parentheses deep with a syntax error, and a 500 KB nested Rust `use` tree, each build to exit 0 in bounded time.
- [ ] After an embed failure, a cancel or a dedupe, the next `graph build` embeds every entity left without a vector. "re-run to embed them" is true.
- [ ] Re-extracting the same chunks never changes a relation's weight. Two chunks stating a relation show `x2` after any number of forced builds, and a statement removed from its document stops counting once its chunk is rebuilt.
- [ ] `graph delete <named>` (and its HTTP twin) during a running build of that graph is refused and leaves the graph intact. No build reports success into a deleted file.
- [ ] `graph dedupe --threshold nan` exits 1 with `--threshold must be in (0, 1]`.
- [ ] The full suite is green, `harness.layering` included. The probes re-run on `apogee-dev` against a scratch `APOGEE_HOME` show each failure inverted.
