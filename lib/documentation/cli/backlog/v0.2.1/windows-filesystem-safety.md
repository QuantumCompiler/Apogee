# On Windows, reset and uninstall remove a link as itself, the file sandbox judges a link where it points, uninstall finishes, and only tools that can run are offered

**What / why.** Five Windows gaps where the CLI assumed POSIX filesystem or process behavior and Windows behaves differently. Two of them are serious on the windows-x64 build. `reset` and `uninstall` empty the *target* of a junctioned data row, so a model store moved to another drive gets wiped. The file tools' sandbox lets a link inside `fs_root` reach anything it points to. The other three make Windows report things that are not true: an uninstall that did finish is reported as a failure, the PowerShell completion is left behind in a redirected Documents folder, and the model is offered shell and git tools that can never run. The first two come from one library fact, measured on 2026-10-31 in the local cross toolchain (Homebrew `mingw-w64` 14.0.0_3, `x86_64-w64-mingw32-g++` 16.2.0, the same GCC/libstdc++ family as CI's UCRT64 windows-x64 row). Its `libstdc++.a(fs_ops.o)` cannot see a link. `std::filesystem::symlink_status` calls `_wstat64`, which follows the link. `read_symlink(path, ec)` is a stub: its body stores `movl $0x28,(%rsi)` (errno 40, ENOSYS) and returns. `create_symlink` fails the same way. Nothing in `fs_ops.o` imports a call that reads reparse points. Its only Win32 imports are `CloseHandle CreateFileW CreateHardLinkW DeleteFileW GetDiskFreeSpaceExW GetFileInformationByHandle GetFullPathNameW GetLastError GetTempPathW MoveFileExW RemoveDirectoryW`, plus CRT `_w*` calls. `fs_dir.o` walks with `_wopendir/_wreaddir/_wclosedir` and `symlink_status`. So on windows-x64, `remove_all`, `recursive_directory_iterator`, `weakly_canonical` and `is_symlink` all treat a junction or symlink as the directory or file it points to. The windows-arm64 build (Clang/libc++) likely sees links. macOS and Linux are not affected.

1. **`reset` and `uninstall` follow a junctioned or symlinked row and empty its target (windows-x64).** `remove_planned` (`presentation/cli/uninstall.cpp:119-135`) calls `std::filesystem::remove_all` at `:126`. `reset` calls it on each row it does not keep (`presentation/cli/reset.cpp:151`) and on each unlisted entry (`:155`). `uninstall` calls it on the whole data directory (`uninstall.cpp:198`). With libstdc++'s walk, a row such as `%USERPROFILE%\.apogee\models`, made with `mklink /J … D:\models` (or a directory symlink) to keep the model store on another drive, is entered and emptied. The link itself is not just removed. `apogee reset --keep sessions` empties `D:\models`, and `apogee uninstall` does the same while removing the data directory. On POSIX only the link goes. This breaks the promise in `uninstall.h:83-84`: "A symlink is removed as itself, never followed." `plan_rows`' own comment says the same at `uninstall.cpp:73`.
2. **The file tools' sandbox does not resolve links, so a link out of `fs_root` escapes it (windows-x64).** `resolve_in_root` (`business/tools/fs.cpp:185-218`) relies on `weakly_canonical` at `:204` and says so at `:201-203`: "a symlink pointing out of the root is judged by where it points". With the stub `read_symlink`, nothing resolves, so `cfg\.ssh\id_ed25519` under a link `cfg -> C:\Users\me` passes `is_within` (`:209`). The `grep_files` walk's guard, `it->is_symlink(code)` at `:881-889`, is never true, and its directory recursion (`:872-877`) enters a junction. Example: a repo cloned with `core.symlinks=true` (Developer Mode), or a pnpm workspace whose `node_modules` entries are junctions, contains `cfg -> C:\Users\me`. A prompt-injected model calls `read_file {"path":"cfg\\.ssh\\id_ed25519"}` or `write_file {"path":"cfg\\AppData\\Roaming\\Microsoft\\Windows\\Start Menu\\Programs\\Startup\\x.cmd"}`. Both resolve "inside" the root and succeed. On macOS and Linux the same calls are refused `outside the allowed root`. The tests do not catch this. `tests/business/tools/fs_test.cpp:64-85` creates its links with `create_symlink` / `create_directory_symlink` and checks only `if (!code)`, so on windows-x64 (always ENOSYS) the escape cases are skipped silently and the test still passes. That contradicts the sandbox table recorded at `MILESTONES.md:4708` (Milestone V, "a symlink pointing out" through every tool) and `DEVELOPER.md:763`.
3. **Shell and git tools are registered and advertised on Windows, but every call fails with wrong advice.** `register_native_toolsets` (`business/tools/toolsets.cpp:72-86`) registers `run_command` (`:76-78`) and the git tools (`:79-86`) without asking `platform::supports_child_processes()`, which is `false` on `_WIN32` (`infrastructure/platform/child_process.cpp:254-260`). The environment note still tells the model "Commands run there, through cmd" (`toolsets.cpp:104-106` → `environment.cpp:56-58`). Every call then hits `start_child`'s blanket Windows refusal (`child_process.cpp:331-340`): "this build cannot spawn child processes: the vendor-CLI backends have no Windows implementation yet. Use a direct-API backend on this platform". That text reaches the model through `process.cpp:36-39`, `shell.cpp:181-184` and `git.cpp:39-41`, and it is wrong advice for a turn that is already on a direct-API backend. `run_command` is a destructive tool (`toolsets.cpp:28-29`), so the user may first be asked to approve a command that can never run. The gap is known everywhere else. `attachments.cpp:54`, `ingest.cpp:26` and `:74`, the four vendor backends (`codex_cli.cpp:63`, `gemini_cli.cpp:92`, `claude_cli.cpp:128`, `ollama_cli.cpp:64`) and `provider_probe.cpp:30` all check the flag, and `shell_test.cpp:28/58/252` SKIP on it. Registration is the one place that does not. This goes against the house principle at `presentation/cli/helpers.cpp:243-244` ("a model is never offered a tool that can only fail") and the Milestone V decision row at `MILESTONES.md:4723` ("Windows shell | `cmd /C` … A recorded per-platform difference, not a skip"), which assumed the shell could run.
4. **`apogee uninstall` on Windows always fails to delete its own running `.exe`, after the data is already gone.** `execute_uninstall` (`uninstall.cpp:192-204`) removes completions, then the data directory, then `plan.binary` last with a plain `remove` (`:202` → `:128`). `plan.binary` is `platform::executable_path()` (`uninstall.cpp:238`), which on Windows is `GetModuleFileNameW(nullptr, …)` (`infrastructure/platform/platform.cpp:86-99`): the running image. Windows will not delete a running image, and nothing renames it aside or schedules its removal. So every Windows uninstall, with `--yes` or a typed `yes`, removes the completions and `%USERPROFILE%\.apogee` as confirmed, then prints `could not remove …\apogee.exe: Access is denied.` and exits 1 (`:263-267`). `%LOCALAPPDATA%\Programs\Apogee\bin\apogee.exe` stays, along with any PATH entry the user added from install.ps1's note (the installer adds none, `install.ps1:97-101`), and an uninstall that otherwise finished is reported as failed. No data is lost that was not confirmed. The only self-removal test (`tests/scripts/sh/install_parity.sh:256-280`) is POSIX-only, and the recorded Windows caveat (`MILESTONES.md:2248`, Milestone K) does not mention this.
5. **Uninstall looks for the PowerShell completion where install.ps1 did not put it.** `completion_candidates` builds `home_directory()\Documents\PowerShell\Completions\apogee.ps1` (`uninstall.cpp:31-41`, the entry at `:40`), with `home_directory()` taken from `USERPROFILE` (`platform.cpp:222`). `install.ps1:78` writes to `[Environment]::GetFolderPath('MyDocuments')\PowerShell\Completions`. These differ whenever Documents is redirected, which OneDrive's Documents backup does on Windows 11 and Group Policy folder redirection also does. install.ps1 reports `installed completions to C:\Users\me\OneDrive\Documents\PowerShell\Completions`. `apogee uninstall` then plans no completion and leaves that `apogee.ps1` behind, still dot-sourced by the user's profile, after the binary is gone. This breaks `DEVELOPER.md:280`'s row for `uninstall.h/.cpp`: the removal is done "by the product rather than by the two installer scripts, so a removal is not written twice and cannot drift".

What already works: POSIX `reset`/`uninstall` remove a linked row as itself (libstdc++ and libc++ `remove_all` do not follow a link there, though no test pins it: `reset_test.cpp` and `lifecycle_test.cpp` make no link today), and the POSIX sandbox refuses every link out (pinned in `fs_test.cpp:64-85`). The vendor backends, attachments, ingest and the provider probe already refuse cleanly on Windows. Uninstall's order (binary last) and its "report every failure, keep going" rule are right and stay.

**Core constraint(s).**
- **`platform/` is the one home of platform `#ifdef`s** (`source/infrastructure/CLAUDE.md`). Link detection, link-aware removal, link resolution, the Documents folder and the running-binary removal are platform calls that `uninstall`, `reset` and the file tools ask for. No `_WIN32` block grows in `business/tools/` or `presentation/cli/`.
- **A check that cannot run on a platform reports skipped, never passing** (CLAUDE.md, the layout invariant's sub-rule). This applies to tests too: a link case that cannot create its link says SKIP with the reason and never passes silently.
- **One layout declaration, and every install path reads it**: uninstall removes what the installers wrote, read from one place. The PowerShell folder is the one install.ps1 resolves, not a second guess at it.
- **Development runs on the dev channel**: there is no Windows host on the dev Mac. The proof is CI's two Windows test jobs (the x64 one is the libstdc++ build this item is about) and `make pr-ci`'s Windows x64 cross-build. Any manual try on a Windows machine uses a dev-channel build, and nothing touches `~/.apogee`.
- **A model is never offered a tool that can only fail** (`helpers.cpp:243-244`, the 25e rule), applied to `run_command` and the git tools.
- Sandbox semantics are unchanged on POSIX: `weakly_canonical` + `is_within` stays the POSIX path, byte for byte.

**Seam + files.**
- `infrastructure/platform/platform.h/.cpp` — new calls, each a plain `std::filesystem` call on POSIX:
  - `is_link(path, ec)`: on Windows, a reparse point whose tag is `IO_REPARSE_TAG_SYMLINK` or `IO_REPARSE_TAG_MOUNT_POINT`.
  - `remove_tree(path, ec)`: removes a link as itself (`RemoveDirectoryW` for a directory junction or symlink, `DeleteFileW` for a file symlink) and recurses only into real directories. POSIX: `remove_all`.
  - `resolve_path(path, ec)`: the longest existing prefix resolved with `CreateFileW(…FILE_FLAG_BACKUP_SEMANTICS)` + `GetFinalPathNameByHandleW`, `\\?\` stripped, the rest normalised. POSIX: `weakly_canonical`.
  - `documents_directory()`: `SHGetKnownFolderPath(FOLDERID_Documents)`, the folder `GetFolderPath('MyDocuments')` returns.
  - `remove_own_binary(path, ec)`: on Windows, renames the running image aside in its own directory (allowed for a running image) and then asks `MoveFileExW(…, nullptr, MOVEFILE_DELAY_UNTIL_REBOOT)`. It returns which of the two happened. POSIX: `remove`.
- `infrastructure/platform/child_process.cpp` — the Windows refusal text made platform-neutral (it starts no program; the vendor backends keep their own messages).
- `presentation/cli/uninstall.cpp/.h` — `remove_planned` through `platform::remove_tree`. The binary through `remove_own_binary`, with the plan and the report saying what Windows did. The PowerShell candidate from `documents_directory()`.
- `presentation/cli/reset.cpp` — unchanged call sites; it already goes through `remove_planned`.
- `business/tools/fs.cpp` — `resolve_in_root` (`:192`, `:204`) and the walk (`:851`, `:872-889`) through `platform::resolve_path` / `platform::is_link`. A linked directory is not recursed into unless it resolves inside the root.
- `business/tools/toolsets.cpp/.h` — `ToolsetOptions` gains `child_processes` (defaults to `platform::supports_child_processes()`). When it is false, no `run_command`, no git tools, and `environment.shell` stays empty.
- `data/modelstore/store.cpp` — `remove_weights` (`:998-1000`) through `platform::remove_tree` (see Open calls).
- Tests:
  - `tests/support/file_link.h/.cpp` (new): makes a directory link (a junction on Windows via `FSCTL_SET_REPARSE_POINT`, which needs no privilege; a directory symlink elsewhere) and a file link (`CreateSymbolicLinkW` with `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` on Windows, SKIP said out loud when Developer Mode is off).
  - `tests/infrastructure/platform/platform_test.cpp`, `tests/presentation/cli/reset_test.cpp`, `tests/presentation/cli/lifecycle_test.cpp` (uninstall), `tests/business/tools/fs_test.cpp`, `tests/business/tools/environment_test.cpp`.
- Docs: DEVELOPER.md's `platform`, `uninstall.h/.cpp` and `fs_test.cpp` rows; the Windows caveat in MILESTONES' record of this item.

**Open calls:**
- [default: a "link" is a reparse point tagged `IO_REPARSE_TAG_SYMLINK` or `IO_REPARSE_TAG_MOUNT_POINT` only. Other reparse points, such as OneDrive cloud-file placeholders and dedup files, are files or directories as themselves, so a OneDrive-backed folder is never mistaken for a link.]
- [default: the sandbox compares a root and a candidate that were both resolved through `platform::resolve_path`, so on Windows both spellings come from `GetFinalPathNameByHandleW` and agree in case and drive form. `is_within` itself is unchanged.]
- [default: `platform::remove_tree` replaces `remove_all` in `remove_planned` and in `remove_weights` (`store.cpp:1000`). `remove_weights` is the other removal that can meet a link the user placed, because a model directory is the thing a user moves to another drive. The other `remove_all` calls (`media.cpp`, `acquire.cpp`, `promote.cpp`, `python_env.cpp`, `work_dir.cpp`, the store's staging dirs, and others: 34 more `remove_all` lines across 19 files at HEAD) remove trees Apogee itself created. The build audits each one and moves any that can hold a user's link, noting which in MILESTONES.]
- [default: on Windows, uninstall renames its running `apogee.exe` aside in its own directory, so `apogee` stops resolving, then asks for removal at reboot. If that request is refused (it needs elevation), the plan says so up front ("binary … (Windows cannot delete a running program: delete <path> after this command exits)") and the run ends with that one line and exit 0, not `could not remove … Access is denied.` and exit 1. A genuine failure, such as the rename itself failing, still exits 1. The order stays binary last.]
- [default: when child processes are unsupported, the `shell` and `git` toolset names stay valid in agent files and `--tools`, so an agent stays portable. The registry simply lacks them, as it lacks `web_search` without an instance. The refusal text becomes "this build cannot start other programs on Windows yet", with no backend advice.]
- [default: this item owns the PowerShell entry of `completion_candidates`, because it needs this item's `platform::documents_directory()`. 57l ([`install-scripts-finish-clean.md`](install-scripts-finish-clean.md)) names the same redirected-Documents case in its finding 4 and lists "the PowerShell stub under the Documents known folder" in its seam. The two are one fix: whichever item builds first lands it through `documents_directory()`, and the other records it as consumed. 57l owns the zsh entries of the same list.]
- (consumed decision) A Windows `CreateProcess` implementation for `start_child` is out of scope (no item is queued; a ROADMAP idea if wanted). When it lands, registration follows the flag with no further change.

**Guardrail(s).** All hermetic: a temporary `APOGEE_HOME` under the test's temp dir, links made by `tests/support/file_link`, no network.
- **Finding 1:** a data row that is a directory link to an outside directory holding a file. Both `apogee reset` (the row not kept) and `execute_uninstall` remove the link and leave the outside file in place, on every platform. On windows-x64 that is the junction case that empties the target today. The test fails if the link's creation is refused rather than skipping silently.
- **Finding 2:** `fs_test.cpp`'s `if (!code)` guards become `file_link`. The directory-link escape (a junction on Windows) runs everywhere and is refused through `resolve_in_root`, `read_file`, `write_file`, `edit_file` and `grep_files`, with the outside file untouched. The file-symlink cases SKIP with the reason where Windows will not create one unprivileged. A unit case pins `platform::is_link` and `platform::resolve_path` on a junction, and confirms that a non-link reparse point (if one can be made) is not a link.
- **Finding 3:** `register_native_toolsets` with `child_processes = false` holds no `run_command` and no `git_*`, and its environment note has no "Commands run there". With `true` (POSIX) both are present. This is testable on every host through the option. On Windows CI the default makes the same assertions.
- **Finding 4:** `execute_uninstall`'s outcome over a fake binary removal that reports "renamed, deletion scheduled" or "renamed, delete it yourself" gives exit 0 with the one-line note, and a fake that fails the rename gives exit 1. A Windows platform test exercises `remove_own_binary` on a file mapped as an image section (`CreateFileMappingW` with `SEC_IMAGE` on a copied `.exe`), which refuses deletion as a running program does. If the mapping does not reproduce the refusal, the mechanism is settled at build.
- **Finding 5:** with `documents_directory()` faked to a redirected folder, `completion_candidates` names `<that folder>\PowerShell\Completions\apogee.ps1`, not `USERPROFILE\Documents\…`.

**Acceptance criteria:**
- [ ] On windows-x64, `apogee reset` and `apogee uninstall` remove a junctioned or symlinked row as a link: its target's contents survive, as on POSIX.
- [ ] On windows-x64, a junction or symlink inside `fs_root` that points outside is refused `outside the allowed root` by every file tool, and `grep_files` does not walk it. The sandbox table runs on Windows instead of being skipped silently.
- [ ] On a build without child processes, the model is offered no `run_command` and no git tools, the environment note claims no shell, no approval is asked for a command that cannot run, and no message tells a direct-API turn to "use a direct-API backend".
- [ ] `apogee uninstall --yes` on Windows ends with exit 0 and either no `apogee.exe` left by name or one line naming the file to delete. It never ends with `Access is denied.` and exit 1 after a removal that otherwise finished.
- [ ] With Documents redirected (OneDrive or policy), `apogee uninstall` plans and removes the `apogee.ps1` that install.ps1 wrote.
- [ ] POSIX behavior and tests are unchanged; the full suite is green on all five CI targets.
