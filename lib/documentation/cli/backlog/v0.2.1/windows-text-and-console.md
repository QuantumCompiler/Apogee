# On Windows, non-ASCII names and text work, Ctrl-C takes three presses, and a classic console shows plain text

**What / why.** On Windows the CLI reads its environment and its arguments in the ANSI code page and writes to a console left in the ANSI code page with virtual-terminal processing off. A user whose profile folder has an accent in it cannot run any command. An accented prompt reaches the model as U+FFFD. The second Ctrl-C kills a command that macOS and Linux let clean up. `check` in a cmd.exe window prints escape codes. The second CLI/GUI bug sweep (2026-10-31) found these four. Re-read at HEAD (`b26550bb`). No Windows host is available here: each Windows-only claim was checked against the source and the toolchain headers, and the one cross-platform claim (entry 2) was re-run on macOS.

1. **A non-ASCII profile name makes every command fail on Windows x64.** `home_directory()` (`infrastructure/platform/platform.cpp:220-238`) returns `std::getenv("USERPROFILE")` (line 222) as raw bytes. `current_root_inputs()` (`data/contracts/paths.cpp:188-190`) reads `APOGEE_HOME` the same way. Both are in the ANSI code page: there is no UTF-8 `activeCodePage` manifest, and no `_wgetenv`. `resolve_root` then builds a `std::filesystem::path` from them: `paths.cpp:166` for `APOGEE_HOME` and `paths.cpp:180-181` for the baked root. On Windows, libstdc++ decodes a `char` range as UTF-8. MinGW GCC 16.2's `bits/fs_path.h:919-925` runs it through `path::_Codecvt<wchar_t>`, which is `codecvt_utf8_utf16` (lines 892-896). When that fails, line 935 calls `__throw_conversion_error`, and lines 783-787 throw `filesystem_error("Cannot convert character sequence", illegal_byte_sequence)`. CI's x64 row builds with that library (`ci.yml:419`, `msystem: UCRT64`). Scenario: user `José`, with `USERPROFILE=C:\Users\José` and `é` = `0xE9` in cp1252. `install.ps1:87` runs `apogee.exe check --fix`, `apogee_home()` throws, and `main.cpp:33-35` prints `apogee: Cannot convert character sequence: Illegal byte sequence` and exits 1. `install.ps1:88` then throws `post-install check failed`, and every later command fails the same way. A non-ASCII `APOGEE_HOME`, or a non-ASCII path argument, fails the same way. Related sites name a path in the wrong encoding:
   - `platform.cpp:197` passes `path.string()` (UTF-8 bytes on libstdc++) to `CreateFileA`, an ANSI API. The owner marker that `create_exclusive_file` writes then lands under a mis-decoded name or fails. `file_lock.cpp:108` (`CreateFileW(path.wstring())`) and `data/modelstore/sidecar.cpp:28-32` (`_wfopen`, "where a narrow one cannot name every path") already do it right.
   - `data/embedstore/store.cpp:73` calls `sqlite3_open(path.string())`. On the arm64 build (libc++, `ci.yml:423`, `CLANGARM64`), `string()` is ANSI, while SQLite reads its argument as UTF-8.

   Not affected: a machine with Windows' system-wide "Beta: Use Unicode UTF-8" setting turned on.
2. **Non-ASCII arguments arrive as ANSI bytes and are silently replaced.** `main(int, char**)` (`main.cpp:28-37`) passes the ANSI argv to `RootCommand::run`, which passes it to CLI11 (`presentation/cli/root.cpp:295`, `app_->parse(argc, argv)`). Nothing converts it. A grep for `ensure_utf8|CLI::argv|GetCommandLineW|wmain|activeCodePage` over `lib/src/cli/source`, `cmake` and the `CMakeLists.txt` files finds nothing. No request body throws, because the text-enters-as-UTF-8 rule mends the bytes at the Harness (`business/harness/harness.h:219-229`, `harness.cpp:16-43`). What happens instead is silent corruption. On cp1252, `apogee complete "¿Qué tal el café?"` (the positional prompt, `presentation/cli/complete.cpp:579`) sends the model `"\ufffdQu\ufffd tal el caf\ufffd?"` and saves the same to the session. Re-run here on macOS with the same cp1252 bytes against the mock backend, using a temp `APOGEE_HOME` and `printf 'hello\n' | apogee chat -m mock --system "$(printf '\xbfQu\xe9 tal el caf\xe9?')"`: exit 0, and the session file holds `"content": "�Qu� tal el caf�?"` and `"system_prompt": "�Qu� tal el caf�?"`. A non-ASCII path argument (`apogee chat --attach C:\Users\me\résumé.pdf`) probably meets entry 1's `Cannot convert character sequence` on x64, exiting 1 through `main.cpp:34`. That part is not verified on this host.
3. **On Windows the second Ctrl-C kills, not the third.** `InterruptScope` installs its handler once (`presentation/cli/interrupt.cpp:27`), and `on_interrupt` (`interrupt.cpp:15-20`) counts presses and calls `_Exit` on the third. The Microsoft CRT resets SIGINT to `SIG_DFL` before it calls a handler, and the handler never re-arms. So on Windows the second Ctrl-C ends the process with `STATUS_CONTROL_C_EXIT`. The documented contract is the third (`interrupt.h:12-13`, "A third Ctrl-C while the child is still winding down exits at once"; [DEVELOPER.md:413](../../assistant/DEVELOPER.md)). Scenario: `apogee models pull <hf-ref>` (eight `InterruptScope` sites in `models_pull.cpp`; also `datasets.cpp`, `task_cmd.cpp`, `train.cpp` and others). The first Ctrl-C starts the cancel. A second one while the partial file and the staging folder are being removed kills the process, which leaves `<model>/<format>/.incoming-*` and its `.owner` marker behind. On POSIX that takes three presses, and the cleanup runs. `presentation/httpserver/serve.cpp:189-190` installs `on_signal` the same way, once. On POSIX a second Ctrl-C is just a second stop. On Windows it kills the server before in-flight turns finish ("An in-flight turn finishes before the pool joins", `serve.cpp:192`).
4. **Plain output on a classic Windows console prints raw escapes and mojibake.** On Windows, `Style::detect` turns color on whenever `_isatty(1)` is true and `NO_COLOR` is unset (`infrastructure/ansi/ansi.cpp:78-98`, `platform.cpp:268-285`). Nothing turns `ENABLE_VIRTUAL_TERMINAL_PROCESSING` on for ordinary output: `full_screen_refusal` (`platform.cpp:365-385`) sets it only to probe, then puts the old mode back (line 382). Nothing sets the console code page to UTF-8 either (no `SetConsoleOutputCP`, `SetConsoleCP` or `CP_UTF8` in `lib/src/cli/source`). Scenario: Windows 10's cmd.exe in classic conhost, running `apogee check`. Rows print as `←[32mpass←[0m …`, and a `—` reads `ΓÇö`. The UTF-8 the CLI writes shows as mojibake: the `·` in the chat and analyze banners (`presentation/cli/analyze.cpp:798`, `882`; `chat_completer.cpp:847`), the `…` (`chat_history.cpp:337`), and the markdown renderer's `•`, `─`, `│` and `☐` (`presentation/markdown/stream_renderer.cpp:13`, `502`, `530`, `553`). Severity: low.

What already works: Windows Terminal, which turns VT processing on and reads UTF-8 itself. The line editor's own prompt: replxx sets code page 65001 and VT while it reads a line, then puts both back (its `terminal.cxx:183-198`). That is why a chat answer streamed after the read is affected and the prompt is not. The full-screen shell: FTXUI turns VT on for its lifetime. The file lock and the model-store sidecars, which already use wide paths. Text a model or a tool returns is already mended to UTF-8 by the Harness rule.

**Core constraint(s).**
- **Text is UTF-8 where it enters, so no JSON dump can throw on it** ([CLAUDE.md](../../assistant/CLAUDE.md#-text-is-utf-8-where-it-enters-so-no-json-dump-can-throw-on-it)): argv and the environment are doors that text comes in through. On Windows they must deliver UTF-8 before anything reads them, so that the Harness's mend is the backstop for bytes that are not text, never a lossy decoder for a person's typing. Valid text passes byte for byte, on every platform.
- **Nothing links the CLI executable** ([CLAUDE.md](../../assistant/CLAUDE.md#-nothing-links-the-cli-executable)): `main.cpp` stays almost empty ("Resist the urge to put a helper here"). The manifest is a resource on the executable target, stamped beside the channel by `apogee_channel_executable` (`source/CMakeLists.txt:102`). The console setup is a `platform/` call made from `RootCommand::run`, not code in `main`.
- **The portability seam** ([CLAUDE.md](../../assistant/CLAUDE.md)'s Platforms line): platform `#ifdef`s live in `infrastructure/platform/` (DEVELOPER's `platform/` row). Every Windows path is named wide or as UTF-8 there, never through an `…A` API.
- Release behavior elsewhere is kept: entry 1's failure today is an uncaught `filesystem_error` through `main`'s catch-all. After the fix the root resolves. macOS and Linux behavior does not change.
- The item's own rules: a Ctrl-C contract has the same count on every platform. Whatever the CLI changes about the console (code pages, VT mode), it puts back on every exit path it controls, because a console's code page outlives the process in cmd.exe.
- **Development runs on the dev channel** ([CLAUDE.md](../../assistant/CLAUDE.md#development-runs-on-the-dev-channel)): probes use a temporary `APOGEE_HOME` under the scratchpad. Any live Windows pass runs `apogee-dev`, never the release `apogee` or `~/.apogee`.

**Seam + files.**
- `source/apogee.manifest` + `source/apogee.rc` (new) — `<activeCodePage>UTF-8</activeCodePage>`. On `WIN32` it is attached by `apogee_channel_executable` (`source/CMakeLists.txt:102-109`), which is called for `apogee` (line 115) and for `apogee_channel_probe` (`tests/CMakeLists.txt:690`), so every channel gets it. `apogee_tests` (`tests/CMakeLists.txt:411`) gets the same manifest, so the Windows test runs see the code page users get.
- `infrastructure/platform/platform.cpp/.h` — `create_exclusive_file` through `CreateFileW(path.wstring())`, as `file_lock.cpp` does. `home_directory()` on Windows through `_wgetenv` → UTF-8, so it does not depend on the manifest. A new `ConsoleScope` (or `prepare_console()`): when stdout or stderr is a console, it saves both code pages and the output mode, sets `CP_UTF8` input and output, and turns VT processing on. It restores all three at scope end and from the interrupt handler's `_Exit` path. Elsewhere it is a no-op. A new `utf8_environment(name)` reads one variable as UTF-8 on Windows, and is `getenv` elsewhere.
- `data/contracts/paths.cpp` — `current_root_inputs()` reads `APOGEE_HOME` through `platform::utf8_environment`. Paths are built from it with `std::filesystem::u8path`-equivalent construction (`path{std::u8string}`), so libstdc++ and libc++ agree.
- `data/embedstore/store.cpp` — `sqlite3_open` takes the path as UTF-8 (`path.u8string()`), on every platform.
- `infrastructure/ansi/ansi.cpp` — `Style::detect` asks the platform whether the console renders VT, and Auto turns color off where it cannot be turned on. Always and `NO_COLOR` keep their meaning.
- `presentation/cli/interrupt.cpp` — under `_WIN32`, `on_interrupt` re-arms itself (`std::signal(SIGINT, on_interrupt)`) before it counts. `presentation/httpserver/serve.cpp` — `on_signal` the same.
- `presentation/cli/root.cpp` — `RootCommand::run` holds the `ConsoleScope` for the run.
- Tests: `tests/infrastructure/platform/platform_test.cpp`, `tests/data/contracts/paths_test.cpp`, `tests/data/embedstore/store_test.cpp`, `tests/infrastructure/ansi/ansi_test.cpp`, `tests/presentation/cli/interrupt_test.cpp` (new, mirroring `interrupt.cpp`), and a new `tests/scripts/cmake/non_ascii_e2e.cmake` (registered as `cli.non_ascii` beside `complete_e2e.cmake`, so it runs on Windows too, where the `scripts/sh` e2e tests do not).
- Docs: DEVELOPER's `platform/` row (the console scope, UTF-8 environment), its `cli/interrupt` row (the count on Windows), and the build section's line on the Windows manifest.

- 2026-10-31: One item, because all four are the Windows console process failing to speak the platform's text and signal semantics as the POSIX build does. Entries 1 and 2 share one root cause (no UTF-8 process code page) and one fix. Entry 4's code-page half is the console counterpart of the same gap. Entry 3 is the remaining Windows-only process semantic that the sweep found.
- 2026-10-31: Entry 2 is silent corruption, not a crash. The sweep's first scenario, a `type_error.316` from the request body, does not happen at HEAD: the Harness mends the message first, and the probe exits 0. The fix is still owed, because the person's words reach the model replaced.

**Open calls:**
- [default: the UTF-8 `activeCodePage` manifest is the fix for argv and the environment, not `wmain`/`GetCommandLineW` plus per-read conversions. One resource covers argv, `getenv`, CLI11 and every narrow CRT and Win32 call, the third-party ones included. The few sites this item rewrites (`CreateFileW`, `_wgetenv`, `u8string` for SQLite) are made encoding-explicit anyway, so they stay right on a pre-1903 Windows, where the manifest element is ignored.]
- [default: on a Windows older than 10 1903 (`GetACP() != CP_UTF8` in a manifested process), `apogee check` shows a Warn row saying non-ASCII arguments may not survive, and nothing refuses to run.]
- [default: Ctrl-C re-arms with `std::signal` at the top of the handler under `_WIN32`, as the finding proposes, rather than moving to `SetConsoleCtrlHandler`. It is the smallest change that keeps one handler on both platforms. The gap between the CRT's reset and the re-arm is a few instructions.]
- [default: the console scope sets both the input and the output code page to UTF-8 and turns VT on for the whole run whenever a standard stream is a console. It restores them at exit and before the third Ctrl-C's `_Exit`. Where VT cannot be turned on (a pre-VT console), Auto color resolves off and the text is written plain.]
- [default: no change to how replxx or FTXUI handle the console. Each already saves and restores its own state, and the outer scope's restore runs after theirs.]

**Guardrail(s).**
- `platform_test`: on Windows, the test binary's `GetACP()` is `CP_UTF8` (the manifest is attached). `home_directory()` with `USERPROFILE` set through `SetEnvironmentVariableW` to `<temp>\José` returns the UTF-8 bytes `…Jos\xC3\xA9`. `create_exclusive_file` on `<temp>/naïve-owner` creates a file that `std::filesystem::exists` finds under that name, and reports `exists` on the second call. `utf8_environment` round-trips a non-ASCII value on every platform.
- `paths_test`: `current_root()` with `APOGEE_HOME` = a temp folder named `Josè-home` resolves without throwing, and its `root` names that folder exactly (wide on Windows, bytes elsewhere). The baked root under a non-ASCII home does the same.
- `store_test`: an embed store opens, writes and reopens under a non-ASCII temp folder.
- `interrupt_test`: inside an `InterruptScope`, `std::raise(SIGINT)` twice leaves the process running, with the token cancelled and the count at 2, on every platform. On CI's Windows rows that case fails today. `serve`'s handler survives two raises in `serve_test` (the server stops once and the test process lives).
- `ansi_test`: `resolve_color` in Auto with a console that does not render VT is off. Always is on. `NO_COLOR` is off.
- `cli.non_ascii` on the real binary (CMake `-P`, so it runs on Windows): a temp `APOGEE_HOME` named with `é`, then `config init` and `config add-backend mock --type mock --model mock-1` (as `complete_e2e.cmake:80-81` does), then `chat -m mock --system "¿Qué tal el café?"` with one piped line. It exits 0, and the session file's `system_prompt` is `¿Qué tal el café?` byte for byte, never U+FFFD.

**Acceptance criteria:**
- [ ] On Windows, a profile folder or `APOGEE_HOME` with non-ASCII characters resolves, `install.ps1`'s `check --fix` passes, and every command runs. No `Cannot convert character sequence` is printed.
- [ ] `apogee complete "¿Qué tal el café?"` on Windows sends and saves `¿Qué tal el café?`, and `--attach` takes a path named `résumé.pdf`.
- [ ] On Windows, the first and second Ctrl-C during `models pull` let the cleanup run and leave no `.incoming-*` folder. The third exits at once, as on POSIX. A second Ctrl-C to `serve` lets in-flight turns finish.
- [ ] In a classic conhost cmd.exe window, `apogee check` shows colored rows with no raw `←[` escapes, and `·`, `…` and `—` read correctly. The console's code pages and mode are what they were once the command exits. These console checks are confirmed by the user on a Windows host, or recorded as unverified with the reason, as the 2026-10-31 Windows entry did.
