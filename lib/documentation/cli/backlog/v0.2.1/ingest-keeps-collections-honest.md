# `embed ingest` keeps a collection honest: no `.git`, dotfiles or `node_modules`, same-named documents from two folders kept apart, one embedder per vector space, and reads not stalled by an ingest

**What / why.** A collection is what a `chat --rag` turn sends to a model, metered backends included, and what `embed query`, the TUI and the macOS app's Collections screen all read. Four faults in how `embed ingest` builds one and how the store is opened let a collection hold what the user never meant to put in it, lose what they did, search across two vector spaces under a `[vector]` label, or read as empty while an ingest runs. Found by the second bug sweep, 2026-10-31, and re-verified against HEAD the same day (temp `APOGEE_HOME`, the built binary, the mock backend):

1. **A directory ingest takes `.git/`, dotfiles and `node_modules`, so secrets reach RAG.** `ingest_path` (`data/embedstore/ingest.cpp:116-125`) walks with `recursive_directory_iterator` and keeps every entry that `is_regular_file`. The only later filter is `read_as_text` (`ingest.cpp:94-103`): empty files and a NUL in the first 8 KiB are skipped. So `.git/config` (a remote URL with a token in it), `.git/logs/HEAD`, the hook samples, `.env` and vendored `node_modules` all become chunks. The attachment walk already leaves hidden entries out and, inside a repository, takes git's own list (`business/agentloop/attachments.cpp:84-90` `hidden`, `:119-133` `git_files`, `:136-152` `walked_files` with `disable_recursion_pending`, `:154-167` `files_under`). The code graph skips vendored directories (`business/graph/code_build.cpp:21-23` `kVendoredDirectories`). No document records hidden or VCS files in an ingest as intended: DEVELOPER.md:438 (the `embedstore/ingest.h/.cpp` row) describes only the binary skip. Probe: a one-file repository whose remote is `https://user:ghp_FAKE@github.com/x/y`, plus `.env` (`SECRET=abc123`) and `node_modules/x/index.js`. `embed ingest proj <repo>` gives 25 sources and 74 chunks: `.env`, 22 `.git/*` files, `main.md`, `node_modules/x/index.js`. `embed query proj ghp_FAKE` returns `0.832  [lexical]  .git/config#0` (the sweep measured 0.839), and `embed query proj abc123` returns `0.866  [lexical]  .env#0` / `SECRET=abc123`. A `chat --rag proj` turn on a metered backend would send that chunk to the provider. The app's Ingest sheet runs the same command (`darwin/source/presentation/knowledge/ViewModels/CollectionsViewModel.swift:32`). It is medium-high rather than high only because the user picks the target and `embed info` lists every source.
2. **Ingesting a second folder silently replaces same-named documents from the first.** A source is named relative to the ingest root (`ingest.cpp:149-151`), and a single file's root is its parent (`ingest.cpp:129`). `Store::replace_source` deletes every chunk with that name before inserting (`data/embedstore/store.cpp:217-222`, `DELETE FROM chunks WHERE source = ?`). So `/b/README.md` overwrites `/a/README.md` in the same collection. It is never duplicated, and the output never mentions the replacement. Probe: `/a/README.md` holds "Alpha project uses Postgres." and `/b/README.md` holds "Beta project uses Redis.". After `embed ingest two /a` and `embed ingest two /b`, `embed info two` shows `chunks: 1` with the one source `README.md`, and `embed query two Postgres` prints `no matches [lexical]`. Project A's README is gone, and its graph provenance goes too at the next graph build's reconcile. DEVELOPER.md:438 records the relative naming ("so a corpus survives being moved") and says nothing about two roots colliding.
3. **Re-ingesting part of a collection under a new embedder relabels the old vectors and mixes vector spaces.** `resolve_ingest_retriever` is given only the embedder's facts (`presentation/cli/embed.cpp:253-254`; `business/agentloop/retriever.cpp:169-207` takes no store facts). After the walk, the ingest rebinds the store to whatever model this run used whenever any vectors exist (`embed.cpp:282-289`, `store.set_embedding_model(embedder->model, stats.dimension)` at `:288`). The query-side check compares only the recorded model and the number of vector widths (`retriever.cpp:54-66`). After a partial re-ingest under model B, the store records B, has one width and no lexical-only chunks, so every chunk embedded under A is ranked by cosine against B's query vector. That breaks the CLAUDE.md rule that a store whose vectors came from another model is "demoted **wholesale** to lexical". The demotion's own hint invites the partial re-ingest: "re-run `apogee embed ingest` with the current model to vector-query" (`retriever.cpp:58-60`). Probe on the mock (two mock backends, `--embedding-model mock-embed-a` and `mock-embed-b`, both 8-d): `notes` was ingested under A (`2 file(s), 2 chunk(s), 2 vector(s) [mock-embed-a]`), then the default embedding was switched to B. `embed query notes zarquon` correctly prints `using lexical search: the collection's vectors are from model 'mock-embed-a' but the embedding backend would use 'mock-embed-b' -- re-run ...`. `embed ingest notes new.md --retriever vector` then prints `1 file(s), 1 chunk(s), 1 vector(s) [mock-embed-b]`. `embed info notes` reports `vectors:     3 of 3 chunk(s), 8-d [mock-embed-b]`, and `embed query notes zarquon` returns `0.857  [vector]  new.md#0`, `0.832  [vector]  two.md#0`, `0.422  [vector]  one.md#0`: A's vectors scored in B's space with no warning. `knowledge reindex` already warns on a mixed store (MILESTONES.md:5468); `embed ingest` does not.
4. **Every store open takes the write lock, so a read stalls behind an ingest and can fail as an empty collection.** `Store::Store` (`store.cpp:68`) sets the 5 s busy timeout (`store.cpp:87`). It then runs every migration and the unconditional `schema_version` upsert (`store.cpp:98-184`) inside `in_transaction`, which is `BEGIN IMMEDIATE` (`data/embedstore/store_impl.h:94-105`), on every open, even when nothing needs migrating. So a read-only open needs SQLite's single writer lock. That covers `embed list` (`embed.cpp:503`, inside `collection_rows`) and RAG's collection listing (`business/tools/rag_query.cpp:200`). An ingest holds that lock for one transaction per source (`store.cpp:217-252`), so the read waits up to 5 s and then fails `database is locked`. A plain WAL reader is not blocked at all. Probe (re-run at HEAD): with a write transaction held on the `notes` store, `embed list --output-format json` took 5.39 s, exited 0 and printed `{"data":[{"chunks":0,"error":"database error: database is locked","name":"notes","sources":0}],"object":"list"}`, while a plain reader on the same file answered `(3,)` in 0.5 ms. The sweep's measurement during a real ingest of a 207 MB text file (461,605 chunks), with `embed list --output-format json` in a loop: `reads 20 failures 0 max-latency-ms 5272`, every read blocked while the file's transaction ran (a 69 MB file gave 12 reads, all slow, none failed). That is at the timeout boundary: a larger file or a slower disk pushes it over. The app's Collections screen polls exactly this read (`CollectionsViewModel.swift:90`), so it would show a collection with zero chunks and an error instead of its contents.

What already works: an explicit single-file target is ingested as named; binaries and empty files are skipped by name; a store whose recorded model differs from the embedder is demoted with a note until something rebinds it; the store's migrations roll back whole on an interrupted first open; WAL lets a plain reader run during a write.

**Core constraint(s).**
- **One retriever per turn, resolved once, reported honestly** (CLAUDE.md): a store whose vectors came from another model, or that holds more than one vector space, is demoted wholesale to lexical with the re-ingest hint, never queried as a fraction. Nothing reports `[vector]` for a search across two spaces. The decision about which model a store is bound to after an ingest is made in one place, in `business/agentloop` beside `resolve_ingest_retriever`, and pinned in its rule table.
- **The spend rule** (same invariant): a whole collection is never vectorised through a metered embedder on Apogee's initiative. Nothing here re-embeds sources the user did not name.
- **What can reach a model is what the user chose to share**, the concern behind CLAUDE.md's *Secrets are unleakable by construction* and *What leaves the machine is asked about by host*: a credential file the user never named must not become a chunk. A directory ingest leaves out hidden entries and, inside a repository, what git ignores, the same rule an attachment walk already follows.
- **Every skip is named** (DEVELOPER.md's ingest row, `embed.cpp:315-325`): a file left out by the new rules is counted and named, never omitted silently. The same goes for a replacement and a refused collision.
- **Four layers** (CLAUDE.md, since Architecture A1): `data/embedstore` may not reach up into `business/agentloop`, so the shared folder listing moves down to where both callers can reach it.
- **The store's migrations roll back whole** (`store.cpp:91-97`): an older store is still migrated inside one `IMMEDIATE` transaction. Only the already-current case stops taking the lock.
- **Development runs on the dev channel**: probes and tests use a temporary `APOGEE_HOME` under the scratchpad; any live pass names `apogee-dev`, never `apogee` or `~/.apogee`.

**Seam + files.**
- `data/embedstore/ingest.cpp/.h`: the directory walk takes the shared listing (finding 1). Sources already in the store from another root are checked before anything is replaced (finding 2). `IngestReport` gains `left_out` (hidden or ignored), `replaced` and `collisions`, each named.
- The shared folder listing: `hidden`, `git_files`, `walked_files` and `files_under` move out of `business/agentloop/attachments.cpp` to a lower layer (`data/` or `infrastructure/platform/`, settled at build), and `attachments.cpp` calls the moved function. Behaviour is unchanged for attachments.
- `data/embedstore/store.cpp/.h`, `store_impl.h`: each source's ingest root is recorded (a new table in the next schema version, migrated in the one transaction). The open reads `schema_version` without a write lock and runs the `IMMEDIATE` migration only when the store is older than `kSchemaVersion` (`store.h:603`) or has no version yet (finding 4).
- `business/agentloop/retriever.cpp/.h`: one function decides the post-ingest binding from the store's facts before the ingest, the sources rewritten and this run's model (finding 3). The demotion hint at `retriever.cpp:58-60` says to re-ingest every source.
- `presentation/cli/embed.cpp`: the ingest reads `facts_for(store)` (`embed.cpp:111`) before it writes, applies the binding decision instead of the unconditional `set_embedding_model` at `:288`, and prints the new warning, replacements, collisions and leave-outs.
- Tests: `tests/data/embedstore/ingest_test.cpp`, `tests/data/embedstore/store_test.cpp`, `tests/business/agentloop/retrieval_test.cpp`, `tests/business/agentloop/attachments_test.cpp` (unchanged behaviour after the move), and `tests/scripts/cmake/config_e2e.cmake` (`cli.config_lifecycle`, whose mock-embed-a/mock-embed-b mismatch block at `:467-480` is where the partial re-ingest goes).
- Docs: DEVELOPER.md's `embedstore/ingest.h/.cpp` and store rows, and `embed ingest`'s help text, which say what a directory ingest takes.

**Reference.** The attachment walk's listing (`attachments.cpp:154-167`): git's tracked and untracked-not-ignored list inside a repository, else a walk, with hidden entries left out either way. The code graph's vendored directories (`code_build.cpp:21-23`). `knowledge reindex`'s warning on a mixed store, and its rule of recording the space the vectors now live in (MILESTONES.md:5468). The existing per-source delete, `apogee embed delete <collection> --source <name>` (`embed.cpp:462`, its `--source` branch at `:477-486`), is the way out offered for a collision. The sibling 57t ([`graph-builds-survive-real-trees.md`](graph-builds-survive-real-trees.md)) covers the graph builds that read these collections.

**Decisions made** (dated):
- 2026-10-31: Specced from the second CLI/GUI bug sweep (the user's call: every finding becomes a v0.2.1 item in its queue, CLI track 57, GUI track 6).
- 2026-10-31: One item, because all four are the same promise broken in different places: a collection holds exactly what the user put in it, from the space it says, and stays readable while it grows. They share the ingest path (`ingest.cpp`, `embed.cpp`'s ingest action) and the store's open, so fixing them apart would edit the same seam four times.
- 2026-10-31: Finding 3 reproduces on the mock (two mock backends with different `--embedding-model` names), so it is pinned by `cli.config_lifecycle` and needs no real embedder.
- 2026-10-31: The app needs no change of its own. Its Ingest sheet and Collections poll run these same commands (`CollectionsViewModel.swift:32`, `:90`), so the CLI fix reaches it.

**Open calls:**
- [default: a directory ingest lists files as an attachment folder does: inside a git work tree, git's tracked and untracked-not-ignored files; outside one, a walk. Hidden entries are left out either way, and a hidden directory is not descended. Outside a repository the walk also leaves out the code graph's vendored directory names (`kVendoredDirectories`), so `node_modules` stays out of a folder git does not govern. Inside a repository git decides.]
- [default: an explicitly named target is always taken. `embed ingest c .env`, or a target that is itself inside a hidden or vendored directory, ingests what was named, because the rules apply to what a walk finds, not to what the user typed. No `--include-hidden` flag for now; a ROADMAP idea if wanted.]
- [default: the ingest summary counts what the walk left out (`left out 23 hidden or ignored file(s)`) and lists those entries only under `--verbose`, so a repository ingest does not print its whole `.git`.]
- [default: a store that already holds `.git/*` or `.env` sources from an earlier build is not cleaned on Apogee's initiative. `embed info` lists them, and the ingest notes that sources the new rules would leave out are still in the collection, naming `embed delete <c> --source <name>`.]
- [default: each source records its ingest root (absolute, generic form). Re-ingesting from the same root replaces as today and is counted (`(1 replaced)`). A same-named source from a different root that still exists on disk is not replaced: it is refused by name with both roots and the way out (`README.md is already in 'two' from /a -- delete it with 'apogee embed delete two --source README.md' to replace it`). A recorded root that no longer exists counts as a moved corpus, so the replacement proceeds and is named (`replaced (moved from /a)`), which keeps "a corpus survives being moved". A source from an earlier build with no recorded root replaces as today, with the replacement named.]
- [default: after a vector ingest, the store is bound to this run's model only if it was already bound to that model, or holds no vectors outside the sources this run rewrote. Otherwise the binding is left saying the store is mixed, so the next query demotes wholesale, and the ingest warns: `warning: 2 source(s) keep vectors from 'mock-embed-a' -- the collection searches lexically until every source is re-ingested with 'mock-embed-b'`. Refusing the partial ingest before it spends was considered and not taken: the new text is still worth storing, and the warning plus the wholesale demotion keep the report honest.]
- [default: the demotion hint at `retriever.cpp:58-60` says to re-ingest every source (`re-run 'apogee embed ingest' over every source with '<model>' to vector-query`), matching the mixed-width hint below it.]
- [default: the open reads `schema_version` with a plain read and takes `BEGIN IMMEDIATE` only when the store is older or new. The `IF NOT EXISTS` self-healing of triggers then runs only during a migration, which is when a store can lack one. A separate read-only open mode is not added.]

**Guardrail(s).** All hermetic: a temp `APOGEE_HOME` or temp directory, the mock backend, no network.
- `ingest_test.cpp`: a temp folder holding `.git/config`, `.env`, `node_modules/x/index.js`, `.hidden/notes.md` and `main.md` ingests `main.md` alone, with the four leave-outs counted. Inside a `git init` work tree (skipped when git is not installed, as `attachments_test.cpp:189-192` does), a git-ignored file is left out and an untracked, not-ignored one is kept. An explicit `.env` target is ingested.
- `ingest_test.cpp`: `/a/README.md` then `/b/README.md` into one store keeps `/a`'s chunk and reports the collision by name. A second ingest of `/a` replaces and counts it. With `/a` removed from disk, ingesting `/b` replaces and names the move.
- `retrieval_test.cpp`: the binding rule's table, covering same model, a different model with untouched vectored sources, a different model rewriting every vectored source, an unrecorded model, and a store with no vectors. Mutation-tested like the rest of the table.
- `cli.config_lifecycle`: after the existing mock-embed-a to mock-embed-b switch, `embed ingest vecs <new file> --retriever vector` prints the mixed warning, `embed info` does not claim `[mock-embed-b]` over A's vectors, and `embed query vecs` runs `[lexical]` with the every-source hint. Re-ingesting every source under B then queries `[vector]`.
- `store_test.cpp`: with a write transaction held on a second connection, opening a current-version store and reading `stats()` returns well inside the busy timeout without `database is locked`. An older-schema store still migrates whole, and an interrupted migration still rolls back.
- `attachments_test.cpp` stays green unchanged after the listing moves.

**Acceptance criteria:**
- [ ] `embed ingest proj <repo>` on the probe's repository ingests `main.md` and leaves out `.git/*`, `.env` and `node_modules/*`, saying how many it left out. `embed query proj ghp_FAKE` and `embed query proj abc123` find nothing.
- [ ] `embed ingest two /a` then `embed ingest two /b` leaves `/a`'s README in the collection (`embed query two Postgres` finds it) and names the collision with the way out. Nothing is replaced without a line saying so.
- [ ] After a partial vector re-ingest under a new model, `embed info` never reports one model over vectors from two, `embed query` runs `[lexical]` with the every-source hint, and the ingest printed a warning naming both models.
- [ ] With an ingest's write transaction open, `embed list --output-format json` returns the collection's real chunk and source counts in well under a second, with no `error`.
- [ ] The full suite is green, and DEVELOPER.md's ingest row records what a directory walk takes.

**Scope note.** Earmarked for v0.2.1 (track 57); ungated. Out of scope: cleaning sources that earlier builds already ingested (named, not removed); an `--include-hidden` or custom-ignore flag; per-chunk model records; the graph builds over these collections (57t); the app's Collections screen, which renders whatever `embed list` and `embed ingest` report and needs no change of its own.
