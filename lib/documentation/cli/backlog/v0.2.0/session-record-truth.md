# The session record tells the truth: compaction, names, numbering, degradations

**What / why.** The CLI/GUI audit (2026-10-22, three-lens verified) found five places where what a session says about itself drifts from what happened. Each one misleads a driver such as the macOS app, which draws only what the protocol tells it:

1. **A failed or empty compaction reports success everywhere.** `compact_conversation` (`chat_history.cpp:502-506`) unconditionally increments `session.compactions` and returns the compactor's name. `agentloop::compact_history` returns the history unchanged on an empty conversation (`content.cpp:114-116`) or a `HarnessError` (`:131-141`, "the caller may be told", but no caller checks). So the `/compact` reply, the driver line's notice (`chat_session.cpp:364-371`, `:1526-1529`), `chats compact` (`chat_history.cpp:537-556`) and `chats show`'s `compacted: N time(s)` all claim a compaction that did not happen. Probe: a `compact` line on an empty conversation answered `history compacted`.
2. **The recall index ignores a chat's custom name.** `summarise_for_recall` writes `RecallEntry.title = session.title` (`chat_recall.cpp:143-146`). `chats title` and `/title` set only `custom_name` (`chat_history.cpp:389-392`; `chat_session.cpp:2405-2408`), and `display_name()` (`data/logger/session.cpp:227-235`) exists for exactly this. So `memory.sessions`' `name` (`json_reporter.cpp:145`, drawn by the GUI's recalled card) shows the stale auto-title forever. 52a's dated decision promised the name heals on re-summary; it cannot.
3. **Resume degradations are invisible to drivers.** `chat_session.cpp:850-855` says resume warnings through the terminal's status writer only (`session_output.h:175`, stderr) and silently clears `session.backend` on `BackendMissing`. `chats show` writes `FieldDropped` warnings to stderr even under `--output-format json` (`chat_history.cpp:368-373`). Probe: a legacy session resumed over stream-json carried only JSON events on stdout, with `[warn] [resume] this chat predates session metadata…` on stderr. The app's `ReadRunner` keeps only the document on success, so a degraded chat looks whole. machine-mode.md's own `notice` event (user-facing, show-and-keep) is the fitting channel (ADR 0002).
4. **`next_turn` contradicts `chats show`'s numbering.** When `session.turns` undercounts the answered exchanges (a legacy file's default 0 at `session.cpp:434`, or `serve` replacing messages while `++turns` runs once per request at `handler.cpp:546-547`), `saved_turns` (`session.cpp:749-768`) renumbers from 1, but `chat --resume`'s `next_turn = turns + 1` (`chat_session.cpp:1410`) does not reconcile. Probe: a session file with 2 answered turns and no count showed turns [1,2] in `chats show` while the resumed session announced `"next_turn":1`. After a live turn, `chats show` numbered [1,2,3], and live turns reused numbers already drawn. machine-mode.md:113-114's "last turn is next_turn minus one" is false.
5. **A running chat undoes `chats title` and resurrects a `chats delete`** (completeness pass, with probe; reproduce first). The session writes its whole in-memory record on every turn, so an outside rename or delete made while it runs is lost. Probe: on a live machine-mode chat, `chats title <id> "Renamed By GUI"` showed the name, and after the next turn the list said "Answer two" again. `chats delete <id>` printed `deleted`, and the next turn put the chat back with 2 turns.

The doc half: **machine-mode.md:432-434** says a `detach`/`set`/`compact` line sent mid-turn "waits for it to end, as an `attach` does". While a question or permission prompt is outstanding, though, every non-answer line is consumed and silently dropped (`json_reporter.cpp:684-688`; `permissions.cpp:379-383`), per 52d's recorded decision ("a host sends set between turns", MILESTONES Milestone AO). The reference documents neither the drop nor the rule.

**Core constraint(s).** **The record and the protocol say what happened**: a compaction that changed nothing says so and counts nothing. A name is the display name. A degradation the terminal states reaches drivers as a `notice` (and `chats show`'s JSON carries its warnings). Numbering is one reconciled count. **Additive protocol** (ADR 0006): notices and a document field are added, nothing renamed. **One session store**: a save never overwrites a newer outside edit of the name or a deletion. The session re-reads (or merges) the on-disk record's identity fields before writing, never a second store. **The 52d drop rule stands** (a recorded decision); the reference states it.

**Seam + files.** `presentation/cli/chat_history.cpp` (compaction's success channel; `chats show` warnings into the document), `business/agentloop/content.cpp` (the compactor reports no-op/failure), `presentation/cli/chat_recall.cpp:144` (`display_name()`), `presentation/cli/chat_session.cpp` (resume warnings as notices; `next_turn` from the reconciled count), `data/logger/session.cpp` (one turn count; save respecting outside rename/delete), `lib/documentation/cli/reference/machine-mode.md` (the between-turns rule and the drop). Tests: compaction no-op and failure matrices (nothing counted, said); recall naming after a rename; a resumed legacy session over stream-json carrying the warning as a `notice`; `chats show --output-format json` carrying warnings; the numbering reconciliation over the probe's fixture; a live session that does not undo an outside rename or delete; schema conformance.

**Open calls:**
- [default: a no-op compaction answers "nothing to compact" and a failed one names the failure; neither increments the count.]
- [default: a running session's save re-reads the on-disk record's name and existence before writing. A deleted chat stays deleted (the live session ends its saving, said), and an outside rename wins.]

**Guardrail(s).** Each finding's probe pinned as a regression test; schema conformance; the additive guarantee over old fixture streams.

**Acceptance criteria:**
- [ ] Compaction reports and counts only what happened, through every door.
- [ ] Recall names a renamed chat by its display name; resume degradations reach drivers as `notice` events and `chats show`'s JSON.
- [ ] `next_turn` agrees with `chats show`'s numbering; an outside rename or delete survives a running session's next save.
- [ ] machine-mode.md states the between-turns rule and the drop; the full suite is green.
