Why does group commit make the WAL cheaper under load? Point me to the pages.

storage-engine-design.pdf300 pages
thought for 6s · embedding · searched 1 document

Because one flush pays for many commits. A transaction is durable once its log record reaches disk, and a single fsync() makes every record appended before it durable, so transactions that commit inside the same flush window share one write.

storage-engine-design.pdfpage 187 of 300
“…a single fsync() makes every record appended before it durable, so committers that arrive inside the same flush window share one write instead of paying for their own…”
strong match

Under load the window fills on its own: while one flush is in flight, the next commits queue behind it and go out together. commit_delay widens the window on purpose, trading up to that much latency per commit for fewer flushes; it’s 0, so off, until you set it.

storage-engine-design.pdfpage 192 of 300
“…commit_delay adds a short sleep before the flush so that other committers can join it; with few concurrent transactions the sleep is simply wasted…”
moderate match
postgresql.conflines 212–214

#commit_siblings = 5 # range 1-1000
weak match
  • Light load: little to gain; each commit still waits for its own flush.
  • Many writers: flushes per second stay flat while commits per second climb.
