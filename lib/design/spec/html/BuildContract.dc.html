How the app talks to Apogee

The desktop app is the sibling application the spec commits to. It runs the apogee binary as child processes and speaks to them over stdin and stdout in machine mode, never over a port. Every change is the command a person would type, and every screen is drawn from a command’s JSON. This board maps each part of the design to that contract, names what the CLI doesn’t offer yet, and records the decisions the design makes. Checked against apogee 0.2.0 (f72f05f6); the named pipelines’ reads are the CLI’s M30 (32e1424c), as its reference documents them.

Starting up

  1. Find the binary. ~/.local/bin/apogee, or the path set in Settings › General. Run apogee version.
  2. Check the vocabulary. apogee __machine-schema carries x-apogee.schema, and every child’s session event repeats it as capabilities.schema. A newer schema still works, since growth is additive; a different protocol_version is refused, naming the build the app needs.
  3. Check health. apogee check --output-format json. Failures show in Settings › Backends & keys with each row’s remedy, and check --fix and bootstrap are buttons.
  4. First reads. models list, models status, chats list and task list, each with --output-format json.
  5. Open the last session. apogee chat --resume <id> --tools --output-format stream-json --input-format stream-json, started when the session comes into view.

Decisions the design makes

Taken while designing; each can be vetoed.

  1. Pipes only. The app starts apogee as children and speaks over their stdin and stdout. No localhost server, ever (SPEC: interactive = pipes).
  2. One live chat child per session in view or mid-turn. Moving away from an idle session ends its child and frees its model; coming back starts it again with --resume. A local model loads inside each child, so two live children on one model would hold it twice: the app never does that.
  3. Read back; don’t mirror. After every change the app runs the read that shows it. It holds no copy of Apogee’s state beyond what is on screen. There is no push channel in protocol 1.
  4. The app’s own files are the app’s. Themes, window layout, open sessions and watched folders live in ~/Library/Application Support/Apogee. ~/.apogee stays the CLI’s, so reset and uninstall keep meaning what they mean.
  5. Media goes to ~/Movies/Apogee and ~/Music/Apogee. The library is the records found there and in folders the person adds. Nothing is ever written over; a taken name gets a number.
  6. Sessions ask; tasks never do. Sessions run with --tools and --permission-mode manual, and the permission card answers. Tasks get explicit --allow grants up front, because a task in machine mode reads nothing.
  7. Types come from the schema. The Swift protocol types are generated from machine-schema.json and regenerated when capabilities.schema moves. A different protocol_version is refused with the build it needs.
  8. SwiftUI first, the core kept portable. macOS 27 or later, on Apple silicon. The protocol client, the process supervisor and the stores stay free of SwiftUI so the Qt and WinUI apps can follow the same shape.
  9. Where it lives. lib/src/darwin, then linux and windows, one app per platform, beside the CLI (SPEC: the GUI sibling applications).
  10. Narrow windows. At least 960 × 640. Below 900 wide the sidebar becomes icons and side panes close.
